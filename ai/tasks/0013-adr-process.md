# Реестр архитектурных решений в docs/adr

## Проблема

Решения (стек, формат тритов, своя ВТМ, метод QAT, правила данных) жили в
переписке и в пояснительных документах. Инженер, пришедший в репозиторий,
не может понять, что выбрано, что отвергнуто и почему.

## Требования

- Формат как в `distributed-db`: `docs/adr/NNNN-<слаг>.md`, разделы Контекст,
  Решение, Альтернативы (таблица), Последствия; статусы accepted/proposed/
  superseded/rejected.
- `docs/adr/README.md` — таблица решений и правила (ADR до реализации, не
  переписывать задним числом, альтернативы обязательны).
- Шаблон `docs/adr/_template.md`.
- Зафиксировать уже принятые решения: 0001 стек, 0002 формат тритов, 0003 своя
  ВТМ, 0004 путь дистилляции, 0005 контракт данных, 0006 метод QAT,
  0007 процесс задач, 0008 инженерные стандарты.
- Правило в `ai/README.md`: решение → сначала ADR, потом задача.

## Критерии приёмки

- [x] 8 ADR на месте, у каждого есть альтернативы и последствия
- [x] README с таблицей и правилами, шаблон есть
- [x] ADR-0008 содержит проверяемые нормы (тесты, детерминизм, ошибки, стиль, коммиты, секреты)
- [x] `ai/README.md` ссылается на процесс ADR
- [x] Коммит ссылается на задачу

## Контекст и ограничения

- Не дублировать `docs/stack.md`: он остаётся пояснением, ADR-0001 — решением.
- Уже сделанные решения помечаются accepted с реальной датой, а не задним числом
  «как будто писали раньше».

## Отчёт исполнителя

Написаны `docs/adr/README.md`, `_template.md` и восемь ADR. Проверено скриптом:

объём 41–87 строк. `ai/README.md` дополнен правилом «сначала ADR».
