# Импорт без трёх копий

## Проблема
Полная 30B: GGUF 18,5 ГБ + q4.bin 18,9 + .vtm 18,9 = 56 ГБ, а диска 9,4 ГБ.
Импорт обязан писать сразу в контейнер (потоково), без промежуточного `q4.bin`
и без второй копии.

## Требования
- `tools/moe_import.py` (или новый `tools/moe_stream.py`): чтение GGUF потоково
  (HTTP Range/локальный файл) → сразу запись сегментов в `.vtm` через
  `vtm_ref.write_vtm_stream`; пик памяти ≤2 ГБ, пик диска ≤ размер контейнера +10%.
- Удалять за собой временные файлы; `--keep-temp` для отладки.
- Проверка: 30B Q4 → `.vtm` 19,3 ГБ на диске, sha256 сегментов совпадает с
  непоточным путём (на срезе), C грузит и считает токен.
- Замер: пик RSS, пик диска, время импорта.

## Критерии приёмки
- [ ] полный 30B импортируется в один .vtm, промежуточных копий нет
- [ ] сегменты побайтово равны непоточному пути (срез)
- [ ] `make test`, полный набор зелёные

## Отчёт исполнителя

Полная Qwen3-30B-A3B Q4_K_M собрана потоковым импортом по HTTP Range в один
`runs/q4/qwen3-30b-a3b.vtm` и прогнана в C-рантайме. Промежуточных копий нет
(пик диска = контейнер × 1,00), пик RSS импорта — 196 МиБ.

### Импорт (HTTP Range с HF, 2026-11-25)

| Что | Значение |
|---|---|
| GGUF источник | 18 556 685 824 Б, куски по 32 МиБ, `--dry-run` до импорта |
| каркас | 33,0 с |
| веса (pwrite) | 9 374,1 с = **2 ч 36 мин**, 1,98 МБ/с — упор в троттлинг HF |
| всего | 9 423,1 с = 2 ч 37 мин |
| контейнер | **18 554 374 000 Б = 17,28 ГиБ**, v0.3 (u64), 1015 тензоров / 579 весов / 677 инструкций |
| пик RSS | **205 979 648 Б = 196 МиБ** |
| пик диска | 18 554 374 000 Б = контейнер × 1,00 (`du`-эквивалент по отчёту тула) |
| сверка `--verify` | 579/579 сегментов, 18 550 722 500 Б, расхождений нет |
| временный файл | 16 МиБ (префикс GGUF), удалён до начала записи |
| sha256 контейнера | `14da8841b69bf1f0dbde0e1ccafb6b3aaa65e1b23a6bd4faf3b36b48a28a1dc7` |

`--dry-run` до импорта предсказал ровно 18 554 374 000 Б — факт совпал байт в
байт. Диагностика канала: одиночный свежий Range — 10–16 МБ/с, 8 параллельных
Range'ей — 0,5 МБ/с суммарно (троттлинг по IP), поэтому параллельность не
помогла бы; `--chunk-bytes` не менялся (32 МиБ для HTTP).

### C-рантайм (`./src/vtm/vtm run … --tokens 151644,872,198 --max-new 4`)

| Прогон | Время | ток/с | RSS | page faults | page reclaims |
|---|---|---|---|---|---|
| холодный (`VTM_Q4K_CHECK_OFF=1`) | 19,21 с | **0,21** | **3,10 ГиБ** | 355 984 | 137 619 |
| тёплый (тот же контейнер) | 18,29 с | **0,22** | **2,95 ГиБ** | 332 636 | 159 836 |
| `VTM_MOE_CACHE_MB=4096` | 25,28 с | 0,16 | 2,77 ГиБ | 416 484 | 581 632 |

Вывод одинаков во всех прогонах: `10061 400 69 2075` («Let $f(x»).
Один forward — 2,6–2,7 с, то есть ~0,37 ток/с в установившемся режиме (7
forward'ов на 3 промпт-токена + 4 новых; `--prefill-batch` не использовался).
Текстовая проверка (`--text "What is the capital of France?" --chat
--tokenizer runs/q4/qwen3-tokenizer.json`): 15 токенов промпта + 8 новых за
63,36 с, ответ «`<think>` Okay, the user is asking» — модель обучена и
контейнер читается правильно.

Почему 0,2 ток/с, а не 1–4: 18,55 ГБ файла не влезают в 16 ГиБ RAM, каждый
токен трогает ~1,5 ГБ через mmap, и время уходит в страничные отказы
(`sys` ≈ 10 с из 19 с; `user` 4,3 с). Диск не виноват (`dd` 128 МБ — 480 МБ/с).

### Паритет

| Проверка | Результат |
|---|---|
| VTM `simd` vs `scalar`, 151 936 логитов (полная 30B) | max\|Δ logprob\| = **1,4e-6**, max\|Δ logit\| = 1,7e-5, argmax совпал (10061), 151936/151936 в пределах 1e-3 |
| VTM vs ollama, полная 30B | **не проводилось**: блоб `qwen3:30b-a3b` (~18,4 ГБ) + контейнер (18,55 ГБ) = ~37 ГБ при 27,6 ГиБ свободных, внешних томов нет |
| VTM vs ollama, срез 4 слоя (docs/moe.md, ранее) | max\|Δ logprob\| 5,2e-3…2,2e-1, argmax совпал; порог 1e-3 не достигнут (причина — f64 vs f32/f16 и дискретный top-8) |

Честная формулировка: числовой паритет на полной модели подтверждён только
внутри VTM (два бэкенда, 1,4e-6). Сравнение с ollama на полной модели
требует либо внешнего диска, либо последовательной схемы «ollama → снять
logprobs → удалить блоб → импорт» с повторным скачиванием 18,5 ГБ (импорт
resume не умеет).

### Критерии приёмки

- [x] полный 30B импортируется в один .vtm, промежуточных копий нет
- [x] сегменты побайтово равны непоточному пути (срез, ранее; на полной —
      `--verify` 579/579)
- [ ] `make test` — не запускался: код в этой задаче не менялся (только
      прогон импорта и документирование замеров)

### Что осталось

* паритет с ollama на полной модели — нужен внешний диск ≥19 ГБ;
* скорость 0,2 ток/с — узкое место mmap/page cache на 16 ГиБ RAM (Q6_K-ядро и
  кэш экспертов — 0171/0172);
* локальный импорт (без сети) — не проверялся на полной модели: локального
  GGUF нет, а скачать его целиком не позволяет диск.
