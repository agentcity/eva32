# Сессии: дедуплицировать SHA и добавить лимит с LRU

## Проблема

0079 оставила два хвоста: в `kv_store.c` лежит своя копия SHA-256 (писалась до того,
как 0078 вынес `src/vtm/sha256.c`), и нет лимита на размер сессий — каталог растёт
без границ.

## Требования

- Убрать статическую копию SHA из `kv_store.c`, использовать `src/vtm/sha256.h`.
  Проверить, что хеши сессий не изменились (совместимость со снимками 0079).
- `vtm_api_sessions_limit(ctx, bytes)`: при превышении удалять самые старые сессии
  (по mtime) — только файлы в каталоге, переданном `vtm_api_sessions_dir`.
- Не удалять файл, который сейчас читается/пишется; ошибки удаления не фатальны.
- Тест: 5 сессий по 2 КБ при лимите 5 КБ → остаётся 2–3 самые новые.

## Критерии приёмки

[ ] сборка без предупреждений, хеш сессии совпадает с прежним (тест на совместимость)
[ ] лимит: старые сессии удаляются, свежие целы (тест)
[ ] make test и полный Python-набор зелёные

## Контекст и ограничения

- Зона: src/vtm/kv_store.c, src/vtm/api.c, src/vtm/api.h, tests/test_vtm_session.c
- Другие файлы НЕ трогать: параллельно работают другие агенты и ещё не закончил
  агент потоков (он держит `backend_*.c`) — их не касайся.
- Сборка: `cd src/vtm && make test`; `-Wall -Wextra -Werror`. По умолчанию `VTM_BACKEND=auto`.
- **Отчёт пиши первым блоком в ответе**, потом детали: агенты этой сессии падают в конце.
- Не коммитить: сдавать правки и отчёт.

## Отчёт исполнителя

Сделано: статическая копия SHA-256 удалена из `kv_store.c` (−129 строк), вызовы
переведены на `vtm_sha256_*`; добавлены `vtm_session_prune()` (сортировка по mtime,
защита `keep_path` по dev/ino, temp-файлы пропускаются) и
`vtm_api_sessions_dir/limit`, вытеснение после успешных save/load.

Проверено архитектором: `make test` зелёный, 51 проверка в `test_vtm_session`,
1061 тест Python зелёный.

Ключевая проверка совместимости: снимок, созданный **до** правки, читается новым
кодом и продолжается теми же токенами (4 39 47); новый снимок **байт-в-байт** равен
старому (2148 Б, sha256 90c0b109…f16f5c). Это важно: дедупликация не изменила формат.

LRU-тест: 5 сессий по 2148 Б при лимите 5120 → остались 2 самые новые (4296 Б).

Риски записаны: под лимит попадает любой обычный файл в каталоге (не только *.vtms);
при равных mtime порядок по имени, то есть не строго LRU; предупреждения идут в stderr —
для демона это может быть шумом.
