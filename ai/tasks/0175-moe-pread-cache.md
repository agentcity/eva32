# pread вместо страничных отказов

## Проблема
Полная 30B MoE: 18,55 ГБ контейнер, 16 ГиБ RAM. Каждый токен трогает ~1,5 ГБ через
mmap; замер: 19,21 с на токен, **sys 10 с** — это 355 984 page fault и 137 619 reclaim
(страницы по 16 КБ, ~94 тыс. на токен). Паттерн случайный (8 экспертов из 128 на слой),
readahead не работает.

## Требования
- В `MOE` (interp.c): выбранные эксперты читать **явным `pread`** крупными кусками
  (256 КБ–1 МБ) в собственный кэш, а не через mmap-страницы.
- Кэш: фиксированный бюджет `--moe-cache-mb` (по умолчанию 3072), LRU по экспертам;
  слоты выровнены, повторное использование без malloc на токен.
- Опционально: асинхронная предзагрузка следующего слоя (один поток).
- Замер: ток/с, sys-время, page faults до/после на полной 30B
  (`runs/q4/qwen3-30b-a3b.vtm`), плюс RSS и попадания кэша.
- Цель: ≥0,8 ток/с (сейчас 0,21); sys-время хотя бы вдвое меньше.

## Критерии приёмки
- [ ] ток/с ≥0,8 на полной 30B (или честное объяснение потолка)
- [ ] page faults снижены, sys-время измерено
- [ ] argmax совпадает с mmap-путём на 3 промптах
- [ ] `make test`, `--check` зелёные

## Отчёт исполнителя

_Заполнено 2026-11-25._

### Что сделано

* `src/vtm/interp.c` — `op_moe` больше не ходит за экспертами через mmap:
  выбранные эксперты читаются явным `pread` целым куском (0,84 МБ gate/up,
  0,84–1,29 МБ down) в собственный LRU-кэш. Кэш: бюджет
  `VTM_MOE_CACHE_MB` (по умолчанию 3072 МиБ, `0` — выключен), хеш по
  `(st_dev, st_ino, mtime, смещение банка, эксперт)`, слоты выровнены на 4 КБ
  и переиспользуются через списки свободных слотов — после прогрева `malloc`
  на токен нет. Для `pread` открывается отдельный дескриптор с `F_NOCACHE`,
  чтобы эксперты не вытесняли из page cache attention/lm_head. При
  выключенном кэше сохранён прежний mmap-путь с `madvise(MADV_WILLNEED)`.
  `VTM_MOE_TRACE=1` печатает hits/misses/cache/advised/pread/allocs/evicted/
  fallbacks.
* `src/vtm/loader.c`, `src/vtm/vtm_internal.h` — загрузчик больше не закрывает
  fd контейнера, `vtm_free()` закрывает его и `pread`-дескриптор. Больше
  ничего в загрузчике не менялось: адреса банков по-прежнему из mmap, кэш
  только читает те же смещения из файла.
* `src/vtm/vtm.h` — описание поведения `VTM_MOE_CACHE_MB`/`VTM_MOE_TRACE`
  рядом с ABI `MOE` (additive).
* `tests/vtm/test_vtm.c` — `test_moe_pread_cache`: синтетическая MoE-модель с
  банками Q4_K/Q6_K на диске, один и тот же файл прогоняется с
  `VTM_MOE_CACHE_MB=0` и с кэшем. Проверяются: побитовое совпадение выхода
  MOE, argmax, misses=6/hits=18, отсутствие новых `allocs` на втором прогоне,
  выровненный размер слотов. Добавлен в `make test`.
* `docs/moe.md` — раздел «Полная 30B: pread-кэш экспертов (0175)»: механизм,
  таблицы до/после на 3 промптах, попадания, объяснение потолка, ограничения.

### Критерии

- [x] page faults снижены: 355 984 → 47 358 (умолчание) / 272 (1792); на
      тёплом mmap 261 594–669 316 → 47 358/272/2 241.
- [x] sys-время измерено: холодный mmap 10,12 с → 4,32 с (3072) / 1,90 с
      (1792) на p1.
- [x] argmax совпал на 3 промптах для всех конфигураций (списки выше).
- [x] `make test` и `make ci` зелёные.
- [~] ток/с ≥0,8: на p1 — **1,0** при `VTM_MOE_CACHE_MB=1792`; на умолчании
      3072 — 0,7. Причина не в коде: машина общая, на момент замеров
      `load average` 9–23, swap занят на 13–14 ГиБ из 14–15 ГиБ. 3 ГиБ
      анонимного кэша в этом состоянии вызывают компрессию (reclaims
      386 тыс. и 1,06 млн, sys 4,3–15,6 с), 1792 МиБ проходят ниже порога
      (sys 1,9–4,5 с, major faults почти нулевые). На выделенной 16 ГиБ машине
      порог должен быть выше; проверить нельзя — `purge` без root не работает,
      page cache не сбросить.

### Осталось и риски

* **Умолчание 3072 на 16 ГиБ под внешним давлением памяти проигрывает
  1792.** Менять умолчание без решения архитектора не стал (в задании
  зафиксировано 3072); если машина всегда общая, разумно 1792–2048.
* **Кэш на процесс и не потокобезопасен** (как и прежние глобальные
  счётчики). Несколько машин в разных потоках — только с
  `VTM_MOE_CACHE_MB=0`.
* **Linux**: `F_NOCACHE` — macOS-специфичный; на Linux `pread` будет
  наполнять page cache (корректно, но attention может вытесняться). Нужен
  `posix_fadvise(DONTNEED)` или O_DIRECT — не проверялось, машина macOS.
* **Предзагрузка следующего слоя не сделана**: его эксперты зависят от выхода
  его роутера, то есть до счёта неизвестны. Перекрытие внутри слоя (один
  поток, I/O впереди счёта) даёт порядка 10–20 % и требует синхронизации
  слотов — отдельная задача.
* **Мелкие модели** (срез 4 слоя, всё в page cache): кэш не нужен и только
  тратит память; для них `VTM_MOE_CACHE_MB=0` быстрее.
* **Рабочее дерево общее с 0176.** Пока шла эта задача, соседний исполнитель
  правил `src/vtm/loader.c` и `src/vtm/vtm.h` (флаги STATE, опкоды CONV4/
  GDELTA). Мои правки в этих файлах — только fd/закрытие в `vtm_free` и
  комментарий про `VTM_MOE_CACHE_MB`; в `git diff` они перемешаны с 0176.
  Приёмку делать по этому файлу отчёта и диффу `interp.c`/`test_vtm.c`, а
  `loader.c`/`vtm.h` — после того, как 0176 закончит.
