# Загрузка контейнера через mmap: память 2×→1×

## Проблема

Файл читается целиком в буфер, потом копируется в арену: для 1.5B это 2,6 ГБ вместо
1,3. На сервере с несколькими моделями это решающая разница.

## Требования

- mmap файла в режиме read-only; тензоры читаются из отображения без копирования.
- Для тритовых тензоров — работать по указателю на сегмент (распаковка на месте);
  для fp16/bf16 — либо отображение, либо копия в fp32 (замерить, что выгоднее).
- Платформы: macOS и Linux; на Windows — фолбэк на прежний fread с честным сообщением.
- Ошибки: файл изменился, mmap не удался, madvise — всё через VTM_E_*, без падений.
- Замер памяти: RSS до/после на demo и на синтетике 512 МБ.

## Критерии приёмки

[ ] `make test` зелёный, результаты совпадают с прежними
[ ] RSS при загрузке большого контейнера ≤ 1,1× размера файла (числа в отчёте)
[ ] фолбэк работает, если mmap недоступен (тест с флагом)
[ ] `python3 -m unittest discover -s tests` зелёный

## Контекст и ограничения

- Зона: src/vtm/loader.c, src/vtm/vtm_internal.h, tests/vtm/test_vtm.c (новые тесты в конце)
- Другие файлы НЕ трогать: параллельно работают другие агенты (0059 — interp.c,
  0060 — loader.c, 0063 — main.c/tokenizer). Пересечение зон запрещено.
- Сборка: `cd src/vtm && make test`; флаги `-Wall -Wextra -Werror`.
- Не менять поведение без новых флагов.
- Не коммитить: сдавать правки и отчёт.

## Отчёт исполнителя

### Что сделано

- `src/vtm/loader.c`: `vtm_load()` на POSIX (macOS/Linux) отображает файл
  `mmap(PROT_READ, MAP_PRIVATE)`. `vtm_load_mem()` остаётся прежним (буфер
  вызывающего копируется в арену). `VTM_NO_MMAP=1`, Windows и big-endian —
  фолбэк на прежний `fread` с сообщением в stderr.
- Неизменяемые тензоры остаются в отображении:
  - `kind 1` (fp32) — `t->f32` указывает прямо в файл;
  - `kind 0` (триты) — `t->words`/`t->scales` указывают в TRT1-сегмент или
    raw-области, копирования слов нет. Только fp16-масштабы конвертируются в
    арену (`float*` других не бывает).
- В арену попадает только то, что интерпретатор пишет: `dst` всех операций
  и `b` у `KVW` (V-кэш), а также fp16/bf16 (их надо развернуть в fp32).
  `HALT.dst` не считается записью — иначе тензор 0 зря копировался бы.
- Все `offset`/`scale_offset`/длины валидируются по фактическому размеру до
  первого доступа; размер файла сверяется `fstat` до и после разбора.
- `VTM_UNALIGNED_LOADS=0` — сборка для строгих платформ (TRT1 копируется в
  выровненную арену); по умолчанию 1 на x86/ARM. Big-endian → `fread`.
- `vtm_free()` снимает отображение и вызывает `vtm_samp_free()` (контракт
  параллельной задачи 0059); 1000 циклов load/free без роста RSS и без
  исчерпания fd.
- Тесты (в конце `tests/vtm/test_vtm.c`): `test_mmap_file_load`,
  `test_mmap_fallback`, `test_mmap_truncated`, `test_mmap_f16_bf16`,
  `test_mmap_trit_f16_scales`, `test_mmap_raw_trit`. Проверяют в т.ч. запись
  в in-place `SCAL`, оба выхода `KVW`, fp16/bf16, RAW-триты и флаг
  `VTM_NO_MMAP=1`.

RSS (macOS, `getrusage`/`task_info`; demo — `demo/model.vtm`):

| Контейнер | mmap | старый путь (фолбэк) |
|---|---|---|
| demo, 116 КиБ | 1 376 КиБ | 1 536 КиБ |
| синтетика 508 125 194 Б (300 МБ fp32 + 208 МБ тритов), загрузка | 177 072 КиБ = **0,35× файла** | 993 744 КиБ = 1,96× |
| она же, после чтения всех тензоров | 497 408 КиБ = **0,98×** | 882 512 КиБ = 1,74× |
| разреженная 1,31 ГБ (1 306 250 608 Б, 5×1e9 тритов + 150 МБ fp32), загрузка | 977 936 КиБ = **0,75×** | 1 987 344 КиБ = 1,52× |
| она же, после чтения всех тензоров | 1 276 960 КиБ = **0,98×** | 2 552 208 КиБ = 1,95× |
| разреженная 1,54 ГБ (1 537 500 720 Б), загрузка | 1 172 848 КиБ = **0,76×** | 2 498 848 КиБ = 1,63× |

Критерий «RSS ≤ 1,1× файла» выполняется и на загрузке, и в установившемся
режиме (0,98×). Синтетика валидна, разреженные файлы читаются как нули
(нулевое слово pack20 — корректные триты), т.е. это настоящий контейнер.

fp16/bf16, 512 МиБ (536 871 024 Б, все веса fp16):
- отображение как есть (касание всех страниц): **525 536 КиБ ≈ 1,0×**;
- копия в fp32: **1 574 160 КиБ ≈ 3,0×** (фолбэк — столько же, 1 574 176 КиБ);
- выбран **копия в fp32**: `vtm_tensor.f32` — это `float*`, а интерпретатор
  (чужая зона) читает его напрямую; «как есть» без правки `interp.c`/`vtm.h`
  невозможно, а поэлементная распаковка в горячем цикле ещё и медленнее.
  Плата — +2 байта/элемент; для тритового контейнера (целевой 1.5B) её нет.

Обрезанный файл:

```
$ head -c $((size-1)) demo/model.vtm > /tmp/demo_trunc1.vtm
$ ./src/vtm/vtm inspect /tmp/demo_trunc1.vtm
vtm: ...: инструкция 0: неизвестный opcode 0x00          # exit 1, без падения
$ head -c 100 demo/model.vtm > /tmp/demo_trunc100.vtm
$ ./src/vtm/vtm inspect /tmp/demo_trunc100.vtm
vtm: ...: таблица тензоров (29 × 52) не влезает в файл   # exit 1
```

### Риски

- **SIGBUS**: для файла, обрезанного *до* загрузки, невозможен — все
  диапазоны проверяются по `fstat`-размеру. Остаётся гонка «усекли во время
  разбора после fstat»: предотвратить её без копирования/обработчика SIGBUS
  нельзя; финальный `fstat` возвращает `VTM_E_IO`, но не отменяет SIGBUS,
  если усечение случилось между проверкой и чтением.
- **Unaligned TRT1**: слова/масштабы начинаются со смещения 18 (2 mod 4).
  На x86-64/ARM64 обычные загрузки это допускают, но формально это UB;
  UBSan ругается. Для строгих платформ/санитайзеров:
  `-DVTM_UNALIGNED_LOADS=0` (копирование в арену).
- **madvise**: на macOS `MADV_DONTNEED` для file-backed mapping не уменьшает
  RSS (проверено: 525 536 КиБ до и после); на Linux должен. Ошибка madvise
  не фатальна и печатается в stderr. Поэтому fp16 на macOS остаётся 3×.
- **Windows**: фолбэк `fread` + сообщение; ветка проверена компиляцией
  (`-D_WIN32`), но не запуском на Windows.
- Если будущая операция начнёт писать не в `dst`/`KVW.b`, карту изменяемых
  тензоров надо расширить, иначе запись в PROT_READ-отображение даст SIGBUS.
