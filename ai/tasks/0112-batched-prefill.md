# Prefill: считать промпт пачкой

## Проблема

Замер 0103 на форме Qwen2.5-1.5B показал главное узкое место — **не декод, а prefill**:

| Промпт | TTFT (4 потока, SIMD) |
|---|---|
| 1 токен | 0,136 с |
| 8 токенов | 0,56 с |
| **512 токенов** | **37,6 с** |

Причина: граф считает **один токен за вызов** (`vtm_run` = один токен, `position++`),
поэтому промпт из N токенов — это N полных проходов по 28 слоям. Системный промпт у
нас 4,4 КБ (≈1000 токенов) — это больше минуты ожидания до первого слова.

## Требования

- Режим prefill: прогнать N токенов за проход, используя `ATTN` с `q_len > 1` (3-D путь
  уже поддерживает q_len, causal/GQA).
- Варианты (выбрать по замеру):
  1. новая инструкция `PREFILL n` / флаг у `EMB`+`KVW`, которая за один проход пишет
     N токенов в кэш;
  2. `vtm_run_batch(m, ids, n)` в ядре — цикл по инструкциям с вектором токенов.
- Требование корректности: результат после prefill обязан совпадать с N последовательными
  `vtm_run` побитово (тест на 3 конфигурациях).
- Замер: TTFT для 8/128/512/1024 токенов до/после; цель — не хуже линейного ×2 от
  одного прохода (то есть 512 токенов ≈ 1–2 с, а не 38).

## Критерии приёмки

- [ ] prefill 512 токенов ускорился в ≥10× (числа в отчёте)
- [ ] логиты после prefill == N обычных прогонов побитово (тест)
- [ ] `make test` и Python-набор зелёные
- [ ] C-ABI и CLI используют новый путь
