# Голос: синтез по предложениям

## Проблема

Сейчас весь ответ синтезируется до воспроизведения: для ответа на 16 секунд первый
звук приходит через ~1 с, но при длинном ответе это растёт. Нужно начинать говорить
после первого предложения.

## Требования

- Разбить ответ на предложения (учитывать «₽», сокращения, кавычки), синтезировать
  первое, запускать воспроизведение, синтезировать следующее параллельно.
- Замер «до первого звука» должен упасть и быть выведен.
- Флаг `--no-stream` для сравнения со старым поведением.
- Не ломать не-скилловые вопросы и `--text`.

## Критерии приёмки

[ ] «до первого звука» меньше, чем при `--no-stream` (числа в отчёте)
[ ] тест: разбиение на предложения (пунктуация, «₽», многоточия)
[ ] `python3 -m unittest tests.test_voice_loop -v` зелёный
[ ] полный набор зелёный

## Контекст и ограничения

- Зона: scripts/voice_loop.py, tests/test_voice_loop.py
- Другие файлы не трогать: параллельно работают другие агенты (0035 — контейнер v0.2,
  0029 — компилятор).
- Только stdlib, сеть в тестах запрещена.
- Не коммитить: сдавать правки и отчёт.

## Отчёт исполнителя

Сделано: `split_sentences` (числа, сокращения, кавычки-ёлочки, многоточия), поток
синтеза по предложениям с `ThreadPoolExecutor(2)`, `--no-stream` для сравнения,
склейка `--out`, расширенный JSON с `chunk_stats`. 67 тестов (было 38).

Проверено архитектором: тесты зелёные; три пары прогонов на одном ответе — поток
1151/1249/1016 мс против 1442/1086/1734, медиана быстрее на ~290 мс.

**Главная находка:** выигрыш упирается в startup `say` (~0,85 с независимо от
длины: заголовок WAV на 535 мс, первые данные на 856 мс). На коротком ответе это
65–130 мс, на длинном (63 с речи) — 393 мс (−29%). Бюджет ADR 0010 на `say`
недостижим, нужен потоковый движок — вопрос вынесен в решение по TTS.
