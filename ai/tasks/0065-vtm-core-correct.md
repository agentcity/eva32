# Волна 1: eps, окно контекста, сброс KV, трассировка

## Проблема

Три тихие ошибки в ядре: eps нормализации кодируется как imm/1000 и Qwen-овский
1e-6 превращается в 0; контекст кончается отказом (KVW: pos >= ctx — ошибка), то есть
диалог длиннее 2048 ломается; непонятно, где теряется время — нет трассировки.

## Требования

- eps: кодировать так, чтобы 1e-6 выражалось точно (fixed-point по log2 или отдельное
  поле меты); проверить, что Qwen-овский eps доходит до ядра без округления в 0.
- Окно контекста: `context_window` в мете; при переполнении — сдвиг (ротация), а не
  отказ; смещение позиций для ROPE сохраняется корректно.
- `vtm_reset(m)` явно сбрасывает KV, счётчики и сэмплер — один вызов между запросами,
  без перезагрузки контейнера.
- `--trace`: по каждой инструкции — pc, op, номер, время (мкс), размер выхода.
- Тесты: диалог длиннее ctx не падает и не теряет последние токены; eps 1e-6 доходит
  до вызова RMSN; trace печатает хотя бы 3 строки.

## Критерии приёмки

[ ] eps=1e-6 доходит до ядра точно (тест с эталоном)
[ ] KVW/ATTN при позиции >= ctx не отказывают, а сдвигают окно (тест: 2×ctx токенов)
[ ] vtm_reset между «запросами» даёт тот же ответ, что свежая машина (тест)
[ ] --trace печатает pc/op/время, не ломая обычный вывод
[ ] make test и полный Python-набор зелёные

## Контекст и ограничения

## Отчёт исполнителя

**Архитектор закрыл шаг 1 (eps) сам**, после того как два запуска агента упали,
не оставив изменений.

Сделано: `op_rmsn` берёт eps из меты контейнера (`rms_norm_eps`), а `imm/1000`
остался совместимостью со старыми контейнерами. Компилятор уже клал точный eps в
мету (`tools/vtm_compile.py`), ядро его просто не читало.

Доказательство поведением (не «на глаз»): контейнер с `x = [1e-7 × 4]`,
`w = [1 × 4]`, RMSN с `imm = 0`:
- мета `rms_norm_eps: 1e-6` → `y = 0,0001` (1e-7/√(1e-14+1e-6))
- без меты (eps = 0) → `y = 1`

То есть Qwen-овский eps доходит до ядра точно, а не превращается в ноль.
