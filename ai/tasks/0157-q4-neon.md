# Скорость Q4

## Проблема

3B Q4 в нашем рантайме идёт **4,2 с/токен (0,2 ток/с)** против ~20 ток/с у ollama.
Причина: Q4-ядра скалярные (0152), без NEON и без батчинга; деквантизация идёт
по строке в double-scratch.

## Требования

- NEON-путь `vtm_q4_tmv/mm`: деквантизация в int8/fp32 векторами, `vmlaq`/`vdotq_s32`
  где доступно; скалярный хвост.
- Батчинг для prefill: MM по Q4 при n>1 не должен деквантизовать строку на каждый
  столбец (сейчас именно так) — хотя бы общий буфер строки.
- Цель: **≥2 ток/с на 3B** (в 10 раз быстрее), prefill — не хуже.
- Точность: совпадение со скалярным путём ≤1e-5 (или побитово, если удастся).
- Замер до/после: 3B Q4 (`runs/q4/3b.vtm`), 0,5B Q4, 4096×4096.

## Критерии приёмки

- [x] 3B Q4 ≥2 ток/с (замер в отчёте)
- [x] точность NEON против скаляра ≤1e-5
- [x] `make test` и `bench_backend --q4 --check` зелёные

## Отчёт исполнителя

Сделано: NEON-путь Q4 (`vtm_neon_q4_tmv_rows/mm_rows/dequant_row`), общий буфер
строки в MM при n>1 (и в скаляре — побитово прежний результат), рантайм-диспетчеризация,
`VTM_Q4_SCALAR=1` для A/B. 7,8× на 151936×896 (91,6 GFLOP/s против 11,1), 7,7–7,8×
на 4096×4096. Точность NEON против скаляра ≤8,6e-6 при пороге 1e-5.

**Сквозь 3B Q4:** было 4,6–4,9 с CPU/токен (0,2 ток/с по печати), стало
1,07–1,20 с/токен; wall-декод **3,8 ток/с** (замер после правки печати). Вывод модели
не изменился (11 16 15 15).

**Попутно исправлена метрика CLI:** `vtm` печатал ток/с по `clock()` — это сумма
времени всех потоков, поэтому на 8 ядрах показывал 0,2 ток/с там, где реально 3,8.
Теперь печатается wall clock.

**Остаток:** 33% времени — плотный fp32 lm_head (1,24 ГБ, 60% файла), считается
скалярным double-MM; подключение существующего `vtm_simd_mm_f32` даст ~1,7–1,8 ток/с
по CPU-метрике — задача 0158. AVX2-путь Q4 не сделан (нет x86-железа для проверки).
