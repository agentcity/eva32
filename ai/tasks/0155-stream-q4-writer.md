# Потоковая запись Q4

## Проблема

Полный 3B Q4 не собирается: `vtm_ref.decode_q4_segment_ex` возвращает `list[int]`
(2,77 млрд значений ≈ 22 ГиБ указателей), а `pack_q4` в `write_vtm` материализует
ещё один такой список — пик ~45 ГиБ на машине с 16 ГиБ.

Сам контейнер влезает: 3B Q4 ≈ 1,92 ГиБ (u32-смещения), 7B ≈ 3,9 ГиБ при fp16-масштабах.

## Требования

- `tools/vtm_ref.py`: запись Q4 **потоково** — чанки по группам 32 (или по строкам),
  без промежуточных `list[int]` на весь тензор.
- `decode_q4_segment_ex` — вариант с итератором/чанками, который не держит весь тензор;
  старый API сохранить для мелких тестов (или сделать тонкой обёрткой).
- Пик памяти на 3B ≤ 2 ГиБ, на 7B ≤ 3 ГиБ; замер в отчёте.
- Проверка: полный 3B Q4 (импорт 0153 → компиляция → контейнер) собирается,
  C запускает 1 токен, паритет с Python ≤1e-5; файл ≤ 4 ГиБ (ADR 0016) или
  документированный отказ для 7B с fp32-масштабами.
- Не менять формат: байты контейнера должны совпадать с текущим побайтово
  (сверка sha256 на срезе).

## Критерии приёмки

- [ ] полный 3B Q4 собран, C считает токен, паритет ≤1e-5
- [ ] пик RSS ≤ 2 ГиБ (замер)
- [ ] байты контейнера совпадают с текущим путём (sha256 на срезе)
- [ ] 7B: либо собран, либо отказ с числами (fp32 vs fp16-масштабы)
