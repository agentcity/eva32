# Холодный старт Silero убивает диалог

## Проблема
Сейчас каждая новая фраза = новый процесс: torch + модель грузятся заново.
Замеры 0193: первая фраза 3,85 с, новая 2,65 с, из кэша 0,4 мс. Для разговора
это недопустимо: фраза 1 с ждёт 3 с.

## Требования
1. **Постоянный worker** `tools/silero_worker.py`: загружает модель один раз,
   принимает фразы по протоколу (JSON-строки или длина+payload через stdin/stdout
   или UNIX-сокет в /tmp), отдаёт путь к WAV/байты, работает до остановки.
2. **eva/tts.py**: ленивый старт worker при первом синтезе, keep-alive,
   авто-перезапуск при падении/таймауте (1 раз), lock — один запрос за раз,
   корректное завершение по atexit.
3. **Цель**: первая фраза после старта ≤2 с (включая загрузку модели),
   последующие ≤1,2 с, память одного процесса (не плодить копии).
4. Откат: worker не поднялся/умер → Piper (как сейчас), без падения чата.
5. Тесты: мок процесса (без реальной модели) — протокол, перезапуск, таймаут,
   конкурентные вызовы; реальный синтез не в тестах.

## Критерии приёмки
- [ ] новая фраза ≤1,2 с, первая ≤2 с (замер)
- [ ] RSS worker один (нет накопления процессов), idle CPU ~0%
- [ ] падение worker → откат на Piper, следующий вызов поднимает заново
- [ ] тесты на моке, полный набор зелёный

## Отчёт исполнителя

Сделано (зона соблюдена; `apps/eva/*`, `src/vtm/*`, `tools/chat_server.py`,
`tools/silero_speak.py` не трогались):

- `tools/silero_worker.py` — новый долгоживущий синтезатор: `torch` и модель
  `v4_ru` загружаются **один раз**, дальше процесс читает JSON-строки со
  stdin и отвечает JSON-строками в stdout (`{"text","speaker","out"}` →
  `{"ok":true,"ms":…}`; без `"out"` — WAV в `wav_b64`; `cmd: ping/shutdown`).
  Стартовая строка `{"ok":true,"ready":true,"load_ms":…,"import_ms":…,
  "model_ms":…,"rss_mb":…}`, `rss_mb`/`cpu_s` в `ready`/`ping` — замеры без
  `ps`. Ошибка фразы → `ok:false`, процесс продолжает работать. EOF и
  `SIGTERM`/`SIGINT` — штатный выход с кодом 0. Загрузка модели и запись WAV
  переиспользуют `tools/silero_speak.py` (приватные хелперы), чтобы
  одноразовый и долгоживущий пути не разъезжались. Дополнительно: отключён
  profiling-executor TorchScript (`SILERO_JIT_PROFILING=0` по умолчанию) —
  второй и следующие вызовы 0,03–0,25 с вместо ~0,85 с, звук бит-в-бит тот
  же (сверено по PCM).
- `eva/tts.py` — `SileroWorker` (клиент протокола: pipes, поток-читатель,
  очередь ответов, таймауты), модульный синглтон (один worker на процесс
  чата, `select_engine` создаёт адаптер на запрос), `RLock` — один запрос за
  раз, ленивый старт при первой фразе, `ping` после `ready`, `describe()` =
  `silero (worker, pid N; …)`, `silero_worker_info()`, один перезапуск при
  падении, таймаут запроса 20 с (`SILERO_WORKER_TIMEOUT`) → worker убит,
  фраза уходит на Piper, следующий вызов поднимает заново, `atexit` →
  `shutdown`/`SIGTERM`/`SIGKILL`. LRU-кэш сохранён (повтор фразы вообще не
  трогает worker). Одноразовый путь 0193 остался под `SILERO_WORKER=0`.
  Добавлен `prewarm_silero_worker()` — фоновый старт worker'а плюс прогрев
  первого `apply_tts` пробной фразой (по умолчанию не вызывается: остаётся
  ленивый старт; вызов — одна строка при старте сервера).
- `tests/test_tts_silero.py` — 53 теста: протокол worker'а in-process на
  фейковом backend'е (ready/ping/synth/WAV/base64/битый JSON/пустой
  текст/чужой голос/сбой модели/shutdown/EOF/SIGTERM/load-fail), клиент на
  эмуляторе пайпов (старт и keep-alive, ping, синглтон, `describe`, env,
  падение → ровно один перезапуск, двойное падение → откат на Piper,
  таймаут → убит и следующий вызов поднимает заново, `ok:false` без
  перезапуска, prewarm с прогревом, stop идемпотентен, lock: 4 потока, ответы
  не путаются), плюс сохранённые тесты одноразового пути и выбора движка.
  Реальный torch не импортируется.
- `docs/hybrid.md` — новый раздел «Worker: модель загружается один раз»,
  переписанные «Как устроен синтез», «Время и память», «Переменные»,
  «Откат», «Проверка» (реальные замеры до/после, протокол, prewarm).
  `README.md` — как устроена озвучка и цифры задержки.

Честно про цель «первая фраза ≤2 с»: **ленивым стартом она не достигается**
(2,6–3,3 с: 1,3–1,8 с старт + ~1,2 с первый `apply_tts`, где TorchScript
оптимизирует граф). Она достигается prewarm'ом: worker поднимается фоном при
старте сервера (готов через 2,4–3,1 с) и первая фраза идёт 0,10–0,17 с.
Сам prewarm-вызов — одна строка в `tools/chat_server.py`
(`prewarm_silero_worker()` рядом с созданием сервера), файл вне моей зоны.
Цель «новая фраза ≤1,2 с» перевыполнена в ~15–30 раз (0,03–0,08 с).

Живая интеграция через `tools/chat_server.py --port 8917` (файл не
менялся): `POST /api/tts` → `audio/wav`, RIFF 48 кГц mono 16 бит; первый
запрос 3,52 с (холодный worker), та же фраза из кэша 0,01 с, новые фразы
0,09 с и 0,04 с. После `SIGTERM` сервера worker не остаётся (pid завершён,
orphan'ов нет).

Риски:

- **Первая фраза без prewarm 2,6–3,3 с.** Причина — не worker, а `import
  torch` (0,8–1,2 с) + `torch.hub.load` (0,7–1,1 с) + первая JIT-оптимизация
  графа (~1,2 с). Меньше сделать нельзя, не переписав загрузку модели;
  закрывается prewarm'ом (вне зоны — одна строка в `tools/chat_server.py`).
- **RSS одного worker'а 0,84–0,93 ГБ** (пик, `ru_maxrss`) — больше, чем 550–
  790 МБ одноразового процесса: torch + модель + планы JIT живут постоянно.
  Это цена одного процесса вместо дерева, но на 8-ГБ машине заметно. Процесс
  ровно один, на 20 фразах PID и RSS стабильны (плато, не течёт).
- **Приватный API torch**: `torch._C._jit_set_profiling_executor(False)`.
  Вызов обёрнут в try/except и отключается `SILERO_JIT_PROFILING=1`; при
  смене torch (вендорный 2.15.0) режим тихо вернётся к дефолтному, синтез не
  сломается — только вторая фраза станет ~0,85 с.
- **Worker — синглтон на процесс.** Две разные конфигурации Silero (разные
  `SILERO_PYTHON`/скрипт) в одном процессе перезапускают worker друг за
  другом, а не живут параллельно. Для чата это норма (конфигурация одна), но
  встраивание с разными env получит лишний старт.
- **Таймаут 20 с не повторяет фразу**: после него текущая фраза уходит на
  Piper (без 2×20 с ожидания), а worker поднимается на следующем вызове.
  Если нужно «дождаться и повторить» — это уже другая политика.
- **stderr worker'а пишется в `TemporaryFile`** и растёт, если torch начнёт
  сыпать предупреждения на каждую фразу. Сейчас предупреждения одноразовые
  (кэш hub), но при отладке `TORCH_LOGS=...` файл может вырасти.
