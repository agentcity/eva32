# GPU выигрывает на пачке, CPU — на декоде

## Замеры 0196 (парные, одна машина)
| | simd (CPU) | metal (GPU) |
|---|---|---|
| prefill 64 токена | 19,6 ток/с (TTFT 3,27 с) | **34,0 ток/с (TTFT 1,88 с)** |
| декод | **19,4 ток/с** | 8,5 ток/с |

То есть **выигрыш GPU — только на батче** (GEMM переиспользует строку весов),
а на декоде (GEMV, 181 вызов, полоса 20–30 ГБ/с) GPU проигрывает в 2,3 раза.

## Задача: гибридный режим
1. `VTM_BACKEND=hybrid`: **батчевые операции** (prefill GEMM kind 4/6/7) идут на
   Metal, **одиночные GEMV** — на NEON. Механизм: в metal-бэкенде GEMV возвращает
   «не умею» (или env `VTM_METAL_DECODE=0`), диспетчер падает на simd; либо явная
   развилка по контексту (batch_tmv/batch_mm → metal; tmv/mm с n=1 → simd).
2. `auto` = hybrid **только если** парный замер показывает, что гибрид быстрее
   чистого simd и в prefill (≥1,3×) и в декоде (≥1,0×). Иначе auto остаётся simd,
   а hybrid — явно.
3. Единый прогон не должен терять корректность: точность (argmax 3/3, Δlogits ≤1e-2),
   откат при любой ошибке Metal → чистый simd.
4. Замеры: prefill 64/128 токенов, TTFT, декод (tok/s), CPU-время; сравнение
   simd / metal / hybrid в одном окне, парно. Размер буферов и RSS.

## Критерии приёмки
- [x] hybrid: prefill ≥1,5× быстрее simd, декод не хуже simd (в пределах шума)
- [x] TTFT 64 токена ≤2 с в гибриде
- [x] точность как у simd (argmax, Δlogits), откат работает
- [x] `auto` выставлен по замеру, решение задокументировано числами
- [x] `make test`, `--check`, TSan, Python-набор зелёные

## Отчёт исполнителя

**Статус: гибрид реализован, `auto` переключён на hybrid по парному замеру.**
Prefill 64 — 1,96–2,00× (TTFT 3,28 → 1,64 с), prefill 128 — 1,86–1,89×
(TTFT 6,6 → 3,6 с), декод 0,98–0,99× (шум: в гибриде те же NEON-ядра и тот же
порядок сложения). Точность: на трёх промптах Δ = 0 (тот же CPU-путь), на
пачке 64 Δ = 2,05e-5 при совпавшем argmax. Откат по `VTM_METAL_FORCE_FAIL`
даёт побитово simd. Памяти гибрид не добавляет: zero-copy 1896,5 МиБ,
копий 0, RSS после prefill одинаков у simd/metal/hybrid.

### Развилка: режим диспетчера, а не «не умею» из ядра

Выбран вариант (б) — явная развилка в диспетчере, но не сравнением имени на
каждой инструкции, а режимом Metal:

- `vtm_backend.h`: `VTM_METAL_OFF | FULL | BATCH`;
  `vtm_metal_active()` = режим ≠ OFF (его спрашивают батчевые пути),
  `vtm_metal_gemv_active()` = только FULL (поштучные GEMV/MM n == 1).
- `backend_metal.m`: режим — атомарный int; `vtm_backend_hybrid()` — копия
  описателя simd с именем `hybrid`; ошибка командного буфера GEMM выключает
  режим, и остаток прогона считает CPU.
- `backend_neon.c`: `VTM_BACKEND=hybrid|auto` ставят BATCH и возвращают
  `vtm_backend_hybrid()` (auto — только если Metal собран и устройство есть);
  без Metal — предупреждение и simd.
- `backend_scalar.c`: `vtm_q4k_tmv`/`vtm_q6k_tmv`/`vtm_i8_gemv` смотрят
  `vtm_metal_gemv_active()`; `vtm_backend_note_active()` переводит имя
  бэкенда в режим (`hybrid` → BATCH, `metal` → FULL, остальное → OFF).
- `interp.c`: батчевые пути по-прежнему по `vtm_metal_active()`;
  `batch_backend_enabled`/`batch_use_simd` знают `hybrid`; сессия отложенной
  очереди декода открывается только при `vtm_metal_gemv_active()`.

Почему (б), а не (а): GEMV kind 4/6/7 вызываются из `interp.c` не через
vtable, а глобальными функциями (`vtm_q4k_tmv`, `vtm_q6k_tmv`, `vtm_i8_gemv`)
— теми же, которыми считает полный `metal` и CPU-откат. «Не умею» из
Metal-ядра пришлось бы возвращать через них же, то есть добавить ту же
проверку, но в ядре, и смешать с `-1`, который уже значит «Metal ошибся»
(теряется диагностика). Режим-бит ставится в одной точке
(`vtm_backend_by_name`/`vtm_backend_note_active`) и не стоит сравнения строк
на каждой инструкции.

### auto

Условие 0198: prefill ≥ 1,3× и декод ≥ 1,0× simd. Замер: 1,86–2,00× и
0,98–0,99× (декод гибрида — буквально те же NEON-ядра; разница — планировщик
занятой машины). Условие выполнено, поэтому `auto` = hybrid, когда Metal
собран и устройство есть; иначе прежний simd (сборка без Metal, машина без
GPU). Вернуть simd: `VTM_AUTO_HYBRID 0` в `backend_neon.c` или
`VTM_BACKEND=simd`.

### Холодный старт (риск, не критерий)

Парный замер выше — установившийся режим в одном процессе (как в 0196).
Первый батчевый GEMM в процессе платит компиляцию MSL (~0,2–0,4 с) и
привязку весов zero-copy (~1900 `MTLBuffer`). В одноразовом `vtm run`
(`--prefill-batch 32`, `--tokens`, время — prefill + 1 токен):

| prefill | simd | hybrid |
|---|---|---|
| 8 токенов | 0,45 с | 1,63 с |
| 32 токена | 1,69 с | 2,04 с |
| 64 токена | 3,27 с | 2,91 с |

То есть одноразовый короткий промпт (8–32 токена) в гибриде медленнее на
~0,4–1,2 с, а 64+ — уже быстрее. Для сервера (модель загружена один раз,
запросов много) это разовая цена; для одноразового CLI с коротким промптом
быстрый путь — `VTM_BACKEND=simd`.

  токен, чем simd: расхождение 2e-5 на логитах пачки переставляет два почти
  равных кандидата; это свойство допуска 1e-2 (0196), а не развилки.
