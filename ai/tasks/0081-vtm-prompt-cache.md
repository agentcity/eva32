# Кэш промпта: не пересчитывать одинаковый префикс

## Проблема

Системный промпт у нас 4,4 КБ и повторяется в каждом запросе. Сейчас каждый прогон
заново считает весь промпт: для голоса это половина задержки. Профиль 0071 показал,
что проход по 512 токенам стоит десятки миллисекунд.

## Требования

- `vtm_cache_prefix(m, ids, n)`: посчитать и запомнить K/V для префикса.
- `vtm_run_with_cache(m, ids, n)`: если начало совпадает с закэшированным префиксом —
  пропустить пересчёт, продолжить с позиции len(prefix); иначе честный полный прогон.
- Сравнение префикса — по хешу (sha256 уже есть в loader.c: `vtm_sha256_*`) или
  побайтово по ids; выбрать и обосновать.
- Инвалидация: `vtm_reset` очищает кэш; смена бэкенда/модели — тоже.
- Замер: 128-токенный префикс + 16 новых токенов, до/после (мс), числа в отчёте.

## Критерии приёмки

[ ] повторный прогон с тем же префиксом даёт те же токены (тест)
[ ] ускорение на префиксе 128 токенов замерено (мс до/после)
[ ] несовпадающий префикс даёт полный прогон и правильный результат (тест)
[ ] make test и полный Python-набор зелёные

## Контекст и ограничения

- Зона: src/vtm/interp.c, src/vtm/vtm.h, src/vtm/vtm_internal.h, tests/vtm/test_vtm.c
- Другие файлы НЕ трогать: параллельно работают другие агенты и ещё не закончил
  агент потоков (он держит `backend_*.c`) — их не касайся.
- Сборка: `cd src/vtm && make test`; `-Wall -Wextra -Werror`. По умолчанию `VTM_BACKEND=auto`.
- **Отчёт пиши первым блоком в ответе**, потом детали: агенты этой сессии падают в конце.
- Не коммитить: сдавать правки и отчёт.
