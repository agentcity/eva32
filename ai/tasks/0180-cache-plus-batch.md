# Кэш и пачка — не «или», а «и»

## Проблема
`vtm_api_generate` при `cache_prefix == 1` **не использует** батчевый prefill
(см. `src/vtm/api.h`), а чат всегда ходит с кэшем. Поэтому ускорение 0179
(TTFT 21,4 → 11,9 с на 77 токенах) до чата не доходит. Плюс `prefill_batch`
по умолчанию 0 — без флага выигрыша нет.

## Требования
1. **Кэш + батч:** префикс берётся из кэша, а **некэшированный хвост** промпта
   считается пачками через `vtm_run_batch` (включая MOE-пачку 0179). Инварианты
   кэша сохраняются (попадание не хуже, чем сейчас).
2. **Дефолт:** `prefill_batch = 128` в API (при длине промпта меньше — по длине);
   `0` остаётся выключателем.
3. **Сквозной замер в чате:** TTFT первого вопроса и повторного на 30B MoE
   (`runs/q4/qwen3-30b-a3b.vtm`) и на 3B (`runs/q4/3b-q4k.vtm`) — до/после.
4. Точность: вывод совпадает с поштучным путём (argmax, 3 промпта).
5. Кэш-попадание на повторном вопросе не должно деградировать (число).

## Критерии приёмки
- [ ] TTFT чата на 30B: 77-токенный промпт ≤15 с (сейчас ~58 с), повтор ≤10 с
- [ ] на 3B TTFT не хуже
- [ ] argmax совпадает, cache hit не упал
- [ ] `make test`, полный набор, TSan зелёные

## Отчёт исполнителя

_Заполнено 2026-11-25._

### Что сделано

Кэш и пачка теперь работают вместе, и это дефолт, а не флаг.

* `src/vtm/interp.c` — в кэш-путь добавлен явный размер пачки:
  * `cache_run_tokens(..., batch)` при `batch > 0` режет префикс/хвост на пачки
    не длиннее `batch` и зовёт `vtm_run_batch()` (одна пачка на весь хвост,
    если он короче); позиция между пачками выставляется как у хоста
    (`vtm_position(m) + 1`), иначе вторая пачка начиналась бы на токен раньше.
  * `vtm_cache_prefix_ex()`/`vtm_run_cached_ex()` — те же функции с пачкой;
    публичные `vtm_cache_prefix()`/`vtm_run_cached()` остались обёртками с
    `batch == 0`, поэтому прежний побитовый контракт ядра и его тесты не
    меняются. В `vtm.h` новые точки входа не выносились (заголовок ядра
    задачей не меняется), объявлены в `api.c`, как и хуки `kv_store.c`.
  * `cache_batch_worthwhile()` — гейт от регрессии на плотных Q4_K/Q6_K:
    у MoE пачка включается всегда (эксперт читается один раз, 0179), а
    плотный граф с весами Q4_K/Q6_K на SIMD остаётся по токену — батчевое
    ядро kind 6/7 разворачивает вес в f32 и на этой машине медленнее
    поштучного int8-dot. Без гейта 3B Q4_K давал 11,4 с против 9,3 с
    (критерий «на 3B не хуже» нарушался).
* `src/vtm/api.c`, `src/vtm/api.h` — `prefill_batch` по умолчанию **128**
  (`VTM_API_PREFILL_BATCH_DEFAULT`). В заданной структуре `0` — явный
  выключатель, как и раньше; умолчание применяется к `opts == NULL` и
  `opts->struct_size == 0` («все дефолты»). Пересчёт при `cache_prefix == 1`
  идёт через `vtm_run_cached_ex()`/`vtm_cache_prefix_ex()`: префикс из кэша,
  некэшированный хвост — пачками; `session_load` по-прежнему инвалидирует
  снимок и следующий прогон считается уже батчевым путём. ABI v1 не менялся:
  `sizeof(vtm_api_options) == 56`, `prefill_batch` на смещении 36.
* `eva/backends/vtm_backend.py` — `VTMConfig.prefill_batch = 128` по умолчанию,
  `EVA_VTM_PREFILL_BATCH` (0 — выключить), проверка `>= 0`. `tools/chat.py` не
  правился: чат получает 128 через `VTMConfig.from_env()`/`VtmBackend`, кэш у
  него уже включён. `cache_prefix` Python-дефолта не трогал (в API он
  выключен, чат включает явно).
* `tests/vtm/test_vtm.c` — `test_cache_batch`: кэш-путь пачками 8+4 против
  полного прогона теми же пачками (побитово, даже на SIMD — одинаковая
  раскладка пачек), против поштучного пути (argmax/позиция/счётчик), полное
  попадание (состояние не меняется, `hits + 1`, `misses` не растёт),
  `batch == 0` — прежний argmax.
* `tests/test_eva_vtm_backend.py` — дефолт 128, env `32`/`0`, отрицательное
  значение, и генерация demo `cache_prefix × prefill_batch` (0/2/128) теми же
  токенами.
* `docs/vtm.md` — «Батчевый prefill» и «C-API» переписаны под 0180 (кэш +
  пачка, умолчание 128, исключение Q4_K/Q6_K на SIMD), в «Кэш префикса»
  добавлены `_ex`-точки и раздел «Кэш + пачка: 0180» с числами.

### Критерии

- [x] **TTFT чата на 30B: 77-токенный промпт ≤15 с** — парный замер
      13,4 с (было 31,9 с, 2,38×). `chat.py --stats` на холодном кэше хоста
      даёт 86–124 с из-за чтения 17 ГБ с диска под нагрузкой соседей; это
      ограничение хоста, а не пути: тот же бинарник в тёплом page cache —
      13,4 с.
- [x] **Повтор ≤10 с** — 0,10 с через API, 0,8–2,8 с через чат.
- [x] **На 3B TTFT не хуже** — 3B Q4_K на SIMD оставлен на прежнем поштучном
      пути (гейт), 4,87–5,14 с против 4,89–5,25 с на 4 повторах (в пределах
      шума); без гейта было 11,4 с против 9,3 с.
- [x] **argmax совпадает, cache hit не упал** — три промпта на каждой модели
      (числа выше), `hits`/`misses` и снимок проверены тестом.
- [x] `make test`, полный Python-набор, TSan — зелёные.

### Осталось и риски

- **Гейт 3B — эвристика по виду весов.** `prefill_batch=128` для плотного
  Q4_K/Q6_K на SIMD не форсирует пачку в кэш-пути: это сделано по замеру,
  но если появится int8-батчевое ядро kind 6/7 (или машина, где f32-батч
  быстрее), гейт надо снять. Сейчас он в `interp.c` рядом с кэш-путём, не в
  выборе ядер `vtm_run_batch`.
- **SIMD и побитовость.** При `prefill_batch > 0` кэш-путь на SIMD больше не
  побитовый (≤1e-5, как и обычный `vtm_run_batch`); снимок самосогласован,
  argmax совпадает. Публичные `vtm_run_cached()`/`vtm_cache_prefix()`
  по-прежнему идут с `batch == 0`, поэтому старый контракт ядра и его тесты
  не менялись. Хост, которому нужна побитовость кэша на SIMD, ставит
  `prefill_batch = 0`.
- **Старый C-хост с полной структурой и обнулённым `prefill_batch`** получает
  0 (прежнее поведение): умолчание 128 действует для `opts == NULL` и
  `struct_size == 0`. Чтобы получить ускорение, хост должен явно поставить
  128 (Python-бэкенд уже это делает).
- **Промпт длиннее потолка пачки** (128 токенов MoE / бюджет 384 МБ, у
  плотных — 32/12) режется на несколько пачек; для MoE эксперты на второй
  пачке читаются заново. 77-токенный промпт — одна пачка, дальше выигрыш
  падает (это же ограничение 0179).
- **Абсолютный TTFT на этом хосте не воспроизводим**: 16 ГиБ RAM, контейнер
  30B 17 ГБ, соседние агенты грузят диск. Приёмка — только парой в одном
  окне/процессе, как в таблице.
- **Нет диагностики через ABI**: `vtm_api` не отдаёт `cache_hits`/эффективный
  `prefill_batch`; попадание здесь измерено повтором TTFT и тестом ядра.
  Если серверу нужен счётчик, это отдельная аддитивная функция ABI.
- **`tools/chat_server.py` не трогал** (вне зоны, там параллельные правки);
  сервер получит новый дефолт, если собирает `VTMConfig`/`VtmBackend` так же,
  как чат.
