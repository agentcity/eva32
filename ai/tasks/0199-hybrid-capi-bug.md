# Гибрид верен в `vtm run`, но ломается в чате

## Симптом (воспроизведено)
```
VTM_BACKEND=simd  python3 tools/chat.py --once "Скажи одно слово: работает?"
  → «В этом ответе я использов…» (связно, хоть и слабо)
VTM_BACKEND=hybrid … та же команда
  → «是（ 的产物， 的产物， 的产物， 的»   ← мусор
```
Через сервер то же: simd отвечает «Да.», hybrid — «оцените, что? Сложно…».

При этом **прямой CLI** (`vtm run --tokens … --prefill-batch 64`) на simd и hybrid
даёт **одинаковые токены** (проверено на 24/40/64 токенах).

## Что это значит
Разница только в пути: `vtm_api_generate` (C-ABI eva-бэкенда) против `vtm run`.
В API-пути работают: кэш префикса, `prefill_batch=256`, сессия командного буфера
на весь прогон. Похоже на гонку/недосыл: GPU-батч возвращает управление, CPU
читает активации до завершения командного буфера (эффект ping-pong `defer_submit`).

## Требования
1. Воспроизвести минимально: `vtm_api_generate` с `cache_prefix=1` и
   `prefill_batch>0` на 3B, оба бэкенда; сравнить токены greedy.
2. Найти место, где результат GPU читается до `waitUntilCompleted` (или где
   `defer_submit` не сбрасывается в конце прогона/перед снимком кэша), и
   исправить в `backend_metal.m`/`interp.c`.
3. **Тест-страж**: паритет «simd vs hybrid» по сгенерированным токенам (greedy,
   3 промпта) через C-ABI, а не только по Δlogits одного forward. Такой тест
   поймал бы это сразу.
4. Только после зелёного теста — вернуть `VTM_AUTO_HYBRID 1` (одна константа).

## Критерии приёмки
- [x] `chat.py`/API на hybrid даёт те же токены, что simd (greedy)
- [x] тест-страж в наборе, падает на старом коде
- [x] prefill-выигрыш сохраняется (≥1,5x к simd)
- [x] `make test`, TSan, полный Python-набор зелёные

## Отчёт исполнителя

**Статус: исправлено. `VTM_AUTO_HYBRID` снова 1.** Причина — не гонка, а
детерминированный шаг строки результата GPU-батча.

### Причина

Гипотезу проверил по порядку вызовов и отверг:

* `vtm_metal_qk_gemm` → `metal_gemm_body` делает `commit` +
  `waitUntilCompleted`, проверяет `status` и только потом копирует из
  `g_gybuf`; чтения «до окончания GPU» нет.
* `cache_store()` снимает K/V уже после возврата `vtm_run_batch`, то есть
  после синхронного копирования.
* в hybrid (`VTM_METAL_BATCH`) отложенная очередь декода вообще не
  открывается (`vtm_metal_gemv_active()` ложно), `defer_submit` в этом пути
  не участвует. `деfer`-сессия — свойство FULL.

Реальный дефект — в `metal_gemm_body` (`backend_metal.m`). Ядро пишет строку
результата шириной `N` выбранного варианта (`gemm8/16/32`) и добивает хвост
пачки нулями в `xt`, а хост копировал

```c
y[r * n_tokens + j0 + j] = yt[r * nt + j];   // было: шаг chunk'а
```

где `nt` — длина последнего chunk'а, а не `N`. При `nt != N` строки
результата сдвигались: 11 токенов → gemm16, 24/31 → gemm32, 44 → 32+12.
Мусором становился не только выход слоя, но и K/V префикса — отсюда
бессвязный текст при верном одиночном forward. Исправлено на шаг ядра:

```c
y[r * n_tokens + j0 + j] = yt[r * vn + j];   // vn = 8/16/32, ширина строки ядра
```

Почему прежние проверки не ловили: `bench_backend --check` брал длины пачки
8/16/32 (там `nt == N`) или < 8 (GEMM отказывал, считал CPU); CLI-прогоны
0198 на «круглых» пачках режутся на полные 32-токенные chunk'и (40 → 32+7,
хвост 7 уходил на CPU). В моём воспроизведении CLI на 24 и 64 токенах тоже
расходится — совпадал только 40.

### Синхронизация (второй дефект, не причина мусора)

В failing-пути гонки нет. Но при разборе нашёлся реальный разрыв замков:
`vtm_metal_defer_gemv` звал `metal_init()`/`metal_bind()` (общий кэш
`g_binds`, `g_init`) только под `g_defer_lock`, тогда как синхронный GEMV и
батчевый GEMM держат `g_lock`. При двух контекстах в разных потоках (FULL +
BATCH) это гонка на LRU-вытеснении MTLBuffer и на инициализации. Закрыто
обёртками `defer_metal_init`/`defer_metal_bind`: они берут `g_lock` на время
init/bind, порядок замков `defer -> g` совпадает с `vtm_metal_forget_all`.
На hybrid это не влияет (defer там не открывается); FULL-режим проверен —
паритет токенов с simd сохранён.

   1e-2 (контракт 0192). **На старом коде падают 8 случаев** с ошибкой

### Риски

- **Глобальный режим Metal.** `vtm_metal_set_mode()` — на процесс, а не на
  контекст: открытие hybrid переводит в BATCH и уже открытый simd-контекст
  (на этом я первый раз получил ложный паритет). Не исправлено — `api.c` вне
  зоны; в тесте поэтому один бэкенд на процесс. Для сервера с одним контекстом
  не проявляется; стоит завести отдельную задачу на режим в контексте.
- **C-ABI-страж зависит от модели:** без `runs/q4/3b-q4k.vtm` тест
  пропускается. Синтетическая проверка в `--check` от модели не зависит, но
  ловит только уровень GEMM, не весь путь `vtm_api_generate`.
- **Паритет по токенам — не побитовый контракт GPU:** при почти равных
  кандидатах argmax может переставиться (0196/0198: Δ логитов ≤ 1e-2). Страж
  фиксирует три промпта, где после правки последовательности совпадают.
- **Холодный старт:** в этом прогоне MSL компилировался 0,57 с; `auto=hybrid`
  для одноразового короткого промпта по-прежнему медленнее simd (риск 0198,
  не решался).
- **Замки закрыты только для init/bind defer-пути;** счётчики статистики
  (`g_fail`, `g_calls`, `g_wait_ns`) по-прежнему пишутся из разных путей без
  общего замка — это диагностика, не данные вычислений; TSan-сборка Metal
  выключает, так что автоматически не ловится.
