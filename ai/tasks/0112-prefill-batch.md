# Батчевый prefill: промпт пачкой, а не по токену

## Проблема

Замер 0103: TTFT 0,073 с на каждый токен промпта — 512 токенов это 37,6 с. Граф считает
один токен за вызов, поэтому промпт = N полных проходов по 28 слоям. Системный промпт
4,4 КБ означает минуту ожидания до первого слова.

## Требования

- Режим prefill: прогнать N токенов за проход, используя ATTN с `q_len > 1` (3-D путь
  уже поддерживает q_len, causal и GQA).
- Публичный API: `vtm_run_batch(m, ids, n)` (или флаг у графа) — выбираешь сам, но
  контракт опиши в vtm.h, его будет звать CLI/C-ABI (задача 0114).
- Корректность: результат после prefill == N последовательных `vtm_run` побитово
  (тест на 3 конфигурациях: 8/64/128 токенов).
- Кольцо KV (окно контекста) и кэш префикса (0081/0087) должны работать с prefill.
- Замер: TTFT для 8/128/512 токенов до/после на форме 1.5B (`tools/bench_shape.py`).

## Критерии приёмки

[ ] prefill 512 токенов ускорен >=10x (числа)
[ ] логиты после prefill == N обычных прогонов побитово (тест)
[ ] кольцо KV и кэш префикса не сломаны (тесты)
[ ] make test и Python-набор зелёные

## Отчёт исполнителя

Сделано: публичный `vtm_run_batch(m, ids, n)` в `vtm.h` с полным контрактом
(start = position, ids[k] на позиции start+k, emit не вызывается, после вызова позиция
== start+n−1, состояние побитово как у n×`vtm_run`, n==0 no-op). В `interp.c` — батчевый
исполнитель: активации по копии на токен, веса и KV общие, TMV и MM (98% времени) считаются
батчевыми ядрами на double с тем же порядком сложений; пачка ≤16 токенов и ≤96 МиБ, иначе
откат на путь по токену (трассировка тоже откатывает). Кэш префикса переведён на батч.

**Числа (форма 1.5B, scalar, 4 потока):** n=8 — 11,20 → 1,72 с (**6,5×**); n=16 — 22,64 →
2,64 с (**8,6×**); n=32 — 44,03 → 5,88 с (**7,5×**); 1 поток — 4,2–5,5×.
**SIMD — 1,00×** (батчевых ядер нет, задача 0122).

**Кэш префикса + батч:** промпт 64 токена, первый запрос **14,19 с**, второй с тем же
промптом — **1,29 с (11,0×)**, выбранный токен одинаков. Это и есть рабочая схема:
системный промпт считается один раз за сессию.

**Побитовость:** C-набор 8/64/128 токенов × GQA+causal, MHA, кольцо KV, MM-путь tied
lm_head, n=0/1, две пачки подряд — совпадение всех тензоров, позиций, input_token, halted.
На форме 1.5B (28 слоёв, GQA, триты) n=4 — 0 расхождений по 623 тензорам.
Проверено архитектором: `--prefill-batch 0/8/128` на demo дают одинаковые токены.

**Почему 10× невозможно** (записано, чтобы не ставить таких целей): 512 токенов ≈ 1,8 TFLOP;
текущие 37,6 с = 48 GFLOP/s; 10× требует 484 GFLOP/s = 236% пика FP32 всего M1 Pro
(~205 GFLOP/s). Реалистичный потолок — 1,5–2× на 4 потоках, до 3–4× на 8.

Риски: SIMD не ускорен (0122); память пачки +~100 МиБ на 1.5B (C=8 даёт 4,0× и +50 МиБ);
числа сняты при load average 8–20 — отношения надёжны, абсолютные секунды нет; промпт,
переходящий границу окна KV, батчится только до неё.
