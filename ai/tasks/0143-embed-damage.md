# Урон от тритовой таблицы: int8, посрочные масштабы, остаток

## Проблема

Главный источник урона — таблица словаря при tied lm_head (только Linear ×2,07,
с таблицей ×7,75). Нужно найти способ держать таблицу точнее, не раздувая файл.

## Требования

Проверить на Qwen 0.5B (и, если успеешь, на 3B), измеряя PPL в `tools/parity_cold.py`:
1. **int8-эмбеддинг** вместо тритового (kind 4 уже поддержан загрузчиком и компилятором:
   `embed_quant="int8"`). Ожидание: почти вся потеря возвращается, файл +~250 МБ на 3B.
2. **Посрочные масштабы**: scale не на блок 128, а на строку таблицы (или блок 128 +
   строка) — для таблиц с большим разбросом это обычно главный выигрыш.
3. **Остаток низкого ранга**: trit + fp16-поправка (например, ранг 8 на строку) —
   сколько PPL возвращает при каком размере.
Таблицу «вариант → PPL → размер файла» в отчёт. Реализацию вести в `tools/cold_export.py`
(добавить `--embed int8|trit|none`, `--embed-scale row|block`) и `tools/vtm_compile.py`
при необходимости; не ломать текущие форматы.

## Критерии приёмки

[ ] три варианта измерены (PPL + размер)
[ ] выбран лучший компромисс с обоснованием
[ ] новшества не ломают существующие контейнеры (тесты)

## Отчёт исполнителя

Сделано: `tools/cold_export.py` — `--embed int8` (сегмент INT8 kind 4, tied lm_head
тоже int8), `--embed-scale block|row`, кусковое кодирование таблицы (пик RSS 1,2 ГиБ),
поля в манифесте; `tools/vtm_compile.py` — строка отчёта про scale_mode; 16 новых тестов.

**Результат на Qwen2.5-0.5B (20 строк, 2047 токенов, bf16 PPL 16,13):**
| таблица | PPL (Linear триты) | ×bf16 | файл |
|---|---|---|---|
| trit/block (дефолт) | 69 984 719 | ×4,3e6 | 117 МБ |
| trit/row | 27 720 135 | ×1,7e6 | 117 МБ |
| int8/block | 10 108 425 | ×6,3e5 | 226 МБ |

**Изоляция (Linear fp32, только таблица):** int8/block 16,15 (×1,001), trit/block
65 223 (×4043), trit/row 4,2e6, fp16 16,13. То есть **int8-таблица возвращает весь
урон таблицы**.

**Главное — поправка к 0136:** на настоящей Qwen основной урон даёт **холодная
третизация Linear** (×7,3e5), а не таблица (добавляет ×6,5 для trit/block или ×1,0
для int8). На демо-моделях было наоборот. Ни один вариант таблицы не спасает: все
декоды — нечитаемый мусор.

**Рекомендация по умолчанию:** формат trit/block не менять; для прод-конфига с
QAT-Linear включать `--embed int8` (+109 МБ на 0,5B, +249 МБ на 3B; в RAM дороже —
int8 материализуется в fp32); `--embed-scale row` — только экспериментально;
приоритет №1 — QAT Linear, а не таблица.
