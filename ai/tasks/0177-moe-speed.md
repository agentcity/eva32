# 30B MoE: от 1,0 ток/с к 2–3

## Что уже есть
pread-кэш (0175): 0,21 → 1,0 ток/с, faults 356k → 272, sys 1,9 с. Кэш 1792 МБ — оптимум
на 16 ГиБ (3072 вызывает компрессию). Потолок «прочитать 1,5 ГБ на токен» = 0,32 ток/с,
то есть 1,0 достигается попаданиями в кэш.

## Рычаги (по ожиданию)
1. **Предзагрузка экспертов следующего слоя** пока считается текущий (один поток pread):
   роутер следующего слоя неизвестен, но можно грузить по предикту (эксперты прошлого
   токена) или грузить все 128 банков следующего слоя веером — измерить.
2. **Кэш по частоте (LFU/pinning)**: распределение экспертов Zipf — закрепить горячие,
   LRU заменить на 2Q.
3. **Батч-декод**: обрабатывать несколько токенов за один проход по весам (draft 0,5B
   или n-граммы) — чтение экспертов амортизируется на N токенов.
4. **Q3 для экспертов** (−25% байт) — только если качество держится (замер argmax).

### Что сделано

Порядок задачи соблюдён: рычаг 1 (предзагрузка) сделан и дал весь выигрыш;
рычаги 2–4 измерены, и три из четырёх оказались хуже текущего пути — это
записано с числами, а не «попробовали».

* `src/vtm/interp.c` — чтение экспертов вынесено в **пул I/O-потоков**
  (`VTM_MOE_IO_THREADS`, по умолчанию **6**, `0` — прежний последовательный
  путь). Сразу после роутера в очередь ставятся `3·top_k` заданий в порядке
  спроса (gate/up/down эксперта 0, затем 1, …); главный поток «требует» ключ —
  попадание сразу, иначе ждёт **именно этот** ключ (если задания не было,
  читает сам). Слоты под счётом закреплены (`pin`), вытеснение закреплённые
  пропускает — иначе воркер освободил бы байты под работающим ядром. Кэш и
  очередь заданий под мьютексом; байт не прибавилось: `pread calls=4488`,
  `pread=4 186 908 КиБ` совпадают с последовательным путём (это же и есть
  доказательство, что prefetch не читает лишнего).
* `src/vtm/interp.c` — диагностика `VTM_MOE_TRACE=1` дополнена разбивкой
  времени (`fetch_ms` — ожидание главного потока, `pread_ms` — сумма по
  воркерам, `compute_ms` — ядра) и счётчиками prefetch (`io`, `pf_jobs`,
  `pf_waits`, `pf_useful`). Без них «MOE 80 % времени» было чёрным ящиком.
  `VTM_MOE_TRACE=2` (выбор экспертов по слоям) использован для замера
  локальности между токенами.
* `src/vtm/interp.c` — умолчание `VTM_MOE_CACHE_MB` = **1792** (было 3072):
  3072 на 16 ГиБ вызывал компрессию, 1792 — оптимум по 0175. `VTM_MOE_NOCACHE=0`
  оставлен для A/B (пускать чтение экспертов в page cache).
* `src/vtm/loader.c`, `src/vtm/vtm_internal.h` — опция `VTM_DENSE_RESIDENT_MB`:
  одна pread-копия dense-весов, которые TMV читает каждый токен (внимание и
  lm_head, 0,77 ГБ), в анонимную память. **По умолчанию выключена** — замер
  показал, что на 16 ГиБ она проигрывает (см. ниже); оставлена для машин с
  запасом RAM.
* `tests/vtm/test_vtm.c` — `test_moe_pread_cache` фиксирует
  `VTM_MOE_IO_THREADS=0` (проверяет последовательный путь: с потоками «кто
  прочитал первым» зависит от планировщика); новый `test_moe_prefetch`
  проверяет prefetch-путь: выход MOE побитово равен mmap-пути, `threads == 2`,
  `jobs >= 6`, `pf_useful <= pf_waits`, `hits + misses == 24` за два прогона,
  `allocs == 6` (повтор не выделяет слотов).
* `docs/moe.md` — раздел «Полная 30B: prefetch экспертов в I/O-потоках (0177)»:
  механизм, таблица до/после на 3 промптах, попадания/стоимость, что измерено и
  отброшено, потолок. Обновлены устаревшие места (умолчание 3072 → 1792,

* `src/vtm/vtm.h` — описание `VTM_MOE_IO_THREADS`, нового умолчания кэша и

### Рычаги 2–4: что измерено

* **Кэш по частоте (LFU/2Q)** — симуляция на реальной трассе выбора (2 304
  обращения за прогон, ёмкость 603 тройки): LRU 32 %, онлайн-LFU 31 %, LFU с
  окном хвоста 31–32 %, статический офлайн-оракул 65 %. Причина: перекрытие
  между соседними токенами 36 %, а ёмкость — 603 тройки на 1 406 уникальных
  (43 %), поэтому выученный онлайн горячий набор устаревает за 4 токена. LRU
  оставлен.
* **Предикт «эксперты прошлого токена»** (`VTM_MOE_TRACE=2`, посерийно по
  слоям): перекрытие 16–55 %, в среднем **36 %** → предзагрузка читала бы
  ~2,8× байт. Отброшено. **«Веером все 128 банков слоя»**: 324 МБ на слой
  против 24 МБ нужных — 13× байт. Отброшено.
* **Батч-декод**: draft-модели нет; на промптах p1–p3 n-граммных повторов нет,
  то есть draft-приёмка ≈ 0 и выигрыша без реализации не будет. Реализуемо для
  prefill (MOE-опа батча не умеет: `--prefill-batch 3` даёт TMV 1 302→621 мс, а
  MOE 8 943 мс без изменений) — это новая операция/семантика, отдельная задача.
* **Q3 для экспертов**: нужен новый контейнер (эксперты 15,3 ГБ), на диске
  7,4 ГиБ свободных; Q3-ядра в бэкенде нет. Не делалось.

### Потолок

На прогон p1 читается 4,09 ГиБ экспертов (не зависит от prefetch) + ~0,8 ГБ
dense через page faults. Замеренная агрегатная скорость чтения — 3,3–3,4 ГБ/с
(1 поток 0,8 ГБ/с, 4 — 2,5, 8 — 2,9), то есть ~1,3 с только I/O на 2,1 с
прогона; остальное — 0,3 с ядер MOE, ~0,2 с TMV и первый проход по 1,79 ГиБ
слотов кэша (172 тыс. мелких отказов). Чтобы взять 2,0 ток/с, нужно **меньше
байт** (Q3-контейнер) или батчевый prefill — оба за пределами этой задачи.

### Осталось и риски

* **Порог 2,0 не взят** (1,88–1,97). Упор — в 4,09 ГиБ `pread` на прогон при
  3,4 ГБ/с; дальше только меньше байт. Честная формулировка: 30B идёт в
  1,8–2,1× быстрее, чем на 0175, и на форварде декода даёт 3,3 ток/с.
* **Резидентные dense-веса проигрывают на 16 ГиБ** (2,9–5,0 с против 2,3–2,6 с,
  sys 3,0–6,4 против 1,4–2,0): +0,77 ГБ анонимной памяти сами вызывают
  компрессию. Опция оставлена выключенной; на выделенной машине её надо
  перемерить.
* **`VTM_MOE_NOCACHE=0` проигрывает сильно** (7,2–8,9 с против 2,1–2,8 с) —
  чтение экспертов из page cache вытесняет dense-веса. Умолчание (F_NOCACHE)
  верное.
* **Потоков теперь 6 I/O + пул ядер.** Кэш потокобезопасен (мьютекс), TSan
  чист, но машина по-прежнему одна на процесс; при нескольких `vtm_t` в разных
  потоках они делят кэш по ключу файла. `VTM_MOE_CACHE_MB=0` — прежний
  mmap-путь без потоков.
* **Хост общий**: во время замеров `load average` 8–13, отдельные окна давали
  2–3× замедление: те же конфигурации на p1 — 2,1 с при load 9 и 6,2 с при
  load 18 (соседние агенты). Таблицы — парные прогоны одной серии,
  минимум/медиана; проверять приёмку надо **парой** (HEAD и рабочее дерево) в
  одном окне, иначе разница нагрузки съест разницу конфигураций.
* **Рабочее дерево общее**: мои правки в `loader.c`/`vtm_internal.h` — только
  `dense_raw`/`dense_bytes` и `dense_make_resident`; остальное в `interp.c`,
  тестах и документации.
