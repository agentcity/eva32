# Кэш промпта в C-ABI

## Проблема

0081 добавила кэш префикса в ядро (`vtm_cache_prefix` / `vtm_run_cached`), но
`api.c` и `kv_store.c` вызывают `vtm_reset` на каждый запрос — то есть через C-ABI
кэш не работает вообще. Весь выигрыш (7,8× на префиксе 128 токенов) остаётся внутри
тестов.

## Требования

- `vtm_api_open(..., &opts)` получает опцию `cache_prefix` (по умолчанию выключена —
  не менять поведение без флага).
- При включённой опции `vtm_api_generate` использует `vtm_run_cached`, а не полный
  прогон; между запросами кэш **не сбрасывается**.
- Инвалидация при `vtm_api_session_load` (состояние машины меняется) и при смене
  бэкенда.
- Замер: два запроса с общим префиксом 100 токенов через C-ABI — время второго
  запроса до/после (числа в отчёте).
- Тест: ответы с кэшем и без совпадают побитово.

## Критерии приёмки

- [x] второй запрос с тем же префиксом быстрее (число в отчёте)
- [x] побитовое совпадение ответов с кэшем и без
- [x] `make test` и полный Python-набор зелёные

## Отчёт исполнителя

Сделано: `vtm_api_options.cache_prefix` (занял первый элемент прежнего `reserved[6]`,
sizeof=56 сохранился — ctypes-хост совместим без правок), `api_run_cached()`: промпт
`[0..n-2)` идёт через `vtm_run_cached`, последний токен — обычным прогоном (кэш не умеет
emit). Инвалидация после `session_load`. +13 проверок (всего 21).

**Замер (C-ABI, ctx=256, промпт 129 токенов):**
- 1 новый токен: 6,96 мс → **0,056 мс (125×)**, потолок 129×;
- 8 новых токенов: 6,71 → 0,475 мс (**14,1×**), потолок 15,2×;
- ответы с кэшем и без — побитово те же.

Риски: промпт из 1 токена обнуляет снимок; отмена не режет прогон префикса (неделимый
`vtm_run_cached`); при prompt+generation > context_window кольцо KV инвалидирует снимок
(корректность есть, выигрыш теряется). `eva/backends` не включает опцию — нужен флаг
конфига (отдельная мелкая задача).
