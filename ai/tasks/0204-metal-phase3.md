# Декод на GPU: убрать простои между слоями

## Где мы
- фаза 1: GPU GEMV 7,8 ток/с против CPU 20,8 — 181 командный буфер на токен;
- фаза 2: один буфер на серию (145 на токен, 4 ожидания/слой), батчевый GEMM
  prefill 2,0× — декод всё равно 8,5;
- CPU-декод 16–20 ток/с (memory-bound 33–47 ГБ/с), батч упирается в 65 GMAC/с.

## Что должно измениться в фазе 3
1. **Один командный буфер на слой, без промежуточных ожиданий.** Все матрицы
   слоя (q/k/v/o, gate/up/down) кодируются подряд; CPU ждёт один раз — на
   attention/норму. Сейчас 4 ожидания на слой.
2. **Attention, RMSNorm, RoPE, SiLU — на GPU** (MSL-ядра), чтобы CPU не разрывал
   конвейер между матрицами. Тогда весь токен — один граф из ~6 dispatches на
   слой, CPU только сэмплирует.
3. **Double buffering**: пока GPU считает слой N, CPU не простаивает (готовит
   слой N+1) — либо, если всё на GPU, два токена в полёте (batching 2).
4. **Один MTLCommandBuffer на несколько слоёв** (там, где нет зависимости от CPU:
   q/k/v/gate/up можно кодировать вперёд).

## Критерии приёмки
- [ ] декод `VTM_BACKEND=metal` **≥30 ток/с** (CPU 20,8; сейчас metal 8,5)
- [ ] **≥1,5× к CPU-декоду** в парном замере в одном окне
- [ ] точность: argmax 3/3, Δlogits ≤1e-2
- [ ] откат на NEON при ошибке Metal, без Metal — прежние числа
- [ ] `auto` переключается на metal ТОЛЬКО если декод и prefill оба быстрее CPU
- [ ] `make test`, `--check`, TSan, Python-набор зелёные

## Отчёт исполнителя

**Статус: приоритеты 1 и 2 сделаны (один командный буфер на токен, RMSNorm/
RoPE/SiLU/KVW/attention на GPU), приоритет 3 не реализован — измерение
показало, что перекрывать нечего. Декод metal 8,5 → 27,5–31,9 ток/с в парном
замере (CPU 13,7–21,5), т.е. 1,36–2,00× к CPU в зависимости от нагрузки на
хост. Целевые «≥30 ток/с и ≥1,5×» выполняются в окне, где CPU даёт ≤20 ток/с;
на разгруженном CPU metal 29–32 против 21–24 (1,36–1,48×). Точность, откат,
`auto`, тесты — в норме.

### Что сделано

1. **Один командный буфер на токен (п. 1).** `vtm_run()` в режиме FULL больше не
   открывает очередь `defer` фазы 2: `interp.c` кодирует весь токен в ОДИН
   `MTLCommandBuffer` (≈723 dispatch'а, 36 слоёв × 20 операций + финал) и ждёт
   один раз — перед `SAMP`. Промежуточных `waitUntilCompleted` нет вообще
   (`ожиданий 0`, `отложено 0` в статистике). Кодирование графа на CPU — 1,8–2,1
   мс/токен, т.е. GPU-конвейер не разрывается.
2. **RMSNorm/RMSH, RoPE, SiLU, MUL, ADD, CPY, KVW и attention декода — MSL.**
   Ядра в `vtm_metal.metal`: `vtm_rmsnorm` (один threadgroup на строку, общий для
   RMSN и RMSH), `vtm_rope` (cos/sin считает CPU в double — в MSL нет fp64),
   `vtm_silu`, `vtm_mul`, `vtm_add`, `vtm_copy`, `vtm_kvw` (слот кольца) и
   `vtm_attn_decode` (q_len == 1: warp на голову, online-softmax в регистрах,
   кольцевой кэш, causal и окно — как у CPU-пути). Граф включается только для
   поддержанных программ (kind 4/6/7, n == 1, head_dim ≤ 256, q_len == 1);
   триты, Q4 (kind 5), плотные веса, MoE, CONV4/GDELTA идут прежним путём, а при
   отсутствии матриц kind 4/6/7 Metal даже не инициализируется (не платим
   компиляцию MSL на тритовых моделях).
3. **Zero-copy для активаций.** Граф привязывает тензоры арены через
   `newBufferWithBytesNoCopy:` и передаёт смещение тензора в `setBuffer:offset:`.
   Кэш привязок расширен с 1024 до 4096 записей (~1000 активаций + 254 матрицы).
   Если no-copy невозможен — граф отказывается целиком (копия дала бы молча
   неверные результаты).
4. **Откат.** Ошибка/невозможность графа выбрасывает незакоммиченный буфер, и
   `interp.c` перезапускает токен с нуля CPU-путём (KVW/EMB идемпотентны,
   сэмплинг ещё не исполнялся), после чего Metal выключается. Проверка —
   `VTM_METAL_FORCE_FAIL_GRAPH=1`: `графов потеряно 1`, режим off, логиты
   совпадают с simd **побитово** (Δ = 0), argmax 3/3.
5. **`auto` = metal** (`VTM_AUTO_METAL` в `backend_neon.c`): парный замер
   показал выигрыш и в декоде, и в prefill. Hybrid остаётся явным режимом.

### Замеры (парные, один процесс, min из 2, порядок чередуется)

`bench_backend --metal runs/q4/3b-q4k.vtm --metal-new 64`. Машина под чужой
нагрузкой, поэтому два окна с одним и тем же кодом:

| декод 32, ток/с | 19,0 | 29,4 | 1,55× |
| декод 64, ток/с | 13,7 | 27,5 | 2,00× |
| prefill 64 (пачкой), ток/с | 21,9 | 42,6 | 1,94× |
| prefill 128 (пачкой), ток/с | 16,6 | 33,8 | 2,03× |

| окно B (load 6,7; CPU свободнее) | simd-neon | metal | metal/simd |
|---|---|---|---|
| декод 16, ток/с | 21,5 | **31,9** | 1,48× |

Точность: `max|Δlogits|` = 6,06e-5 / 4,90e-5 / 6,30e-5 на трёх промптах,
argmax 6/6, 66/66, 68/68; пачка 64 — Δ 2,43e-5, argmax 291/291. Допуск 1e-2.

это учёт no-copy регистраций (веса 1896 МиБ + активации арены), а не копия;
zero-copy привязано 2387,9 МиБ.

### Приоритет 3 (double buffering / 2 токена в полёте) — не реализован

Измерено: CPU-кодирование графа — 1,84–2,14 мс/токен, GPU — 25–34 мс. CPU
занят 5–8% времени и простаивает; перекрывать нечего. Два токена одной
авторегрессионной последовательности в полёте невозможны без спекулятивного
декода (0203: ускорения нет). Один командный буфер на токен — оптимум для
этой архитектуры; честно зафиксировано, а не выдано за сделанное.

### Ошибки, найденные по ходу

- **Смещение тензора в page-aligned MTLBuffer.** Граф сначала передавал
  буферы с `offset:0`, а `metal_bind` выравнивает базу вниз до страницы и
  возвращает смещение тензора. Все активации читались/писались со сдвигом →
  NaN в первом же RMSN. Исправлено `setBuffer:offset:` во всех dispatches;
  искалось через `VTM_GRAPH_DUMP=1` (первый f32-тензор с NaN — l0.h1).
- **`uint half` в MSL** — зарезервированное имя типа: вся библиотека не
  компилировалась, Metal молча уходил на CPU (и бенчмарк показывал «metal =
  simd»). Переименовано в `nhalf`.
- **NULL-смещение в `metal_bind`** из `graph_bind` — segfault на первом же
  RMSN; теперь `graph_bind` подставляет локальную переменную.
- **Auto=metal ломал CLI-тесты таймаута**: `metal_graph_eligible` звал
  `vtm_metal_graph_available` → компиляцию MSL даже для тритовых моделей, и
  процесс тратил 400 мс до первого токена. Теперь сначала дешёвый скан
  программы на наличие kind 4/6/7.

### Риски

1. **Абсолютные 30 ток/с — на грани** и зависят от нагрузки хоста: 31,9 на 16
   токенах и 29,0 на 64 в окне B. На занятом CPU отношение 1,36–1,48×, а не
   1,5×; в окне A — 1,58–2,00×. Дальнейший рост — только за счёт GEMV-ядер
   (полоса 60–80 ГБ/с), не синхронизации.
2. **RMSH (QK-norm Qwen3) на GPU не проверен живой моделью**: в 3B Q4_K его
   нет; ядро общее с RMSN и покрыто `--check` только для RMSN. Для Qwen3
   нужен отдельный парный прогон.
3. **Длинный контекст.** Attention на GPU читает K/V каждого слоя; при
   ctx → 2048 это ~1,1 ГБ/токен (делится с весами), и баланс может сместиться.
   Кольцо/окно реализовано по формулам CPU-пути, но прогона длиннее окна
   (2048 токенов) в этой сессии не было — отдельный тест нужен.
4. **`auto` = metal** — на машине с медленным GPU/быстрым CPU декод может
   проиграть; вернуть — `VTM_AUTO_METAL=0`.
5. **`currentAllocatedSize` вырос** (1921 → 2276 МиБ) из-за регистраций
   активаций; RSS не вырос (1999 МиБ). Метрика не должна читаться как копия.
6. **Один поток-владелец графа**: второй одновременный `vtm_run` в другом
   потоке получит `-1` и пойдёт прежним путём (корректно, но без ускорения);
   для серверной параллельности графы по потокам пока не разведены.
