# Почему prefill упирается в счёт, а не в память

## Факты (0211)
- Холодный prefill 250 токенов: **7,4 с (30–34 ток/с)** metal, 13,1 с simd.
- Цель была ≤2 с — не взята, и дело НЕ в пачке (250 токенов уже одна пачка).
- Профиль 250 токенов (metal): GPU 3,73 с (2024 GEMM), хост-CPU **3,62 с**,
  стена 8,65 с → **~40% времени не на GPU**, а на перекладку активаций,
  привязки буферов и ожидания.
- CPU int8 даёт ~74 GMAC/s; Metal под нагрузкой 120–200 GMAC/s.
- Чтобы 100 ток/с на prefill, нужно **366 GMAC/s**.

## Что делать
1. **Тайлинг батч-GEMM**: текущее ядро делает GEMM без разделяемой памяти
   (threadgroup) — каждая нить перечитывает веса. Сделать классический
   тайл (например 64×32, simdgroup 32×32 через `simdgroup_matrix`), переиспользуя
   B-фрагмент из threadgroup. Это главный рычаг: 2–3× к GMAC/s.
2. **Один командный буфер на матрицу** (сейчас на слой, но активации
   перекладываются на хосте между матрицами) — держать активации в GPU-памяти,
   не копировать туда-обратно; при необходимости `MTLBuffer` с `hazardTrackingMode`
   или два буфера ping-pong.
3. **Убрать 40% хостового времени**: привязки буферов — заранее (кэш
   привязок уже есть, но на пачке он переполняется), активации — в одном
   большом буфере со смещениями, без промежуточных копий.
4. **int8/полуточность для батча**: Q4_K × int8 активации уже есть в NEON;
   на GPU — `simdgroup_half8x8` для f16-накопления там, где допустимо (Δ≤1e-2).
5. Замеры: `bench_backend --metal --metal-new`, `--prefill-ttft`, GMAC/s,
   разбивка GPU/хост/ожидание; точность argmax + Δ.

## Критерии приёмки
- [ ] prefill 250 токенов **≤2 с** (≥125 ток/с), 500 ≤4 с
- [ ] GEMM ≥300 GMAC/s в синтетике, ≥250 в живом prefill
- [ ] точность: argmax совпадает, Δlogits ≤1e-5 (для f16-накопления — ≤1e-2
      с честной пометкой)
- [ ] декод не хуже 29 ток/с
- [ ] `make test`, `--check`, `make tsan`, Python-набор зелёные

## Отчёт исполнителя

**Статус: сделано частично.** Холодный prefill 250 токенов: **7,43 → 3,95 с**
(34 → 63 ток/с), 500: **17,10 → 9,15 с** (29 → 55 ток/с), хост-CPU на 250
токенах **3,65 → 0,44 с**. Цели «250 ≤ 2 с, 500 ≤ 4 с» не взяты: после правок
prefill упирается в ГПУ-счёт (~280 GMAC/s), а не в хост; для 2 с нужно
≥450 GMAC/s устойчиво. Синтетика ≥300 GMAC/s взята на длинных матрицах
(307–325 GMAC/s GPU), на коротких (2048×2048) — нет (98–192 из-за «хвоста»
волн в 128 threadgroup'ах). Декод 29,7–30,2 ток/с (порог 29) — не хуже.
Точность: пачка против CPU — max|Δlogits| = 2,58e-5, argmax 291/291.

### Что было не так (профиль 0211 + разбор кода)

На КАЖДУЮ матрицу слоя хост: (1) транспонировал вход пачки в `b->xt`
(`batch_tmv_apply`), (2) ещё раз — в `g_gxbuf` (`metal_gemm_body`), (3) после
ожидания командного буфера разносил выход `yt` по слотам токенов. Плюс
отдельный `MTLCommandBuffer` с `waitUntilCompleted` на каждый chunk (8 chunk'ов
на матрицу при 250 токенах) и no-copy привязка «на матрицу». А attention пачки
считался на CPU в double: 1,44 с из 5,0 с стены на 250 токенах и 5,8 с из 15 на
500 — самый дорогой опкод prefill.

### Что сделано

1. **Тайловый GEMM** (`vtm_q4k/q6k/i8_gemm_t16/t32`): два ряда на поток вместо
   одного — один `float4` активаций из threadgroup-памяти идёт в 8 MAC (2 Б LDS
   на MAC вместо 4), 16 строк на threadgroup; вес читается один раз. Новый
   `GemmArgs` (56 Б) несёт `x_off/y_off/x_stride/y_stride/y_rstride`, поэтому
   ядро само читает вход и пишет выход по слотам токенов. Старые ядра
   gemm8/16/32 и путь «base» удалены (они писали выход в другой раскладке;
   оставлять A/B-ключ, который молча даёт неверные числа, нельзя).
2. **Арена пачки вместо calloc** (`interp.c`): `posix_memalign` на страницу +
   `memset`, запас `VTM_METAL_GEMM_PAD` = 32 токена в хвосте (ядро варианта NT
   читает/пишет ровно NT). Привязка к Metal — одна на `vtm_run_batch`
   (`vtm_metal_batch_arena`/`_drop`), дальше матрица передаёт только смещение.
   Хост-транспонирований и разноски выхода больше нет: `op=0x01` (TMV) на 250
   токенах — **12 мс** вместо 2,5 с «внутри TMV» по профилю 0211.
3. **Один командный буфер на группу матриц**: q/k/v и gate/up кодируются в один
   `MTLCommandBuffer`, CPU ждёт только когда числа нужны (перед первой не-GEMM
   инструкцией, перед копированием «умершего» тензора в машину — точная
   проверка `batch_gpu_store_hazard`, и в конце пачки). `VTM_METAL_GEMM_GROUP=0`
   возвращает «буфер на матрицу» для A/B.
4. **Attention пачки на GPU** (`vtm_attn_prefill`): граф декодный (q_len == 1),
   поэтому пачка — C независимых «декодных» вниманий; у токена i видимы ключи
   `[max(0, pos+imm+1-win), pos+imm]`, K/V всех токенов уже в кольце (KVW идёт
   раньше). Ядро — копия `vtm_attn_decode`, threadgroup выбирает (токен, голова).
   CPU-attention 1,44 с → 3 мс dispatch (+~30 мс GPU за пачку). Отказ ядра —
   прежний поштучный путь.
5. **`lm_head`**: подготовлен короткий путь «считать только последний токен,
   если dst MM больше никто не трогает» — на этой модели НЕ срабатывает: после
   MM стоит SAMP, который читает логиты каждого токена (порядок ГПСЧ важен).
   Оставлен как безопасное общее правило, в замеры не входит.

### Риски

1. **Цель 2/4 с не взята** (3,95/9,15 с). Упор — в ГПУ-счёт: 915/1830 GMAC при
   ~280 GMAC/s. Дальше нужен f16-путь через `simdgroup_matrix` (де-квантование
   в threadgroup-память): это +50–100% GMAC/s, но Δlogits ~1e-3 (проектный
   допуск 1e-2 позволяет, строгий 1e-5 — нет). Отдельная задача.
2. **`--metal-gemm` на коротких матрицах даёт 98–192 GMAC/s** (2048 строк = 128
   threadgroup'ов): «хвост» волн. Лечится либо 8 строками на threadgroup (вдвое
   больше групп, вдвое больше чтений x), либо split-K; не делалось.
3. **Машина под нагрузкой 9–12** (соседние задачи, load average), разброс
   одиночных прогонов до ±40%. Все сравнения — min из 2 и в одном окне; на
   разгруженной машине числа должны быть лучше, но цель 2 с всё равно требует
   другого ядра.
4. **f32-накопление, Δ = 2,58e-5**: выше строгого 1e-5 из 0211, в проектный
   допуск 1e-2 (0204) укладывается; побитовость — только `VTM_BACKEND=simd`.
5. **Одна привязка арены на прогон**: арена освобождается в конце
   `vtm_run_batch` (`vtm_metal_batch_arena_drop` до `free`). Если появится
   второй одновременный батчевый контекст в другом потоке — слотов четыре
   (`VTM_METAL_ARENA_MAX`), дальше вытеснение первого; на поток-на-контекст
   рассчитано.
6. **`lm_head` считается для всех токенов пачки** — 0,5 с GPU из 3,3 на 250
   токенах; короткий путь упирается в SAMP (см. выше), трогать его без
   отдельной задачи по семантике сэмплинга не стал.
