# CLI и C-ABI для батчевого prefill

## Проблема

Даже когда ядро научится считать промпт пачкой (0112), CLI и C-ABI должны это
использовать: сейчас `vtm run --tokens ...` гоняет по токену, а `vtm_api_generate` — так
же. Без проводки выигрыш останется в тестах.

## Требования

- CLI: `--prefill-batch N` (0 = по токену, как раньше) — промпт считается пачками по N.
- C-ABI: `vtm_api_options.prefill_batch` (занять элемент из `reserved`, sizeof сохранить) —
  тот же смысл; по умолчанию 0, поведение не меняется.
- Использовать `vtm_run_batch` из задачи 0112 (если её ещё нет — сделать заглушку,
  которая зовёт прежний путь, и переключиться, когда появится).
- Замер: TTFT на demo и на 1.5B-форме с --prefill-batch 32/128 против 0.

## Критерии приёмки

[ ] CLI --prefill-batch работает, результаты побитово те же (тест)
[ ] cache_prefix/prefill_batch в api.h без смены sizeof (проверка)
[ ] TTFT до/после замерен
[ ] make test и Python-набор зелёные

## Контекст и ограничения

- Зона: src/vtm/main.c, src/vtm/api.c, src/vtm/api.h, tests/test_vtm_api.c
- Другие файлы НЕ трогать: параллельно работают семь других агентов по своим зонам.
  В частности `interp.c` — 0112, `backend_*.c` — 0113, `main.c/api.c/api.h` — 0114,
  `eva/server.py` — 0115, `docs/` — 0116, `tools/ci.py` — 0117, `loader.c` — 0118,
  `prompts/` — 0119.
- **Запрещено:** pip, сеть, запуск сервера на порту, git-коммиты, скачивание моделей.
- **Отчёт пиши первым блоком ответа** — агенты этой сессии падают на финальном шаге.
- Проверка: `python3 -m unittest discover -s tests` (сейчас 1517 тестов) и, где нужно,
  `cd src/vtm && make test`.
- Если нужен API из чужой зоны (например `vtm_run_batch` из 0112) — опиши контракт в
  отчёте и используй заглушку, не правь чужой файл.

## Отчёт исполнителя

### Что сделано

* `src/vtm/main.c` — `--prefill-batch N` (0 = по токену, по умолчанию 0;
  значения 0..1e6). Промпт гоняется пачками через `vtm_run_batch()`:
  в режиме `--max-new > 0` — все токены, кроме последнего (последний, как и
  раньше, отдельным `vtm_run()` с колбэком SAMP: только на нём выбирается
  первый ответ), в режиме `--max-new 0` — все токены. Общий помощник
  `prompt_prefill()`; таймаут проверяется между пачками (пачка неделима).
  Строка «prefill: пачками по N токен(ов)» в шапке — только когда N > 0.
* `src/vtm/api.h` — `vtm_api_options.prefill_batch` занял элемент прежнего
  `reserved[5]` (`reserved[4]` осталось). **sizeof(vtm_api_options) = 56,
  не изменился** (смещения: struct_size 0, flags 4, backend_name 8, backend 16,
  max_new_tokens 24, eos_token_id 28, cache_prefix 32, prefill_batch 36,
  reserved 40). Старый хост, обнулявший reserved, получает 0 и прежнее
  поведение. Значение > INT_MAX — ошибка open().
* `src/vtm/api.c` — тот же смысл в `vtm_api_generate()`: промпт, кроме
  последнего токена, пачками; отрицательные id проверяются до прогона (пачка
  неделима); N больше промпта = одна пачка. `cache_prefix == 1` приоритетнее:
  у кэша префикса свой путь (`vtm_run_cached()`), батч там не применяется.
* Слабая зависимость от 0112: `vtm_run_batch()` объявлен и **определён слабо**
  (заглушка = прежний цикл по токену) в `api.c` и `main.c`. Слабое
  *определение*, а не только объявление: в Mach-O неразрешённая слабая ссылка
  — ошибка линковки, а слабое определение линкуется везде и перекрывается
  сильным из `libvtm.a`. Проверено `nm`: у `vtm`/`test_vtm_api` символ
  `external` (сильный, из `interp.o`), заглушка в `main.o`/`api.o` — `weak`.
  **0112 сдана во время работы** (vtm.h/interp.c, 14:03–14:05) с ровно тем
  контрактом, на который рассчитан вызов (`vtm_status vtm_run_batch(vtm_t *,
  const int32_t *, int)`, start = `vtm_position(m)`, emit не вызывается,
  позиция после = start + n - 1). Правок не потребовалось: заглушка
  перекрыта автоматически. Добавочно проверено подставным сильным
  определением (печатало маркер): батч 32 → одна пачка `n=4` на промпте из 5,
  батч 3 → пачки 3 + 1, ответ тот же.
* `tests/test_vtm_api.c` — 4 typedef-проверки ABI (sizeof 56, смещения
  cache_prefix/prefill_batch/reserved не компилируются при смене);
  `test_prefill_batch()`: N = 0/1/2/3/32/128/1e6 дают побитово те же коды и
  токены, повтор на том же контексте, промпт из 1 токена, id < 0 → VTM_E_ARG,
  N > INT_MAX → ошибка open, `cache_prefix=1 + prefill_batch=32` — те же
  токены, session_save/load с батчем, отмена до старта, скалярный бэкенд
  (единственный, где 0112 реально батчит до 0113) — batch 32 == batch 0
  побитово; `test_prefill_batch_cli()`: `./vtm run ... --prefill-batch
  1/2/32/128` и `--backend scalar --prefill-batch 32` дают ту же строку
  «вывод:».

### TTFT до/после (demo и 1.5B-форма; `--max-new 1`, в stderr `--stats`)

Протокол как у `tools/bench_shape.py`: stats.время = от старта генерации до
первого токена (загрузка не входит). Форма 1.5B —
`runs/bench_shape/shape_h1536_l28_v151936_c2048.vtm` (345 МиБ, собрана
`tools/bench_shape.py`), промпт — детерминированные id (seed 7).

| модель / бэкенд | промпт | batch=0 (было) | batch=32 | batch=128 |
|---|---|---|---|---|
| demo, scalar, 20 повторов | 7 | 2,0 мс | **1,4 мс (1,42×)** | **1,3 мс (1,48×)** |
| 1.5B, scalar, 2 повтора | 8 | 10,04 с | **5,94 с (1,69×)** | **5,87 с (1,71×)** |
| 1.5B, scalar, 1 прогон | 32 | 45,43 с | **11,09 с (4,10×)** | **11,58 с (3,92×)** |
| 1.5B, auto/simd-neon, 1 прогон | 128 | таймаут 420 с (машина) | 15,79 с | 15,24 с |

Ответы модели (строка «вывод:») у всех настроек совпали побитово — и на demo,
и на 1.5B.

Оговорки к числу:

* Выигрыш есть **только на скалярном бэкенде** — по контракту 0112 батчевых
  ядер на SIMD пока нет (0113), там `vtm_run_batch()` идёт по токену, выигрыша
  нет и быть не может. Замер `auto/simd-neon` на 1.5B почти не удался: семь
  агентов параллельно гоняли такие же 1.5B-прогоны (load average 8–20 на 10
  ядрах), batch=0 на 128 токенах не уложился в 420 с, отдельные прогоны
  различались в разы. До 0112 (спокойная машина, `runs/bench_shape/prefill.json`)
  TTFT был 0,1356 с на 1 токене, 0,5619 с на 8 и **37,58 с на 512**.
* Число пачек 32 и 128 на промптах 8/32 не различается (весь промпт — одна
  пачка); 512 токенов на scalar не померил — под нагрузкой это часы.

### Риски и что осталось

1. **До 0113 `--prefill-batch` бесполезен на бэкенде по умолчанию** (auto →
   simd-neon): 0112 там деградирует до поштучного прогона. Ожидаемый выигрыш —
   только с SIMD-батч-ядрами; после 0113 нужно повторить замер на спокойной
   машине (это же место у 0117 — perf smoke).
2. `cache_prefix == 1` приоритетнее батча: с кэшем префикса пачки не
   применяются (задокументировано в api.h). Совмещать оба ускорения — отдельная
   задача (снимок кэша от батчевого прогона 0112 пока не создаёт).
3. Пачка неделима: отмена/таймаут проверяются между пачками, не между
   токенами — как у `vtm_run_cached()` (0087). При N = 512 отмена придёт
   позже.
4. `eva/backends/vtm_backend.py` зеркалит раскладку `vtm_api_options` как
   `reserved[5]` — sizeof и смещения не изменились, поэтому Python-хост
   работает как раньше, но задать `prefill_batch` из Python (0115) он пока не
   умеет: нужно поле в ctypes-структуре (чужая зона).
5. Заглушка в `api.c`/`main.c` перекрывается сильным определением только если
   `vtm_run_batch` лежит в объекте, который уже линкуется (`interp.o` — так и
   есть). Если 0112/0113 перенесут его в новый .c, который больше никому не
   нужен, слабая ссылка не вытянет член архива — батч молча не включится
   (тест `scalar: batch=32 == batch=0` этого не поймает, он пройдёт и на
   заглушке). Проверка на будущее — маркер вызова или `nm` на `interp.o`.
6. Замеры 1.5B под нагрузкой семи агентов — ориентир, а не эталон: числа
   завышены в 3–20 раз, batch=0 на 128 токенах (auto) не уложился в таймаут.
   Для приёмки нужно повторить на спокойной машине, минимум по 3 повтора.
