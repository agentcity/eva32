# Таблица словаря в f32 — потолок скорости

## Проблема

0169 показала: int8-ядра Q4_K/Q6_K дают 1,76–1,86×, но сквозной декод упирается в
**lm_head — f32-таблицу 151936×2048 = 1,24 ГБ на токен**, 36,6 мс (34 ГБ/с — уже
полоса памяти). Потолок ~27 ток/с при любых ядрах.

У ollama выходная голова квантована, поэтому 45+ ток/с.

## Требования

- `loader.c`: упакованная таблица (kind 6 Q4_K / int8) в арене вместо f32-развёртки;
  материализация только строки, которая нужна (для GEMV логитов — по строке на vocab).
- `tools/gguf_import.py`/`vtm_compile.py`: писать emb.w упакованной (квантование таблицы
  уже поддержано для kind 0/4 — распространить на 6 или int8).
- `interp.c`: lm_head через int8/GEMV по упакованной таблице.
- Проверка: 3B Q4_K — argmax 20/20 golden (как в 0169), Δlogits ≤1e-2, декод ≥30 ток/с.
- Память: RAM 3B Q4_K ≤5 ГБ.

## Критерии приёмки

- [ ] декод ≥30 ток/с
- [ ] argmax 20/20, Δlogits ≤1e-2
- [ ] `make test`, `--check` зелёные

## Отчёт исполнителя

### Итог

Таблица словаря (tied `lm_head`, `emb.w` [151936, 2048]) больше не
разворачивается в fp32: загрузчик держит её упакованной (kind 4), в арене
только fp32-масштабы (9,7 МиБ), `EMB` разворачивает одну строку, `MM`/`TMV`
считают GEMV по int8-таблице (SDOT, тот же приём квантования активаций, что
в 0169).

- **lm_head: 24,86 мс → 3,72–4,19 мс** (`--i8-gemv` на полной форме, один
  прогон, чередование в одном процессе), **6,0–6,7×**; байт на токен
  **1,24 ГБ → 0,31 ГБ**.
- **argmax 160/160 шагов (20/20 промптов), top-5 100 %, max|Δlogits| =
  1,12e-05** (порог 1e-2), последовательности совпали 20/20.
- **RSS 3B Q4_K: 3,25 ГБ → 2,02 ГБ** (−1,23 ГБ), при пределе 5 ГБ.
- **Критерий ≥30 ток/с не выполнен**: на этой машине в этом окне декод
  2,1–10,4 ток/с (было 0,5–3,0 на том же контейнере с fp32-таблицей), машина
  под нагрузкой 20–24 и свапом 10,6/11,3 ГБ — page cache не держит 1,98 ГБ
  на токен, время уходит в подкачку. По компонентам: 2,77 Г MAC kind 6/7 при
  измеренных 0169 59 Г MAC/с = 47 мс + 4,2 мс lm_head = 51 мс ⇒ **потолок
  ~20 ток/с даже с бесплатной головой**: остаток упёрся в декодные ядра
  Q4_K/Q6_K, а не в голову.

### Что сделано

- `src/vtm/loader.c` — kind 4 в памяти упакован:
  * `plan_tensor`: арена = `n_scales·4` (fp32-масштабы); байты `q` в
    mmap-режиме ссылаются в отображение (`copy_i8` только при
    `VTM_NO_MMAP`/`load_mem`/writable);
  * `fill_tensor_planned`: масштабы конвертируются в fp32 один раз (fp16 →
    fp32), `t->i8` — байты `q`, `t->f32 = NULL`, kind остаётся `4`;
  * `vtm_i8_emb_mode()/vtm_i8_emb_set_mode()` (новые, аддитивно в `vtm.h`):
    `VTM_I8_EMB=0` — прежний путь (fp32-развёртка в арене, kind 1, флаг
    `VTM_TENSOR_FLAG_INT8_SOURCE`), `=1` — заставить упакованный, не задано —
    авто: упакован только если есть int8-dot GEMV (`vtm_q4k_i8_mode() > 0`),
    иначе (x86 без VNNI-ядра) остаётся fp32-развёртка, чтобы не получить
    регресс 2× на переносимом пути.
- `src/vtm/backend_scalar.c` — переносимые ядра int8-таблицы:
  `vtm_i8_tmv`/`vtm_i8_mm` (эталон в double: сумма по блоку 128 × масштаб),
  `vtm_i8_dequant_row` (строка EMB), `vtm_i8_gemv` (диспетчер: NEON int8-dot,
  иначе переносимый f32-путь по блокам 128).
- `src/vtm/backend_neon.c` — `vtm_neon_i8_gemv()`: GEMV по int8-таблице на
  SDOT; активации квантуются тем же кодом, что декод kind 6/7 (0169) —
  под-блоки 32 значения, 1–3 int8-плоскости; сетка масштабов таблицы (блок
  128) кратна под-блокам, поэтому `sc` применяется к сумме четырёх
  под-блоков. Тело под-блока развёрнуто, у каждого свой f32-аккумулятор.
  Скорость на полной форме: mode 2 — 3,72 мс (83,7 ГБ/с), mode 3 — 4,19 мс
  (74,2 ГБ/с), точные активации (mode 0) — 49,85 мс.
- `src/vtm/interp.c` — `req_i8()`; `EMB` по kind 4 (одна строка), `MM` по
  kind 4 (`n == 1` — `vtm_i8_gemv`, иначе `vtm_i8_mm`), `TMV` по kind 4
  (транспонирование отвергается, как у kind 5/6/7). Батчевый prefill int8
  не берёт (`batch_*_ready` → путь по токену), т.е. считается верно, просто
  без батчевого ядра.
- `src/vtm/vtm.h` — поле `t->i8` и два аддитивных объявления режима.
- `src/vtm/vtm_backend.h` — контракт `vtm_i8_*` (аддитивно).
- `tools/gguf_import.py`, `tools/vtm_compile.py` — правок логики не
  потребовалось: `--embed int8` (умолчание для `--format q4`) уже пишет
  INT8-сегмент, а компилятор собирает `EMB`/`MM` по kind 4. Обновлены
  docstring'и (что загрузчик больше не разворачивает таблицу).
- `docs/vtm.md` — kind 4 в памяти, `EMB`/`MM` по int8, цена RAM, ограничения.
- Тесты:
  * `tests/vtm/test_vtm.c` — `test_int8_packed`: kind остаётся int8,
    `t->f32 == NULL`, EMB-строка и `MM` сверяются с `q·scale·x` для fp32- и
    fp16-масштабов, `VTM_I8_EMB=0` даёт тот же результат (kind 1);
  * `tests/vtm/bench_backend.c` — `--check`: TMV/GEMV (режимы 0/2/3), MM
    `n>1`, EMB-строка против double-эталона (формы 128/256/300/1024, 300 —
    отказ SIMD и переносимый путь); `--i8-gemv [--f32-table]` — скорость
    ядра и сравнение с fp32-таблицей; `--emb-check PATH --prompts FILE` —
    A/B по сырым логитам (эталон — отдельная загрузка с `VTM_I8_EMB=0`).

### Числа

Ядро lm_head (`bench_backend --i8-gemv --rows 151936 --cols 2048 --iters 3
--f32-table`):

| путь | мс | ГБ/с | байт на токен |
|---|---:|---:|---:|
| fp32-таблица (0159, было) | 24,86 | 50,1 | 1,24 ГБ |
| int8-таблица, mode 2 | 3,72 | 83,7 | 0,31 ГБ |
| int8-таблица, mode 3 | 4,19 | 74,2 | 0,31 ГБ |
| int8-таблица, mode 0 (точные активации) | 49,85 | 6,2 | 0,31 ГБ |

`max|Δ|` int8 (mode 3) против fp32-таблицы на той же таблице — 7,75e-07.

Модель 3B Q4_K, 20 промптов golden, 8 новых токенов, `--emb-check`:

| argmax | top-5 | max\|Δlogits\| | последовательности |
|---:|---:|---:|---:|
| 160/160 шагов (20/20 промптов) | 100 % | 1,12e-05 (max\|ref\|=44,16) | совпали 20/20 |

Память (3B Q4_K, 4 новых токена, `/usr/bin/time -l`): 3,25 ГБ (fp32-таблица)
→ **2,02 ГБ** (упакованная), −1,23 ГБ; байт на токен 2,9 ГБ → 1,98 ГБ.

Декод, парный замер в одинаковых условиях (чередование порядка, 8 токенов,
4 повтора, `--stats`): fp32-таблица 1,73–2,97 ток/с (медиана 2,3),
упакованная 2,12–10,38 ток/с (медиана 6,9) — **×3,0 по медиане, ×3,5 по
лучшему**. Абсолютные числа в этом окне непригодны: load average 20–24,
swap 10,6 из 11,3 ГБ, страницы модели вытесняются (172 тыс. page fault на
4 токена в одном из прогонов) — 0169 видел то же самое.

### Критерии приёмки

- [ ] декод ≥30 ток/с — **нет**. На машине в текущем состоянии 2–10 ток/с
  (было 0,5–3,0). Проекция по компонентам: kind 6/7 2,77 Г MAC при 0169 59
  Г MAC/с = 47 мс + lm_head 4,2 мс ⇒ ~20 ток/с, то есть цель 30 недостижима
  без ускорения декодных ядер Q4_K/Q6_K. Сама задача исходила из того, что
  голова — 36,6 из 90 мс; после её снятия остаётся 47 мс, а не ~29.
- [x] argmax 20/20, Δlogits ≤1e-2 — да: 160/160 шагов, 1,12e-05.
- [x] `make test`, `--check` зелёные — `python3 tools/ci.py`: все 6 проверок
  (C-тесты, 2336 Python-тестов, perf-smoke, tasks, docs); UBSan-сборка
  `test_vtm` и `bench_backend --check` — чисто.
- [x] RAM 3B Q4_K ≤5 ГБ — 2,02 ГБ.
- [x] откат — `VTM_I8_EMB=0` (полный прежний путь; на x86 он же умолчание).

### Что осталось и риски

1. **Декодные ядра Q4_K/Q6_K — теперь узкое место** (47–80 мс/токен на этой
   машине). Нужна отдельная задача: 2 строки за проход (0169 оценивал
   +20–25 %), меньше инструкций на под-блок, лучше баланс потоков. У ollama
   45 ток/с соответствуют ~150 Г MAC/с или работе по полосе ~86 ГБ/с — наши
   ядра дают 48–61 Г MAC/с в этих условиях.
2. **x86**: декодного int8-ядра (VNNI) нет, поэтому авто-режим оставляет
   fp32-развёртку — регресса нет, но и выигрыша тоже. VNNI-ядро — follow-up.
3. `VTM_Q4_I8=0` с упакованной таблицей считает точные активации переносимым
   путём (49,9 мс) — это не откат; полный откат — `VTM_I8_EMB=0`.
4. **Параллельный агент перезаписал `src/vtm/interp.c`** (как и в 0169):
   правки 0170 в `interp.c` (ветки kind 4 в `op_tmv`/`op_mm`/`op_emb`,
   `req_i8`, `#include "trit.h"`) пришлось накатывать повторно. При приёмке
   свериться `git diff src/vtm/interp.c`: в дереве есть и чужие правки
   (prefill-пачка 0168), они не мои.
5. Замеры скорости — с машины под нагрузкой 20–24 и почти полным свапом;
   отношения (ядро lm_head, RSS, argmax/Δlogits) устойчивы, абсолютные ток/с
   между сессиями плывут в разы. `VTM_SKIP_HASH=1` в замерах — чтобы не
   читать 2 ГБ на каждую загрузку (на корректность не влияет).
