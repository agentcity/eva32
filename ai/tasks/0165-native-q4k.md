# Q4_K как есть

## Проблема

Сейчас Q4_K_M из ollama переквантовывается в наш Q4_1: **rel-RMS 5,1%** (0160).
Это не «плохой формат», это лишняя ступень: веса Q4_K хранят масштабы и минимумы
умнее (супер-блок 256, 8 под-блоков по 32, 6-битные масштабы, fp16 d/dmin).

Если хранить Q4_K **нативно** — потерь от импорта нет вообще, качество равно ollama.

## Требования

- Новый kind 6 = Q4_K: сегмент хранит блоки как в GGML (256 значений: d fp16,
  dmin fp16, 6-битные scales/mins, нибблы), без переквантования.
- `tools/vtm_ref.py`: запись/чтение сегмента, валидация длин; тест round-trip.
- `src/vtm/loader.c`: разбор kind 6 без fp32-материализации (указатели в mmap).
- Ядра: деквантизация Q4_K на лету (распаковка 6-битных масштабов) — в
  `backend_scalar.c` эталон, `backend_neon.c` быстрый путь.
- `tools/gguf_import.py`: `--q4-kind q4_k` (по умолчанию для 3B), без re-quant.
- `tools/vtm_compile.py`: читать сегменты kind 6.
- Проверка: 3B из ollama Q4_K_M собирается, паритет C↔Python ≤1e-6, **rel-RMS к
  исходным весам = 0** (нет переквантования), текст = как в ollama («Париж», «Москва»).
- Размер 3B ≈ как Q4_0 (1,92 ГиБ) + mins; 7B — оценить (может не влезть в 4 ГиБ).

## Критерии приёмки

- [ ] kind 6 round-trip Python↔C, паритет ≤1e-6
- [ ] 3B Q4_K собран из реального GGUF, rel-RMS 0 к весам GGUF
- [ ] текст совпадает с ollama на 3 промптах (Париж/Москва/CRM)
- [ ] `make test`, полный набор, `check_docs_dates` зелёные
