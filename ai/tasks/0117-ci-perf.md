# CI: порог регрессии производительности

## Проблема

CI проверяет корректность, но не скорость: мы уже дважды меняли ядра и узнавали о
регрессии только по ручным замерам. Нужен быстрый тест, который ловит падение скорости
больше чем на N%.

## Требования

- В `tools/ci.py` добавить шаг «perf smoke»: бенч на demo (короткий, 1–2 с) — сравнение с
  сохранёнными эталонами (`tests/fixtures/perf_baseline.json`), допуск ±25%.
- Эталоны хранить в репозитории с датой и машиной; на другой машине шаг скипается с
  предупреждением (или сравнивает только относительные величины).
- Тест: при искусственном замедлении шаг краснеет.
- Не делать шаг блокирующим на чужих машинах — только предупреждение, если эталона нет.

## Критерии приёмки

[ ] perf smoke в CI, краснеет при регрессе >25% (проверено искусственно)
[ ] на машине без эталона — skip с предупреждением
[ ] полный прогон CI не дольше 60 с

## Контекст и ограничения

- Зона: tools/ci.py, tests/test_ci_perf.py
- Другие файлы НЕ трогать: параллельно работают семь других агентов по своим зонам.
  В частности `interp.c` — 0112, `backend_*.c` — 0113, `main.c/api.c/api.h` — 0114,
  `eva/server.py` — 0115, `docs/` — 0116, `tools/ci.py` — 0117, `loader.c` — 0118,
  `prompts/` — 0119.
- **Запрещено:** pip, сеть, запуск сервера на порту, git-коммиты, скачивание моделей.
- **Отчёт пиши первым блоком ответа** — агенты этой сессии падают на финальном шаге.
- Проверка: `python3 -m unittest discover -s tests` (сейчас 1517 тестов) и, где нужно,
  `cd src/vtm && make test`.
- Если нужен API из чужой зоны (например `vtm_run_batch` из 0112) — опиши контракт в
  отчёте и используй заглушку, не правь чужой файл.
