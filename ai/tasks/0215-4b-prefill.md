# 4B умнее, но думает в 4 раза дольше

## Замеры (мои, тёплый процесс, одинаковый промпт ~300 токенов)
| модель | первый токен | параметров |
|---|---|---|
| 3B Qwen2.5 | **7,02 с** (43 ток/с) | 3,09 млрд |
| 4B Qwen3 | **31,14 с** (10 ток/с) | 4,02 млрд |

Разница параметров — 1,3×, а prefill — 4,4×. Значит дело не в размере, а в
пути исполнения. Подозрения:
1. **QK-norm (RMSH)** у Qwen3 не поддержан в батчевом/Metal-пути → per-token
   фолбэк на часть графа;
2. 4B: 8 KV-голов против 2 у 3B → внимание при prefill дороже (но O(n²) при
   n≈300 не даёт 4×);
3. head_dim/раскладка KV в 4B может ломать векторный путь;
4. tied lm_head + vocab 151 936: lm_head на пачке считается для всех токенов
   (0214 отмечал ~0,5 с на 250 токенов у 3B).

## Требования
1. Профиль 4B prefill по операциям (`--trace-summary`, VTM_BATCH_TRACE):
   GEMM/attention/RMSN/RoPE/lm_head — где 4B теряет время против 3B.
2. Проверить, попадает ли RMSH в батчевый путь, и если нет — добавить
   батчевый RMSH (CPU и Metal).
3. Убрать лишние проходы: lm_head только для последнего токена пачки (без
   изменения семантики SAMP — либо через флаг, либо через отдельный вызов).
4. Цель: prefill 4B ≈ 3B × 1,3–1,5, т.е. 250 токенов ≤5 с (сейчас 13–31).
5. Точность: argmax совпадает, Δ≤1e-5 (или документированный допуск).

## Критерии приёмки
- [ ] таблица «операция → время» для 3B и 4B на 250 токенах
- [ ] prefill 250 токенов 4B ≤5 с
- [ ] живой сервер: TTFT 4B на 250-токенном промпте ≤2 с (с кэшем префикса)
- [ ] тесты и `--check` зелёные

## Отчёт исполнителя

**Статус: сделано.** Причина 4,4× найдена и устранена: у 4B Qwen3 плотный
батчевый prefill был **выключен целиком** из-за `RMSH` (QK-norm) в графе, и
промпт считался по токену (2,5 ГиБ весов × 250). После снятия запрета, батчевого
`RMSH` и lm_head только на последний токен: 250 токенов 4B — **1,81 с** против
1,34 с у 3B, то есть **1,35×** при 1,19× арифметики на токен (цель была 1,3–1,5
и ≤ 5 с). Живой сервер: TTFT 4B на 253-токенном промпте **2,31 с** без кэша
префикса и **1,58 с** с кэшем (было 14,17 / 8,32 с). Точность: `max|Δlogits| = 0`,
argmax и последовательности через C-API совпадают побитово.

### Что было не так

`batch_classify` (`interp.c`) выключал пачку, если в программе есть `RMSH`:
`if (in->opcode == VTM_OP_RMSH && !b->has_moe) goto done;`. У MoE этот запрет
сняли в 0179, а Qwen3-4B — единственная **плотная** модель с QK-norm, поэтому
именно она шла прежним путём по токену: 250 проходов по всем слоям, каждый
заново читал и распаковывал 2,5 ГиБ Q4_K. 3B (без `RMSH`) считался пачкой.
Отсюда 4,4× при 1,3× параметров. Замеры по токену это подтверждают: 4B на
hybrid — 20,3 с/250 токенов, то есть ~81 мс на токен (это полоса чтения весов,
а не счёт), и ровно столько же, сколько 3B (69 мс/токен), — параметры тут почти
не при чём.

Второй, независимый резерв: lm_head (tied MM) считался для всех токенов пачки,
хотя в машину попадает только слот последнего. Короткий путь 0214
(`last[dst] == pc`) на этих моделях не срабатывал никогда: логиты читает `SAMP`,
поэтому `last[dst]` — pc сэмплинга, а не матрицы. Плюс `SAMP` при prefill'е
вызывался 250 раз подряд (по ~0,2–3 мс каждый).

### Что сделано

1. **`RMSH` в пачке + батчевое CPU-ядро `batch_rmsh_apply`.** Запрет снят
   (инструкция не читает позицию и не пишет KV, работает по последней оси
   тензора — её результат для токена не зависит от соседних). Ядро выносит из
   `op_rmsh` то, что не зависит от токена: `need`/`req_f32`/`same_count` и
   `meta_number()` (strstr по JSON меты) — они делались 18 000 раз за пачку.
   Арифметика — тот же double-цикл в том же порядке, результат **побитово**
   равен поштучному пути. Откат: `VTM_BATCH_RMSH=0`.
2. **lm_head только на последний токен пачки (SAMP-safe).** `batch_classify`
   отмечает MM, чей dst читают **только** `SAMP`'ы, а токен `SAMP`'а не читает
   ни одна инструкция графа (`mm_last_only`). Такой MM считается для одного
   последнего вектора, а `SAMP` исполняется на нём одном (`batch_samp_last`),
   со счётчиком `m->generated`, доведённым до C, как в поштучном пути.
   **Семантика `SAMP` не меняется**: оптимизация включается только при
   стратегии-argmax (`imm == VTM_SAMP_ARGMAX`, ни одного обращения к ГПСЧ) и
   выключенном штрафе за повторы (`repetition_penalty == 1` или `window == 0`,
   историю никто не читает). При температуре/top-p/штрафе — прежний полный путь.
   Откат: `VTM_BATCH_LAST=0`.
3. **C=4 для одного вектора.** Ядра kind 5/6/7 разворачивают токены четвёрками,
   хвост 1–3 добивают скалярным double-циклом по строке: lm_head на C=1 стоил
   230 мс, на C=4 — 20 мс. Единственный нужный вектор дублируется до четвёрки,
   читается/пишется только его столбец.
4. **Диагностика.** В `VTM_BATCH_TRACE` добавлена строка `lm_head-last: N пачек,
   SAMP-last: M` — иначе «SAMP 0,3 с» не отличить от «оптимизация не
   включилась». В `bench_backend --help` описаны `VTM_BATCH_RMSH`/`VTM_BATCH_LAST`.

### Что осталось / для 0216

- `RMSH` на hybrid стоит 314 мс/250 и почти всё это — **ожидание GPU**: CPU-я
  инструкция стоит между q/k/v-GEMM и attention и закрывает очередь 0214
  (на чистом CPU те же 72 инструкции — 83 мс). Ядро `RMSH` на Metal или QK-norm
  внутри RoPE/attention убрало бы ~0,3 с из 1,8 — это зона Metal-файлов (0216).
- lm_head — kind 5 (Q4), Metal-путь знает только kind 6/7 и int8, поэтому
  последний вектор считается на CPU: чтение 194 МБ таблицы на запрос. На пачке
  это амортизируется, на коротком хвосте даёт ~0,2 с фиксированных (до ~1 с при
  пустом page cache) — отсюда «пол» TTFT живого сервера ~1,3 с. GEMV kind 5 на
  GPU (или `VTM_Q4_I8`-путь) — следующий рычаг.
- Пачка по-прежнему режется кольцом KV (`batch_kv_window`): у 4B контекст 1024,
  промпт длиннее окна считается несколькими пачками (не regress, но и не «одна
  пачка на любой промпт»).
- ATTN на CPU у 4B в 2,09× дороже, чем у 3B (32 головы против 16) — единственная
  операция, где 4B обгоняет рост параметров; на hybrid её считает GPU.
