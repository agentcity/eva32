# Q4_K → Q4_1, а не Q4_0

## Проблема

3B Q4 в нашей ВТМ работает, но **качество деградировало**: на «Столица Франции?»
отвечает «Столица Франции - это Пгврф. Я ошибсясь!» (ollama на том же вопросе: «Столицей
Франции является Париж.»).

Причина — ступень переквантования при импорте: Q4_K_M (супер-блок 256, 8 под-блоков
по 32, масштабы **и минимумы** по 6 бит) → **симметричный Q4_0** (один fp32-масштаб на
32, без минимумов). Отчёт импорта: **10,0% rel-RMS** — это много.

Формат (kind 5) и ядра (0152) **уже поддерживают Q4_1** (`q4_is_asym`, `q4_mins`).
Импортёр пишет только sym.

## Требования

- `tools/gguf_import.py`: писать Q4_1 (asym) с минимумом на группу 32 вместо Q4_0 sym:
  для каждой группы из 32 значений подобрать `min` и `scale` по исходным (де-квантованным
  из Q4_K) значениям, значения `q = round((w - min)/scale)` в 0..15.
- Убедиться, что `vtm_compile` читает Q4_1 (флаг asym, mins) и `vtm run` считает.
- Замер: rel-RMS против исходных весов (должно быть заметно ниже 10%), текст на тех же
  промптах («Столица Франции?», «Сколько будет 17*23?»), паритет C↔Python ≤1e-5.
- Размер: Q4_1 добавляет 4 байта на группу (+0,125 Б/вес); 3B ≈ +0,35 ГБ — проверить,
  что контейнер остаётся ≤4 ГиБ.
- Если Q4_1 не улучшает текст — честно записать числа и предложить следующий шаг.

## Критерии приёмки

- [ ] rel-RMS ниже, чем у Q4_0 (числа до/после)
- [ ] текст на «Столица Франции?» осмысленный (Париж) либо объяснено, почему нет
- [ ] контейнер 3B ≤4 ГиБ, паритет C↔Python ≤1e-5
