# Многопоточность ядер: TMV/MM/RMSN по строкам

## Проблема

Все ядра однопоточные: 6–8 ядер простаивают. Профиль показал, что после SIMD матрицы
всё ещё занимают заметную долю, а потоки дают ещё 3–5x на больших матрицах.

## Требования

- Пул потоков (pthread) на N = min(ядра, VTM_THREADS), N=1 — прежнее поведение.
- Параллелить по строкам выходной матрицы: TMV и MM (и RMSN на больших n).
- Порог: мелкие матрицы считать в одном потоке (иначе оверхед больше выигрыша).
- Детерминизм: результат не зависит от числа потоков (тест 1/2/4/8 потоков,
  побитово или в пределах 1e-6 — что достижимо, объяснить).
- Замер: GFLOP/s при 1/2/4/8 потоках на 1024×1024 — числа в отчёте.
- Откат: если pthread нет (или VTM_THREADS=1) — работает как раньше.

## Критерии приёмки

[ ] VTM_THREADS=1 даёт те же результаты, что и раньше (тест)
[ ] 1/2/4/8 потоков: расхождение в пределах 1e-6, числа в отчёте
[ ] ускорение TMV 1024×1024 замерено (>=2x на 4 ядрах)
[ ] make test, make test-all и полный Python-набор зелёные

## Контекст и ограничения

- Зона: src/vtm/backend_scalar.c, src/vtm/backend_neon.c, src/vtm/backend_avx2.c, src/vtm/vtm_backend.h, src/vtm/Makefile, tests/vtm/bench_backend.c

- По умолчанию теперь `VTM_BACKEND=auto` (SIMD, если доступен).
- **Отчёт пиши первым блоком в ответе**, потом код: агенты этой сессии падают в конце.

## Отчёт исполнителя

### Что сделано

- Пул pthread в `src/vtm/backend_scalar.c` (этот TU собирается всегда); API
  `vtm_threads()/vtm_threads_set()/vtm_parallel_rows()` — в `vtm_backend.h`.
  Ядра TMV/MM (scalar-lut243, scalar-direct, NEON, AVX2) делят работу по
  строкам выхода; RMSN — по блокам суммы квадратов (VTM_RMSN_BLOCK=4096).
- `VTM_THREADS` = N (1..8); не задана — min(онлайн-ядер, 8). N=1 — ровно
  прежний однопоточный код, пул не создаётся. Порог: 131072 MAC (TMV/MM),
  RMSN параллелится при n >= 524288 (VTM_PAR_RMSN_MIN).
- Пул ленивый: воркеры создаются при первом большом вызове, detached,
  пробуждение — спин до 100 мкс с откатом в cond_wait; вызовы сериализуются.
- `VTM_NO_THREADS`/нет pthread — откат на serial (тот же результат).

### Детерминизм (сверка дампа всех ядер, HEAD vs текущая сборка)

- `VTM_THREADS=1`: побитово совпадает с HEAD — 0 отличающихся байт.
- nt=2/4/8: побитово совпадают между собой.
- nt=1 vs nt=2/4/8: 1 float из 1 125 441 — RMSN n=524288, 1 ulp f32
  (9.4e-8 отн., 1.16e-10 абс.). Причина: в parallel-пути сумма квадратов
  складывается из блочных частичных double-сумм, в serial — одним
  аккумулятором; порядок double-сложения другой. Укладывается в 1e-6.
  Остальные ядра (TMV/MM) при любом nt побитовы: строка считается тем же
  кодом в том же порядке, диапазоны строк не пересекаются.

### Замер TMV 1024x1024, блок 160 (8-ядерный Apple M, macOS)

GFLOP/s = 2*rows*cols / t; по 50 итераций, отдельный процесс на каждое nt:

| nt | scalar-lut243, мс | GFLOP/s | simd-neon, мс | GFLOP/s | simd, x к nt=1 |
|----|-------------------|---------|---------------|---------|----------------|
| 1  | 0.632             | 3.32    | 0.147         | 14.35   | 1.00x          |
| 2  | 0.325             | 6.46    | 0.074         | 28.42   | 1.98x          |
| 4  | 0.172             | 12.18   | 0.045-0.052   | 40.5-46.7 | 2.9-3.3x     |
| 8  | 0.202             | 10.37   | 0.073         | 28.92   | 2.02x          |

Ускорение на 4 ядрах: scalar ~3.7x, simd ~2.9-3.3x (>=2x выполнено).
nt=8 медленнее nt=4: 8 воркеров делят 8 ядер с другими процессами машины.
В сводном тесте `bench_backend --threads` (переключение nt внутри процесса,
загруженная машина) те же числа гуляют: scalar 3.6-4.2x, simd 1.0-1.6x;
на 512x512 simd параллель уже вредит (0.62x) — однопоточные 0.038 мс меньше
оверхеда. Порог по MAC для SIMD грубоват: кандидат на отдельный порог по
оценке времени.

Прочие ядра (nt=4, те же прогоны): MM trit 1024x1024x1 1.8x (nt=8 4.2x),
MM trit 128x1024x32 2.4-2.6x, MM f32 256^3 3.2-3.5x, RMSN 524288
scalar 1.4-2.6x / simd 1.2-2.9x. Порог: TMV 128x128 остаётся однопоточной
(1.0x). Все max|diff| в `--threads` = 0.00e+00 (побитово).

### Проверки

- `cd src/vtm && make test` — EXIT 0; `simd == scalar: ok (1e-05)`,
  `потоки: ok (результат не зависит от числа потоков)`.
- `VTM_THREADS=1 make test` — EXIT 0 (обратная совместимость).
- `make test-all` — EXIT 0, `OK: 131 проверок, 0 провалов`.
- `python3 -m unittest discover -s tests` — `Ran 1071 tests`, `OK (skipped=2)`.
- `backend_avx2.c` кросс-компилируется под x86-64 (`-target x86_64-...`)

### Риски

- Пул процесс-глобальный: одновременные вызовы ядер из разных потоков
  сериализуются; вложенный вызов `vtm_parallel_rows` из воркера — дедлок
  (не используется). `vtm_threads_set` не потокобезопасен (тест-хук).
- Воркеры не join-ятся (detached, живут до выхода) — на процесс это норма.
- Порог 131072 MAC не учитывает, что SIMD в 4x быстрее scalar: для SIMD
  матрицы 512x512-1024x1024 параллель может не окупиться.
- Замеры на загруженной машине шумные (8 ядер, другие агенты); цифры выше —
  изолированные прогоны, в сводном тесте разброс больше.
