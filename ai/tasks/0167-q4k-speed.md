# Вернуть скорость нативному Q4_K

## Проблема

Нативный Q4_K (0165) дал rel-RMS 0 к весам ollama, но **потерял скорость**:

| | Q4_1 (переквант) | Q4_K (нативный) |
|---|---|---|
| декод | 6,1 ток/с | **2,6 ток/с** |
| prefill 128 токенов | 17 с | **73 с** |

Причины: (а) в NEON-ядрах Q4_K/Q6_K накопление в **f64** (так получался паритет),
(б) батчевых ядер для kind 6/7 нет вовсе.

## Требования

1. **f32-накопление в NEON** с допустимой точностью: f32 даёт max|Δ| ≈ 1,07e-6 —
   это по-прежнему ≤1e-6…1e-5. Сделать основным, f64 оставить эталоном;
   `VTM_Q4K_STRICT=1` возвращает f64.
2. **Батчевый prefill для kind 6/7** (по образцу 0162): строка деквантизуется один раз
   на пачку, вектор по токенам.
3. Цель: декод ≥5 ток/с, prefill 128 токенов ≤25 с (сейчас 73 с).
4. Точность: паритет C↔Python ≤1e-6 или ≤1e-5 с обоснованием; вывод модели не меняется.
5. Замеры до/после: `runs/q4/3b-q4k.vtm`, декод и prefill 64/128/256.

## Критерии приёмки

- [x] декод ≥5 ток/с, prefill 128 ≤25 с
- [x] точность в допуске, вывод тот же
- [x] `make test`, `--check` зелёные

## Отчёт исполнителя

### Что сделано

1. **f32-накопление в NEON для kind 6/7** (`backend_neon.c`). Произведение
   `Σ q·x` копится в f32 (4 независимых аккумулятора), `d·sc`/`−dmin·m`
   применяются к сумме в f32, сумма по под-блокам — в double:
   `q4k_dot32_f32`, `q4k_row_dot_f32`, `q4k_sum32_f32`, `q6k_dot16_f32`,
   `q6k_row_dot_f32`. Копий активаций в double больше нет (у Q6_K — вообще
   без malloc). Эталон 0165 (`q4k_dot32`, `q6k_dot16` и строки на f64)
   остался и включается `VTM_Q4K_STRICT=1`; strict-режим заодно выключает
   батчевое ядро, то есть остаётся полностью double-эталоном.
2. **Батчевый prefill kind 6/7** (`backend_neon.c` + `backend_scalar.c` +
   `interp.c`): `vtm_q4k/q6k_tmv_batch`, `vtm_q4k/q6k_mm_batch`. Строка
   блоков деквантизуется в f32 один раз на пачку (`q4k_block_to_f32`,
   `q6k_block_to_f32`), затем 4 токена считаются одним набором FMA
   (вес — broadcast, токен — дорожка); группа 32 значения копится в f32,
   складывается в double. Проводка — `batch_tmv_ready`/`batch_mm_ready`
   и ветки ядер; отказ ядра (`-1`, cols не кратен 256/нет памяти) уходит
   на поштучный путь, как у 0162.
3. **Тесты и бенч** (`tests/vtm/bench_backend.c`): независимая
   double-деквантизация Q4_K/Q6_K, проверки TMV/MM/батча (включая строки,
   не кратные 256, и хвосты 1-3 токена), режим `--q4k` — поштучное ядро
   против батчевого на одной форме.

### Замеры (`runs/q4/3b-q4k.vtm`, 8 потоков)

Машина 16 ГиБ, рядом работает другой агент: loadavg в сеансе 8-32, поэтому
wall-clock шумит в 2-4 раза. Первичная метрика — CPU-время (`user`), оно
стабильно (разброс ≤2 %), wall — «лучшее при loadavg ≤9» и с пометкой.

Декод (`--tokens 151644,8948 --max-new 16`):

| | было (f64) | стало (f32) | множитель |
|---|---|---|---|
| wall, с | 2,70-3,15 (5,1-5,9 ток/с) | 1,94-2,07 (**7,8-8,3 ток/с**) | 1,4-1,5x |
| CPU, с | 16,2-16,4 | 12,2-12,4 | **1,33x** |
| wall при loadavg 11-18 | 5,9-17,7 | 3,8-10,1 | 1,6-1,8x |

Prefill (`--max-new 0`, промпты 64/128/256, тот же промпт, что в декоде +):

| промпт | было, с | стало, с | CPU было/стало | CPU-множитель |
|---|---|---|---|---|
| 64 | 26,9* | 13,7* | 59,0-60,2 / 45,0-46,0 | 1,31x |
| 128 | 27,9 / 23,1 | **15,9** / 19,5 | 116-122 / 85-87 | 1,37x |
| 256 | 55,3 | 47,1 | 238,2 / 172,4 | 1,38x |

\* в одном окне нагрузки (loadavg ~20), поэтому сравнимы между собой, а не с 128.

Ядро kind 6/7, изолированно (`--q4k`, синтетика, loadavg ~8):

```

Q6_K 11008x2048 x16: поштучно 15,60 мс (23,1 G MAC/s) → пачкой 6,68 мс (54,0) = 2,34x
Q4_K 2048x2048  x16: 2,86 → 1,11 мс = 2,58x;  Q6_K: 3,18 → 1,20 мс = 2,66x
```

Реальные тензоры 3B (то же ядро, данные из контейнера):

```
l0.gate_proj.w 11008x2048 (Q4_K): token 13,5 мс → batch 6,4 мс (2,11x)
l0.down_proj.w 2048x11008 (Q6_K): token 20,5 мс → batch 15,6 мс (1,31x)
l0.q_proj.w 2048x2048: 2,14 → 1,32 (1,62x);  k: 0,39 → 0,24;  v (Q6_K): 0,44 → 0,23
```

f32 против f64 на одном тензоре (11008x2048, 16 токенов):
wall 17,2 → 10,2 мс, CPU 90,3 → 49,4 мс (**1,83x**) — это и есть вклад
f32-накопления; остаток выигрыша сквозного декода съедают неизменные
lm_head (GEMV f32, 311М MAC) и RMSN/ATTN.

### Точность

- `bench_backend --check`: все случаи Q4_K/Q6_K ok (порог 1e-5):
  TMV 64x2048 — 9,5e-7 (|ref| 14,9); Q6_K TMV 3,8e-6 (|ref| 18,2);
  батч 2048x11008x4 — 3,0e-7 (|ref| 3,3), т.е. относительная ~1e-7.
- `bench_backend --prefill-check runs/q4/3b-q4k.vtm --batch-tokens 32`:
  `max|logits(пачка) − logits(по токену)| = 8,58e-6` (|ref| 12,26),
  argmax 872 = 872 — **ok** (порог 1e-5). Запас к порогу ~15 %.
- Вывод модели не меняется: 32 токена подряд совпали побитово у трёх
  конфигураций — старый бинарь (f64), новый (f32), новый с
  `VTM_Q4K_STRICT=1` (f64).
- Причина, по которой f32 проходит порог: q ∈ 0..15 (Q4_K) и q−32 (Q6_K) —
  целые, точно представимые в f32; ошибка — только округление сумм
  (относительно ~1e-7), а не формата весов.

### Чем проверено

```
make -C src/vtm test                     # все тесты, simd == scalar, потоки — ok
./src/vtm/bench_backend --check          # ok (включая новые Q4_K/Q6_K)
./src/vtm/bench_backend --q4k --rows 11008 --cols 2048 --iters 5
./src/vtm/bench_backend --q4k --rows 2048 --cols 2048 --iters 5
./src/vtm/bench_backend --prefill-check runs/q4/3b-q4k.vtm --batch-tokens 32
./src/vtm/vtm run runs/q4/3b-q4k.vtm --tokens 151644,8948 --max-new 32   # x3 конфигурации
```

### Что не вышло / осталось

- **Батчевый путь prefill на этой модели всё ещё медленнее поштучного**:
  128 токенов `--prefill-batch 16` — 159,5 с CPU / 36,3 с wall против
  85-87 с / 15,9-19,5 с у поштучного. Само батчевое ядро быстрее в 1,3-2,7
  раза, и без него (VTM_Q4K_BATCH=0 → double-эталон) путь стоил бы ~3x
  дороже, т.е. ядро работает; дорогая — сама машинерия пачки. Это не
  особенность kind 6/7: на Q4_1 та же картина (32 токена: 25,5 с CPU
  поштучно против 32,6 с пачкой). Нужна отдельная задача на накладные
  расходы батчевого пути (копии xt/yt на инструкцию, per-token ops в
  пачке, scratch).
- **AVX2 не сделан**: ядер kind 6/7 в `backend_avx2.c` нет и раньше не было;
  на x86 kind 6/7 идёт скалярным double-эталоном (как до задачи). Проверить
  на этой машине (arm64) нельзя.
- **Запас по точности небольшой** (8,6e-6 при пороге 1e-5). Если порог
  когда-нибудь ужесточат, `VTM_Q4K_STRICT=1` — готовый эталонный режим.
- **ADR 0018 устарел** в частях «цена скорости» и «батчевый prefill не
  сделан»; правка ADR — вне зоны задачи (docs: false), нужна архитектору.
- Абсолютные tok/s зависят от внешней нагрузки: при loadavg ≤8 декод
  8,1 ток/с и prefill 128 = 15,9 с (цели 5 ток/с и 25 с выполнены), при
  loadavg 17-32 те же прогоны дают 1,6-4,2 ток/с и 24,5-36 с.
