# Батчевые SIMD-ядра

## Проблема

`vtm_run_batch` (0112) даёт ускорение **только на скалярном бэкенде** — на нём батч
обрабатывается пачкой. На SIMD (а это дефолт после `auto`) ядра по-прежнему считают один
вектор за раз, поэтому батчевый prefill не ускоряет ничего (замер: 1,00×).

Замер 0114 (форма 1.5B, промпт 32, scalar): 45,4 с → 11,1 с (**4,1×**). На SIMD —
без выигрыша.

## Физический потолок (записать в отчёт, чтобы не ставить невыполнимых целей)

```
prefill 512 токенов × 1,5 GMAC = 768 GMAC = 1536 GFLOP
сейчас 37,6 с   →  41 GFLOP/s  (20% пика M1 Pro CPU ~200)
2×              →  82 GFLOP/s  (41%)
4×              → 163 GFLOP/s  (82%)  — маловероятно
10×             → 409 GFLOP/s  (204%) — невозможно
```

## Требования

- Батчевые SIMD-ядра для TMV/MM: обрабатывать N токенов против одной матрицы весов,
  переиспользуя загруженные веса (главный выигрыш — меньше обращений к памяти и
  амортизация накладных расходов).
- Цель: **≥1,8× на 4 потоках** для prefill 32–128 токенов на форме 1.5B, при побитовом
  (или ≤1e-5) совпадении с батчевым скалярным путём.
- Не ломать однопоточный путь и `bench_backend --check`.
- Замер: prefill 32/128 на SIMD до/после; заодно проверить, не вырос ли декод.

## Критерии приёмки

- [ ] prefill на SIMD ускорен ≥1,8× (числа в отчёте)
- [ ] результат совпадает с батчевым скалярным (≤1e-5)
- [ ] декод не замедлился (замер)
- [ ] `make test` и Python-набор зелёные

## Отчёт исполнителя

**Итог: prefill на SIMD 1.5B-формы ускорен 2,14× (32 токена) и 2,15× (128
токенов); декод не изменился.** Ускорение end-to-end, живой замер CLI
(`--max-new 0` = чистый prefill, wall по `--stats`, `VTM_THREADS=4`):

| prefill | до (`--prefill-batch 0`, по токену) | после (`--prefill-batch 32/128`) | ускорение |
|---|---|---|---|
| 32 токена | 2,160 с (2,122 / 2,225 / 2,160) | 1,008 с (1,016 / 1,008 / 0,993) | **2,14×** |
| 128 токенов | 8,779 с (8,779 / 8,887 / 8,502) | 4,086 с (4,086 / 4,068 / 4,173) | **2,15×** |

Контракт `--prefill-batch` режет пачку по `VTM_BATCH_TOKENS = 16`, поэтому 32
и 128 — это 2 и 8 пачек. Если после prefill сгенерировать 1 токен
(`--max-new 1`, так меряет CLI-таймер `время:`), к обеим сторонам добавляется
последовательный токен: 2,145 → 1,251 с (1,72×) для 32 и 8,64 → 4,56 с
(1,89×) для 128.

Декод (та же 1.5B-форма, промпт 5, `--max-new 24`, wall): до 1,846 с, после
1,850 с — в пределах шума; demo-модель 200 токенов: 7,54 мс до, 7,40 мс
после. Путь декода (`vtm_run`/`tmv_blocks`/`mm_trit`/`rmsnorm`) не менялся.

Kernel-level (`bench_backend --batch`, N=16, 4 потока, все матрицы графа
28 слоёв + lm_head): 986,8 → 537,7 мс на пачку, **1,84×**; по матрицам
q/k/v/o 2,65×, gate/up 1,89×, down 1,41×, lm_head 1,69×. Это ниже живых
2,14×, потому что per-token путь в реальном графе платит за повторное чтение
362 МиБ весов из page cache (в бенче матрица помещается в кэш).

Что сделано:

- `src/vtm/vtm_backend.h` — интерфейс батчевых ядер: `vtm_simd_tmv_blocks_batch`,
  `vtm_simd_mm_batch` (трит), `vtm_simd_tmv_f32_batch` и
  `vtm_simd_mm_f32_batch` (плотный, скалярный double-эталон). Раскладка
  `x[t*N+j]`/`y[r*N+j]`, как у батчевого scalar-пути interp.c; 0/-1; n_tokens
  == 1 уходит в прежнее одноколоночное ядро.
- `src/vtm/backend_neon.c` — NEON-ядро: по вектору N токенов, слово pack20
  распаковывается и переводится в f32 один раз на строку и блок; 8 токенов
  за шаг (2×4 ленты, 4 независимых f32-аккумулятора на группу), затем 4, а
  хвост 1–3 токенов — по столбцам (contiguous f32), а не в скалярном double
  (скалярный хвост был в 3,4× медленнее целой пачки 16 — исправлено).
  Скалярные откаты `trit_batch_scalar`/`dense_batch` — на любой сборке.
  Регистрация в `g_simd` + откат, если ядро NULL/не собрано.
- `src/vtm/backend_avx2.c` — то же для AVX2 (8 лент, хвост 4 × `__m128`,
  затем 1–3 по столбцам); проверено под Rosetta: `vtm_avx2_*` напрямую,
  `max|diff| ≤ 2,4e-6` на формах вплоть до 8960×1536×N16 (включая N=3/7/15).
- `src/vtm/interp.c` — проводка (зона расширена архитектором): гейт
  `batch_scalar_backend` заменён на `batch_backend_enabled` (scalar + SIMD),
  тритовые TMV/MM в пачке идут в ядра 0122, плотные — прежними строками;
  кэш префикса 0081 оставлен по токену на SIMD (побитовый контракт `vtm.h`).
- `tests/vtm/bench_backend.c` — `--check` проверяет батчевые ядра против
  независимого скалярного батчевого эталона (10 форм × блоки 128/160 + f32),
  новый режим `--batch` — kernel-level замер и проекция prefill.
- `tests/vtm/test_vtm.c` — `batch_check_same` получил допуск: на скаляре
  строго побитово (tol = 0), на SIMD ≤1e-5 с печатью `max|diff|` и имени
  тензора; выбранный токен сверяется точно. Комментарий «батчевых ядер там
  нет» обновлён.

Точность: `max|diff|` батчевых ядер против батчевого скаляра: малые формы
(scale 1.0) ≤ 3,8e-6, реальные формы 1.5B (scale 0.02) ≤ 1,8e-6 — с запасом
от 1e-5. Токены не меняются: demo `--prefill-batch 0/1/2/3/4/5/8/16/32/128`
(и scalar) дают `17 59 31`; 1.5B-форма — 60888 при 32 токенах и 80742 при
128 для batch 0 и batch N; argmax проверен и в тесте.

Проверки (выполнены): `cd src/vtm && make test` — зелёный (test_vtm,
test_vtm_api, test_vtm_session, test_sha256, `bench_backend --check`,
`bench_backend --threads`); `./bench_backend --check` — 146 проверок ok;
`./bench_backend --check --threads` — «потоки: ok»; `python3 -m unittest
discover -s tests` — 1734 теста, OK (32 skip).

Осталось / риски:

- **Узкое место после батча — сами TMV/MM**: 128 токенов prefill = 4,09 с =
  31,9 мс/токен, а kernel-level проекция «после» — 33,6 мс/токен, т.е.
  non-TMV операции (RMSN/ROPE/ATTN/EMB/SILU) по-прежнему ~1,5% и следующим
  кандидатом не стали. Дальше упираемся в f32 FMA + распаковку тритов
  (~98 GFLOP/s на 4 потоках); рост — только int8-dot (SDOT/VNNI) или пачка
  больше 16 (сейчас ограничена 96 МиБ scratch: ~4,7 МиБ/токен).
- AVX2 на настоящем x86 не замерялся: только кросс-компиляция и численная
  проверка под Rosetta (Rosetta не объявляет AVX2, поэтому диспетчер там
  идёт в скалярный откат — этот откат тоже проверен).
- В `src/vtm/vtm.h` остался устаревший комментарий «на SIMD батчевых ядер
  пока нет» (файл вне зоны) — поправить при приёмке.
- Замеры сняты на загруженной общей машине: абсолютные числа плавают ±10%,
  в отчёте — медиана 3 прогонов (для 128 один выброс 13,9 с отброшен).
