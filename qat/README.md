# QAT: тернарное дообучение Qwen2.5-1.5B

Заготовка quantization-aware training для пилота EVA32. На арендованной GPU-машине
остаётся поставить зависимости и запустить; всё остальное — в этом каталоге.

Тернарными становятся только `Linear` в attention и FFN: `q_proj`, `k_proj`, `v_proj`,
`o_proj`, `gate_proj`, `up_proj`, `down_proj`. Эмбеддинги, `lm_head`, layernorm, bias
и возможные роутеры MoE остаются в fp32 и обучаются как обычно.

## Что в каталоге

| Файл | Зачем |
|---|---|
| `ternary.py` | квантование, STE, упаковка тритов; чистая математика без torch |
| `train.py` | цикл обучения, лог, чекпоинты, `--resume`, `--dry-run` |
| `export.py` | `ternary.pt`, `ternary.trit`, `manifest.json` |
| `config.py` | YAML-конфиг и валидация |
| `data.py` | JSONL «вопрос → ответ», chat-темплейт, маска на вопрос |
| `model.py` | загрузка Qwen2.5, тернарные Linear, оптимизатор, LR |
| `checkpoint.py` | атомарное сохранение/загрузка, ротация |
| `configs/qwen1.5b.yaml` | все параметры с комментариями |
| `requirements-qat.txt` | torch, transformers, bitsandbytes, accelerate, pyyaml, numpy |

Проверки формата — `../tests/test_ternary.py` (unittest, без torch).

## Установка (только GPU-машина)

Нужны Python 3.10–3.12 и CUDA-сборка torch.

```bash
python3 -m pip install -r qat/requirements-qat.txt
```

Если pip поставил CPU-сборку torch:

```bash
python3 -m pip install torch --index-url https://download.pytorch.org/whl/cu124
```

## Порядок запуска на аренде

```bash
# 1. Быстрая проверка: 3 шага на случайных данных, без датасета.
#    Проверяет загрузку модели, память, backward, чекпоинт и лог.
python3 -m qat.train --dry-run

# 2. Пилот (8 GPU-часов на 4090 ориентировочно).
python3 -m qat.train --config qat/configs/qwen1.5b.yaml \
    --data distill/out/pairs.jsonl --out runs/pilot1

# 3. Если оборвалось — продолжить с последнего чекпоинта.
python3 -m qat.train --config qat/configs/qwen1.5b.yaml \
    --out runs/pilot1 --resume

# 4. Дотянуть прогон, если 2000 шагов мало.
python3 -m qat.train --config qat/configs/qwen1.5b.yaml \
    --out runs/pilot1 --resume --max-steps 3000

# 5. Экспорт троичных весов.
python3 -m qat.export --run runs/pilot1 --out export/
```

`--dry-run` по умолчанию пишет в `runs/dryrun`, не в `runs/pilot1`; модель при этом
скачивается настоящая. Если не хотите писать чекпоинт на 9–10 ГБ — `--no-save`.
Перед долгим прогоном зафиксируйте `model.revision` коммитом, а не `main`.

## Данные

`distill/out/pairs.jsonl`, по строке на пару:

```json
{"question": "Как отменить подписку?", "answer": "В разделе «Тарифы» …", "meta": {...}}
```

* применяется `tokenizer.apply_chat_template(..., add_generation_prompt=True)`;
* вопрос и padding получают `label = -100`, учим только на ответе и `eos`;
* пара длиннее `data.max_seq_len` отбрасывается (не обрезается), счётчики отбросов
  видны в логе и в `run.json` при разборе;
* `datasets` не нужна — JSONL читается напрямую.

### KL по логитам учителя (опция)

`data.use_teacher_logits: true` включает KL, если в строке есть поле `logits` /
`teacher_logits` — список распределений по токенам ответа. По умолчанию выключено:
обычная cross-entropy на тексте учителя.

Ограничения KL, о которых надо знать заранее:

* словарь учителя обязан совпадать со словарём ученика, иначе KL бессмыслен
  (код сравнивает размерность и падает с понятной ошибкой);
* полные логиты — это `длина_ответа × 151936` чисел на пример; для 100 тыс. пар
  это сотни гигабайт. Практично только для коротких пилотов или top-k формата,
  которого здесь пока нет;
* KL считается по кускам (`data.kl_chunk_size`), но память всё равно выше, чем у CE.

## Квантование и STE

Правило (зафиксировано в задаче, не пересматривается):

```
scale = absmax(блок 128 элементов вдоль входной размерности)
trit  = clamp(round_half_away(w / scale), -1, +1)
w_tern = trit * scale
```

* `scale = 0` у полностью нулевого блока — все триты 0, без деления на ноль;
* округление — «половина от нуля», одинаково в чистом Python и в torch;
* forward использует `w_tern`, backward — тождественный градиент:

```python
w_tern = quantize(w).detach()
w_used = w + (w_tern - w).detach()   # forward = w_tern, dL/dw = dL/dw_tern
```

В задаче STE записан как `w_tern + (w - w_tern).detach()`. В прямом проходе эта
запись даёт `w`, то есть квантование не попадает в forward; поэтому реализована
эквивалентная по смыслу форма `w + (w_tern - w).detach()`. Это единственное место,
где формула из ТЗ поправлена; в `ternary.ternary_ste_torch` есть комментарий.

Мастер-веса — fp32, forward — bf16 autocast. bf16-мастер для QAT не годится:
при `lr ~3e-5` обновления меньше шага округления bf16 и просто исчезают.

Чекпоинт хранит fp32-веса, поэтому один чекпоинт ≈ 9–10 ГБ (веса + 8-bit Adam).
`keep_last_checkpoints: 2` ограничивает диск ~25–30 ГБ (пик — при записи нового чекпоинта); при `save_every: 100`
на 2000 шагов это 20 сохранений, старые удаляются.

## Память, время, что крутить

Ориентир для 1.5B: fp32-веса 6,2 ГБ + fp32-градиенты 6,2 ГБ + 8-bit Adam ~3,1 ГБ
+ активации/логиты 2–5 ГБ. На 4090 24 ГБ это впритык, поэтому:

* `micro_batch_size: 4` — стартовое значение; при OOM ставьте 2 или 1;
* `max_seq_len: 2048` — следующее, что уменьшают (1024);
* CE считается кусками (`loss_chunk_size`), а `logits_to_keep` (если transformers
  умеет) срезает lm_head до хвоста, где лежит ответ — это заметно экономит VRAM;
* gradient checkpointing включён; без него память вырастет;
* если bitsandbytes не поставился, будет AdamW: веса те же, но состояния в fp32,
  и на 24 ГБ, скорее всего, не влезет.

Скорость: ориентир из `docs/distillation.md` — ~5 часов чистого счёта на 4090 на
30 млн токенов × 3 эпохи. Реальный tok/s печатается каждый `log_every` шагов.

Переменная окружения, помогающая фрагментации памяти:

```bash
export PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True
```

## Чекпоинты и возобновление

```
runs/pilot1/
  run.json                  # конфиг, модель, данные, статус
  log.jsonl                 # step, loss, ce, lr, tok/s, GPU, grad_norm
  latest.txt                # имя последнего чекпоинта
  DONE                      # прогон дошёл до max_steps
  checkpoints/
    step_000100/
      model.pt              # state_dict параметризованной модели (fp32)
      optimizer.pt          # 8-bit Adam (опционально)
      trainer_state.pt      # шаг, samples_seen, конфиг, RNG, отпечаток данных
```

* сохранение — в `.tmp` и атомарное переименование; оборванный чекпоинт не
  выглядит валидным;
* `--resume` без значения берёт последний; можно указать каталог явно;
* поток данных возобновляем: `samples_seen` + seed эпохи дают ту же
  последовательность, отдельного состояния DataLoader нет;
* если файл данных изменился, `--resume` остановится; осознанное продолжение —
  `--allow-data-change`;
* SIGINT/SIGTERM не убивают прогресс: обучение завершает текущий шаг и пишет
  чекпоинт (второй сигнал — немедленный выход);
* если состояние оптимизатора не читается (другая версия bitsandbytes), веса и шаг
  загрузятся, моменты Adam начнутся заново — с предупреждением.

## Экспорт

```bash
python3 -m qat.export --run runs/pilot1 --out export/
```

Пишет:

* `ternary.pt` — по тензорам `trits` (int8, `-1/0/+1`) и `scales` (fp16/fp32),
  плюс конфиг, шаг и метаданные;
* `ternary.trit` — те же данные, упакованные по 20 тритов в 32-битное слово
  (3^20 < 2^32), сегментами формата TRT1: заголовок, масштабы, слова;
* `manifest.json` — ревизия базовой модели, конфиг, шаг, число шагов, таблица
  тензоров со смещениями в `.trit`, sha256 файлов.

Триты и масштабы в `.pt` — основной артефакт. Нетернарные веса (эмбеддинги,
`lm_head`, нормы, bias) в экспорт не входят: они остаются в `model.pt` чекпоинта,
`manifest.json` фиксирует их число и источник. Сборщик инференс-модели должен
взять их оттуда.

### Масштаб 128 против блока 160 в docs/trit-format.md

`docs/trit-format.md` §2 описывает блок 8 слов = 160 тритов с одним масштабом,
но §8 оставляет размер группы масштаба открытым. QAT-конфиг фиксирует 128
(требование задачи), поэтому в экспорте:

* слова упакованы по 20 тритов и добиты до 8 слов на 160-тритовый блок —
  32-байтовое выравнивание сохранено, как в документе;
* `n_blocks` в заголовке — число групп масштаба по 128, а не 160-тритовых блоков;
* `manifest.json` явно пишет `scale_block: 128` и пояснение.

Это осознанное расширение черновика; если формат утвердят на 160, менять надо
`quant.block_size` и заголовок одновременно (версия формата), а не только кодек.

## Известные ограничения

* **Одна GPU.** DistributedDataParallel/FSDP и шардирование чекпоинтов не реализованы;
  `accelerate` стоит в requirements, но цикл однопроцессный.
* **Нет валидации и early stopping.** Качество мерить отдельно (`eval/`), по
  чекпоинтам; в логе только train-loss.
* **absmax даёт много нулей.** Для нормально распределённых весов порог
  `0.5·absmax` обнуляет ~85% весов блока. Это следствие зафиксированного правила;
  BitNet обычно использует absmean. Если качество просядет, это первый кандидат
  на эксперимент, но менять надо осознанно и с переобучением.
* **KL практически неприменим на больших данных** из-за полного словаря (см. выше).
* **Экспорт не собирает готовую HF-модель.** Нетернарные слои надо соединить
  с тернарными отдельным загрузчиком; формат `.trit` для этого и нужен.
* **Память 24 ГБ впритык.** Первый запуск — `--dry-run`: он покажет реальный
  пик VRAM на вашей карте до траты часов аренды.
* **Python 3.14** на машине разработчика не является целевым: GPU-стек ставится
  на 3.10–3.12, где есть колёса torch/bitsandbytes.
