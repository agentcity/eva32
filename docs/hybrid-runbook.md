# Рунбук гибрида: запуск, настройка, метрики

> Актуально на 2026-11-24.

Операционная часть к контракту [docs/hybrid.md](hybrid.md) и решению
[ADR 0009](adr/0009-hybrid-router.md): как поднять гибрид, подключить его из orioncode
и понять, куда ушли деньги.

Не зафиксированное контрактом сверено с кодом на 2026-11-24; что осталось — раздел 10.

## 1. Что запускается

Один процесс, за ним три источника: скиллы (0 ₽, из каталога), малая модель
(локально, дёшево), большая модель (по API, дорого). Наружу — `POST /v1/chat/completions`
и `GET /health`, только stdlib Python, без внешних пакетов. Если сервер слушает
не только loopback, нужен токен — раздел 3.

## 2. Настройка `.env`

Секреты — только в `.env` (он в `.gitignore`), в репозиторий кладётся `.env.example`.
Провайдер большой модели задаётся переменными, не кодом (`docs/hybrid.md`, правило 3).

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `EVA_SMALL_BASE` | `http://127.0.0.1:8001/v1` | база OpenAI-совместимого API малой модели |
| `EVA_SMALL_KEY` | пусто | ключ малой модели (локальной — любой) |
| `EVA_SMALL_MODEL` | `eva-small` | имя малой модели |
| `EVA_BIG_BASE` | пусто | база API большой модели — из панели провайдера |
| `EVA_BIG_KEY` | пусто | ключ большой модели |
| `EVA_BIG_MODEL` | пусто | имя большой модели |
| `EVA_MAX_COST_RUB` | `5.0` | бюджет на запрос, ₽ (`none` — без лимита) |
| `EVA_BIG_PRICE_PROMPT` / `_COMPLETION` | `0.4` / `1.2` | ₽ за 1000 токенов — по ним считается цена |
| `EVA_SMALL_TIMEOUT` / `EVA_BIG_TIMEOUT` | `30` / `60` | таймаут вызова, сек |
| `EVA_AUTH_TOKEN` | пусто | Bearer-токен HTTP-сервера; пусто — без аутентификации |
| `EVA_RATE_LIMIT_PER_MIN` | `60` | запросов в минуту на ключ (`0` — без лимита) |

Значения — из `eva/config.py` (сверено 2026-11-24); там же `EVA_*_RETRIES`,
`EVA_MAX_TOKENS` и пороги классификатора. Пустые `EVA_BIG_BASE`/`EVA_BIG_MODEL`
означают «большой модели нет»: всё, что не скилл, уйдёт в малую.

```bash
cd /path/to/eva32
cp -n .env.example .env
$EDITOR .env          # заполнить EVA_* и ключ большого провайдера
```

Ключ большого провайдера не попадает ни в лог, ни в `logs/eva.jsonl`.

## 3. Доступ: токен и лимиты

Сервер слушает `127.0.0.1` и по умолчанию `Authorization` не проверяет — это
режим разработки. Наружу (и вообще в сеть, где есть кто-то ещё) — только с
токеном: иначе любой, кто дотянется до порта, тратит бюджет на большие модели.

### 3.1. С токеном (боевой режим)

`EVA_AUTH_TOKEN` включает проверку: без `Authorization: Bearer <токен>` или с
чужим токеном — `401` и JSON `{"error": {"code": "unauthorized", ...}}`;
маршрутизатор (а значит, и модели) не вызывается. Открыт только `GET /health`:
по нему проверяют живость процесса. `GET /v1/models`, чат и незнакомые пути
требуют токен. Сам токен не попадает ни в ответ, ни в журнал, ни в
`logs/eva.jsonl`.

`eva` читает переменные из окружения и `.env` сам не загружает: либо
`set -a; . ./.env; set +a`, либо экспорт вручную. В `.env.example` этих двух
переменных пока нет — впишите их в свой `.env`.

```bash
python3 -c 'import secrets; print(secrets.token_urlsafe(32))'   # кандидат в токен
# в .env: EVA_AUTH_TOKEN=<эта строка>
set -a; . ./.env; set +a
python3 -m eva --port 8010
```

```bash
curl -sS http://127.0.0.1:8010/health                         # 200 без токена
curl -sS -o /dev/null -w '%{http_code}\n' \
  -X POST http://127.0.0.1:8010/v1/chat/completions \
  -H 'Content-Type: application/json' \
  -d '{"messages":[{"role":"user","content":"привет"}]}'      # 401
curl -sS -X POST http://127.0.0.1:8010/v1/chat/completions \
  -H "Authorization: Bearer $EVA_AUTH_TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{"messages":[{"role":"user","content":"привет"}]}'      # 200
```

### 3.2. Лимит запросов

`EVA_RATE_LIMIT_PER_MIN` (по умолчанию `60`) — запросов в минуту на ключ.
Ключ — предъявленный Bearer-токен: при одном настроенном токене это общий
лимит на сервер. В режиме без токена ключом служит адрес клиента, и клиенты с
разных адресов друг другу не мешают. Окно скользящее: считаются
запросы за последние 60 секунд. Сверх лимита — `429` с заголовками
`Retry-After` (секунды до освобождения слота), `X-RateLimit-Limit`,
`X-RateLimit-Remaining: 0` и JSON `{"error": {"code": "rate_limited", ...}}`.
Неудачная аутентификация квоту не тратит: `401` не считается запросом.
`EVA_RATE_LIMIT_PER_MIN=0` выключает лимит — наружу так не надо.

```bash
# низкий порог, чтобы увидеть 429 сразу
EVA_RATE_LIMIT_PER_MIN=2 python3 -m eva --port 8010

for i in 1 2 3; do
  curl -sS -o /dev/null -w '%{http_code}\n' \
    -X POST http://127.0.0.1:8010/v1/chat/completions \
    -H "Authorization: Bearer $EVA_AUTH_TOKEN" \
    -H 'Content-Type: application/json' \
    -d '{"messages":[{"role":"user","content":"привет"}]}'
done                                    # 200, 200, 429
```

### 3.3. Без токена (localhost)

Если `EVA_AUTH_TOKEN` пуст, поведение прежнее: `Authorization` не проверяется,
`401` не бывает. При старте в журнал уходит `WARNING` о работе без
аутентификации. Лимит в этом режиме считается на адрес клиента, чтобы
локальный «умный» клиент тоже не выжёг бюджет. Предупреждение — не защита:
порт не пробрасывать и не слушать `0.0.0.0` без токена.

## 4. Запуск и первый ответ

```bash
python3 -m eva.cli ask "сколько стоит тариф Старт" --explain
python3 -m eva.cli serve --port 8000
```

`ask --explain` печатает ответ с маршрутом и ценой — быстрая проверка, что скиллы
и модели на месте, без HTTP. `serve` держит процесс на переднем плане.

Порт `8000` тут уже занят прод-`vLLM` (его же проверяет `make status`), поэтому
локально удобнее `--port 8010`: флаг из контракта, маршрутизация от порта не зависит.

## 5. Проверка после старта

```bash
curl -sS http://127.0.0.1:8000/health
curl -sS -X POST http://127.0.0.1:8000/v1/chat/completions \
  -H 'Content-Type: application/json' \
  -d '{"model":"eva-hybrid","messages":[{"role":"user","content":"сколько стоит тариф Старт"}]}' \
  | python3 -m json.tool
```

``/health` отвечает 200, если процесс жив. В ответе кроме `choices[0].message.content`
есть поле `eva` с маршрутом, скиллом и ценой — его читают разделы 6–7. Если задан
`EVA_AUTH_TOKEN`, в запрос к `/v1/chat/completions` добавьте
`-H "Authorization: Bearer $EVA_AUTH_TOKEN"`, иначе будет `401` (раздел 3.1).

## 6. Подключение из orioncode

Для orioncode гибрид — обычный OpenAI-провайдер, отдельный клиент не нужен:

- **base URL** — `http://127.0.0.1:8000/v1` (или адрес машины с `serve`); есть и `/v1/models`;
- **API key** — значение `EVA_AUTH_TOKEN` сервера; если токен не задан (localhost-режим), годится любая непустая строка (раздел 3);
- **model** — любое имя, оно лишь возвращается в ответе, маршрут выбирается сам; по
  умолчанию `eva-hybrid`.

Аккаунт провайдера заводится один раз; маршрут гибрид выбирает сам, клиент об этом
не знает. Поле `eva` дополнительное: клиент, который его не знает, его игнорирует.

Если orioncode ходит из контейнера, `127.0.0.1` — сам контейнер, а не хост: нужен
адрес хоста (`host.docker.internal`) или общая сеть. Частая причина «недоступен».

## 7. Маршруты и стоимость

Три источника, по возрастанию подробности: поле `eva` в ответе (маршрут
`skill`/`small`/`big`, скилл, `cost_rub`); `logs/eva.jsonl` — строка на ответ (время,
маршрут, скилл, токены, рубли, латентность); агрегат по логу — отчёт по маршрутам и дням.

```bash
tail -n 5 logs/eva.jsonl
python3 tools/usage_report.py --path logs/eva.jsonl
```

Много `big` на простых вопросах — классификатор уводит в облако лишнее (дорого);
много `small` на сложных — наоборот, качество. Доля `skill` растёт с наполнением
каталога. Цена на 1000 запросов — цифра для решения «выгоден ли гибрид», её и
сравнивают с «всегда большая модель»; цена = токены/1000 × `EVA_*_PRICE_*`.

## 8. 429, таймауты и прочие отказы

Фолбэки заданы в `eva/policy.py` (`docs/hybrid.md`): малая → большая при
ошибке/таймауте, большая → малая при 429 и превышении `EVA_MAX_COST_RUB`. Ретраи с
backoff уже внутри клиента — повторять запрос снаружи не нужно.

| Симптом | Вероятная причина | Действие |
|---|---|---|
| 429 от большой модели | лимит/слоты провайдера | ответ уже отдан малой; смотреть долю `big`; при частых 429 — бюджет или классификатор |
| 429 от гибрида (`rate_limited`, есть `Retry-After`) | сработал `EVA_RATE_LIMIT_PER_MIN` | подождать `Retry-After`; лимит поднимать осознанно, не выключать наружу (раздел 3.2) |
| таймаут малой модели | локальная модель не поднята | `curl` по `EVA_SMALL_BASE`, поднять/перезапустить её |
| «перегружена, секунду» | ретраи исчерпаны, пришёл `ClientError` | штатный фолбэк; искать серию подряд в `logs/eva.jsonl` |
| обрыв по бюджету | `EVA_MAX_COST_RUB` меньше цены запроса | поднять бюджет осознанно или отдать вопрос малой модели |
| 401 от гибрида (`unauthorized`) | клиент не прислал `Authorization: Bearer` или токен не совпал с `EVA_AUTH_TOKEN` | передать токен; это не ошибка модели (раздел 3.1) |
| 401 от большой модели | ключ большого провайдера | ошибка конфигурации — править `.env`, ретраить бессмысленно |

429 — не ошибка гибрида, а сработавшая политика. Разбирать нужно не код ответа, а
`reason` маршрута: фолбэк на каждом втором запросе = конфиг или классификатор.

## 9. Замер

### 9.1. Качество маршрутов

```bash
python3 tools/eval_hybrid.py
python3 -m unittest tests.test_eval_hybrid -v
```

Замер идёт с заглушками моделей: ни сети, ни ключей, ни денег. Печатает точность
маршрутов, долю скиллов и цену на 1000 запросов; тест фиксирует метрики от регрессии.
Замеры бандла (`make dev`, `make eval`) — про качество текста, а не про маршруты.

### 9.2. Латентность и поведение под нагрузкой

Средняя латентность по одному запросу ничего не говорит о хвостах: сервер может
быть «в среднем быстрым» и на каждом сотом запросе думать втрое дольше. Для
решения «выставлять ли наружу» нужны p50/p95/p99 и throughput — их считает
`tools/bench_eva.py`. Для генеративной модели одной цифры мало и внутри запроса:
время до первого токена (**TTFT**, почти весь prefill) и время между токенами
(**ITL**, decode) ведут себя по-разному и оптимизируются разными рычагами —
раздел 9.3.

```bash
# 1. Код и маршрутизация под нагрузкой, без сети и ключей:
python3 tools/bench_eva.py --offline --n 100 --concurrency 4

# 2. Без сети, но с искусственной задержкой заглушки 50 мс — видно, как
#    параллельность поднимает throughput:
python3 tools/bench_eva.py --offline --n 200 --concurrency 8 --stub-latency-ms 50

# 3. Живой сервер (поднят по разделу 4):
python3 -m eva --port 8010 &               # или python3 -m eva.cli serve --port 8010
python3 tools/bench_eva.py --http http://127.0.0.1:8010 --n 100 --concurrency 4

# 4. С токеном и в машинном виде — для нескольких прогонов подряд:
python3 tools/bench_eva.py --http http://127.0.0.1:8010 --n 200 \
  --token "$EVA_AUTH_TOKEN" --json > bench.json

# Тесты самого бенчмарка (без сети):
python3 -m unittest tests.test_bench_eva -v
```

Что печатает:

- **латентность** — p50/p95/p99, min/mean/max по успешным запросам, мс;
- **throughput** — запросов в секунду от старта пула до последнего ответа;
- **маршруты** — доля `skill`/`small`/`big` среди успешных ответов;
- **цена за 1000** — оценка по распределению маршрутов и токенам (та же модель,
  что у `eval_hybrid.py`); в HTTP-режиме рядом печатается сумма из поля `eva`,
  которую насчитал сам сервер;
- **ошибки и таймауты** — отдельными счётчиками, с первым текстом отказа.

Таймаут HTTP-запроса — `--timeout` (по умолчанию 30 с), в offline-режиме вызов
нельзя прервать снаружи: запрос, который шёл дольше, помечается таймаутом
постфактум и в перцентили не входит. Ошибки и таймауты не роняют прогон; код
возврата 1 — только если не удался ни один запрос (или превышен бюджет p95).

Бюджет. В `docs/hybrid.md` бюджета латентности на 2026-11-18 нет, поэтому строка
«бюджет p95» просто сообщает об этом. Если бюджет появится там строкой вида
«бюджет … p95 ≤ N мс», он подхватится автоматически; задать вручную —
`--p95-budget-ms N`. Превышение — код возврата 1, удобно для CI.

Как читать и чего не путать:

| Что видно | Смысл | Что делать |
|---|---|---|
| `--offline`: p50 — единицы мс | накладные расходы роутера, скиллов и заглушек, **не** латентность моделей | сравнивать прогоны между собой, а не с боевыми цифрами |
| `--offline --concurrency 4`: хвост вырос | потоки делят GIL на CPU-bound коде | для оценки модели — только `--http` |
| `--http`: p99 в разы выше p50 | очередь сервера, холодный старт модели, ретраи/фолбэк | смотреть `latency_by_route_ms` в JSON: если тянет `big` — это модель, а не HTTP |
| много `429`/таймаутов | лимит `EVA_RATE_LIMIT_PER_MIN`, мёртвая малая модель, медленный провайдер | поднять лимит/таймаут осознанно, проверить `EVA_SMALL_BASE` (раздел 8) |
| доля `big` выше ожидаемой | классификатор уводит в облако лишнее | сверять с `eval_hybrid.py`, править пороги, а не «среднюю» |

Шум. На загруженной машине цифры смещаются сильнее, чем хочется: фоновые
процессы, троттлинг, частота CPU и сеть дают разброс в разы на p99. Поэтому:
первый запрос не считается (`--warmup 1` по умолчанию — прогрев тянет ленивые
импорты), p99 при `--n` меньше сотни — статистика на трёх-пяти значениях;
один прогон ничего не доказывает, нужно 3–5 подряд и сравнение разброса, а не
одного числа. Замеры на разных машинах и под разной нагрузкой сравнивать
бессмысленно; для боевого решения — `--http` на том же хосте, что и сервер.

### 9.3. Из чего складывается задержка ВТМ: кэш префикса и потоки

Если малая модель — своя ВТМ, к задержке добавляются рычаги, которых нет у HTTP-клиента:
повторный префикс промпта (системный промпт 4,4 КБ повторяется в каждом запросе —
[0081](../ai/tasks/0081-vtm-prompt-cache.md)) и число потоков ядер. Сейчас **сервер в ВТМ
не ходит**: он ждёт OpenAI-совместимый эндпоинт, а интеграция через C-ABI — задача
[0089](../ai/tasks/0089-eva-vtm-backend.md) в работе ([status.md](status.md)). Поэтому
числа ниже — про ВТМ, а не про текущий HTTP-путь; но это те рычаги, которые дадут
задержку «своей модели».

| Что | Было → стало | Ускорение | Источник |
|---|---|---|---|
| Кэш префикса, 128 токенов + 16 новых, ctx 256, SIMD | 6,21 → 0,79 мс/запрос | **7,83×** | [0081](../ai/tasks/0081-vtm-prompt-cache.md) |
| Прогрев кэша (разово) | +5,6 мс; одна экономия 5,42 мс, окупается со второго запроса | — | [0081](../ai/tasks/0081-vtm-prompt-cache.md) |
| Серия из 7 запросов с общим префиксом | амортизированно | 3,9× | [0081](../ai/tasks/0081-vtm-prompt-cache.md) |
| Потоки, TMV 1024×1024 скаляр, 4 потока | 0,662 → 0,172 мс; 3,17 → 12,21 GFLOP/s | **3,85×** | [0077](../ai/tasks/0077-vtm-threads.md) |
| Потоки, TMV SIMD, 4 потока | 0,147 → 0,045–0,052 мс | 2,9–3,3× | [0077](../ai/tasks/0077-vtm-threads.md) |
| Потоки, 8 вместо 4 | 0,202 мс скаляр / 0,073 SIMD — медленнее | — | [0077](../ai/tasks/0077-vtm-threads.md) |
| SIMD, сквозной проход demo | 2 535 → 14 870 ток/с | 5,9× | [0050](../ai/tasks/0050-vtm-simd.md) |
| Блочный attention, ctx 2048 | 0,472 → 0,191 мс/шаг | 2,4× | [0076](../ai/tasks/0076-vtm-attn-tiling.md) |
| Сэмплинг, словарь 150k, top-k 40 | 15,4 → 0,46 мс/токен | 33,3× | [0059](../ai/tasks/0059-vtm-samp-perf.md) |
| Профиль полного прохода, ctx 128 | TMV занимает 92% на scalar (0,248 мс/шаг); с SIMD 0,027 мс/шаг (9,2×), проход 0,271 → 0,049 мс (5,5×) | — | [0071](../ai/tasks/0071-vtm-bench.md) |

Оговорки, без которых числа врут:

- **3,85× — это скалярный TMV**, лучший случай: 0,662 → 0,172 мс в замере из коммита
  `0b0cfee`; в тексте отчёта 0077 стоит «scalar ~3,7×» (0,632 → 0,172) — тот же порядок,
  разные прогоны на загруженной машине. На SIMD потоки дают 2,9–3,3× и нестабильны
  (упирается в память), на 512×512 параллель уже вредит. В снимке [status.md](status.md)
  стоит сводное «≈3,4× (3,2–3,7×)», и он же держит 0077/0081 «в работе»: снимок 08:28
  старше приёмки этих задач, номера здесь — из их отчётов.
- **Кэш через C-ABI не работает.** `api.c` и `kv_store.c` зовут `vtm_reset` на каждый
  запрос, поэтому весь выигрыш 7,8× остаётся внутри тестов ядра — задача
  [0087](../ai/tasks/0087-api-cache.md) `pending`. В сервере его мерить рано: сначала 0087.
- Кэш инвалидируется `vtm_reset`, сменой бэкенда, записью KVW ниже позиции префикса и
  переполнением кольца KV ([0081](../ai/tasks/0081-vtm-prompt-cache.md)). В бою это
  «поменяли системный промпт» и «контекст длиннее окна» — оба раза полный пересчёт.
- Пул потоков процесс-глобальный: вложенный вызов ядра даёт дедлок, `VTM_THREADS=1` —
  ровно прежний однопоточный код ([0077](../ai/tasks/0077-vtm-threads.md)).
- Все числа — demo/синтетика (ctx 256, hidden 128). На 1.5B проход не измерен
  ([status.md](status.md) §ВТМ), абсолютные миллисекунды переносить нельзя, тренды — можно.

### 9.4. Что мерить на сервере

Порядок — от «где время» к «сколько стоит»; каждый пункт даёт число, а не мнение.

1. **Prefill и decode раздельно.** `vtm run --stats` печатает только сумму (токены,
   время, ток/с), поэтому prefill меряется прогоном с `--max-new 1`, decode — с
   `--max-new 32/128`; разница — цена одного токена. Аккуратнее — `bench_vtm.py`:
   `--gen 1` против `--gen 128` на одинаковом `--contexts`:

   ```bash
   python3 tools/bench_vtm.py --model demo/model.vtm --contexts 128,512,2048 \
     --gen 1,32,128 --backends scalar,simd --json-out runs/bench-vtm.json
   ```

2. **Потоки.** Один и тот же промпт при 1/2/4/8 потоках; ждать выигрыш до 4, на 8 —
   деградацию. Заодно проверить, что ответ не меняется (`--stats` + одинаковый вывод).
3. **Кэш префикса.** До [0087](../ai/tasks/0087-api-cache.md) — только тестами ядра;
   после — два запроса через C-ABI с общим префиксом и счётчик `vtm_cache_stats`
   (попадания/промахи). Критерий: второй запрос быстрее, ответ побитово тот же.
4. **Бэкенд.** `VTM_BACKEND=auto|simd|scalar` на одном промпте: разница 5,9× на demo —
   если на сервере она исчезла, смотреть, что выбрал `auto`.
5. **HTTP-путь.** `bench_eva --http --json`: `latency_ms` — клиент (сеть + очередь +
   сервер), `server_latency_ms` — сам сервер, `latency_by_route_ms` — по маршрутам.
   Разница первых двух и есть накладные расходы сети.
6. **По маршрутам из лога.** `tools/usage_report.py --path logs/eva.jsonl` печатает по
   каждому маршруту запросы, долю, p50/p95 и рубли — там видно, тянет ли хвост `big`.
7. **Отказы.** Доля `429`/таймаутов и первый текст ошибки — отдельными счётчиками;
   они уже есть в выводе бенчмарка (раздел 8).

Чего не делать: мерить `--offline` и называть это задержкой модели (это накладные
расходы роутера и GIL); делать вывод по одному прогону; сравнивать ВТМ с vLLM на разных
машинах; обещать выигрыш кэша в сервере до 0087. Бюджета p95 в [docs/hybrid.md](hybrid.md)
по-прежнему нет — цифра «бюджет p95» в выводе честно об этом сообщает, пока её не задали
строкой в контракте или флагом `--p95-budget-ms`.

## 10. Что сверить до боевого запуска

- значения по умолчанию и пороги — `eva/config.py` (сверено 2026-11-24);
- `EVA_AUTH_TOKEN` задан, если сервер доступен не только с loopback; лимит
  `EVA_RATE_LIMIT_PER_MIN` — осознанный (раздел 3);
- URL баз малой и большой модели — панель провайдера, не догадка;
- `tools/eval_hybrid.py` на заглушках: каталог 45 строк — 45/45, 44/45, 10,42 ₽/1000;
  исторический набор 80 строк (`--golden eval/hybrid_golden.jsonl`) — 80/80, 44/80,
  128,94 ₽/1000 ([0105](../ai/tasks/0105-golden-classes.md),
  [0119](../ai/tasks/0119-prompt-shorten.md)); `tools/usage_report.py` — агрегат по
  `logs/eva.jsonl`;
- флаги `--explain` у `ask` и `--port` у `serve` — `eva/cli.py` (проверено
  2026-11-24); `--http/--json/--token/--p95-budget-ms` — `bench_eva.py --help`;
- интеграция с ВТМ сделана: `EVA_LOCAL_MODEL`, `EVA_LOCAL_MODEL_PRIORITY`,
  `EVA_VTM_BACKEND`, `EVA_VTM_CACHE`, `EVA_VTM_THREADS`
  ([0104](../ai/tasks/0104-eva-router-vtm.md), [0089](../ai/tasks/0089-eva-vtm-backend.md));
  маркер `local` в телеметрии — [0109](../ai/tasks/0109-telemetry-local.md);
- кэш префикса в C-ABI есть ([0087](../ai/tasks/0087-api-cache.md)); в `eva`-бэкенде
  он включается `EVA_VTM_CACHE=1`, в `tools/chat.py` — по умолчанию;
- `VTM_THREADS` — осознанно (1 — прежнее поведение, 8 на 8 ядрах часто медленнее 4,
  [0077](../ai/tasks/0077-vtm-threads.md)).

Пока пункт не сверен, поведение считается неизвестным, а не «работает по
умолчанию»: в гибриде неизвестная переменная стоит денег молча.
