# VTM — виртуальная троичная машина (v0.2)

Своя машина вместо bitnet.cpp: мы контролируем формат, ядра и поведение, и можем
заменить бэкенд, не переписывая модель.

## Зачем своя

bitnet.cpp — форк llama.cpp: он диктует формат весов (i2_s/tl1), прячет ядра в
своих LUT-таблицах и тянет весь llama.cpp как зависимость. Нам нужно:

1. **Формат наш** — `.trit` с 20 тритами в 32-битном слове (`docs/trit-format.md`),
   который уже умеет `qat/export.py` и `tools/trit_codec.py`.
2. **Поведение наше** — модель исполняется детерминированно, без скрытых эвристик.
3. **Бэкенд отделён от байткода** — сегодня скалярный C и SIMD (NEON/AVX2), в
   будущем троичное железо. Модель при этом не перекомпилируется.

## Три слоя

```
модель (.trit + manifest)  →  компилятор (Python)  →  программа (.vtm)
                                                          ↓
                                          интерпретатор (C) → бэкенд (ядро)
```

- **Компилятор** (`tools/vtm_compile.py`) — граф модели → байткод. Без него
  интерпретатор не знает, какие слои в каком порядке.
- **Интерпретатор** (`src/vtm/`) — читает `.vtm`, исполняет инструкции по одной.
- **Бэкенд** — набор ядер: скалярный C (`scalar-lut243`/`scalar-direct`) и SIMD
  (NEON на ARM64, AVX2 на x86-64); см. `docs/vtm-perf.md`. В будущем — троичное
  железо.

## Контейнер `.vtm`

Версия формата — **2** (ADR 0011): размерности тензоров хранятся как `u32 × 4`,
поэтому в контейнер влезает словарь Qwen (151 936 токенов). Заголовок остался
32 байта, порядок секций — прежний. Файлы v0.1 (`version=1`, запись тензора
44 байта) не читаются: загрузчик отвергает их с ошибкой
«формат v0.1 не поддерживается» — ценных артефактов v0.1 нет, синтетика
пересобирается за секунды.

```
┌─ заголовок (32 байта) ──────────────────────────────────┐
│ "VTM1" | версия u16 = 2 | флаги u16 | n_instr u32        │
│ n_tensors u32 | n_program u32 | program_offset u32       │
│ meta_offset u32 | meta_len u32                           │
├─ таблица тензоров (n_tensors × 52 байта) ────────────────┤
│ имя[24] | kind u8 | ndim u8 | dims u32×4 | offset u32     │
│ scale_offset u32 | резерв u16                             │
├─ данные тензоров (выровнены на 32 байта) ────────────────┤
├─ метаданные JSON (опционально, дополнены нулями до 32) ──┤
├─ программа (n_instr × 16 байт, последняя секция) ────────┤
└──────────────────────────────────────────────────────────┘
```

Смещения в записи тензора: `name` 0, `kind` 24, `ndim` 25, `dims` 26–41,
`offset` 42, `scale_offset` 46, резерв 50–51. `offset` — смещение от начала
секции данных; `offset` и `scale_offset` (если используется) кратны 32.
`dims` — до 4 измерений по `u32`: поле вмещает до 4 294 967 295, но загрузчик
ограничивает произведение `2^30` элементами и запрещает нулевые измерения;
недостающие измерения — нули.

`kind`: `0` — триты, `1` — fp32, `2` — fp16, `3` — bf16. `kind 4` (int8 +
масштабы) зарезервирован, но контейнером **не читается**: int8-эмбеддинги
отложены (нужен и `src/vtm/loader.c`, и `tools/vtm_ref.py`; задача 0043).

Флаги заголовка: бит 0 (`0x0001`) — raw-триты хранят масштабы fp32 (иначе
fp16); бит 15 (`0x8000`, расширение C) — неоднозначное число масштабов
считать блоком 160. `n_program` — размер программы в байтах; загрузчик
принимает 0 (не проверять) или `n_instr·16`.

### Раскладки тритов

Тритовая матрица (`kind 0`) хранится одним из двух способов:

- **TRT1-сегмент** (`scale_offset == 0xFFFFFFFF`): по `offset` лежит
  `"TRT1"`, version u8 = 1, flags u8 (бит 0 — масштабы fp32), `n_trits u64`,
  `n_scale u32`, затем `n_scale` масштабов, затем `ceil(n_trits/160)·8` слов
  pack20. `n_trits` обязан совпадать с произведением `dims`.
- **raw** (`scale_offset != 0xFFFFFFFF`): по `offset` — слова pack20, по
  `scale_offset` — масштабы; ширина масштаба берётся из флага заголовка.
  Raw-раскладка использует блок 160 — это расширение C, Python-эталон её не
  пишет.

Размер блока масштаба: `docs/trit-format.md` фиксирует 160 тритов на масштаб,
а Python-эталон (`tools/vtm_ref.py`) — 128 (блок QAT); упаковочный блок при
этом всё равно 160 = 8 слов. C читает оба варианта: по `n_scale` определяет
128 или 160; если для маленького тензора числа совпали — берёт 128 (канон
Python), а флаг `0x8000` принудительно выбирает 160. Подробнее — в
`src/vtm/README.md`.

> Нетернарные веса (`kind` 1–3) — это место для эмбеддингов, norm-весов и
> `lm_head`: загрузчик приводит fp16/bf16 к fp32 в арене, интерпретатор читает
> их как обычные `float`. Тритовый контейнер и плотный могут сосуществовать в
> одном файле. Тритовой (`kind 0`) может быть **любая** матрица, включая
> таблицу словаря — см. «Эмбеддинги в тритах».

### Эмбеддинги в тритах

`quant.quantize_embeddings: trit` у QAT-эксперимента (0027) доводится до
рантайма целиком (0043):

- **экспорт** (`qat/export.py`) квантует таблицу словаря тем же правилом, что
  и Linear-веса (`scale = absmax(блок 128)`,
  `trit = clamp(round_half_away(w/scale), -1, 1)`), и пишет её сегментом
  `model.embed_tokens.weight` в `ternary.trit`; в `non_ternary.bin` её нет. В
  манифесте: `architecture.embed = "trit"`, запись тензора с `kind: trit`,
  `role: embed`, раздел `embeddings: {mode, storage, bytes}`. При
  `tie_word_embeddings` запись `lm_head.weight` ссылается на неё через
  `tied_to` и fp32-копии не имеет. `int8` пока отложен: экспорт завершается
  ошибкой с объяснением, а не молча пишет fp32;
- **компилятор** (`tools/vtm_compile.py`) при `embed: trit` читает таблицу из
  `ternary.trit` и эмитит `EMB` с тритовым `a`; tied `lm_head` остаётся `MM`
  с `A = emb.w` (тритовая матрица `[vocab, hidden]`), `B = [hidden, 1]`;
- **интерпретатор** (`src/vtm/interp.c`) расквантовывает триты на месте:
  `EMB` читает строку `token·dim …` через LUT243 (слово pack20 = 4 группы по
  5 тритов, группа 0..242 — пять тритов из таблицы), `w = trit · scale`;
  `MM` с тритовым `A` считает так же, без копии таблицы в fp32 (у Qwen это
  233 М элементов). `kind 1..3` в `MM`/`EMB` работают как раньше.

Если нужна скорость, а не симметрия с fp32-путём, tied lm_head можно считать
и `TMV` (`A = emb.w`, `rows = vocab`): TMV-ядро на тритах быстрее
поэлементного MM. Сейчас компилятор эмитит `MM` — так tied lm_head
проверяется на той же таблице, что `EMB`.

### Метаданные (meta)

После секции данных и перед программой может лежать **JSON-объект** с
гиперпараметрами модели. В заголовке это последние 12 байт, которые спека
называет резервом:

```
20  program_offset u32   абсолютное смещение программы в файле
24  meta_offset u32      абсолютное смещение JSON (0 = меты нет)
28  meta_len u32         длина JSON в байтах (без выравнивания)
```

Раскладка: `data_start + data_size = meta_offset`, JSON дополняется нулями до
32 байт, `program_offset = meta_offset + align32(meta_len)`, программа
по-прежнему последняя. C-загрузчик находит программу как
`file_size - n_instr*16`; `program_offset` он не читает, а `meta_offset` и
`meta_len` только уточняют границу данных. Контейнер без меты (нули в этих
словах) читается как раньше.

Читаются ключи, которые меняют исполнение:

| Ключ | Тип и кламп | Смысл | Без ключа |
|---|---|---|---|
| `rope_theta` | number; принимается `(0; 1e15]` | база RoPE (у Qwen2.5 — `1e6`) | `10000` |
| `rms_norm_eps` | number; первое вхождение в JSON | точный eps RMSN; приоритетнее `imm/1000` | `imm/1000` (совместимость со старыми контейнерами) |
| `rope_layout` | строка `"half"` \| `"interleaved"`; иное игнорируется | пары RoPE: `(i, i+d/2)` или `(2i, 2i+1)` | `"half"` |
| `context_window` | number; берётся `1..2^31-1`, усекается к int; иное (NaN, `<= 0`, строка, bool) — ключа нет | длина кольцевого KV-окна; больше длины кэша — окно равно кэшу | длина кэша (`ctx`) |
| `vocab_size` | целое `1..2^30` (синоним `vocab`) | размер словаря | неизвестен (`0`), брать из `dims` EMB |
| `tied_embeddings` | bool (синоним `tie_word_embeddings`); принимается и `0`/`1` | `lm_head` — та же таблица, что эмбеддинги | `false` |
| `temperature` | number; `< 0` и NaN → `0`, `> 1e6` → `1e6` | температура SAMP; `0` — жадно | `1.0` |
| `top_k` | число, усекается к int; `<= 0` → `0`, `> 1e9` → `1e9` | top-k для стратегии 2; `0` — не отсекать | `0` |
| `top_p` | number; NaN → `1.0`, `<= 0` → `0`, `>= 1` → `1` | top-p для стратегии 3; `1.0` — не отсекать | `1.0` |
| `repetition_penalty` | number; NaN и `<= 0` → `1.0`, `> 1e6` → `1e6` | штраф за повторы; `1.0` — выключен | `1.0` |
| `repetition_window` | число, усекается к int; `<= 0` → `0`, `> 256` → `256` | окно штрафа в токенах | `64` |
| `sample_seed` | число `0..2^53-1`, усекается к uint64 | зерно ГПСЧ SAMP | `0` |

Остальные ключи (`format`, `generator`, `n_layers`, `hidden_size`, `lm_head`,
`embed`, `quantize_embeddings`, `context_len`, `scale_block`, `model`,
`sampling`, `synthetic`, `expected`) как параметры не читаются: они
нужны инструментам и отладке. При этом обход идёт по всему JSON, поэтому
известный ключ, вложенный в `model` или в другой объект, всё равно будет
найден. Значения типов, отличных от ожидаемых, пропускаются так же, как битая
мета.

Опциональный блок целостности — `meta["integrity"]`:

```json
{"integrity": {"algo": "sha256",
               "data_sha256": "<64 hex>",
               "meta_sha256": "<64 hex>"}}
```

`data_sha256` — SHA-256 секции данных (`data_start .. meta_offset`);
`meta_sha256` — SHA-256 JSON-меты, в котором значение самого `meta_sha256`
заменено 64 символами `'0'`. Если блок есть, C-загрузчик проверяет оба хеша до
разбора тензоров и при расхождении возвращает `VTM_E_INTEGRITY`; неполная пара
полей — тоже ошибка. Поле `algo` C не анализирует: проверяются только сами
64-символьные hex-значения. Контейнер без блока читается как раньше, а
`VTM_SKIP_HASH=1` отключает сверку с предупреждением в stderr. По умолчанию
писатель хеш не пишет: его включает `write_vtm(..., integrity=True)` или
`VTM_WRITE_HASH=1`. Проверка с блоком — дополнительный проход по данным при
загрузке.

Ключи ищутся на любом уровне вложенности (компилятор дублирует конфигурацию в
`meta["model"]`), регистр учитывается; верхний уровень приоритетнее вложенного.
При `tied_embeddings` отдельного тензора
`lm_head` нет: программа ссылается на таблицу эмбеддингов как на матрицу
`[vocab, hidden]` — `MM` (A=E, B=h, так делает `tools/vtm_compile.py`) или
плотный `TMV` (при необходимости с флагом `VTM_FLAG_TMV_TRANSPOSED`, когда
таблица хранится как `[hidden, vocab]`).

Разбор **терпимый**: нет меты, битый или обрезанный JSON, неверный тип ключа,
смещения/длина мимо файла, мета больше 64 МиБ — это не ошибка загрузки (но
блок `integrity`, если он есть, проверяется и у большой меты).
Контейнер грузится, а незаданные параметры берутся из колонки «Без ключа»
(для ROPE это прежние `10000`/`half`). Python-эталон на битой мете падает с
`ValueError`; C намеренно мягче — битая мета не должна превращать контейнер в
кирпич. Прочитать мету из C можно через
`vtm_meta_present()` / `vtm_meta_rope_theta()` / `vtm_meta_rope_layout()` /
`vtm_meta_vocab_size()` / `vtm_meta_tied_embeddings()` / `vtm_meta_json()`.
Эффективные параметры сэмплинга (после клампа) отдаёт `vtm_sampling_params()`.

## Инструкция (16 байт)

```
0  opcode u8 | 1 flags u8 | 2 dst u16 | 4 a u16 | 6 b u16 | 8 c u16
10 padding u16 | 12 imm i32
```

- тензоры адресуются индексами в таблице, не указателями — программа
  переносима между машинами;
- `imm` — целое по смещению **12** (байты 10–11 — выравнивание, в каноне 0);
  интерпретация зависит от операции (позиция, число голов, эпсилон в
  тысячных, номер стратегии сэмплинга);
- `flags` локальны для опкода: `CAUSAL` `0x01` (SM, ATTN), `INPLACE` `0x02`
  (подсказка), `EMB_INPUT` `0x01` (EMB), `ROPE_INTERLEAVED` `0x02` (ROPE),
  `TMV_TRANSPOSED` `0x04` (TMV).

## Набор операций v0.2

| Код | Имя | Семантика |
|---|---|---|
| 0x01 | `TMV` | `y = W·x`; `W` — тритовая матрица (`trit · scale`) или плотная fp32/fp16/bf16. `TMV_TRANSPOSED` (только для плотной `W`) читает её как `[cols, rows]` и считает `Wᵀ·x` |
| 0x02 | `MM` | `Y = A·B`; `A` — тритовая или fp32/fp16/bf16, `B` и `Y` — fp32/fp16/bf16; все три — 2D, `dst` не совпадает с входами |
| 0x03 | `RMSN` | `y = x / rms(x) · w`; `imm` = eps×1000 (неотрицательный), но `meta["rms_norm_eps"]` приоритетнее |
| 0x04 | `ROPE` | поворот `x`; `b` — число голов (не индекс тензора), `imm` — смещение позиции; база и раскладка — из меты, флаг `0x02` перекрывает раскладку |
| 0x05 | `SM` | softmax по последней оси; `flags & CAUSAL`; `imm` — смещение causal-маски |
| 0x06 | `SILU` | `x · sigmoid(x)` поэлементно |
| 0x07 | `MUL` | `dst = a · b` поэлементно (буква `c` в старой записи — это `dst`) |
| 0x08 | `ADD` | `dst = a + b` поэлементно |
| 0x09 | `EMB` | `y = E[token]`, `a` — таблица `[vocab, dim]` kind 0..3; `imm` — token id; с флагом `EMB_INPUT` токен из `vtm_set_token()`, `imm` игнорируется |
| 0x0A | `KVW` | записать K (`a`) в K-кэш `dst`, V (`c`) в V-кэш `b` на глобальную позицию `m->position + imm`; слот — `pos % win` (кольцо) |
| 0x0B | `ATTN` | `out = softmax(Q·Kᵀ/√d)·V` с маской `flags`; `imm` — `q_start` только для 2D-кэша; видны последние `win` ключей |
| 0x0C | `SAMP` | выбрать токен из логитов; `imm` — стратегия 0..3; `dst` необязателен |
| 0x0D | `CPY` | копировать тензор |
| 0x0E | `SCAL` | `y = x · (imm/1000)` |
| 0x0F | `HALT` | останов |

Поля инструкций (тензорные индексы; `—` — поле не используется):

| Op | dst | a | b | c | imm |
|---|---|---|---|---|---|
| `TMV` | `y` | `W` | `x` | — | — |
| `MM` | `Y` | `A` | `B` | — | — |
| `RMSN` | `y` | `x` | `w` | — | eps×1000 (мета приоритетнее) |
| `ROPE` | `y` | `x` | heads | — | смещение позиции |
| `SM` | `y` | `x` | — | — | смещение causal |
| `SILU` | `y` | `x` | — | — | — |
| `MUL` | `y` | `a` | `b` | — | — |
| `ADD` | `y` | `a` | `b` | — | — |
| `EMB` | `y` | `E` | — | — | token id |
| `KVW` | K-кэш | K | V-кэш | V | смещение позиции |
| `ATTN` | `out` | `Q` | `K` | `V` | `q_start` (только 2D-кэш) |
| `SAMP` | token (опц.) | logits | — | — | стратегия 0..3 |
| `CPY` | `y` | `x` | — | — | — |
| `SCAL` | `y` | `x` | — | — | k×1000 |

Прямолинейный поток: переходов нет. Ветвление (генерация в цикле) делает
хост, вызывая `vtm_run()` на каждый токен — так проще отлаживать.

### Внимание (`KVW`/`ATTN`): кольцо, окно и блочный softmax

**Кольцевой KV-кэш.** `KVW` пишет K и V на глобальную позицию
`p = m->position + imm` в слот `p % win`, где
`win = min(ctx, meta["context_window"])`, а `ctx` — первая размерность
K/V-кэша. Кэш — кольцо: когда позиция доходит до `win`, самый старый слот
затирается. Поэтому **позиция `>= ctx` больше не ошибка** — диалог длиннее
кэша продолжается, теряя только старейшие ключи. Без ключа
`context_window` окно равно длине кэша, то есть прежнему поведению.

**Чтение окна.** `ATTN` с 2-D кэшем для запроса на глобальной позиции
`q = q_start + qi` читает только последние `win` ключей: диапазон
`[max(0, q - win + 1), q]` при `CAUSAL` (без маски — `[max(0, key_count - win),
key_count - 1]`). Слот глобальной позиции `j` — `j % win`; ключи
перебираются в хронологическом порядке. В 3-D-раскладке (K/V без кэша)
окна нет: видны все ключи `0..kv_len-1` с прежней causal-границей.

**Блочный softmax.** `ATTN` не материализует матрицу оценок: softmax
считается онлайн, блоками по 64 ключа (`ATTN_KEY_BLOCK`). Для каждой головы
и каждой строки запроса хранятся running max `m`, running sum `l` и
накопитель `acc[head_dim]` в `double`; при росте максимума `acc` и `l`
домножаются на `exp(m_old - m_new)`. Память — `O(head_dim + 64)`: ни матрицы
оценок на весь ключевой диапазон, ни буфера размером с `ctx` не выделяется.
`Q·Kᵀ` считается в `double` четырьмя независимыми аккумуляторами, `exp` на
ключ — один раз. Итог — `acc / l`.

**RoPE по глобальной позиции.** `ROPE` применяется к Q и K до `KVW` и
берёт `m->position + imm`, а не индекс слота кольца. Кольцо не меняет
значения векторов — только место хранения, поэтому поворот остаётся
корректным при любой длине диалога.

Python-эталон (`tools/vtm_ref.py`) повторяет и кольцо, и окно: `KVW` пишет
в `pos % win`, `ATTN` читает последние `win` слотов, `context_window`
разбирается из меты с теми же клампами. Паритет на 2×ctx токенах проверяет
`tests/test_vtm_sampling.py::TestKvWindowParity`: на скалярном бэкенде
логиты совпадают побитово (`max|Δ| = 0`), на `auto`/SIMD — на уровне
1e-6…1e-5 из-за иного порядка суммирования в NEON/AVX2.

### Сэмплинг (`SAMP`)

`imm` — номер стратегии:

| `imm` | Стратегия | Что делает |
|---|---|---|
| 0 | argmax | жадно: сравнение строго `>`, первый максимум; NaN не выигрывает у конечных значений, но NaN в позиции 0 оставляет токен 0 (как в v0.1) |
| 1 | temperature | `p = softmax(logits / temperature)`, выбор по `p` |
| 2 | top-k | температура, затем `top_k` старших логитов |
| 3 | top-p | температура, затем минимальное ядро с суммой `>= top_p` |

`imm` вне 0..3 — `VTM_E_UNSUPPORTED`. Старая конвенция Python-эталона
(`imm` = температура × 1000) больше не поддерживается: эталон приведён к
номерам стратегий, байткод с такими `imm` надо перекомпилировать.

Порядок обработки: **штраф за повторы → температура → top-k/top-p → одно
случайное число**. Штраф действует во всех стратегиях (и в argmax): каждый
токен, встретившийся среди последних `repetition_window` сгенерированных,
штрафуется один раз (как в CTRL) — логит `> 0` делится на
`repetition_penalty`, иначе умножается на неё. Повтор внутри окна не
усиливает штраф.

Детерминизм: в argmax `SAMP` переводится при условиях:

| `imm` | Условие перехода в argmax |
|---|---|
| 0 | всегда |
| 1 | `temperature <= 0` |
| 2 | `temperature <= 0` или `top_k == 1` |
| 3 | `temperature <= 0` или `top_p <= 0` |

Argmax не потребляет ГПСЧ, поэтому `temperature 0` и `top-k 1` побитово равны
argmax, а `top_p 1.0` ничего не отсекает (ядро — весь словарь).

ГПСЧ — **xorshift64\*** с засевом **splitmix64** (фиксировано для паритета с
`tools/vtm_ref.py`):

```
seed = meta["sample_seed"] (0 по умолчанию)
rng  = splitmix64(seed ^ 0x9E3779B97F4A7C15)
если rng == 0: rng = 0x2545F4914F6CDD1D
splitmix64(x): x += 0x9E3779B97F4A7C15
               x  = (x ^ (x >> 30)) * 0xBF58476D1CE4E5B9
               x  = (x ^ (x >> 27)) * 0x94D049BB133111EB
               return x ^ (x >> 31)
next(): x = rng; x ^= x << 13; x ^= x >> 7; x ^= x << 17; rng = x
        return x * 0x2545F4914F6CDD1D          # всё в арифметике mod 2^64
uniform = (next() >> 11) * 2^-53                # [0, 1)
```

Сэмпл без перехода в argmax и хотя бы с одним конечным логитом потребляет
ровно одно `next()`. Логиты переводятся в `double`, веса считаются как
`exp((logit - max) / temperature)` и накапливаются в том же порядке (по
убыванию логита, при равенстве — по возрастанию индекса), что и в
Python-эталоне. Благодаря этому при одном `seed` C и Python дают одну и ту же
последовательность токенов; проверка — `tests/test_vtm_sampling.py` (сверяет
вывод C-рантайма с `vtm_ref.execute`).

Состояние сэмплера (ГПСЧ и кольцо последних 256 токенов) живёт в машине,
поэтому `vtm_reset()` возвращает его в начало: повторный прогон с тем же
`seed` даёт ту же последовательность. Потокобезопасности у API нет (как и у
`vtm_last_error()`), одну машину нельзя использовать из двух потоков.

## Память

- `vtm_load()` на POSIX отображает файл `mmap(PROT_READ, MAP_PRIVATE)`:
  неизменяемые fp32-тензоры и слова тритов на x86/ARM64 читаются прямо из
  отображения (на строгих к выравниванию платформах TRT1 копируется).
  В арену копируется только то, что интерпретатор может писать (`dst`,
  V-кэш `KVW`), и fp16/bf16 (их нужно развернуть в fp32). `vtm_load_mem()`,
  `VTM_NO_MMAP=1` и Windows копируют все тензоры в арену.
- Арена — один `malloc`, начало и каждый тензор выровнены на 64 байта; живёт
  до `vtm_free()`, поштучно тензоры не освобождаются.
- KV-кэш — обычные fp32-тензоры в общей арене (компилятор создаёт их под
  каждый слой); отдельной арены и отдельного времени жизни у кэша нет.
- Буфер кандидатов `SAMP` (кандидаты, веса, метки окна, счётчики radix)
  выделяется один раз на машину и переиспользуется; освобождается в
  `vtm_free()`.
- `ATTN` выделяет на вызов один буфер `2·head_dim` чисел `double` (q-строка и
  накопитель выхода) и держит блок из 64 оценок на стеке; временного массива
  на `key_count`/`ctx` нет, память не зависит от длины контекста.

## Контракт бэкенда

```c
typedef struct vtm_backend {
    const char *name;
    int (*tmv)(float *y, const uint8_t *w, const float *scales,
               const float *x, int rows, int cols);
    int (*rmsnorm)(float *y, const float *x, const float *w, int n, float eps);
    int (*silu)(float *y, const float *x, int n);
    int (*mul)(float *y, const float *a, const float *b, int n);
    int (*add)(float *y, const float *a, const float *b, int n);
    int (*scal)(float *y, const float *x, float k, int n);
    int (*softmax)(float *y, const float *x, int rows, int cols,
                   int causal, int offset);
    int (*emb)(float *y, const float *e, int dim, int token);
    int (*copy)(float *y, const float *x, int n);
    int (*tmv_blocks)(float *y, const uint8_t *w, const float *scales,
                      const float *x, int rows, int cols, int scale_block);
} vtm_backend;
```

Любое поле `NULL` — интерпретатор берёт скалярную реализацию. `tmv_blocks`
получает явный блок масштаба (128/160); старый `tmv` умеет только 160, для 128
интерпретатор откатывается на скалярный LUT. Полей для MM/ATTN/ROPE/KVW в
структуре нет: ROPE/ATTN/KVW остаются скалярными, а SIMD-ядра MM
(`vtm_simd_mm_trit`/`vtm_simd_mm_f32` из `src/vtm/vtm_backend.h`) `op_mm()`
вызывает напрямую, когда выбран бэкенд с именем `simd*` и CPU его умеет.
Выбор бэкенда: `VTM_BACKEND=auto|simd|scalar|lut|direct` (по умолчанию
`scalar-lut243`) или `vtm run --backend ...`. Так SIMD подключается без
изменения байткода; подробности и числа — в `docs/vtm-perf.md`.

## CLI

```
vtm run model.vtm --tokens 1,2,3 --max-new 8 [--backend ...]
vtm run model.vtm --text "вопрос" [--tokenizer tokenizer.json] [--max-new 8] [--backend ...]
vtm run model.vtm --text "вопрос" --chat [--system "..."]
vtm run model.vtm --text "вопрос" --stream [--max-new 8]
vtm inspect model.vtm
vtm bench [--rows N --cols N --iters N] [--scale-block 128|160]
vtm --help
```

`--backend auto|simd|scalar|lut|direct` перекрывает `VTM_BACKEND`; без обоих
работает `scalar-lut243` (поведение по умолчанию не меняется).

Дополнительные опции `vtm run`: `--stop "текст"` (только с `--text`:
остановиться, когда декодированный текст кончается на строку; можно
повторять; в строке понимаются `\n`, `\t`, `\r`, `\\`), `--timeout SEC`
(прервать генерацию, код 124), `--stats` (токены/время/ток-в-секунду в
stderr) и `--max-tokens N` (синоним `--max-new`).

`--text` кодирует промпт BPE-токенизатором (`tokenizer.json` формата
HuggingFace), прогоняет модель по одному токену и декодирует вывод обратно в
UTF-8. Без `--tokenizer` путь ищется так: `$VTM_TOKENIZER` (если файл
существует), затем `tests/vtm/fixtures/tokenizer.json` при подъёме от
текущего каталога вверх, затем `./tokenizer.json`. Явный `--tokenizer`
открывается как указан (относительно текущего каталога).

`--stream` (только вместе с `--text`) печатает ответ по мере генерации: после
каждого токена готовый текст сразу пишется в stdout и сбрасывается
(`fflush`), без ожидания конца строки. В stdout в этом режиме попадает
**только текст ответа** (его читают голос и SSE), а служебные строки —
`модель:`, `prompt:`, `вывод:`, `время:`, `стоп-токен:` / `стоп: --stop` — идут
в stderr. Без `--stream` вывод прежний: всё в stdout, текст ответа — в строке
`ответ:`.

Декодер накапливает байты между токенами: BPE-токен может содержать половину
UTF-8 символа (у кириллицы 2 байта, и они легко расходятся по двум токенам).
Наружу отдаются только завершённые символы, недописанный хвост (до 3 байт)
ждёт следующий токен. В конце генерации хвост тоже не теряется: если символ
так и не дописался, вместо сырых байт печатается U+FFFD, поэтому stdout
всегда остаётся валидным UTF-8.

В `--stream` спецтокены (`<|im_end|>`, `<|im_start|>`, `<|im|>` и прочие
`added_tokens` с `special == true`) в текст не попадают, а стоп-токены
обрывают генерацию. Стоп-токены берутся из того же `tokenizer.json`: это
`model.eos_token` и special added_tokens с типовым маркером конца (`im_end`,
`endoftext`, `end_of_text`, `eot_id`, `eos`); в коде их id не захардкожены.
При срабатывании в stderr появляется `стоп-токен: <id>`.

Без `--stream` используется полный декодер `vtm_tok_decode`: он отдаёт все
сгенерированные id до `--max-new` и не фильтрует special/stop-токены.
Остановка по тексту в этом режиме — через `--stop` (или по `--timeout`).

`--chat` оборачивает текст в чат-шаблон Qwen2.5:

```
<|im_start|>system
{system}<|im_end|>
<|im_start|>user
{text}<|im_end|>
<|im_start|>assistant
```

Ход `system` появляется только при `--system "..."` — так же ведёт себя
официальный шаблон Qwen, если системного сообщения нет. Токены
`<|im_start|>`/`<|im_end|>` и их id берутся из `added_tokens`
(`special == true`) того же `tokenizer.json`, в коде их нет: словарь с
другими id даёт другие id в промпте, словарь без этих токенов — ошибку с
кодом 2. Без `--chat` поведение прежнее: в токенизатор уходит ровно текст
из `--text`, символ в символ.

## C-API для хоста

Для сервера и любого не-CLI хоста есть тонкий слой `src/vtm/api.h`
(публичный заголовок — C99; реализация `api.c` использует C11
`<stdatomic.h>`): `vtm_api_open` / `vtm_api_generate` / `vtm_api_cancel` /
`vtm_api_close` / `vtm_api_last_error`.

- `vtm_api_options`: `struct_size`, `backend_name` (или готовый `backend`),
  `max_new_tokens` (0 — без лимита), `eos_token_id` (`< 0` — не задан).
  Неизвестные поля при большем `struct_size` игнорируются; ненулевые
  `flags`/`reserved` — ошибка.
- `vtm_api_generate()` на каждом вызове делает `vtm_reset()` (позиция,
  счётчик, состояние SAMP), но переиспользует тензоры и KV-кэш: позиции,
  которые читает ATTN, перезаписываются новым промптом. Промпт — `int32_t`
  id, без токенизатора; текст декодирует хост.
- Колбэк получает по одному токену; возврат `!= 0` — `VTM_API_STOPPED`.
  Коды `VTM_API_OK` (лимит/конец программы), `VTM_API_EOS` (выбран
  `eos_token_id`, токен уже отдан колбэку) и `VTM_API_CANCELLED` — штатные
  остановки, а не ошибки.
- `vtm_api_cancel()` — атомарный флаг, безопасен из любого потока; отмена
  проверяется между токенами, а не внутри `vtm_run()`. Своих потоков API не
  создаёт; `vtm_api_generate()` — один поток на контекст, второй параллельный
  вызов вернёт `VTM_E_ARG`. `vtm_api_close()` нельзя звать параллельно с
  работающим `generate()`.

## Что этот путь стоит

Свой рантайм — это **месяцы**, а не дни: полная модель требует RoPE, GQA,
KV-кэш, BPE-токенизатор и отладку численных расхождений. bitnet.cpp уже умеет
это, но не даёт контроля. Мы платим временем за независимость — сознательно.

Первые два этапа дают проверяемый результат за недели, а не месяцы: если
синтетический слой совпал с эталоном, архитектура верна, и дальше это работа,
а не исследование.

## Что не реализовано

Ниже — не «в планах», а честный список того, чего в текущем коде нет.

- **Многопоточность.** Все ядра однопоточные: нет `pthread`/OpenMP, нет
  разбиения TMV/MM/ATTN по строкам или головам. Базовый `vtm_t` не
  потокобезопасен (в том числе ленивая инициализация LUT243), одну машину
  нельзя использовать из двух потоков. В C-API (`api.h`) есть только
  `vtm_api_cancel()` — атомарный флаг, безопасный из другого потока;
  `vtm_api_generate()` остаётся «один поток на контекст» и своих потоков не
  создаёт.
- **Кэш промпта.** В ядре есть кэш префикса (`vtm_cache_prefix` / `vtm_run_cached`),
  в C-API — опция `cache_prefix` (0081, 0087); в Python-бэкенде `eva` она пока не
  включается (0096). Снимков KV между процессами нет: каждый
  `vtm run` (и каждый `vtm_api_generate()`) заново прогоняет весь промпт;
  токенизация — забота хоста. Внутри одного запуска KV-кэш живёт в тензорах и
  переиспользуется между `vtm_run()`, но наружу его не отдают и не
  восстанавливают.
- **Внимание.** `ATTN` уже блочный: онлайн-softmax блоками по 64 ключа,
  память `O(head_dim + 64)`, кольцевое окно `context_window` и законные
  позиции `>= ctx`. Не реализованы SIMD-ядра ATTN, многопоточность и
  prefill-батчи (`q_len > 1` — один запрос, а не батч).
- **Батчинг.** Одна последовательность на машину: batch-размерности нет,
  несколько промптов параллельно не обслуживаются. `q_len > 1` — это один
  запрос, а не батч.
- **Сессии KV.** Нет API «сохранить/восстановить/форкнуть» состояние KV, нет
  вытеснения и привязки сессии к запросу; кэш — обычные тензоры, живущие до
  `vtm_free()`, а `vtm_reset()` их не обнуляет.
- **Windows.** Не поддерживается: под `_WIN32` сборка останавливается одним
  `#error` со списком того, что нужно портировать (mmap/fsync каталога/pthread/
  POSIX-таймеры). Прежнего `fread`-пути больше нет. MSVC/gcc под Windows не
  проверялись; AVX2-ядра проверены только под Rosetta 2, ARMv7 и 32-битный NEON
  не поддерживаются. Порядок портирования — раздел «Портируемость».

Кроме этого, не реализованы: `int8`-эмбеддинги (`kind 4` зарезервирован),
загрузчик модели в C (`.vtm` собирает `tools/vtm_compile.py`), per-call
параметры сэмплинга (только из меты при загрузке), beam search, проверка
перекрытия тензоров, SIMD для остальных операций
(ROPE/ATTN/SM/SILU/ADD/MUL/SCAL/EMB/CPY остаются скалярными). Блок
`integrity` реализован, но по умолчанию не пишется. Загрузчик доверяет
пределам `n_elements ≤ 2^30` и размеру файла ≤ 4 ГиБ — это защита от абсурда,
а не от злонамеренного OOM.

## Паритет и бэкенды

Побитовый паритет с Python-эталоном даёт **только скалярный бэкенд** (`max|Δ| = 0`
на 50 случайных конфигурациях). SIMD-ядра переупорядочивают суммирование, поэтому
расходятся на 1e-5…1e-4 (медиана 6,1e-06, p95 2,6e-05, максимум 1,05e-04). При этом
**argmax не меняется** (0 смен из 50): минимальный отрыв top-1 от top-2 в наборе —
8,7e-03, то есть в 41 раз больше худшего расхождения.

Практические правила:
- `parity_random` и `parity_real` гоняют C со `VTM_BACKEND=scalar` (переопределяется
  `VTM_PARITY_BACKEND`), иначе порог 1e-5 бессмысленен;
- замер расхождения бэкендов — `tools/parity_simd.py` (числа, смены argmax, запас
  отрыва); вердикт и подробности — `docs/quantization.md`.

## Портируемость

ВТМ собрана и проверена на little-endian POSIX-хостах: macOS/ARM64 (Apple M1)
и x86-64 (Rosetta 2). Всё остальное — не «работает, но медленно», а осознанно
не поддерживается, и отказ **явный**: big-endian получает
`VTM_E_UNSUPPORTED` при загрузке, Windows — `#error` при компиляции.
Молчаливого чтения мусора нет ни там, ни там.

### Что уже сделано

- **Big-endian.** Контейнер little-endian: `u32`/`f32` лежат в файле как есть,
  и загрузчик читает их без свопинга (`rd32`/`rd_f32` в `src/vtm/loader.c`).
  В mmap-режиме он идёт дальше и отдаёт наружу `float*`/`uint32_t*` прямо в
  отображение (слова тритов, fp32-масштабы, неизменяемые fp32-тензоры) —
  свопинг в функциях чтения этого не спас бы, пришлось бы копировать всё в
  арену и потерять главный выигрыш mmap. Поэтому проверка одна и на входе:
  `VTM_HOST_BIG_ENDIAN` (`src/vtm/vtm.h`) — константа времени компиляции,
  `load_core()` смотрит её **один раз, до разбора контейнера** (не в цикле),
  и возвращает `VTM_E_UNSUPPORTED` с текстом «big-endian хост не
  поддерживается …». В little-endian сборке эту ветвь выбрасывает компилятор,
  в циклах чтения проверок нет вовсе. Эмуляция BE-хоста без BE-железа:
  `-DVTM_HOST_BIG_ENDIAN=1`; в такой сборке `tests/vtm/test_vtm.c` проверяет
  только сам отказ (остальные тесты смысла не имеют — ни один контейнер не
  должен загрузиться). SHA-256 (`src/vtm/sha256.c`) побайтовый и от порядка
  байт не зависит; аппаратное ARMv8-ядро — только LE-AArch64, но на BE оно не
  исполняется, потому что загрузка обрывается раньше. Отдельный случай —
  снимки сессий KV (`kv_store.c`): заголовок у них little-endian, а K/V лежат
  сырыми host-endian f32, то есть снимок и сейчас не переносится между хостами
  с разным порядком байт; при полной BE-поддержке это придётся либо свопить,
  либо явно объявить снимок «для того же хоста».
- **Windows.** `src/vtm/vtm.h` даёт один `#error` со списком того, что нужно
  портировать, — вместо десятков ошибок «нет `sys/mman.h`». Прежний путь
  «под `_WIN32` прочитать файл целиком через `fread`» больше не собирается:
  это и есть честный отказ — сборки под Windows не «сломана», её нет.

### Что не портировано и в каком порядке делать

| # | Что | Где | Почему нельзя «как есть» | Что нужно |
|---|---|---|---|---|
| 1 | Порядок байт | `loader.c` (`rd*`, `fill_tensor_planned`, `plan_tensor`), `kv_store.c` (снимки) | файл LE, хост BE; mmap отдаёт `float*`/`uint32_t*` в отображение; K/V в снимке — host-endian | уже есть отказ; полная поддержка = на BE всегда `can_reference = 0` (копия в арену) + свопинг при загрузке, свопинг снимков сессий, плюс тесты на BE-железе |
| 2 | `mmap`/`munmap`/`madvise` | `loader.c` | POSIX API | `CreateFileMapping`/`MapViewOfFile`; без них — `fread` целиком (память), `madvise(MADV_DONTNEED)` не нужен |
| 3 | `fsync` каталога + `rename` | `kv_store.c` (контракт — `api.h`, ADR 0008) | POSIX-гарантия «temp → fsync → rename → fsync каталога» | `FlushFileBuffers` + `ReplaceFile`/`MoveFileEx(MOVEFILE_WRITE_THROUGH)`; проверить, что снимок сессии переживает падение |
| 4 | Пул потоков на pthread | `backend_scalar.c` | `pthread_*`, `pthread_once`, `clock_gettime` | Win32 threads или `std::thread`; `VTM_NO_THREADS` уже есть как аварийный выключатель |
| 5 | POSIX-таймеры и сигналы | `main.c` (`--timeout`) | `clock_gettime`, `sigaction`/`alarm` | `QueryPerformanceCounter` + `SetConsoleCtrlHandler` |
| 6 | Сборка и CI | весь `src/vtm` | `-std=c99 -Wall -Wextra -Werror`, `__attribute__`, `ssize_t`, NEON/AVX2 intrinsics, VLA | MSVC/clang-cl или mingw, отдельный набор флагов; AVX2 — `_M_IX86`/`_M_X64` и MSVC-intrinsics; `unistd.h`/`sys/stat.h`/`sys/mman.h` → `<io.h>`/`_stat64` |

Порядок: 1 — порядок байт (отказ уже есть, дальше полная поддержка через
копию в арену), 2–3 — файлы и сохранность (mmap и атомарная запись), 4 —
потоки, 5 — таймеры, 6 — сборка/CI. Каждый шаг закрывается тестом на той
платформе, а не обещанием: BE — эмуляцией макроса и затем железом, Windows —
хотя бы компиляцией в CI (mingw).

### Чем это проверяется

```sh
cd src/vtm && make test                      # LE: полный набор
python3 -m unittest discover -s tests        # Python-эталон и инструменты

# big-endian: эмуляция хоста, BE-железо не нужно
make clean && make CPPFLAGS="-D_POSIX_C_SOURCE=200809L -DVTM_HOST_BIG_ENDIAN=1" test_vtm
./test_vtm     # big-endian: загрузчик отказал (VTM_E_UNSUPPORTED)

# Windows: ровно один #error на единицу трансляции, а не каскад
cc -D_WIN32 -I. -c loader.c
```

UBSan на текущей платформе (`-fsanitize=undefined`) указывает на
misaligned-загрузки `words[wi]`/`scales[...]` в `src/vtm/backend_neon.c`: это
цена оптимизации «TRT1 читается прямо из mmap» — слова и масштабы идут по
смещению 2 mod 4. Сборка с `-DVTM_UNALIGNED_LOADS=0` (TRT1 копируется в арену)
UBSan-чистая, но теряет mmap-резидентность тензоров: это выбор между памятью и
формальной чистотой, и решать его нужно в ядрах (загрузка слова через
`memcpy`), а не в загрузчике — отдельная задача.
