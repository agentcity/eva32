# VTM — виртуальная троичная машина (v0.2/v0.3)

> Актуально на 2026-11-26.

Своя машина вместо bitnet.cpp: мы контролируем формат, ядра и поведение, и можем
заменить бэкенд, не переписывая модель.

## Зачем своя

bitnet.cpp — форк llama.cpp: он диктует формат весов (i2_s/tl1), прячет ядра в
своих LUT-таблицах и тянет весь llama.cpp как зависимость. Нам нужно:

1. **Формат наш** — `.trit` с 20 тритами в 32-битном слове (`docs/trit-format.md`),
   который уже умеет `qat/export.py` и `tools/trit_codec.py`.
2. **Поведение наше** — модель исполняется детерминированно, без скрытых эвристик.
3. **Бэкенд отделён от байткода** — сегодня скалярный C и SIMD (NEON/AVX2), в
   будущем троичное железо. Модель при этом не перекомпилируется.

## Три слоя

```
модель (.trit + manifest)  →  компилятор (Python)  →  программа (.vtm)
                                                          ↓
                                          интерпретатор (C) → бэкенд (ядро)
```

- **Компилятор** (`tools/vtm_compile.py`) — граф модели → байткод. Без него
  интерпретатор не знает, какие слои в каком порядке.
- **Интерпретатор** (`src/vtm/`) — читает `.vtm`, исполняет инструкции по одной.
- **Бэкенд** — набор ядер: скалярный C (`scalar-lut243`/`scalar-direct`) и SIMD
  (NEON на ARM64, AVX2 на x86-64); см. `docs/vtm-perf.md`. В будущем — троичное
  железо.

## Контейнер `.vtm`

Текущих версий две. **v0.2** (ADR 0011) — размерности `u32 × 4`, запись
тензора 52 байта, смещения `u32`; заголовок 32 байта, порядок секций прежний.
**v0.3** (ADR 0019, задача 0173) — `offset` и `scale_offset` в записи тензора
стали `u64` (запись 60 байт), поэтому контейнер может быть больше 4 ГиБ.
`dims` остались `u32 × 4`: произведение всё равно ограничено `2^30`
элементами. Файлы v0.1 (`version=1`, запись 44 байта) не читаются: загрузчик
отвергает их с ошибкой «формат v0.1 не поддерживается» — ценных артефактов
v0.1 нет, синтетика пересобирается за секунды.

Писатель (`tools/vtm_ref.py`) по умолчанию работает в режиме `auto`: пишет
v0.2, пока файл меньше 4 ГиБ, и переключается на v0.3, только когда иначе не
влезает. Выбор v0.3 печатается в stderr; явные `container_version=2|3` (CLI —
`--container-version 2|3`) принудительны. Старый бинарь на v0.3 обязан
отказать по версии, а не прочитать таблицу 52-байтными записями.

```
┌─ заголовок (32 байта) ──────────────────────────────────┐
│ "VTM1" | версия u16 = 2 | флаги u16 | n_instr u32        │
│ n_tensors u32 | n_program u32 | program_offset u32       │
│ meta_offset u32 | meta_len u32                           │
├─ таблица тензоров (v0.2: n×52 Б | v0.3: n×60 Б) ─────────┤
│ имя[24] | kind u8 | ndim u8 | dims u32×4                  │
│ v0.2: offset u32 | scale_offset u32 | резерв u16         │
│ v0.3: offset u64 | scale_offset u64 | flags u16          │
├─ данные тензоров (выровнены на 32 байта) ────────────────┤
├─ метаданные JSON (опционально, дополнены нулями до 32) ──┤
├─ программа (n_instr × 16 байт, последняя секция) ────────┤
└──────────────────────────────────────────────────────────┘
```

Смещения в записи тензора: `name` 0, `kind` 24, `ndim` 25, `dims` 26–41.
В v0.2: `offset` u32 42, `scale_offset` u32 46, `flags` 50–51 (бывший резерв).
В v0.3: `offset` u64 42–49, `scale_offset` u64 50–57, `flags` u16 58–59.
`offset` — смещение от начала секции данных; `offset` и `scale_offset` (если
используется) кратны 32. Маркер «смещения нет» в обеих версиях —
`0xFFFFFFFF`: настоящий адрес кратен 32, поэтому маркер не может совпасть
с адресом даже в u64-поле.
`dims` — до 4 измерений по `u32`: поле вмещает до 4 294 967 295, но загрузчик
ограничивает произведение `2^30` элементами и запрещает нулевые измерения;
недостающие измерения — нули.

`kind`: `0` — триты, `1` — fp32, `2` — fp16, `3` — bf16, `4` — int8 с
масштабами по блоку 128 (задача 0044), `5` — Q4 с масштабами на группу 32
(задача 0151).

`kind 4` — самодостаточный сегмент по `offset`: `"INT8"`, version `1`,
flags u8 (бит 0 — масштабы fp32, иначе fp16), `n_values u64`,
`n_scale u32`, затем `n_scale` масштабов и `n_values` знаковых байт `q`.
`w = q · scale`, `q ∈ −127..127` (симметрично, zero-point 0), масштаб — на
каждые 128 элементов, `n_scale = ceil(n_values/128)`; `n_values` обязан
совпадать с произведением `dims`. `-128` запрещён (ошибка `VTM_E_SCALE`):
диапазон намеренно симметричный, как у QAT. `scale_offset` у kind 4 —
`0xFFFFFFFF` (масштабы внутри сегмента). С 0170 таблица в памяти остаётся
**упакованной**: байты `q` читаются из отображения файла, в арене лежат
только fp32-масштабы (`n_scale·4` байт), `EMB` разворачивает одну строку,
а `MM`/`TMV` по такой матрице считают GEMV ядрами `vtm_i8_*` (см. «Эмбеддинги
в int8»). Прежнее поведение (fp32-развёртка в арене, тензор приходит как
`kind 1`, признак источника — `VTM_TENSOR_FLAG_INT8_SOURCE`) возвращает
`VTM_I8_EMB=0`. Побайтово формат описан в
`tools/vtm_ref.py` (`encode_int8_segment`/`decode_int8_segment`).

Флаги заголовка: бит 0 (`0x0001`) — raw-триты хранят масштабы fp32 (иначе
fp16); бит 15 (`0x8000`, расширение C) — неоднозначное число масштабов
считать блоком 160. `n_program` — размер программы в байтах; загрузчик
принимает 0 (не проверять) или `n_instr·16`.

Поле `flags` записи тензора (смещение 50, бывший резерв): бит 0
(`VTM_TENSOR_FLAG_KV_CACHE`) — K/V-кэш без payload'а; биты 1..2 — хранение
тритов (`0` — `packed20`, `1` — `native`; только для kind 0); бит 3
(`VTM_TENSOR_FLAG_STATE`, `0x0008`) — состояние рекуррентного слоя
`CONV4`/`GDELTA` (payload'а нет, буфер создаёт загрузчик, `vtm_reset()`
обнуляет). STATE осмыслен только у fp-тензоров: у kind 0 биты 1..2 заняты
хранением тритов. Остальные биты резервированы и при чтении игнорируются,
поэтому старые контейнеры (там 0) читаются прежним путём.

### Заголовок v0.3

Заголовок остаётся 32 байта, но «резерв» (байты 20–31) читается иначе:

```
20  meta_offset u64    абсолютное смещение JSON (0 = меты нет)
28  meta_len u32       длина JSON (без выравнивания)
```

`program_offset` в v0.3 не хранится: программа, как и раньше, последняя, и
загрузчик берёт её как `file_size - n_instr*16`. Это и даёт мете и данным
уходить за 4 ГиБ без расширения заголовка. В v0.2 на этих местах лежат
`program_offset u32 | meta_offset u32 | meta_len u32` (20/24/28), и старые
файлы читаются прежним путём — версия в заголовке решает, какая раскладка.

Загрузчик C принимает обе версии: для v0.2 файл обязан быть меньше 4 ГиБ
(иначе `VTM_E_BOUNDS` с текстом про u64-смещения), для v0.3 — до 1 ТиБ.
Общий предел — `VTM_MAX_FILE_BYTES` (`src/vtm/vtm.h`).

### Раскладки тритов

Тритовая матрица (`kind 0`) хранится одним из двух способов:

- **TRT1-сегмент** (`scale_offset == 0xFFFFFFFF`): по `offset` лежит
  `"TRT1"`, version u8 (1 — `packed20`, 2 — хранение в битах 1..2 `flags`),
  flags u8 (бит 0 — масштабы fp32), `n_trits u64`, `n_scale u32`, затем
  `n_scale` масштабов, затем слова (`packed20`: `ceil(n_trits/160)·8`; `native`:
  `ceil(n_trits/4)`). `n_trits` обязан совпадать с произведением `dims`.
- **raw** (`scale_offset != 0xFFFFFFFF`): по `offset` — слова pack20, по
  `scale_offset` — масштабы; ширина масштаба берётся из флага заголовка.
  Raw-раскладка использует блок 160 — это расширение C, Python-эталон её не
  пишет.

### Хранение тритов: `packed20` и `native`

Упаковка — сменный слой (задача 0057), интерпретатор о ней не знает.
Хранений два (идентификатор — в TRT1 version 2, биты 1..2 `flags`, и
дубликат в битах 1..2 `flags` записи тензора):

| id | имя | как лежит | байт на `n` тритов |
|---|---|---|---|
| 0 | `packed20` (по умолчанию) | 20 тритов в `u32`, цифры 0/1/2 | `ceil(n/160)·32` |
| 1 | `native` | 1 знаковый байт на трит (`-1/0/+1`) | `ceil(n/4)·4` |

Контейнеры до 0057 — это TRT1 version 1, то есть всегда `packed20`; они
читаются байт-в-байт как раньше. `native` пишется TRT1 version 2, и старый
загрузчик отвергает его с `VTM_E_VERSION`, а не читает байты как слова
`pack20` (иначе веса были бы правдоподобными, но чужими). Новый загрузчик
разбирает оба хранения через контракт `vtm_trit_store` (`src/vtm/trit.h`:
`fetch`, `count`, `scale_of`) и переупаковывает `native` в `pack20` в арене,
поэтому `interp.c`/`backend_*.c` не меняются. Прямое чтение `native` ядрами
(без нормализации) — отдельная задача: она трогает горячий цикл.

Цена `native`: ровно **в 5 раз** больше байтов на массив тритов (32 → 160
байт на 160 тритов); для таблицы 1.5B-модели (233 373 696 тритов) —
46 674 752 против 233 373 696 байт. Поэтому по умолчанию всегда `packed20`;
`native` — для троичной памяти и отладки. 2-битной упаковки нет: 2 бита на
трит хуже плотности `packed20` (1,60 бита).

Совместимость по поведению: одинаковый массив в обоих хранениях даёт
побитово одинаковые логиты (C↔Python-паритет — 0,0 на тесте `EMB`), потому
что нормализация происходит до исполнения.

Размер блока масштаба: `docs/trit-format.md` фиксирует 160 тритов на масштаб,
а Python-эталон (`tools/vtm_ref.py`) — 128 (блок QAT); упаковочный блок при
этом всё равно 160 = 8 слов. C читает оба варианта: по `n_scale` определяет
128 или 160; если для маленького тензора числа совпали — берёт 128 (канон
Python), а флаг `0x8000` принудительно выбирает 160. Подробнее — в
`src/vtm/README.md`.

> Нетернарные веса (`kind` 1–3) — это место для эмбеддингов, norm-весов и
> `lm_head`: загрузчик приводит fp16/bf16 к fp32 в арене, интерпретатор читает
> их как обычные `float`. Тритовый контейнер и плотный могут сосуществовать в
> одном файле. Тритовой (`kind 0`) может быть **любая** матрица, включая
> таблицу словаря — см. «Эмбеддинги в тритах».

### Эмбеддинги в тритах

`quant.quantize_embeddings: trit` у QAT-эксперимента (0027) доводится до
рантайма целиком (0043):

- **экспорт** (`qat/export.py`) квантует таблицу словаря тем же правилом, что
  и Linear-веса (`scale = absmax(блок 128)`,
  `trit = clamp(round_half_away(w/scale), -1, 1)`), и пишет её сегментом
  `model.embed_tokens.weight` в `ternary.trit`; в `non_ternary.bin` её нет. В
  манифесте: `architecture.embed = "trit"`, запись тензора с `kind: trit`,
  `role: embed`, раздел `embeddings: {mode, storage, bytes}`. При
  `tie_word_embeddings` запись `lm_head.weight` ссылается на неё через
  `tied_to` и fp32-копии не имеет. `int8` пока отложен: экспорт завершается
  ошибкой с объяснением, а не молча пишет fp32;
- **компилятор** (`tools/vtm_compile.py`) при `embed: trit` читает таблицу из
  `ternary.trit` и эмитит `EMB` с тритовым `a`; tied `lm_head` остаётся `MM`
  с `A = emb.w` (тритовая матрица `[vocab, hidden]`), `B = [hidden, 1]`;
- **интерпретатор** (`src/vtm/interp.c`) расквантовывает триты на месте:
  `EMB` читает строку `token·dim …` через LUT243 (слово pack20 = 4 группы по
  5 тритов, группа 0..242 — пять тритов из таблицы), `w = trit · scale`;
  `MM` с тритовым `A` считает так же, без копии таблицы в fp32 (у Qwen это
  233 М элементов). `kind 1..3` в `MM`/`EMB` работают как раньше.

### Эмбеддинги в int8 (kind 4, задачи 0044 и 0170)

«План Б», если триты теряют качество: таблица словаря — int8 + масштабы.
Контейнер, Python-эталон и интерпретатор этот путь умеют; с 0170 таблица
**не разворачивается в fp32** ни при загрузке, ни при счёте логитов:

- **контейнер** (`tools/vtm_ref.py`) пишет таблицу INT8-сегментом kind 4
  (`w = q · scale`, `q ∈ −127..127`, масштаб на блок 128, `f32`/`f16` по
  флагу сегмента). `EMB` в Python читает `dense()` = `q · scale`;
- **загрузчик** (`src/vtm/loader.c`) проверяет сегмент (magic/версию/
  `n_values`/`n_scale`/границы/`q ≠ −128`/масштабы конечны и неотрицательны)
  и оставляет матрицу упакованной: `t->i8` — байты `q` (в mmap — прямо в
  отображение), `t->scales` — fp32-масштабы в арене (`n_scale·4` байт;
  fp16-масштабы конвертируются один раз при загрузке). `VTM_I8_EMB=0`
  возвращает прежний путь: fp32-развёртка в арене, `kind` в памяти — `1`,
  флаг `VTM_TENSOR_FLAG_INT8_SOURCE`;
- **интерпретатор** (`src/vtm/interp.c`): `EMB` разворачивает одну строку
  (`vtm_i8_dequant_row`, точно: `q·scale`), `TMV`/`MM` по int8-матрице идут
  GEMV без fp32-копии (`vtm_i8_gemv`, `n == 1`; общий `n` — эталон
  `vtm_i8_mm`). Tied `lm_head` — это `MM` по той же таблице: 151 936×2048
  int8 = 0,31 ГБ на токен вместо 1,24 ГБ fp32;
- **компилятор** (`tools/vtm_compile.py`) принимает `embed: int8`,
  `ModelConfig(embed_quant="int8")` и собирает `EMB`/`MM` по int8-таблице
  (`--embed int8` у `tools/gguf_import.py` — умолчание для `--format q4`).

Скорость (задача 0170, 3B Q4_K, [151936, 2048]): ядро GEMV по упакованной
таблице — **5,4 мс** (0,31 ГБ, ~58 ГБ/с) против 36,6 мс у f32-таблицы
(1,24 ГБ при 34 ГБ/с — полоса памяти, потолок ~27 ток/с). Точность: веса
int8 представимы в int8 точно, квантуются только активации — по под-блокам
32 значения (сетка масштабов таблицы кратна), плоскости int8 — `VTM_Q4_I8`,
как у декода kind 6/7 (задача 0169); `VTM_Q4_I8=0` считает активации точно
в f32 (ядро медленнее, ~40 мс, но точнее по активациям).

Цена памяти: в арене — `n_scale·4` байт вместо `4·n` (для таблицы 1.5B это
1,1 МиБ против 890 МиБ). Размер файла честно между тритами и fp16: для
`128×128` — 3826 Б (trit) < 16 914 Б (int8) < 32 768 Б (fp16); для таблицы
1.5B (233 373 696 элементов) — 53 967 698 / 240 666 642 / 466 747 392 Б
(`int8/trit = 4,46`, `int8/fp16 = 0,516`). Экспорт из QAT
(`qat/export.py`) по-прежнему отказывает `quantize_embeddings: int8`
с объяснением — это отдельная задача.

### Q4 (kind 5, задача 0151)

Четвёртый числовой вид — 4-битные веса с масштабом на **группу 32**: то, что
нужно, чтобы «7B Q4» из GGUF влезал в контейнер без fp32-материализации.

**Сегмент** (по образцу INT8/TRT1, `scale_offset = 0xFFFFFFFF`):

```
magic "Q4_0" | "Q4_1" (4 байта) | version u8 (=1)
      | flags u8 (бит 0: 1 = fp32-масштабы, 0 = fp16)
      | n_values u64 | n_groups u32
[Q4_1] | n_mins u32            — явное число min, обязано быть n_groups
масштабы: n_groups * (4 или 2) байта
[Q4_1] min: n_mins * (4 или 2) байта
q:     n_groups * 16 байт
```

`n_groups = ceil(n_values/32)`, `n_values` обязан совпадать с произведением
`dims`. Группа — **32 значения в 16 байтах**, раскладка как в GGML Q4_0 (её
ждут ядра 0152 и импорт GGUF 0153): **байт `j` группы хранит значение `j`
в младшем ниббле и значение `j+16` в старшем**. Нибблы — 0..15.

- **Q4_0** (симметричный): `w = (nibble − 8) · scale`; ниббл 8 — ноль.
- **Q4_1** (асимметричный): `w = nibble · scale + min`, `min` — fp32 (или
  fp16 по флагу) на группу. Число min вынесено в `n_mins`, чтобы отсутствие
  массива min в обрезанном сегменте не приняли за выравнивающий padding:
  `n_mins != n_groups` — `VTM_E_FORMAT`, молча считать Q4_0 нельзя.

Хвост последней группы (если `n_values` не кратно 32) дополняется нибблом 8;
читатель обрезает его по `n_values`. Масштабы конечны и неотрицательны,
`min` конечен.

**Загрузчик** (`src/vtm/loader.c`) сегмент разбирает, но в fp32 **не
материализует**: упакованные байты остаются в `t->words` (`q[g*16 + (i & 15)]`),
fp32-масштабы — в `t->scales` (`n_scales = n_groups`, `scale_block = 32`), у
Q4_1 — в `t->q4_mins`; `t->f32 == NULL`, `t->q4_is_asym` — 0/1. В mmap-режиме
нибблы (и fp32-масштабы/min на платформах, где допустимы невыровненные
загрузки) читаются прямо из отображения; в остальных случаях в арену
копируются только нибблы и/или масштабы. Ядра 0152 деквантизуют строку на
лету в маленький scratch и сразу умножают — fp32-копии матрицы нет.

Размер для таблицы 1.5B (233 373 696 элементов, 7 292 928 групп): Q4 с
fp32-масштабами — **145 858 578 Б** (116 686 848 упакованных + 29 171 712
масштабов + 18 заголовка), с fp16-масштабами — **131 272 722 Б**. Для
сравнения: trit 53 967 698 Б, int8 240 666 642 Б, fp16 466 747 392 Б. То есть
Q4 — 4,5–5 бит на вес: 4 бита данных + 0,125/0,0625 Б масштаба на элемент.

**Компилятор** (`tools/vtm_compile.py`, задача 0154) читает `q4.bin` из
манифеста импорта GGUF (0153): запись `dtype: q4_0` с `q4_offset`/
`q4_length` разбирается `decode_q4_segment_ex` и становится `Tensor` kind 5
(нибблы + масштабы, Q4_1 — ещё и `min`). `matrix_tensor` принимает kind 5 в
`TMV`, `architecture.lm_head='q4'` означает `TMV` по Q4-матрице; при
`tie_word_embeddings: true` отдельной матрицы нет и логиты, как раньше,
считает `MM` по таблице словаря. Транспонированный Q4
(`VTM_FLAG_TMV_TRANSPOSED`) ядра 0152 не поддерживают — компилятор
отвергает такой граф с внятной ошибкой, а не пишет неисполнимый контейнер.

**Импорт 7B в предел 4 ГиБ** (задача 0156). Формат умел fp16-масштабы Q4 и
тритовую таблицу словаря с 0151/0043, но `tools/gguf_import.py` писал только
fp32-масштабы и int8-эмбеддинг, а 7B Qwen2.5 Q4_K_M (7,07 млрд весов в
Linear+lm_head и 0,545 млрд в словаре) с ними не влезает:

| Схема | Размер, 10⁹ Б | Доля от 4 ГиБ |
|---|---|---|
| fp32-масштабы + int8-эмбеддинг | 4,98 | 116 % |
| fp16-масштабы + int8-эмбеддинг | 4,54 | 105,7 % |
| fp16-масштабы + тритовый эмбеддинг | 4,10 | 95 % |

Факт (собранный `qwen2.5:7b` Q4_K_M): `q4.bin` 3 977 042 066 Б,
`ternary.trit` 126 030 674 Б, `non_ternary.bin` 1 333 248 Б; контейнер
**4 113 979 440 Б = 3,831 ГиБ = 95,79 %** от 4 ГиБ (запас 181 МБ). C-рантайм
загружает и считает токен.

Поэтому у импортёра два флага: `--q4-scale-dtype fp32|fp16` (пишет масштабы
в fp16 и снимает бит 0 flags Q4-сегмента; fp16-масштаб округляется **до**
выбора нибблов, чтобы не складывать две ступени ошибки) и
`--embed int8|trit|fp16` (`trit` кладёт `model.embed_tokens.weight` TRT1-
сегментом в `ternary.trit`, `architecture.embed='trit'`). Для 7B работает
только их комбинация; каждая по отдельности предел не пробивает.

Цена: таблица словаря в тритах — 0,12 ГиБ вместо 0,53 ГиБ (int8), но
rel-RMS против исходного Q6_K — 43,5 % против 0,65 % (выборка 1/64 строк
7B; правило TWN `scale=1,5·mean|w|`; постичь-absmax дал бы 77 %). Это
осознанный размен ради 4 ГиБ: логиты и паритет C↔Python на срезах 7B — в
отчёте задачи 0156.

**Q4_1 и 7B несовместимы.** Асимметричный Q4_1 (умолчание импорта с 0160,
`min` на группу 32) добавляет к 7B ещё 0,44 ГБ при fp16-`min`: 4,10 → 4,54
ГБ, то есть 106 % предела. Поэтому 7B собирается с `--q4-kind q4_0`
(симметричный), а Q4_1 остаётся умолчанием для моделей, которые влезают
(3B). Один `kind` на все размеры не выбрать: это не настройка, а предел
u32-смещений.

### Q4_K/Q6_K (kind 6/7, задача 0165)

Ollama раздаёт Qwen в Q4_K_M, а это **смесь** форматов: супер-блоки Q4_K
(256 значений, 144 байта) и Q6_K (256 значений, 210 байт), плюс fp32-нормы.
Переквантовать их в kind 5 (0153/0160) — значит сложить лишнюю ступень
потерь: 5,1 % rel-RMS на Linear, которых у ollama нет. Поэтому оба вида
хранятся **нативно, байт-в-байт** (ADR 0018).

**Сегмент** (та же схема, что у kind 5, `scale_offset = 0xFFFFFFFF`):

```
magic "Q4K " | "Q6K " (4 байта) | version u8 (=1) | reserved u8 (=0)
      | n_values u64 | n_blocks u32
блоки: n_blocks * (144 у Q4_K / 210 у Q6_K) байт — ровно блоки ggml
```

`n_blocks = ceil(n_values/256)`, `n_values` обязан совпадать с произведением
`dims`. `reserved` — не маска флагов: ненулевое значение отвергается
(`VTM_E_FORMAT`), чтобы будущее расширение не читалось как «почти то же».
Хвост последнего блока (если `n_values` не кратно 256) дополняется нулями и
читателем игнорируется; `d`/`dmin` каждого блока проверяются на конечность —
NaN в контейнере дал бы тихие NaN-логиты.

- **Q4_K**: `d fp16 | dmin fp16 | scales 12 байт | qs 128 байт`. 8 под-блоков
  по 32 значения; 6-битные `scale`/`min` под-блока `j` берутся
  `get_scale_min_k4`. Кусок `qs[32k:32k+32]` даёт два под-блока: **младшие
  нибблы — под-блок `2k` (32 значения подряд), старшие — `2k+1`** (это не
  раскладка Q4_0 с `j`/`j+16`). `w = d·sc·q − dmin·m`, `q ∈ 0..15`.
- **Q6_K**: `ql 128 | qh 64 | scales 16×int8 | d fp16`. 16 под-блоков по 16
  значений: `q = (ql-ниббл | (2 бита из qh) << 4)`, `w = d·sc·(q − 32)`.

**Загрузчик** (`src/vtm/loader.c`) в fp32 **не материализует**: блоки лежат
в `t->qblocks` (`t->n_qblocks` блоков, `scale_block = 256`), `t->f32 == NULL`.
В mmap-режиме (и там, где допустимы невыровненные загрузки) указатель
смотрит в отображение: сегмент начинается с выровненного `offset`, но блоки
идут с 18-байтового заголовка, поэтому `d`/`dmin` читаются через `memcpy`.
Иначе блоки копируются в арену — сама матрица всё равно остаётся блоками.

**Ядра** (`vtm_q4k_*`, `vtm_q6k_*`; `src/vtm/backend_scalar.c` — эталон в
double, `backend_neon.c` — быстрый путь Q4_K). Под-блок деквантизуется в
стековый scratch (32 значения у Q4_K, 16 у Q6_K) и сразу умножается на
активации; пиковая память ядра — 256 Б на поток, fp32-копии матрицы нет.
NEON-ядро Q4_K считает `Σ q·x` в f64 (`vfmaq_f64`) после приведения
активаций к double: f32-произведения давали 1,07e-6 на логитах среза 3B,
f64 — 5e-9 (то же, что скалярный эталон). Q6_K пока считается скалярно
(это 16 из 36 `ffn_down` и 20 `attn_v` у 3B). Батчевого prefill здесь ещё нет
(появится в 0167): пачка падает на поштучный `op_tmv`, результат тот же,
prefill медленнее. С 0167/0189 у kind 6/7 есть батчевые ядра, включая int8
GEMM, — см. «Плотный prefill: int8 GEMM (0189)».

**Импорт** (`tools/gguf_import.py --q4-kind q4_k`): сырые байты тензора GGUF
копируются в `q4.bin` без деквантования и повторного квантования — Q4_K
становится kind 6, Q6_K — kind 7. `rel-RMS` к весам GGUF = 0 **по
построению**, и это проверяется дважды: sha256 региона GGUF сверяется с
sha256 блоков сегмента (пишется в манифест как `blocks_sha256`), а `--stats`
дополнительно сравнивает декодер импортёра (`_dequant_q4_k`/`_dequant_q6_k`)
с декодером контейнера (`vtm_ref.q4k_block_values`/`q6k_block_values`).
`auto` выбирает `q4_k`, если все Linear/lm_head — Q4_K/Q6_K и оценка
влезает в 4 ГиБ; у 3B это ~1,9 ГиБ, у 7B Q4_K_M — больше предела, поэтому
7B остаётся на kind 5 до u64-смещений (ADR 0016).

**Компилятор** (`tools/vtm_compile.py`) читает записи `dtype/kind:
"q4_k"|"q6_k"` и отдаёт `Tensor.q4k(...)` — окно в mmap `q4.bin`, без
копирования блоков; `dense()` (Python-эталон) декодирует блоки.

Замер на реальном `qwen2.5:3b` (Q4_K_M: 216 тензоров Q4_K, 36 Q6_K,
эмбеддинг int8): импорт 3 м 38 с (против 44 мин с переквантованием в Q4_1),
`q4.bin` 1,55 ГиБ, контейнер **1,86 ГиБ** — меньше Q4_0 (1,92 ГиБ) и Q4_1
(2,245 ГиБ). Все 252 сегмента kind 6/7 совпали с GGUF по sha256 (rel-RMS 0).
Паритет C↔Python на срезе (1 слой, vocab 512) — 9,56e-07, скалярный эталон
C даёт 5e-09. Декод — 2,6 ток/с против 6,1 у Q4_1: f64-накопление в NEON-ядре
Q4_K и скалярный Q6_K (цена критерия паритета, см. ADR 0018).

7B Q4_K_M нативно **не влезает** в 4 ГиБ: Linear-блоки 3,94 ГиБ, с
int8-эмбеддингом 4,46 ГиБ (с тритовым — 4,06 ГиБ). 7B остаётся на kind 5.

**Совместимость:** `kind` — это значение байта 24 записи тензора; новые виды
additive и пишутся как в v0.2, так и в v0.3. Старые контейнеры (kind 0..4)
читаются прежним путём, а старый бинарь на kind 5/6/7 останавливается с
`VTM_E_FORMAT` «неизвестный kind N» ещё до чтения данных — тот же tripwire,
что в ADR 0015 (ADR 0017/0018). Версию контейнера меняет только ширина
смещений (v0.3, ADR 0019), а не вид тензора.

тритовым эмбеддингом против 4,3e-06 без него, argmax и top-5 совпадают
([0099](../ai/tasks/0099-trit-embeddings.md)). Выигрыш: таблица словаря 1.5B — 445 МиБ
fp16 против ~56 МиБ тритов. Цена риска: при `tie_word_embeddings` таблица работает и
как выходной слой, поэтому ошибка квантования идёт прямо в логиты; качество после
обучения проверяется на eval, откат — `quant.quantize_embeddings: none`
([0099](../ai/tasks/0099-trit-embeddings.md)).

Для tied-таблицы путь один — `EMB` + `MM` (`A = emb.w`, `rows = vocab`):
компилятор отвергает `tie_word_embeddings` вместе с `lm_head: tmv` (тритовая
таблица идёт через `EMB`, а `MM` читает её без копии в fp32). Поэтому tied
lm_head всегда считается по той же таблице, что `EMB`, — отдельного TMV-пути
для него нет.

### Метаданные (meta)

После секции данных и перед программой может лежать **JSON-объект** с
гиперпараметрами модели. В заголовке это последние 12 байт, которые спека
называет резервом:

```
20  program_offset u32   абсолютное смещение программы в файле
24  meta_offset u32      абсолютное смещение JSON (0 = меты нет)
28  meta_len u32         длина JSON в байтах (без выравнивания)
```

Раскладка: `data_start + data_size = meta_offset`, JSON дополняется нулями до
32 байт, `program_offset = meta_offset + align32(meta_len)`, программа
по-прежнему последняя. C-загрузчик находит программу как
`file_size - n_instr*16`; `program_offset` он не читает, а `meta_offset` и
`meta_len` только уточняют границу данных. Контейнер без меты (нули в этих
словах) читается как раньше.

Читаются ключи, которые меняют исполнение:

| Ключ | Тип и кламп | Смысл | Без ключа |
|---|---|---|---|
| `rope_theta` | number; принимается `(0; 1e15]` | база RoPE (у Qwen2.5 — `1e6`) | `10000` |
| `rms_norm_eps` | number; первое вхождение в JSON | eps RMSN, представимый в `imm` (компилятор пишет `round(eps·1000)/1000`); точный — в `rms_norm_eps_exact`. Приоритетнее `imm/1000` | `imm/1000` (совместимость со старыми контейнерами) |
| `rope_layout` | строка `"half"` \| `"interleaved"`; иное игнорируется | пары RoPE: `(i, i+d/2)` или `(2i, 2i+1)` | `"half"` |
| `context_window` | number; берётся `1..2^31-1`, усекается к int; иное (NaN, `<= 0`, строка, bool) — ключа нет | длина кольцевого KV-окна; больше длины кэша — окно равно кэшу | длина кэша (`ctx`) |
| `vocab_size` | целое `1..2^30` (синоним `vocab`) | размер словаря | неизвестен (`0`), брать из `dims` EMB |
| `tied_embeddings` | bool (синоним `tie_word_embeddings`); принимается и `0`/`1` | `lm_head` — та же таблица, что эмбеддинги | `false` |
| `temperature` | number; `< 0` и NaN → `0`, `> 1e6` → `1e6` | температура SAMP; `0` — жадно | `1.0` |
| `top_k` | число, усекается к int; `<= 0` → `0`, `> 1e9` → `1e9` | top-k для стратегии 2; `0` — не отсекать | `0` |
| `top_p` | number; NaN → `1.0`, `<= 0` → `0`, `>= 1` → `1` | top-p для стратегии 3; `1.0` — не отсекать | `1.0` |
| `repetition_penalty` | number; NaN и `<= 0` → `1.0`, `> 1e6` → `1e6` | штраф за повторы; `1.0` — выключен | `1.0` |
| `repetition_window` | число, усекается к int; `<= 0` → `0`, `> 256` → `256` | окно штрафа в токенах | `64` |
| `sample_seed` | число `0..2^53-1`, усекается к uint64 | зерно ГПСЧ SAMP | `0` |

Остальные ключи (`format`, `generator`, `n_layers`, `hidden_size`, `lm_head`,
`embed`, `quantize_embeddings`, `context_len`, `scale_block`, `model`,
`sampling`, `synthetic`, `expected`) как параметры не читаются: они
нужны инструментам и отладке. При этом обход идёт по всему JSON, поэтому
известный ключ, вложенный в `model` или в другой объект, всё равно будет
найден. Значения типов, отличных от ожидаемых, пропускаются так же, как битая
мета.

Опциональный блок целостности — `meta["integrity"]`:

```json
{"integrity": {"algo": "sha256",
               "data_sha256": "<64 hex>",
               "meta_sha256": "<64 hex>"}}
```

`data_sha256` — SHA-256 секции данных (`data_start .. meta_offset`);
`meta_sha256` — SHA-256 JSON-меты, в котором значение самого `meta_sha256`
заменено 64 символами `'0'`. Если блок есть, C-загрузчик проверяет оба хеша до
разбора тензоров и при расхождении возвращает `VTM_E_INTEGRITY`; неполная пара
полей — тоже ошибка. Поле `algo` C не анализирует: проверяются только сами
64-символьные hex-значения. Контейнер без блока читается как раньше, а
`VTM_SKIP_HASH=1` отключает сверку с предупреждением в stderr. По умолчанию
писатель хеш не пишет: его включает `write_vtm(..., integrity=True)` или
`VTM_WRITE_HASH=1`. Проверка с блоком — дополнительный проход по данным при
загрузке.

Ключи ищутся на любом уровне вложенности (компилятор дублирует конфигурацию в
`meta["model"]`), регистр учитывается; верхний уровень приоритетнее вложенного.
При `tied_embeddings` отдельного тензора
`lm_head` нет: программа ссылается на таблицу эмбеддингов как на матрицу
`[vocab, hidden]` — `MM` (A=E, B=h, так делает `tools/vtm_compile.py`) или
плотный `TMV` (при необходимости с флагом `VTM_FLAG_TMV_TRANSPOSED`, когда
таблица хранится как `[hidden, vocab]`).

Разбор **терпимый**: нет меты, битый или обрезанный JSON, неверный тип ключа,
смещения/длина мимо файла, мета больше 64 МиБ — это не ошибка загрузки (но
блок `integrity`, если он есть, проверяется и у большой меты).
Контейнер грузится, а незаданные параметры берутся из колонки «Без ключа»
(для ROPE это прежние `10000`/`half`). Python-эталон на битой мете падает с
`ValueError`; C намеренно мягче — битая мета не должна превращать контейнер в
кирпич. Прочитать мету из C можно через
`vtm_meta_present()` / `vtm_meta_rope_theta()` / `vtm_meta_rope_layout()` /
`vtm_meta_vocab_size()` / `vtm_meta_tied_embeddings()` / `vtm_meta_json()`.
Эффективные параметры сэмплинга (после клампа) отдаёт `vtm_sampling_params()`.

## Инструкция (16 байт)

```
0  opcode u8 | 1 flags u8 | 2 dst u16 | 4 a u16 | 6 b u16 | 8 c u16
10 padding u16 | 12 imm i32
```

- тензоры адресуются индексами в таблице, не указателями — программа
  переносима между машинами;
- `imm` — целое по смещению **12** (байты 10–11 — выравнивание, в каноне 0);
  интерпретация зависит от операции (позиция, число голов, эпсилон в
  тысячных, номер стратегии сэмплинга);
- `flags` локальны для опкода: `CAUSAL` `0x01` (SM, ATTN), `INPLACE` `0x02`
  (подсказка), `EMB_INPUT` `0x01` (EMB), `ROPE_INTERLEAVED` `0x02` (ROPE),
  `TMV_TRANSPOSED` `0x04` (TMV).

## Набор операций v0.2

| Код | Имя | Семантика |
|---|---|---|
| 0x01 | `TMV` | `y = W·x`; `W` — тритовая матрица (`trit · scale`), Q4 (kind 5, ядра 0152), Q4_K/Q6_K (kind 6/7, ядра 0165) или плотная fp32/fp16/bf16. `TMV_TRANSPOSED` (только для плотной `W`) читает её как `[cols, rows]` и считает `Wᵀ·x` |
| 0x02 | `MM` | `Y = A·B`; `A` — тритовая, Q4 или fp32/fp16/bf16, `B` и `Y` — fp32/fp16/bf16; все три — 2D, `dst` не совпадает с входами |
| 0x03 | `RMSN` | `y = x / rms(x) · w`; `imm` = eps×1000 (неотрицательный), но `meta["rms_norm_eps"]` приоритетнее |
| 0x04 | `ROPE` | поворот `x`; `b` — число голов (не индекс тензора), `imm` — смещение позиции; база и раскладка — из меты, флаг `0x02` перекрывает раскладку |
| 0x05 | `SM` | softmax по последней оси; `flags & CAUSAL`; `imm` — смещение causal-маски |
| 0x06 | `SILU` | `x · sigmoid(x)` поэлементно |
| 0x07 | `MUL` | `dst = a · b` поэлементно (буква `c` в старой записи — это `dst`) |
| 0x08 | `ADD` | `dst = a + b` поэлементно |
| 0x09 | `EMB` | `y = E[token]`, `a` — таблица `[vocab, dim]` kind 0..7 (kind 4 разворачивается построчно ядром `vtm_i8_dequant_row`, kind 5/6/7 — ядрами 0152/0165); `imm` — token id; с флагом `EMB_INPUT` токен из `vtm_set_token()`, `imm` игнорируется |
| 0x0A | `KVW` | записать K (`a`) в K-кэш `dst`, V (`c`) в V-кэш `b` на глобальную позицию `m->position + imm`; слот — `pos % win` (кольцо) |

### Один токен за проход: prefill

Граф и API считают **один токен за вызов** `vtm_run()`: `ATTN` приходит с
`q_len = 1` (3-D путь `ATTN` умеет `q_len > 1`, но граф не собирает пачку
токенов).
Поэтому промпт из N токенов — это N полных проходов по всем слоям, и TTFT растёт
линейно с длиной промпта: на форме Qwen2.5-1.5B 0,136 с на 1 токене, 0,56 с на 8
и **37,6 с на 512** (4 потока, mmap;
[0103](../ai/tasks/0103-bench-shape.md); подробности — `docs/vtm-perf.md`).

Батчевый prefill — задачи [0112](../ai/tasks/0112-prefill-batch.md) (ядро,
`vtm_run_batch`), [0114](../ai/tasks/0114-prefill-cli.md) (CLI/ABI) и
[0180](../ai/tasks/0180-cache-plus-batch.md) (кэш префикса и пачка вместе,
умолчание 128):

- CLI: `vtm run --prefill-batch N` — считать промпт пачками по N токенов; `0`
  (по умолчанию) — по токену, как раньше; `N > 1 000 000` и отрицательное —
  ошибка [0114](../ai/tasks/0114-prefill-cli.md);
- C-ABI: `vtm_api_options.prefill_batch` — то же для хоста; поле заняло элемент
  прежнего `reserved[5]`, `sizeof` не изменился. Умолчание для `opts == NULL`
  и `opts->struct_size == 0` — **128** (`VTM_API_PREFILL_BATCH_DEFAULT`), в
  заданной структуре `0` — явный выключатель. Последний токен промпта всё
  равно идёт отдельным `vtm_run()` с колбэком `SAMP` (иначе неоткуда взять
  первый ответ);
- **кэш и пачка вместе** ([0180](../ai/tasks/0180-cache-plus-batch.md)): при
  `cache_prefix == 1` префикс берётся из кэша, а некэшированный хвост
  считается пачками через `vtm_run_batch()` (включая MoE-пачку 0179). На
  скалярном бэкенде ответы побитово те же, что при `prefill_batch == 0`; на
  SIMD тритовые батчевые ядра дают ≤1e-5 (argmax и последовательность
  совпадают), а Q4_K/Q6_K с 0189 — побитово (int8 GEMM повторяет арифметику
  поштучного ядра строки). Плотный граф с Q4_K/Q6_K на SIMD больше не
  исключение: гейт «12 токенов / по токену» снят (`VTM_BATCH_DENSE=0`
  возвращает его для A/B). У MoE пачка включается всегда: эксперт читается
  один раз на всех, кому он нужен;
- `vtm_run_batch(m, ids, n)` — публичный API ядра (`vtm.h`); в `api.c`/`main.c`
  осталась слабая заглушка «по токену» на случай сборки без `interp.o`, но
  сильное определение из `libvtm.a` её перекрывает.

Контракт, на который рассчитаны CLI и C-ABI (его реализует
[0112](../ai/tasks/0112-prefill-batch.md)): `vtm_run_batch` прогоняет `ids[0..n)`
от текущей позиции машины; токен `k` считается на позиции `start + k`, где
`start = vtm_position(m)` до вызова; `emit` не вызывается (это prefill, а не
генерация); после вызова `vtm_position(m) == start + n - 1`, а состояние машины
(K/V, счётчик, сэмплер) побитово равно состоянию после n последовательных
`vtm_run()`; `n == 0` — no-op, `VTM_OK`; пачка неделима — таймаут и отмена
проверяются между пачками. Кольцо KV и кэш префикса (0081/0087) обязаны
работать: батч не должен их ломать.

### Внимание (`KVW`/`ATTN`): кольцо, окно и блочный softmax

**Кольцевой KV-кэш.** `KVW` пишет K и V на глобальную позицию
`p = m->position + imm` в слот `p % win`, где
`win = min(ctx, meta["context_window"])`, а `ctx` — первая размерность
K/V-кэша. Кэш — кольцо: когда позиция доходит до `win`, самый старый слот
затирается. Поэтому **позиция `>= ctx` больше не ошибка** — диалог длиннее
кэша продолжается, теряя только старейшие ключи. Без ключа
`context_window` окно равно длине кэша, то есть прежнему поведению.

**Чтение окна.** `ATTN` с 2-D кэшем для запроса на глобальной позиции
`q = q_start + qi` читает только последние `win` ключей: диапазон
`[max(0, q - win + 1), q]` при `CAUSAL` (без маски — `[max(0, key_count - win),
key_count - 1]`). Слот глобальной позиции `j` — `j % win`; ключи
перебираются в хронологическом порядке. В 3-D-раскладке (K/V без кэша)
окна нет: видны все ключи `0..kv_len-1` с прежней causal-границей.

**Блочный softmax.** `ATTN` не материализует матрицу оценок: softmax
считается онлайн, блоками по 64 ключа (`ATTN_KEY_BLOCK`). Для каждой головы
и каждой строки запроса хранятся running max `m`, running sum `l` и
накопитель `acc[head_dim]` в `double`; при росте максимума `acc` и `l`
домножаются на `exp(m_old - m_new)`. Память — `O(head_dim + 64)`: ни матрицы
оценок на весь ключевой диапазон, ни буфера размером с `ctx` не выделяется.
`Q·Kᵀ` считается в `double` четырьмя независимыми аккумуляторами, `exp` на
ключ — один раз. Итог — `acc / l`.

**RoPE по глобальной позиции.** `ROPE` применяется к Q и K до `KVW` и
берёт `m->position + imm`, а не индекс слота кольца. Кольцо не меняет
значения векторов — только место хранения, поэтому поворот остаётся
корректным при любой длине диалога.

Python-эталон (`tools/vtm_ref.py`) повторяет и кольцо, и окно: `KVW` пишет
в `pos % win`, `ATTN` читает последние `win` слотов, `context_window`
разбирается из меты с теми же клампами. Паритет на 2×ctx токенах проверяет
`tests/test_vtm_sampling.py::TestKvWindowParity`: на скалярном бэкенде
логиты совпадают побитово (`max|Δ| = 0`), на `auto`/SIMD — на уровне
1e-6…1e-5 из-за иного порядка суммирования в NEON/AVX2.

### Сэмплинг (`SAMP`)

`imm` — номер стратегии:

| `imm` | Стратегия | Что делает |
|---|---|---|
| 0 | argmax | жадно: сравнение строго `>`, первый максимум; NaN не выигрывает у конечных значений, но NaN в позиции 0 оставляет токен 0 (как в v0.1) |
| 1 | temperature | `p = softmax(logits / temperature)`, выбор по `p` |
| 2 | top-k | температура, затем `top_k` старших логитов |
| 3 | top-p | температура, затем минимальное ядро с суммой `>= top_p` |

`imm` вне 0..3 — `VTM_E_UNSUPPORTED`. Старая конвенция Python-эталона
(`imm` = температура × 1000) больше не поддерживается: эталон приведён к
номерам стратегий, байткод с такими `imm` надо перекомпилировать.

Порядок обработки: **штраф за повторы → температура → top-k/top-p → одно
случайное число**. Штраф действует во всех стратегиях (и в argmax): каждый
токен, встретившийся среди последних `repetition_window` сгенерированных,
штрафуется один раз (как в CTRL) — логит `> 0` делится на
`repetition_penalty`, иначе умножается на неё. Повтор внутри окна не
усиливает штраф.

Детерминизм: в argmax `SAMP` переводится при условиях:

| `imm` | Условие перехода в argmax |
|---|---|
| 0 | всегда |
| 1 | `temperature <= 0` |
| 2 | `temperature <= 0` или `top_k == 1` |
| 3 | `temperature <= 0` или `top_p <= 0` |

Argmax не потребляет ГПСЧ, поэтому `temperature 0` и `top-k 1` побитово равны
argmax, а `top_p 1.0` ничего не отсекает (ядро — весь словарь).

ГПСЧ — **xorshift64\*** с засевом **splitmix64** (фиксировано для паритета с
`tools/vtm_ref.py`):

```
seed = meta["sample_seed"] (0 по умолчанию)
rng  = splitmix64(seed ^ 0x9E3779B97F4A7C15)
если rng == 0: rng = 0x2545F4914F6CDD1D
splitmix64(x): x += 0x9E3779B97F4A7C15
               x  = (x ^ (x >> 30)) * 0xBF58476D1CE4E5B9
               x  = (x ^ (x >> 27)) * 0x94D049BB133111EB
               return x ^ (x >> 31)
next(): x = rng; x ^= x << 13; x ^= x >> 7; x ^= x << 17; rng = x
        return x * 0x2545F4914F6CDD1D          # всё в арифметике mod 2^64
uniform = (next() >> 11) * 2^-53                # [0, 1)
```

Сэмпл без перехода в argmax и хотя бы с одним конечным логитом потребляет
ровно одно `next()`. Логиты переводятся в `double`, веса считаются как
`exp((logit - max) / temperature)` и накапливаются в том же порядке (по
убыванию логита, при равенстве — по возрастанию индекса), что и в
Python-эталоне. Благодаря этому при одном `seed` C и Python дают одну и ту же
последовательность токенов; проверка — `tests/test_vtm_sampling.py` (сверяет
вывод C-рантайма с `vtm_ref.execute`).

Состояние сэмплера (ГПСЧ и кольцо последних 256 токенов) живёт в машине,
поэтому `vtm_reset()` возвращает его в начало: повторный прогон с тем же
`seed` даёт ту же последовательность. Потокобезопасности у API нет (как и у
`vtm_last_error()`), одну машину нельзя использовать из двух потоков.

## Память

- `vtm_load()` на POSIX отображает файл `mmap(PROT_READ, MAP_PRIVATE)`:
  неизменяемые fp32-тензоры и слова тритов на x86/ARM64 читаются прямо из
  отображения (на строгих к выравниванию платформах TRT1 копируется).
  В арену копируется только то, что интерпретатор может писать (`dst`,
  V-кэш `KVW`), и fp16/bf16 (их нужно развернуть в fp32). `vtm_load_mem()`,
  `VTM_NO_MMAP=1` и Windows копируют все тензоры в арену.
- Арена — один `malloc`, начало и каждый тензор выровнены на 64 байта; живёт
  до `vtm_free()`, поштучно тензоры не освобождаются.
- KV-кэш — обычные fp32-тензоры в общей арене (компилятор создаёт их под
  каждый слой); отдельной арены и отдельного времени жизни у кэша нет.
  Payload кэшей в контейнер не пишется: тензоры помечены
  `VTM_TENSOR_FLAG_KV_CACHE`, `offset = 0`, а загрузчик выделяет буферы в арене
  через `calloc` ([0101](../ai/tasks/0101-kv-lazy-alloc.md)); до неё это были
  пустые буферы на весь контекст в файле — 4 МиБ из 5,25 МиБ tiny-модели
  ([0100](../ai/tasks/0100-kv-in-container.md)). Для 1.5B кэш — **112 МиБ**
  памяти (ctx 2048, kv_dim 256, 28 слоёв), но не файла; подробности — раздел
  «KV-кэши: не в файле».
- int8-тензоры (`kind 4`) в арене занимают `n_scale·4` байт — только
  fp32-масштабы; байты `q` читаются из отображения файла (задача 0170). Для
  таблицы 1.5B это 1,1 МиБ вместо 890 МиБ fp32-развёртки (при `VTM_I8_EMB=0`
  — снова `4·n`). Триты `native` переупаковываются в `pack20` в арене, то есть
  занимают как `pack20`, а не как `native` в файле.
- Q4-тензоры (`kind 5`) в fp32 **не** расквантовываются: в mmap-режиме
  упакованные нибблы (16 байт на 32 значения) и fp32-масштабы читаются из
  отображения, иначе в арену копируются только упакованные байты и масштабы
  (0,5 + 0,125 Б на элемент, без `4·n`). Прямое чтение и деквантизация на
  лету — ядра 0152.
- Буфер кандидатов `SAMP` (кандидаты, веса, метки окна, счётчики radix)
  выделяется один раз на машину и переиспользуется; освобождается в
  `vtm_free()`.
- `ATTN` выделяет на вызов один буфер `2·head_dim` чисел `double` (q-строка и
  накопитель выхода) и держит блок из 64 оценок на стеке; временного массива
  на `key_count`/`ctx` нет, память не зависит от длины контекста.

## Контракт бэкенда

```c
typedef struct vtm_backend {
    const char *name;
    int (*tmv)(float *y, const uint8_t *w, const float *scales,
               const float *x, int rows, int cols);
    int (*rmsnorm)(float *y, const float *x, const float *w, int n, float eps);
    int (*silu)(float *y, const float *x, int n);
    int (*mul)(float *y, const float *a, const float *b, int n);
    int (*add)(float *y, const float *a, const float *b, int n);
    int (*scal)(float *y, const float *x, float k, int n);
    int (*softmax)(float *y, const float *x, int rows, int cols,
                   int causal, int offset);
    int (*emb)(float *y, const float *e, int dim, int token);
    int (*copy)(float *y, const float *x, int n);
    int (*tmv_blocks)(float *y, const uint8_t *w, const float *scales,
                      const float *x, int rows, int cols, int scale_block);
} vtm_backend;
```

Любое поле `NULL` — интерпретатор берёт скалярную реализацию. `tmv_blocks`
получает явный блок масштаба (128/160); старый `tmv` умеет только 160, для 128
интерпретатор откатывается на скалярный LUT. Полей для MM/ATTN/ROPE/KVW в
структуре нет: ROPE/ATTN/KVW остаются скалярными, а SIMD-ядра MM
(`vtm_simd_mm_trit`/`vtm_simd_mm_f32` из `src/vtm/vtm_backend.h`) `op_mm()`
вызывает напрямую, когда выбран бэкенд с именем `simd*` и CPU его умеет.
Выбор бэкенда: `VTM_BACKEND=auto|hybrid|metal|simd|scalar|lut|direct` (по
умолчанию `auto`: **metal** — весь токен декода одним графом на GPU, — если
Metal собран и устройство есть; иначе SIMD, если он собран и CPU его умеет;
иначе `scalar-lut243`) или `vtm run --backend ...`. Так SIMD подключается без
изменения байткода; подробности и числа — в `docs/vtm-perf.md`. Почему `auto`
стал metal — раздел «фаза 3 (0204)» ниже: после переноса RMSNorm/RoPE/SiLU/
KVW/attention на GPU парный замер дал 1,55–2,00× на декоде и 1,9–2,0× на
prefill. `hybrid` (0198) остаётся явным режимом для машин, где декод на GPU
медленнее CPU.

### Metal-бэкенд (задачи 0192/0196/0198, ADR 0021)

`VTM_BACKEND=metal` (или `--backend metal`) подменяет матричные операции,
которые в декоде/prefill считают веса: kind 6 (Q4_K), kind 7 (Q6_K) и
int8-таблицу словаря kind 4 (`tied lm_head`). Триты, RMSNorm, softmax,
attention, KV-кэш и сэмплинг остаются на CPU: бэкенд `metal` отдаёт те же
ядра, что `simd`, и подменяет лишь перечисленные GEMV/GEMM. Сборка —
`src/vtm/backend_metal.m`, MSL — `src/vtm/vtm_metal.metal`. С 0198 рядом стоит
`hybrid` — тот же исполнитель, но только для батчевого prefill (см. «фаза 3»).

- **Zero-copy.** Веса не копируются: `MTLBuffer` создаётся через
  `newBufferWithBytesNoCopy:` на выровненный вниз до страницы (16 КиБ на Apple
  Silicon) срез mmap-региона, а смещение тензора внутри среза передаётся ядру
  аргументом. Кэш буферов — по (указатель, длина), вытеснение LRU; при
  `vtm_free()` кэш сбрасывается до `munmap`, иначе Metal держал бы старые
  страницы. Если no-copy невозможен, маленькие буферы (тесты, арена) один раз
  копируются, большие — отказ и CPU-откат.
- **Сборка без Metal Toolchain.** Исходник MSL встраивается в
  `vtm_metal_kernels.h` и компилируется в рантайме через
  `newLibraryWithSource:`. `make metallib` собирает `vtm.metallib` через
  `xcrun metal`, если Toolchain установлен (в Xcode 26 это отдельный
  скачиваемый компонент); бэкенд загрузит `vtm.metallib` из текущего каталога
  или `VTM_METAL_LIB`, иначе компилирует исходник. Время компиляции видно в
  `VTM_METAL_STATS=1`.
- **Точность.** Порядок суммирования на GPU иной, побитового паритета с CPU
  нет: контракт — argmax и `max|Δlogits| ≤ 1e-2` (на 3B Q4_K замер дал
  `≤ 8.4e-5`, argmax совпал на трёх промптах; батчевый GEMM расходится с CPU
  на `≤ 1.3e-5` на матрицу, int8 — `≤ 2.4e-7`).
- **Порог.** Операция меньше `VTM_METAL_MIN_MAC` MAC (по умолчанию 1M)
  остаётся на CPU: накладные Metal на мелких формах (K/V-проекции 256×2048)
  больше выигрыша — ADR 0021 §5. `VTM_METAL_MIN_MAC=0` отдаёт GPU всё.
- **Откат.** Нет устройства, не собрался MSL, ошибка командного буфера,
  неверная форма — ядро возвращает `-1`, диспетчер `backend_scalar.c` идёт
  прежним CPU-путём, в stderr одна строка с причиной. Прогон не падает.
  Отложенная очередь декода при ошибке командного буфера выключает Metal и
  **пересчитывает все поставленные GEMV на CPU** (`metal_defer_replay` в
  `interp.c`); проверить можно инъекцией `VTM_METAL_FORCE_FAIL=1` — точность
  остаётся в допуске, дальше прогон идёт на NEON.
- **Диагностика.** `VTM_METAL_STATS=1` печатает на выходе время инициализации
  и MSL, число вызовов/отказов/GEMV в общем буфере/ожиданий и время ожидания
  GPU, zero-copy и скопированные байты, `MTLDevice.currentAllocatedSize`;
  `VTM_METAL_TRACE=1` — время GPU каждого вызова и каждого отложенного
  командного буфера; `bench_backend --metal PATH` — точность на трёх
  промптах, декод SIMD против metal, prefill 64 токена пачкой и footprint.
  `currentAllocatedSize` считает и no-copy регистрации (растёт на размер
  весов), поэтому реальное отсутствие копий подтверждается
  `copy_bytes ≈ 0` и `phys_footprint` в том же отчёте.

#### Фаза 2 (задача 0196): меньше командных буферов, GEMM пачкой, ping-pong

Диагноз фазы 1: 181 синхронный GEMV на токен, каждый — свой
`MTLCommandBuffer` + `waitUntilCompleted` (0,15–0,25 мс), то есть накладные
больше полезной работы. Что сделано:

1. **Один командный буфер на пачку GEMV.** `interp.c` больше не зовёт GEMV по
   одному: `vtm_run()` открывает сессию `vtm_metal_defer_begin()`, подряд
   идущие TMV/MM kind 4/6/7 уходят в общий `MTLCommandBuffer`
   (`vtm_metal_defer_gemv`), а синхронизация (`vtm_metal_defer_wait`) — только
   перед инструкцией, которая читает/пишет недосчитанный тензор
   (`metal_defer_conflicts` по `dst/a/b/c`). На слой это QKV-группа, O,
   gate+up, down: 181 буфер на токен → ~145, и на каждый слой 4 ожидания
   вместо 7.
2. **Батчевый GEMM prefill.** Новые MSL-ядра `vtm_q4k_gemm*`,
   `vtm_q6k_gemm*`, `vtm_i8_gemm*` (N = 8/16/32 токенов — параметр сборки,
   цикл токенов развёрнут): 4 колонки на дорожку (`uchar4` веса + `float4`
   активаций), 8 строк на threadgroup, активации половины блока (128 колонок ×
   N) коллективно грузятся в threadgroup-память. `vtm_metal_qk_gemm()` зовётся
   из `batch_tmv_kernel`/`batch_mm_kernel`; int8 lm_head пачкой включается в
   `batch_mm_ready` только при активном Metal (иначе прежний поштучный путь).
   На 2048×2048, 11008×2048 и 2048×11008 ядро даёт 100–220 GMAC/s против
   55–65 GMAC/s у CPU-батча (парный замер в одном процессе).
3. **Ping-pong и семафоры.** Две сцены staging (`VTM_METAL_STAGES = 2`): пока
   GPU считает одну, CPU кодирует другую; ожидание — `dispatch_semaphore`,
   который сигналит `addCompletedHandler`, а не `waitUntilCompleted`.
   `vtm_metal_defer_submit()` отдаёт накопленную сцену, не дожидаясь её —
   интерпретатор зовёт его перед CPU-инструкцией, чтобы attention/RMSN шли
   параллельно уже отданным матрицам. На последовательном графе трансформера
   перекрытие ограничено зависимостями (O зависит от attention, gate/up от
   нормы, down от silu), поэтому выигрыш ping-pong меньше, чем у batched GEMM.

**Почему `auto` остался simd после фазы 2.** Парный замер 0196
(`bench_backend --metal`, одна загрузка модели, min из 2, M1 Pro 16 ГиБ под
нагрузкой 12–13):

| | simd-neon | metal |
|---|---|---|
| декод, ток/с | **18,8–19,7** | 8,8–9,2 |
| prefill 64 токена, ток/с | 16,9–19,3 | **31,1–35,2** (1,6–2,0×) |
| Δlogits / argmax | — | ≤ 8,4e-5, 3/3 |

Metal выиграл только prefill, декод — в 2 раза медленнее: 1,9 ГБ весов на
токен читаются с эффективной полосой ~20–30 ГБ/с (и CPU, и GPU упираются в
неё), а 181 dispatch на токен дают 60–75 мс GPU-времени даже без ожиданий.
Критерий фазы 2 разрешал `auto = metal` только когда **и** декод, **и**
prefill быстрее CPU; тогда это было не так, поэтому `auto` остался SIMD, а
Metal включался явно. Отсюда же вывод фазы 3: на GPU отдавать только батч.

#### Фаза 3 (задача 0198): hybrid — GPU на prefill, CPU на декод

`VTM_BACKEND=hybrid` (или `--backend hybrid`): **батчевые GEMM** prefill
(`batch_tmv_kernel`/`batch_mm_kernel` в `interp.c`, kind 6/7 и int8 lm_head)
уходят на Metal, **поштучные GEMV/MM** (n == 1: `vtm_q4k_tmv`, `vtm_q6k_tmv`,
`vtm_i8_gemv` и отложенная очередь декода) остаются на NEON.

Развилка — в диспетчере, а не в ядре. У Metal три режима (`vtm_backend.h`):
`VTM_METAL_OFF`, `VTM_METAL_FULL` (`metal` — всё на GPU) и `VTM_METAL_BATCH`
(`hybrid` — только батчевые GEMM). `vtm_backend_by_name("hybrid")` возвращает
описатель с именем `hybrid` и ядрами simd и ставит режим BATCH.
`vtm_metal_active()` истинно в FULL и BATCH (его спрашивают батчевые пути),
`vtm_metal_gemv_active()` — только в FULL (его спрашивают поштучные GEMV и
сессия декода). Почему так, а не «ядро вернуло "не умею"»: GEMV kind 4/6/7
вызываются из `interp.c` не через vtable, а глобальными функциями
`vtm_q4k_tmv`/`vtm_q6k_tmv`/`vtm_i8_gemv` (их же зовёт откат), поэтому «не
умею» пришлось бы возвращать из тех же функций, которыми считает и `metal`;
режим-бит в одной точке диспетчера проще и не требует сравнения строк на
каждой инструкции. Имя бэкенда — единственный источник правды:
`vtm_backend_note_active()` (его зовёт `vtm_set_backend`) переводит `hybrid` в
BATCH, `metal` в FULL, всё остальное — в OFF.

Замер 0198 (M1 Pro, 16 ГиБ, `bench_backend --metal runs/q4/3b-q4k.vtm`,
одна загрузка модели, min из 2, порядок бэкендов чередуется):

| | simd-neon | metal | hybrid |
|---|---|---|---|
| prefill 64, ток/с | 19,5 | 39,1 (2,00×) | **38,4 (1,96×)** |
| TTFT 64, с | 3,28 | 1,64 | **1,67** |
| prefill 128, ток/с | 19,3 | 35,3 (1,83×) | **35,8 (1,86×)** |
| TTFT 128, с | 6,63 | 3,63 | **3,59** |
| декод, ток/с | **20,2** | 8,7 | 19,9 (0,99×) |
| CPU-время prefill 64 | 16,5 с | 0,55 с | 0,55 с |
| точность (3 промпта × 5) | — | Δ 8,0e-5, argmax 3/3 | **Δ 0, argmax 3/3** |
| точность пачки 64 | — | Δ 2,1e-5, argmax 1/1 | Δ 2,1e-5, argmax 1/1 |
| RSS после prefill 64 | 2006 МиБ | 2007 МиБ | 2007 МиБ |

Декод hybrid побитово равен simd: в нём те же NEON-ядра и тот же порядок
сложения (0,99× — шум). Памяти гибрид не добавляет: те же 1896,5 МиБ
zero-copy, копий 0, RSS после prefill одинаков у всех трёх путей.

**Почему `auto` стал hybrid.** Критерий 0198: prefill ≥ 1,3× и декод не хуже
simd. Гибрид даёт 1,86–1,96× на prefill 64/128 и декод в пределах шума,
поэтому `auto` = hybrid, когда Metal собран и устройство есть; иначе (сборка
без Metal, машина без GPU) — прежний simd. Вернуть `auto = simd` можно
константой `VTM_AUTO_HYBRID` в `backend_neon.c`.

**Холодный старт.** Первый батчевый GEMM в процессе компилирует MSL (~0,2–0,4 с)
и привязывает веса zero-copy (до ~1900 `MTLBuffer`). В парном замере выше эта
цена уже уплачена предыдущими прогонами (методика 0196 — «одно окно»). В
одноразовом `vtm run` первый prefill платит её целиком: на 64 токенах hybrid
всё равно быстрее simd (2,9 против 3,3 с в CLI), а на коротком промпте
(8–32 токена) — медленнее (1,6–2,0 против 0,45–1,7 с). Для сервера (модель
загружена один раз, запросов много) это разовая цена; для одноразового CLI с
коротким промптом быстрый путь — `VTM_BACKEND=simd`.

**Откат.** Ошибка Metal в батчевом GEMM (неверная форма — не ошибка: сразу
CPU-путь) выключает режим (`vtm_metal_set_mode(VTM_METAL_OFF)`), и остаток
прогона считает CPU. Проверка — `VTM_METAL_FORCE_FAIL=1` в
`bench_backend --metal`: первый GEMM теряет результат, режим становится off,
логиты пачки совпадают с simd побитово (Δ = 0), отказов 1.

**Диагностика.** `bench_backend --metal PATH [--metal-new N]
[--metal-lens 64,128]` меряет три бэкенда в одном окне: точность (3 промпта и
пачка), декод, prefill любых длин, TTFT, CPU-время, RSS/zero-copy и откат.

#### 0199: C-ABI-паритет — шаг строки GPU-батча, а не гонка

Симптом 0198: `vtm run` на simd и hybrid совпадал, а `vtm_api_generate`
(`cache_prefix=1`, `prefill_batch=256`) на hybrid выдавал мусор. Гипотеза
была — гонка асинхронной отправки (`defer_submit`/`waitUntilCompleted`).
Она не подтвердилась: `vtm_metal_qk_gemm` вызывает `waitUntilCompleted` и
проверяет статус **до** копирования из `g_gybuf`, кэш префикса снимается уже
после возврата батча, а отложенная очередь декода в hybrid не открывается
вовсе (она только для FULL, `vtm_metal_gemv_active()`). Гонки в этом пути
нет; дефект детерминированный.

Причина — в `metal_gemm_body` (`backend_metal.m`). Ядро всегда пишет строку
результата шириной `N` выбранного варианта (`gemm8/16/32`), а хвост пачки
добивает нулями. Хост же копировал `yt[r*nt + j]`, где `nt` — длина последнего
chunk'а (она может быть меньше `N`: 11 → gemm16, 24/31 → gemm32, 44 → 32+12).
При `nt != N` строки результата сдвигались, и мусором становился не только
выход слоя, но и K/V префикса — отсюда бессвязный текст. Совпадало только
там, где `nt == N` (8/16/32, а также хвост < 8, который GEMM отвергает и
считает CPU), поэтому прежние проверки `bench_backend --check` (длины 8/16/32)
и CLI-прогоны на «круглых» пачках баг не ловили.

Исправление: читать staging с шагом ядра `yt[r*vn + j]` (`vn` — 8/16/32),
а не с шагом chunk'а. Тесты-стражи:

* `bench_backend --check` — GPU-батч против CPU-батча на длинах
  8/11/16/24/31/32/44 (Q4_K и Q6_K), допуск 1e-2; на коде до 0199 падают
  8 случаев с ошибкой порядка самих сумм (0,25–0,75 при max|ref| 0,4–0,6),
  после — 4e-8…1e-7.
* `bench_backend --api-tokens PATH --backend simd|hybrid` +
  `tests/vtm/test_hybrid_api_parity.py` — ровно путь чата: `cache_prefix=1`,
  `prefill_batch=256`, жадный SAMP, три промпта (15/24/45 → prefill 14/23/44),
  каждый дважды (второй раз — из кэша префикса). Один бэкенд на процесс:
  режим Metal глобален. На коде до 0199 тест падает, после — токены
  совпадают с simd побитово, включая второй прогон из кэша.

Парный замер после правки (`bench_backend --metal`, M1 Pro, занятая машина,
min из 2, порядок чередуется): prefill 64 — 19,1 → 38,9 ток/с (**2,03×**),
prefill 128 — 15,4 → 35,5 ток/с (**2,31×**), декод 19,5 → 19,9 ток/с (1,02×),
точность — argmax 3/3 и 291/291, пачка Δ 2,05e-5. `chat.py` на обоих
бэкендах даёт один и тот же текст.

**Диагностика C-ABI.** `bench_backend --api-tokens PATH --backend simd|hybrid`
печатает `PROMPT`/`TOK` для трёх промптов; запускать по одному бэкенду на
процесс (глобальный режим Metal).

#### Фаза 3 (задача 0204): весь токен — один командный буфер

Диагноз фазы 2: на слой приходилось 4 ожидания CPU (после QKV, после O,
после gate+up, после down), 145 командных буферов на токен. Причина — RMSNorm,
RoPE, SiLU, KVW и attention считались на CPU, а перед каждой такой
инструкцией интерпретатор обязан был дождаться GPU. Итог: декод 8,5 ток/с
против 20,8 у CPU, хотя отдельные GEMV уже были не виноваты.

Что сделано:

1. **RMSNorm/RMSH, RoPE, SiLU, MUL, ADD, CPY, KVW и attention декода — MSL.**
   Новые ядра в `src/vtm/vtm_metal.metal`: `vtm_rmsnorm` (один threadgroup на
   строку, f32-сумма с `simd_sum` и добором через threadgroup-память; общий
   для RMSN и RMSH), `vtm_rope` (CPU считает cos/sin в double — в MSL нет
   fp64, — а ядро применяет пары), `vtm_silu`, `vtm_mul`, `vtm_add`,
   `vtm_copy`, `vtm_kvw` (запись K/V в слот кольца) и `vtm_attn_decode`
   (q_len == 1: один warp на голову, online-softmax в регистрах, K/V читаются
   из кольцевого кэша, causal-граница и окно — те же, что у CPU-пути).
2. **Граф токена.** `backend_metal.m` получил сессию
   `vtm_metal_graph_{begin,end}` и постановку операций
   (`vtm_metal_graph_gemv/norm/rope/silu/mul/add/copy/kvw/attn`). `interp.c`
   при режиме FULL и подходящей программе кодирует ВСЕ инструкции токена в
   ОДИН `MTLCommandBuffer` (≈723 dispatch'а, 36 слоёв) и ждёт один раз —
   перед `SAMP`. Между слоями CPU не ждёт вообще.
3. **Zero-copy для активаций.** Граф привязывает тензоры арены
   `newBufferWithBytesNoCopy:` и передаёт смещение тензора в
   `setBuffer:offset:`; staging-копий нет. Кэш привязок — 4096 записей
   (было 1024: графу нужно ~1000 активаций + 254 матрицы). Если no-copy
   невозможен, граф отказывается (копия дала бы молча неверные результаты —
   GPU писал бы в копию, а CPU читал арену).
4. **Откат.** Любая ошибка (нет zero-copy, командный буфер не завершился)
   выбрасывает НЕзакоммиченный граф; `interp.c` перезапускает программу токена
   с нуля CPU-путём (KVW идемпотентен, EMB перезаписывает x, сэмплинг ещё не
   исполнялся) и выключает Metal. Тест —
   `VTM_METAL_FORCE_FAIL_GRAPH=1`: `bench_backend --metal` печатает
   «графов потеряно 1», режим off, логиты совпадают с simd **побитово**
   (Δ = 0).
5. **Границы.** Граф включается только если в программе есть kind 4/6/7 и все
   инструкции поддержаны: TMV/MM kind 4/6/7 с n == 1, RMSN/RMSH, ROPE
   (head_dim ≤ 256), SiLU, MUL, ADD, CPY, KVW, ATTN с q_len == 1 и 2D-кэшем,
   EMB (первой) и SAMP/HALT. Триты, Q4 (kind 5), плотные веса, MoE, CONV4/
   GDELTA и prefill пачкой идут прежним путём. Preflight дешёвый: при
   отсутствии матриц kind 4/6/7 Metal даже не инициализируется (компиляция
   MSL не платится на тритовых моделях).

**Замеры.** Парные прогоны `bench_backend --metal runs/q4/3b-q4k.vtm
--metal-new 64` (одна загрузка модели, simd/metal/hybrid чередуются, min из 2).

| декод 64, ток/с | 21,4 | 29,0 | 1,36× |
| prefill 64 пачкой, ток/с | 24,2 | 57,1 | 2,36× |
| prefill 128 пачкой, ток/с | 23,1 | 53,1 | 2,30× |
| точность (3×5) | — | Δ 6,1/4,9/6,3e-5, argmax 3/3 | |

То есть абсолютный ориентир 30+ ток/с достигнут (30,8–31,9 на 16 токенах,
27,5–29,0 на 64), отношение ≥1,5× держится, когда CPU в тех же условиях даёт
≤20 ток/с (окно A); на разгруженном CPU (окно B) metal быстрее в 1,36–1,48×.
Причина, почему декод не уходит выше: GPU-время токена — 34,5 мс, из них ~95%
— чтение 1,7 ГБ весов Q4_K/Q6_K; эффективная полоса GEMV — 60–80 ГБ/с.
Ускорять дальше нужно сами GEMV-ядра, а не синхронизацию: ожиданий в декоде
больше нет (0 `waitUntilCompleted` до сэмплинга).

**Double buffering / два токена в полёте (п. 3 задачи).** Не реализовано
сознательно, и вот измерение: кодирование графа на CPU — **1,84–2,14 мс на
токен** (281–354 мс на 153 токена в бенчмарке), GPU-время — 25–34 мс. CPU
занят 5–8% времени токена и всё равно простаивает; перекрывать нечего. Два токена в полёте для одной
авторегрессионной последовательности невозможны без спекулятивного декода
(0203: паритет есть, ускорения нет). Поэтому оптимум для этой архитектуры —
один командный буфер на токен, что и сделано.

**Что не сработало.** GEMV с 4 строками на warp (переиспользование x вместо
8-кратных повторных чтений) сначала был медленнее: массив
`device const uchar *rp[4]` компилятор вынес в local-память. Переписанный без
массивов (`vtm_q4k_gemv4`, явные указатели и аккумуляторы) в изолированном
`--qk-proj` даёт 0,42–0,82 мс против 0,40–0,71 у однострочного на 11008×2048
(шум занятой машины), на 2048×2048 — стабильно быстрее; но в полном графе CLI
он оказался медленнее: 14,6 против 16,7 ток/с (3 пары прогонов, 32 токена).
Поэтому по умолчанию выключен (`VTM_METAL_GEMV4=1` включает для A/B).
Однострочные ядра Q6_K/int8 не менялись.

**auto.** После 0204 оба условия выполнены (декод и prefill быстрее CPU),
поэтому `auto` = metal (`VTM_AUTO_METAL` в `backend_neon.c`); вернуть прежний
simd — `VTM_AUTO_METAL=0`, hybrid — явный `VTM_BACKEND=hybrid`. Hybrid в этих
же окнах на prefill 64 чуть быстрее metal (40,3 против 33,8 в окне B): в FULL
часть мелких матриц пачки идёт поштучным GPU-путём. На декоде hybrid остаётся
CPU-скоростью.

**Холодный старт (важно для одноразового CLI).** Первый токен в процессе
платит компиляцию MSL (0,14–0,23 с) и zero-copy привязку весов (~1900
`MTLBuffer`) + активаций графа (ещё ~1000). В одноразовом `vtm run --max-new 8`
это видно как «metal 6,4 ток/с против simd 10,8»: 8 токенов короче, чем
разовая инициализация. В установившемся режиме (сервер, много запросов) эта
цена не входит в ток/с — именно его и меряет `bench_backend --metal`, где
прогоны прогреты. Для коротких одноразовых промптов быстрый путь — явный
`VTM_BACKEND=simd`.

**Память.** `copy_bytes = 0`; RSS после prefill 64 — 1999,7 МиБ у simd и
2000,0 у metal (веса не дублируются). `MTLDevice.currentAllocatedSize` —
2276 МиБ: это учёт no-copy регистраций (веса 1896 МиБ + активации арены), а не
копия; критерий отсутствия копий — `copy_bytes ≈ 0` и равный RSS.

**Диагностика.** `VTM_METAL_STATS=1` печатает число токенов/операций графа,
его отказы и время CPU-кодирования; `VTM_METAL_TRACE=1` — по инструкциям
(`graph pc=... op=...`); `VTM_GRAPH_DUMP=1` — максимум/argmax логитов и первый
f32-тензор с NaN/inf (этим искался баг со смещением буфера).

## CLI

```
vtm run model.vtm --tokens 1,2,3 --max-new 8 [--backend ...] [--trace | --trace-summary]
vtm run model.vtm --text "вопрос" [--tokenizer tokenizer.json] [--max-new 8] [--backend ...]
vtm run model.vtm --text "вопрос" --chat [--system "..."]
vtm run model.vtm --text "вопрос" --stream [--max-new 8] [--trace-summary]
vtm inspect model.vtm
vtm bench [--rows N --cols N --iters N] [--scale-block 128|160]
vtm --help
```

`--backend auto|hybrid|metal|simd|scalar|lut|direct` перекрывает
`VTM_BACKEND`; без обоих работает `auto`: metal (весь токен декода одним
графом на GPU) после 0204, если Metal собран и устройство есть; иначе SIMD,
если он собран и CPU его умеет; иначе `scalar-lut243`. Явный `simd` — быстрый
CPU-путь без GPU, `hybrid` — GPU только на батчевый prefill (0198),
`metal` — всё на GPU, `scalar`/`lut` — для отладки и побитового паритета.

Дополнительные опции `vtm run`: `--stop "текст"` (только с `--text`:
остановиться, когда декодированный текст кончается на строку; можно
повторять; в строке понимаются `\n`, `\t`, `\r`, `\\`), `--timeout SEC`
(прервать генерацию, код 124), `--stats` (токены/время/ток-в-секунду в
stderr), `--max-tokens N` (синоним `--max-new`) и `--prefill-batch N` (промпт
пачками по N токенов; `0` — по токену, по умолчанию; пока это только обвязка
0114, ускорение даст ядро 0112 — см. «Один токен за проход»).

### Трассировка (`--trace`, `--trace-summary`)

`--trace` печатает в stderr строку на каждую инструкцию
(`TMV pc=3 seq=12 out=128 dur=3500.0 ns`), `--trace-summary` — сводку по опкодам
(вызовы, время, доля, байты) в конце прогона. Время — не оценка, а реальный замер:
интерпретатор читает `clock_gettime(CLOCK_MONOTONIC)` до и после операции и отдаёт
длительность через хук `vtm_set_trace()`, который срабатывает и на `HALT`, и на
неуспешной инструкции ([0082](../ai/tasks/0082-vtm-metrics.md)).

Оверхед (demo, Apple M1 Pro, ARM64, `-O2`): `--trace-summary` — **+1,6%** при ctx 128
(simd) и **+2,4%** при ctx 512 (simd), на скаляре +0,0…0,2%; это штатный режим для
профиля. `--trace` дорог из-за `fprintf` на каждую инструкцию (+47,4% и +33,1%): его
цена — вывод, а не замер ([0082](../ai/tasks/0082-vtm-metrics.md)). Без
установленного колбэка часы не читаются, поэтому выключенная трассировка ничего не
стоит; `vtm_reset()` её не снимает.

Сводка `--trace-summary` покрывает 99,0–100,9% времени прогона (остаток — цикл
диспетчеризации; [0082](../ai/tasks/0082-vtm-metrics.md)), и именно её использует
`tools/bench_vtm.py`, когда нужна разбивка по операциям вместо оценки дублированием.

`--text` кодирует промпт BPE-токенизатором (`tokenizer.json` формата
HuggingFace), прогоняет модель по одному токену и декодирует вывод обратно в
UTF-8. Без `--tokenizer` путь ищется так: `$VTM_TOKENIZER` (если файл
существует), затем `tests/vtm/fixtures/tokenizer.json` при подъёме от
текущего каталога вверх, затем `./tokenizer.json`. Явный `--tokenizer`
открывается как указан (относительно текущего каталога).

`--stream` (только вместе с `--text`) печатает ответ по мере генерации: после
каждого токена готовый текст сразу пишется в stdout и сбрасывается
(`fflush`), без ожидания конца строки. В stdout в этом режиме попадает
**только текст ответа** (его читают голос и SSE), а служебные строки —
`модель:`, `prompt:`, `вывод:`, `время:`, `стоп-токен:` / `стоп: --stop` — идут
в stderr. Без `--stream` вывод прежний: всё в stdout, текст ответа — в строке
`ответ:`.

Декодер накапливает байты между токенами: BPE-токен может содержать половину
UTF-8 символа (у кириллицы 2 байта, и они легко расходятся по двум токенам).
Наружу отдаются только завершённые символы, недописанный хвост (до 3 байт)
ждёт следующий токен. В конце генерации хвост тоже не теряется: если символ
так и не дописался, вместо сырых байт печатается U+FFFD, поэтому stdout
всегда остаётся валидным UTF-8.

В `--stream` спецтокены (`<|im_end|>`, `<|im_start|>`, `<|im|>` и прочие
`added_tokens` с `special == true`) в текст не попадают, а стоп-токены
обрывают генерацию. Стоп-токены берутся из того же `tokenizer.json`: это
`model.eos_token` и special added_tokens с типовым маркером конца (`im_end`,
`endoftext`, `end_of_text`, `eot_id`, `eos`); в коде их id не захардкожены.
При срабатывании в stderr появляется `стоп-токен: <id>`.

Без `--stream` используется полный декодер `vtm_tok_decode`: он отдаёт все
сгенерированные id до `--max-new` и не фильтрует special/stop-токены.
Остановка по тексту в этом режиме — через `--stop` (или по `--timeout`).

`--chat` оборачивает текст в чат-шаблон Qwen2.5:

```
<|im_start|>system
{system}<|im_end|>
<|im_start|>user
{text}<|im_end|>
<|im_start|>assistant
```

Ход `system` появляется только при `--system "..."` — так же ведёт себя
официальный шаблон Qwen, если системного сообщения нет. Токены
`<|im_start|>`/`<|im_end|>` и их id берутся из `added_tokens`
(`special == true`) того же `tokenizer.json`, в коде их нет: словарь с
другими id даёт другие id в промпте, словарь без этих токенов — ошибку с
кодом 2. Без `--chat` поведение прежнее: в токенизатор уходит ровно текст
из `--text`, символ в символ.

## C-API для хоста

Для сервера и любого не-CLI хоста есть тонкий слой `src/vtm/api.h`
(публичный заголовок — C99; реализация `api.c` использует C11
`<stdatomic.h>`): `vtm_api_open` / `vtm_api_generate` / `vtm_api_cancel` /
`vtm_api_close` / `vtm_api_last_error`.

- `vtm_api_options`: `struct_size`, `backend_name` (или готовый `backend`),
  `max_new_tokens` (0 — без лимита), `eos_token_id` (`< 0` — не задан),
  `cache_prefix` (0 — выключен; см. «Кэш префикса» ниже). Поле заняло первый
  элемент прежнего `reserved[6]`, `sizeof` остался 56 — ctypes-хост совместим
  без правок ([0087](../ai/tasks/0087-api-cache.md)). Неизвестные поля при
  большем `struct_size` игнорируются; ненулевые `flags`/`reserved` — ошибка.
- `prefill_batch` — размер пачки prefill. Умолчание 128 для `opts == NULL` и
  `opts->struct_size == 0`; в заданной структуре `0` — выключатель. Работает и
  с `cache_prefix == 1` (0180): кэшированный префикс восстанавливается, а
  некэшированный хвост считается пачками. Поле заняло элемент прежнего
  `reserved[5]`, `sizeof` не менялся.
- `vtm_api_generate()` без `cache_prefix` на каждом вызове делает `vtm_reset()`
  (позиция, счётчик, состояние SAMP), но переиспользует тензоры и KV-кэш:
  позиции, которые читает ATTN, перезаписываются новым промптом. С включённым
  `cache_prefix` кэш между запросами **не сбрасывается**, а промпт, кроме
  последнего токена, идёт через `vtm_run_cached()` (кэш не умеет отдавать
  выбранный токен, поэтому последний токен прогоняется обычным путём)
  ([0087](../ai/tasks/0087-api-cache.md)). При `prefill_batch > 0` хвост
  считается пачками (0180), см. «Батчевый prefill» выше. Промпт — `int32_t`
  id, без токенизатора; текст декодирует хост.
- Колбэк получает по одному токену; возврат `!= 0` — `VTM_API_STOPPED`.
  Коды `VTM_API_OK` (лимит/конец программы), `VTM_API_EOS` (выбран
  `eos_token_id`, токен уже отдан колбэку) и `VTM_API_CANCELLED` — штатные
  остановки, а не ошибки.
- `vtm_api_cancel()` — атомарный флаг, безопасен из любого потока; отмена
  проверяется между токенами, а не внутри `vtm_run()`. Своих потоков API не
  создаёт; `vtm_api_generate()` — один поток на контекст, второй параллельный
  вызов вернёт `VTM_E_ARG`. `vtm_api_close()` нельзя звать параллельно с
  работающим `generate()`.
- Отмена во время prefill (задача 0185). Пачка `vtm_run_batch()` больше не
  неделима: C-ABI ставит ядру необязательный признак отмены
  (`vtm_set_cancel(m, should_stop, user)`), и интерпретатор опрашивает его
  перед инструкциями пачки и перед переходом к следующей пачке, а в
  поштучном пути (`batch_sequential`) — перед каждым токеном. Отмена
  возвращает `VTM_E_CANCELLED` (новый код `vtm_status`, без изменения
  раскладки `vtm_api_options`), `vtm_api_generate()` переводит его в
  `VTM_API_CANCELLED`. Гранулярность внутри пачки — одна инструкция: на
  плотной 3B это единицы-десятки мс, на MoE с пачкой 256 — дольше (один
  проход инструкции), но не весь промпт. После отмены состояние машины
  частичное: следующий `vtm_api_generate()` начинает с `vtm_reset()` и
  считает промпт заново; снимок кэша префикса при отмене не создаётся
  (`cache_store` не доходит), поэтому кэш не отравляется.

### Кэш префикса (0081, 0087, 0096)

Системный промпт повторяется в каждом запросе, и прогон 512 токенов стоит десятки
миллисекунд — поэтому ядро умеет не считать повторяющийся префикс. K/V префикса уже
лежат в тензорах машины (`KVW` пишет их туда), так что «кэш» — это не копия K/V, а
запись о том, что текущее состояние соответствует прогону ровно `ids[0..n)`: SHA-256
от ids, длина, позиция и снимок состояния сэмплера. Сравнение по хешу, а не побайтово
по ids: копия ids потребовала бы `malloc`, который `vtm_free()` не освободит
([0081](../ai/tasks/0081-vtm-prompt-cache.md)).

- `vtm_cache_prefix(m, ids, n)` — `vtm_reset()` и прогон префикса (на скалярном
  бэкенде пачкой, на SIMD по токену), затем снимок; `vtm_run_cached(m, ids, n)` —
  при совпадении префикса восстанавливает снимок и продолжает с позиции `n`,
  иначе считает всё заново и делает кэшем всю последовательность. `emit` не
  вызывается: это прогон промпта, а не генерация. C-ABI зовёт внутренние
  `vtm_cache_prefix_ex`/`vtm_run_cached_ex` с `prefill_batch` (0180): тогда и
  префикс, и хвост идут пачками, а на SIMD это осознанно не побитовый путь
  (≤1e-5, argmax совпадает).
- После `vtm_run_cached()` состояние машины (позиция, счётчик, история, ГПСЧ и K/V)
  побитово равно состоянию после полного прогона тех же ids на скалярном бэкенде;
  на SIMD с пачками — в пределах точности батчевых ядер.
- Инвалидация: `vtm_reset()`, смена бэкенда, запись `KVW` на позицию меньше длины
  префикса и переполнение кольца KV. `vtm_cache_prefix_len()` и `vtm_cache_stats()`
  отдают длину годного кэша и счётчики попаданий/промахов.

Числа. В ядре на demo (ctx 256, SIMD, префикс 128 + 16 новых токенов): 6,21 → 0,79 мс
на запрос (**7,83×**), прогрев 5,6 мс разово
([0081](../ai/tasks/0081-vtm-prompt-cache.md)). Через C-ABI, промпт 129 токенов:
6,96 → **0,056 мс** на 1 новый токен (**125×**, потолок 129×) и 6,71 → 0,475 мс на 8
новых (**14,1×**); ответы с кэшем и без — побитово те же
([0087](../ai/tasks/0087-api-cache.md)). Python-бэкенд `eva` включает опцию флагом
`EVA_VTM_CACHE=1`; по умолчанию выключена, поведение прежнее
([0096](../ai/tasks/0096-eva-cache-flag.md)).

Ограничения: промпт из одного токена обнуляет снимок; отмена прерывает прогон
хвоста/префикса только на границах инструкций пачки (задача 0185, см. «C-API»);
при `prompt + generation > context_window` кольцо KV инвалидирует снимок —
корректность сохраняется, выигрыш теряется.

### Кэш + пачка: 0180

C-ABI и Python-бэкенд по умолчанию включают `prefill_batch = 128`; чат ходит с
`cache_prefix = 1`, поэтому до 0180 весь его prefill шёл по токену (на SIMD —
побитовый путь кэша). Теперь кэшированный префикс восстанавливается, а
некэшированный хвост считается пачками. Замер — честная пара в одном процессе
(общий page cache, чередование, первый токен, 77-токенный промпт,
`VTM_Q4K_CHECK_OFF=1`):

| модель | было (`prefill_batch=0`) | стало (умолчание 128) | ускорение |
|---|---|---|---|
| 30B MoE, `runs/q4/qwen3-30b-a3b.vtm` | 31,9 с | **13,4 с** | 2,38× |
| 3B Q4_K, `runs/q4/3b-q4k.vtm` | 4,87 с | 4,89 с | ~1,0× (тот же путь) |

На 30B повторный тот же запрос — 0,10 с (полное попадание в кэш: пачки не
запускаются). Ответы на 30B (промпты 32/64/80 токенов, `--max-new 4`) и на 3B
(32/64/96) совпали с поштучным путём: `13 576 38835 374`,
`71816 11 2053 16199`, `2937 3635 264 11682`; на 3B — `13 576 5458 374`,
`71816 11 2053 16199`, `34208 916 279 15678`.

Абсолютные секунды `tools/chat.py --once … --stats` на этом хосте (16 ГиБ,
контейнер 30B — 17 ГБ, соседние агенты) не показательны: первый вопрос
включает холодное чтение экспертов с диска, и TTFT гуляет от 19 до 124 с при
одном и том же коде; в одном окне «до/после» отношение остаётся, а повторный
вопрос — 0,8–2,8 с. Сравнивать только парой в одном окне.

Исключение по 3B (0180) снято в [0189](../ai/tasks/0189-dense-prefill-gemm.md):
батчевое f32-ядро kind 6/7 (0167) действительно было медленнее поштучного
int8-dot (7,1 с против 3,9 с на 64 токенах), поэтому плотный граф шёл по
токену. Теперь у пачки есть int8-dot GEMM — см. ниже.

### Плотный prefill: int8 GEMM (0189)

Плотный prefill 3B Q4_K упирался не в арифметику, а в две вещи: вес читался
на каждый токен и разворачивался в f32 на пачку. В 0189 сделано ядро
`vtm_neon_qk_batch_i8` (`src/vtm/backend_neon.c`):

* строка весов разворачивается в int8 **один раз на строку** и умножается на
  все токены пачки; SDOT даёт 16 MAC за инструкцию против 4 у FMA;
* арифметика, порядок f32-сложения и double-свёртка — буквально те же, что у
  поштучного ядра строки (`qk_i8_row_q4k/q6k`), поэтому результат пачки
  **побитово** равен N вызовам поштучного ядра;
* размер пачки больше не режет гейт «12 токенов» (он был про L1 у f32-ядра):
  предел ставит бюджет активаций по упакованному слоту (0181), умолчание
  `VTM_BATCH_TOKENS=32`, `VTM_BATCH_MB`/слот — верхняя граница.

Замеры (3B Q4_K, `runs/q4/3b-q4k.vtm`, парные прогоны в одном процессе,
`bench_backend --prefill-ttft`, 64 токена, min из 2):

| путь | wall | CPU | ток/с | точность к поштучному |
|---|---|---|---|---|
| по токену (как было в чате) | 3,84 с | 19,5 с | 16,7 | эталон |
| пачка f32-ядром 0167 | 7,10 с | 35,0 с | 9,0 | 1,15e-4 |
| пачка int8 (умолчание) | **3,54 с** | 16,9 с | **18,1** | **0 (побитово)** |
| пачка int8, `VTM_Q4K_BATCH_KERNEL=fast` | 4,06 с | 20,1 с | 15,8 | 1,15e-4 |
| пачка int8/fast, `VTM_Q4K_BATCH_I8=1` | **2,12 с** | 9,9 с | **30,2** | 2e-3 |

`--prefill-check` на этой модели: было `max|Δlogits| = 1,154e-4` (FAIL, argmax
совпадал), стало **0,000e+00** (ok). Дело в дискретности квантования
активаций: расхождение 1e-7 на строку после 36 слоёв даёт 1e-4 на логитах, и
никакая «почти та же» арифметика порог 1e-5 не держит — только побитовая.

Почему не 100 ток/с. На этой машине (M1 Pro, 10 ядер, 8 потоков) предел
ядер — SDOT 8,1 G/s на поток, но в смешанном потоке инструкций (загрузки
активаций, cvt, fma, масштабы) реально выходит 13–14 G MAC/s на поток, то есть
~60–70 G MAC/s на процесс: 3B Q4_K — это 3,09 G MAC на токен, значит 18–20
ток/с. Три плоскости int8 (цена побитовости) стоят ровно вдвое: с одной
плоскостью то же ядро даёт 28,5 G MAC/s на поток. Для сравнения, llama.cpp на
**этом же CPU** (тот же класс модели, `-ngl 0 -t 8`) считает промпт на 36
токенов 37–39 ток/с, на 89 — 20–23 ток/с, а `ollama` с Metal GPU — 182–393
ток/с (и 2777–3231 ток/с при попадании в кэш префикса). То есть цель «≥100
ток/с» для CPU-пути на этой машине недостижима в принципе: это уровень GPU.

Свип размера пачки (тот же стенд, 64 токена): C=8 — 4,18 с (CPU 18,6 с),
C=16 — 4,05 с (17,9), C=32 — **3,72 с** (17,0), C=64 — 3,83 с (16,9). L1-обрыв,
как у f32-ядра в 0168 (оптимум 8–12), здесь не наступает: рабочее множество
int8-ядра — строка весов (2 КБ) плюс квантованные активации, а не f32-копия
активаций пачки (cols·C·4). После 32 токенов время на токен перестаёт падать.

Переключатели: `VTM_BATCH_DENSE=0` — прежний путь по токену (A/B),
`VTM_BATCH_TOKENS` — потолок пачки плотного графа (4…256),
`VTM_Q4K_BATCH=0` — выключить батчевые ядра kind 6/7 совсем,
`VTM_Q4K_BATCH_I8=0|1|2|3` — ступень/плоскости (0 — f32-ядро 0167),
`VTM_Q4K_BATCH_KERNEL=fast` — быстрый вариант без побитовости.

### Prefill 0211: кэш растёт с историей, пачка — от RAM

Задача 0211 пришла с живыми замерами чата: 40 токенов — 0,34 с, 154 — 6,3–9,9 с,
251–268 — 7–13,3 с, то есть «провал в 4–8 раз на токене между 40 и 154». Разбор
показал, что обрыва в батчевом prefill нет: на 3B Q4_K время на токен ровное на
всех длинах (таблица ниже), а «118 ток/с на 40» — это попадание в кэш префикса:
системный промпт у свежего диалога тот же, и считался только хвост.

Две настоящие причины.

1. **Снимок кэша не продлевался.** `vtm_run_cached_ex()` на попадании намеренно
   оставляет СТАРЫЙ короткий префикс (ветвление «тот же префикс, другой хвост»
   этого и хочет). Для чата с растущей историей это патология: после первого
   вопроса снимок навсегда оставался на его длине, и каждый следующий запрос
   пересчитывал всю историю от первого вопроса — отсюда 6–13 с при 154–268
   токенах. C-ABI теперь после прогона префикса зовёт
   `vtm_cache_prefix_extend()` (`api.c` → `interp.c`): снимок двигается вперёд до
   только что посчитанных токенов, но по-прежнему начинается с токена 0.
2. **Бюджет активаций пачки был 96 МиБ.** У 3B Q4_K упакованный слот — 609 КиБ
   на токен, то есть фактический `C` был 12: промпт 250 токенов резался на 21
   пачку и 21 раз читал 2 ГиБ весов. Теперь бюджет — RAM/16 (16 ГиБ → 1 ГиБ,
   `VTM_BATCH_MB` переопределяет), потолок `VTM_BATCH_TOKENS` — 256: 250 токенов
   считаются одной пачкой, 500 — двумя. Память под пачку на 3B — ~156 МиБ.
   Выигрыш оказался скромным (веса — доли секунды из 7–8 с, ниже): prefill
   упирается в арифметику, а не в повторное чтение.

Замер (`bench_backend --prefill-ttft … --prefill-batch-only`, 3B Q4_K, парные
окна, машина под чужой нагрузкой load 7–8). TTFT — весь промпт одной пачкой,
включая последний токен:

|---|---|---|---|
| 32  | 1537 (20,8) | 1675 (19,1) | 1921 (16,7) |
| 48  | 2218 (21,6) | 1439 (33,4) | 1583 (30,3) |

simd 12,56/28,91 → 13,11/32,31 с (разница в пределах дрейфа нагрузки).

Кэш через C-ABI (`bench_backend --api-cache`, один контекст, `cache_prefix=1`,

То есть повторный запрос — это один декод-токен (35–185 мс), а запрос с

это отдельная работа по GEMM (батч-тайлинг), а не «правильно порезать промпт».

Точность. CPU-пачка (int8-ядро 0189) побитова поштучному пути: `--prefill-check`
на 3B — max|Δlogits| = 0, argmax совпадает. Metal-батч — f32-накопление:
Δ = 2,43e-5 на логитах (argmax 291/291), это выше строгого 1e-5 из 0211, но
укладывается в проектный допуск 1e-2 (0204); для побитовости нужен
`VTM_BACKEND=simd`. `bench_backend --check` (включая Metal GEMM 8/11/16/24/31/32/44)
зелёный.

GEMM (по умолчанию 32), `VTM_METAL_GEMM_RPT=1..16` — строк на threadgroup
(по умолчанию 16; 32 на этой машине даёт неверный результат на NT=32).

### Декод: потоки, память и полоса (задача 0201)

Задача ставилась так: декод 3B Q4_K даёт 17,5 ток/с при 8 потоках и 33 ГБ/с
полосы из ~200 ГБ/с у M1 Pro, значит «упирается в память». Замеры 0201
показывают, что это не так — и что именно надо крутить.

**Что на самом деле упирается.** Проба `bench_backend --qk-proj` считает
ядра декода на реальных формах модели, блоки синтетические и лежат в памяти
(никакой подкачки), поэтому она меряет ядро, а не файл:

| потоков | мс/токен | ГБ/с (1,98 ГБ весов на токен) |
|---|---|---|
| 1 | 220,0 | 9,0 |
| 2 | 115,1 | 17,2 |
| 4 | 58,9 | 33,6 |
| 6 | 41,9 | 47,2 |
| 8 (P-ядра) | **34,0** | **58,3** |

Масштабирование почти линейное до 8: пропускная способность на поток 8,8 ГБ/с
и она **не растёт** от добавления потоков, а 8 потоков дают 8×9 ГБ/с. Будь
дело в полосе, 6 потоков уже упирались бы в потолок. Значит предел — счёт на
поток (SDOT + загрузки активаций занимают конвейер), а полоса — следствие.

**1. Потолок параллелизма: 6 → P-ядра.** В `vtm_parallel_rows()` стоял
зашитый `VTM_PAR_THREADS_TOP 6` (замер на другой, 1.5B-форме), поэтому
`VTM_THREADS=8` всё равно давал 6 потоков. Теперь потолка нет: берётся
`vtm_threads()`, а он по умолчанию — число **P-ядер**
(`sysctlbyname("hw.perflevel0.physicalcpu")`, на M1 Pro 8; нет ключа — как
раньше, онлайн-ядра). E-ядра не берутся по умолчанию: барьер задания ждёт
самый медленный поток, и одно E-ядро (втрое медленнее) добавляет к заданию
свою порцию — замер: 9 потоков дали 46–54 мс/токен против 34–37 на 8,
10 потоков — 46–66. Явно: `VTM_THREADS=10`.

Парный замер до/после (одно окно, `--qk-proj`, min из 4):

| потоков | было (пул 6) | стало (пул 8) | |
|---|---|---|---|
| 1 | 220,0 мс | 221,1 мс | 1,00x (потолок не при чём) |
| 4 | 58,9 мс | 59,5 мс | 1,00x |
| 8 | 41,7 мс | **36,5 мс** | **1,14x** |

**2. SiLU вектором.** `--trace-summary` на 3B: `SILU` — 24,4 мс на 13
проходов (1,84 мс на токен, 3,7% декода; 51 мкс на вызов 11008 значений).
Считался скалярным `silu_scalar()` с `exp()` в double на элемент. Добавлен
`silu_neon` (backend_neon.c): `e^t` для f32x4 приведением `t = n·ln2 + r`,
многочленом 6-й степени (|ошибка| ≤ 3e-9 на |r| ≤ ln2/2) и масштабом `2^n`
сдвигом в экспоненту; итог 24,4 → **5,2 мс** на те же 468 вызовов (4,7x).
Точность: `--logits` на 3B (f32-путь, эталон — scalar-lut) даёт
`max|Δlogits| = 6,2e-06` против 8,6e-06 у прежнего пути — то есть правка
внутри шума f32-пути, argmax совпал. `VTM_Q4_I8`-путь не затронут.

**3. Что проверили и что не помогло** (отрицательные результаты — тоже
результат, они снимают вопрос):

* *Опережающее чтение строк* (`__builtin_prefetch` блоков на 3 вперёд,
  `VTM_GEMV_PF=1`): 1 поток — 1,63 против 1,62 мс, 4 потока — 0,430 против
  0,430 (10 и 12 повторов). Строки идут в памяти подряд, аппаратный префетчер
  M1 тянет этот поток сам, а ядро упирается в инструкции: лишний `prfm` на
  16 байт весов — это +4% инструкций и ноль пользы. По умолчанию выключено.
* *Две-четыре строки на поток* (общий `x` на две строки, у каждой свои 8
  аккумуляторов): -7% на горячей форме (0,311 против 0,287 мс). Причина
  измеримая: 16 аккумуляторов + 4 вектора масштабов + 6 векторов активаций не
  влезают в 32 SIMD-регистра — clang выдал 563 обращения к стеку против 14 у
  однострочного ядра. Вариант с 4 аккумуляторами на строку влезает, но меняет
  порядок f32-сложения, а на нём держится побитовое равенство декода и
  батчевого prefill (`--prefill-check` = 0,000e+00) — не стали.
* *`VTM_Q4_PREFETCH`* (madvise WILLNEED): для 3B Q4_K он инертен — в модели
  нет тензоров kind 5, `q4_prefetch()` вызывается только на упакованном Q4.
  Подозрительные 0,26 ток/с на 1 потоке — не madvise: это page fault/своп
  (замер: 8 токенов = +63 223 pageins и +104 901 swapin при 16 ГиБ RAM и
  ~11,5 ГиБ занятого свопа).
* *Меньше плоскостей int8*: `VTM_Q4_I8=2` даёт +15% на Q4_K (0,245 против
  0,287 мс), но это уже другая точность (`Δ` ядра 1,0e-05 против 1,2e-07).
  Умолчание оставлено 3 — побитовость к f32-эталону важнее.

**4. Живой декод на этой машине.** Декод читает 1,98 ГБ весов на токен из
mmap; при занятой памяти страницы вытесняются, и время уходит в page fault.
Парный прогон 3B Q4_K, 9+8 токенов, min из 6, `--trace-summary`: было
808 мс, стало 833 мс (в пределах разброса 808–913). То есть выигрыш ядра
(1,14x) в живой декод **не переходит** — узкое место здесь не ядро. Для
сравнения, проба без подкачки на тех же формах даёт 34 мс/токен против
47 мс/токен живьём.

Переключатели: `VTM_THREADS` (1..10; по умолчанию P-ядра), `VTM_GEMV_PF=1` —
префетч строк, `VTM_Q4_I8=1|2|3` — плоскости int8 (точность/скорость),
`VTM_SILU=0` — прежний скалярный SiLU (побитово как до 0201; точность
векторного проверена отдельным юнит-замером: max|Δ| = 9,5e-07, max|Δотн| =
2,3e-07 на сетке [−10, 10], `−inf → 0` и `+inf → +inf` как у скаляра).

### Спекулятивный декод ([задача 0203](../ai/tasks/0203-speculative-decode.md))

Идея: 0,5B-черновик (Qwen2.5-0.5B-Instruct) предлагает K токенов, целевая
модель (3B/30B) проверяет их **одним** вызовом `vtm_run_batch()` и отдаёт
argmax каждой позиции; совпавший префикс принимается, к нему добавляется
токен цели, при расхождении — откат на принятый префикс. На greedy выход
обязан совпасть с обычным декодом **токен в токен** — это и проверяется.

**Почему понадобился C-помощник.** Публичный C-ABI (`api.h`) не отдаёт
argmax на каждой позиции пачки: `vtm_run_batch()` не вызывает `emit` (это
prefill), а после пачки в машине остаются логиты только последнего токена.
Но `op_samp()` кладёт выбранный токен в историю повторов машины
(`samp_hist`) на **каждом** SAMP, в том числе внутри пачки; для жадного SAMP
это ровно argmax позиции. `tools/vtm_spec_probe.c` (новый файл, `src/vtm` не
тронут) подключает `vtm_internal.h` так же, как это делают
`tests/vtm/test_vtm.c`, линкуется с готовым `libvtm.a` и отдаёт наружу
`prefill`/`feed`/`batch`/`rewind`. Собирается из Python (`eva/speculative.py`)
тем же `cc`, что и `libvtm.dylib` в `eva/backends/vtm_backend.py`
(`EVA_VTM_SPEC_PROBE` — готовая библиотека, `EVA_VTM_CC` — компилятор).

**Откат — это `vtm_set_position()` назад.** KV-кэш адресуется глобальной
позицией, `ATTN` читает только позиции до текущей, а `KVW` перезаписывает
строку при следующем токене, поэтому копировать K/V не нужно. Штраф за
повторы принудительно выключен (`repetition_window = 0`), иначе история
увидела бы отвергнутые черновые токены; помощник умеет сохранять и
восстанавливать историю (`vtm_spec_hist_*`), но декодер этим не пользуется,
потому что при выключенном штрафе она на выход не влияет.

**Формула раунда.** Состояние обеих машин — KV принятого префикса и
`pending` (argmax следующей позиции, ещё не выданный). Итерация:

* `pending_target != pending_draft` — выдать токен цели, скормить его обеим
  машинам, раунд кончился (спекулировать было нечем);
* иначе выдать `pending_target` (B), черновик генерирует ещё K−1 кандидатов
  (`D1..D_{K-1}`, K−1 форвардов), цель считает пачку
  `[B, D1, ..., D_{K-1}]` (позиции p+1..p+K) и отдаёт `y[0..K-1]`:
  `y[i]` проверяет `D_{i+1}`, `y[K-1]` — бонус цели. Принимается префикс
  `D1..Dj`, выдаётся он и бонус `y[j]`; бонус становится следующим
  `pending_target` (он же первый токен следующей пачки — поэтому лишнего
  поштучного прохода цели нет).

Выход за раунд: `2 + Σ_{i=1..K-1} a^i` токенов (B + принятые + бонус), цена —
пачка K токенов цели + K−1 (или K) форвардов черновика.

**Замеры.** Машина M1 Pro, 16 ГиБ, в момент замеров была занята (load average
≈11, своп 7,9 из 9,2 ГиБ), поэтому абсолютные ток/с ниже обычных; сравнение —
парное, в одном процессе, min/один прогон.

3B Q4_K, `--backend simd`, K=4, 24 новых токена, три промпта:

| промпт | токенов | target-only, ток/с | spec, ток/с | acceptance | ср. принятый префикс | паритет |
|---|---|---|---|---|---|---|
| 1 (рус.) | 39 | 6,8 | 4,6 | 0,57 | 1,71 | да |
| 2 (англ.) | 32 | 8,1 | 5,3 | 0,72 | 2,17 | да |
| 3 (код) | 36 | 7,6 | 5,0 | 0,76 | 2,29 | да |

То есть спекуляция **в 1,5 раза медленнее** обычного декода при acceptance
57–76% и точном паритете. Разбор раунда (промпт 1): 7 пачек по 224 мс
(1,57 с), 4 отказа на первом токене + prefill (2,28 с), черновик 1,31 с;
24 токена за 5,26 с против 3,50 с у target-only.

CPU-время (отдельный прогон, 17-токенный промпт, 14 новых токенов, CLI
`python3 -m eva.speculative`): target-only 1,6 с wall и **10,2 с CPU**,
спекуляция 2,2–2,5 с wall и **15,1 с CPU**. То есть на тот же выход
спекуляция тратит ~1,5× CPU: черновик — это дополнительная арифметика, а
батчевое ядро CPU не экономит (см. ниже). Тот же прогон дал acceptance 1,00
(промпт простой, «Столица Франции — это»), поэтому разброс acceptance по
промптам — 0,57…1,00, а не «всегда 70 %».

Почему так — не «плохая реализация», а два измеренных свойства машины:

1. **Пачка на CPU не дешевле поштучного декода на токен.** 3B Q4_K, simd,
   3 плоскости int8: один токен 48 мс; пачка K=4 — 190 мс против 4×48=192 мс
   (×1,00); K=8 — 273 мс (×1,4 на токен); K=16 — 516 мс (12+4). Батчевое
   int8-ядро `kind 6/7` даёт ~65–83 Г MAC/с (3 плоскости / 1 плоскость), а поштучный декод и так
   memory-bound на 64 Г MAC/с: вес читается один раз, но арифметики на пачку
   столько же, сколько у K отдельных GEMV. На `hybrid` (Metal, GEMM только
   для пачки ≥8) K=12 стоит 296 мс (24,7 мс/токен, ×1,9–2,4 к поштучному в
   том же окне) — это единственный режим, где пачка реально дешевле, но
   выигрыш съедает черновик.
2. **Черновик здесь всего вдвое дешевле цели, а не в 6 раз.** 0.5B Q4_1 на
   этой машине — 23–25 мс/токен (не 8 мс, как ждёт «в 6 раз меньше весов»:
   маленькие матрицы не добирают полосу, а lm_head — 136 М MAC из 420 М на
   токен). При K=4 раунд стоит 190 мс пачки + 3×23 мс черновика = 259 мс и
   даёт при a=0,7 около 3,5 токена — 73 мс/токен против 48 мс. Отсюда 0,66×.

Сводка: при `a≈0,8` спекуляция на 3B окупается только если пачка дешевле
поштучного прохода хотя бы в 2,5–3 раза на токен; на этой машине этого нет
ни на одном бэкенде (кроме `metal` при K≥16, где мешает цена черновика).

30B MoE (`qwen3-30b-a3b.vtm`, 18,5 ГБ > 16 ГиБ RAM — файл живёт в mmap, часть
страниц вытесняется): загрузка 74 с, prefill 8 токенов 6,0 с (первый, холодный;
на тёплом page cache те же 10 токенов ≈1,2 с), поштучный форвард 0,6–1,1 с,
пачка 4 токена 2,5 с (0,63 с/токен, ×1,4 к поштучному).
Здесь пачка выгодна (у экспертов общий читатель), но при K=4 выигрыш ещё мал:
раунд 2,5 с + 3×0,1–0,2 с черновика на 3–4 токена — примерно паритет с
0,6–1,1 с/токен у цели. Для ×1,3 нужно K≥8–16 (тогда экспертов на пачку
меньше), но столько же форвардов делает и черновик, а RAM не держит 30B и
черновик одновременно без свопа — замер с K=16 на этой машине не снят (см.
«Риски» отчёта задачи 0203).

Важно: мета 30B — `temperature 1.0`, `top_k 8` (у 3B — `sampling: greedy`).
Спекулятивный декод проверяет argmax, поэтому и черновик, и цель принудительно
переводятся в жадный режим; `--speculative` в чате печатает предупреждение,
что выход тогда отличается от обычного (сэмплирующего) чата. Паритет на 30B
проверялся бы против обычного декода с `VTM_TEMPERATURE=0`; без rejection
sampling (этап 5) спекуляция с температурой не поддерживается.

**Что включено.**

* `eva/speculative.py` — `SpeculativeDecoder` (два контекста в одном
  процессе), `SpecStats` (acceptance, средний префикс, времена по фазам),
  CLI замеров `python3 -m eva.speculative`;
* `tools/chat.py --speculative --draft PATH [--spec-k K]` — тот же чат, но
  `inner.stream_ids` подменён спекулятивным генератором; шаблон, стриминг,
  рассуждение и страж зацикливания остаются прежними, `--stats` печатает
  acceptance;
* `tests/test_speculative.py` — самоспекуляция на tiny-модели (паритет,
  статистика), конфигурация CLI, паритет на 3B под `EVA_SPEC_MODELS=1`.

**Ограничения.** Только greedy: помощник отдаёт argmax, а не вероятности,
поэтому rejection sampling с температурой не реализован (этап 5 задания
отвергнут осознанно — без логитов он был бы «на глазок»). Черновик
`runs/q4/0.5b-q4.vtm` — Q4_1, а не Q4_K: все доступные GGUF
`Qwen2.5-0.5B-Instruct` в Q4_K_M (Qwen, bartowski, lmstudio) содержат
тензоры **Q5_0**, которые `tools/gguf_import.py` отвергает, а расширение
импортёра — вне зоны задачи. Q4_0 из официального репозитория импортируется
как Q4_1 (авто-режим) и на роль черновика этого достаточно: acceptance
считается по совпадению argmax, а не по качеству текста.

### Чат-шаблон и бюджет рассуждений (задача 0200)

`tools/chat.py` и `tools/chat_server.py` ходят в `VtmBackend`, а он до 0200
собирал промпт как `role: content` + `assistant:`. Это переносимый дефолт для
демо, но **не** ChatML Qwen: модель не видит структуру реплик и не отключает
рассуждение. На 30B размышление идёт теми же ~1–2 ток/с, что и ответ, поэтому
300 токенов `<think>` — это минуты до первого слова, а если `max_tokens`
кончается раньше — ответа нет вовсе.

Теперь `eva/chat_template.py` (без Jinja, только stdlib):

- рендер ChatML: `<|im_start|>role\ncontent<|im_end|>\n` +
  `<|im_start|>assistant\n`;
- `enable_thinking=False` — после `assistant` пустой **закрытый** блок
  `<think>\n\n</think>\n\n` — ровно так рендерит официальный шаблон Qwen3;
  модель отвечает сразу. `enable_thinking=True` — только `assistant\n`:
  модель открывает `<think>` сама;
- шаблон включается автоматически, если рядом с `tokenizer.json` есть
  `tokenizer_config.json` с ChatML-шаблоном (`<|im_start|>`); для
  `runs/q4/qwen3-tokenizer.json` это `qwen3-tokenizer_config.json` (в нём
  есть `enable_thinking` — модель «умеет рассуждать»). В
  `runs/q4/tokenizer.json` (Qwen2.5) ChatML есть, а `<think>` нет.
  Не-ChatML шаблоны игнорируются — остаётся прежний `role: content`
  (`format_chat_prompt`). Ручной `prompt_builder` важнее автоматики,
  `VtmBackend(chat_template="plain")` — аварийный выключатель;
- `/no_think` в последнем сообщении пользователя — опция
  (`no_think_suffix`, по умолчанию выключена): пустого закрытого `<think>`
  достаточно, а суффикс меняет текст запроса.

Бюджет (`--think --reasoning-budget N`, по умолчанию 256):

1. первый прогон ограничен N токенами — это рассуждение;
2. если модель не закрыла `</think>` сама, рассуждение закрывается
   принудительно (`</think>\n`), и **вторым прогоном** досказывается ответ:
   промпт `…assistant\n<think>рассуждение</think>\n`, лимит — `--max-tokens`;
3. модель закрыла `</think>` сама — второй прогон продолжает с этого места;
   первый прогон закончился EOS — ответ уже целиком получен, второго нет.

Поэтому `max_tokens` — лимит **ответа**, а полный лимит новых токенов —
`reasoning_budget + max_tokens`. Это же — потолок C-контекста
(`_native_token_limit`): без него C-рантайм обрезал первый прогон по
`max_tokens`, и бюджет 64 молча становился 32 (поймано на 30B).

В API: `VtmBackend(think=True, reasoning_budget=64)`; `chat`/`stream_chat`
считают `max_tokens` лимитом ответа, `usage` несёт
`reasoning_tokens`/`answer_tokens`. `tools/chat_server.py` получает
`--think`/`--reasoning-budget`, UI по-прежнему сворачивает `<think>` в
«рассуждение», а в историю диалога рассуждение не пишется.

Замеры 2026-11-26 на `runs/q4/qwen3-30b-a3b.vtm`
(`VTM_Q4K_CHECK_OFF=1`, `runs/q4/qwen3-tokenizer.json`, 16 ГиБ RAM,
load average 7–12 — машина общая, поэтому разброс):

| режим | промпт | ответ | TTFT | первое слово ответа | декод ответа | всего |
|---|---|---|---|---|---|---|
| без `--think` | 19 ток | 7 ток | 7,5–10,5 с | 7,5–10,5 с | 4,0–6,5 ток/с | 8,5–12,3 с |
| `--think --reasoning-budget 64` | 15 ток | 64 размышл. + 53 | 8,6 с | **55,8 с** | 2,08 ток/с | 81,2 с |

В режиме с рассуждением 37,0 с ушло на 64 токена `<think>`, 18,6 с — на
prefill второго прогона (промпт + рассуждение не попадают в кэш префикса:
кэш хранит состояние после промпта, а не после генерации), 25,4 с — на 53
токена ответа. Ответ досказан до конца (`finish=stop`), блок `<think>` в
ответ не попал (остался в «рассуждении»). Без рассуждения 30B отвечает
«The capital of France is Paris.» — тега `<think>` в потоке нет вообще.
3B Q4_K (`runs/q4/3b-q4k.vtm`, `runs/q4/tokenizer.json`): 7 токенов,
TTFT 13,3 с (включая загрузку контекста), 33 ток/с — ChatML применяется и
там, просто без блока рассуждений (Qwen2.5).

Проверка: `python3 -m unittest tests.test_chat_template -v` (рендер, детект,
бюджет, «ответ не теряется», по умолчанию без `<think>`).

## Что этот путь стоит

Свой рантайм — это **месяцы**, а не дни: полная модель требует RoPE, GQA,
KV-кэш, BPE-токенизатор и отладку численных расхождений. bitnet.cpp уже умеет
это, но не даёт контроля. Мы платим временем за независимость — сознательно.

Первые два этапа дают проверяемый результат за недели, а не месяцы: если
синтетический слой совпал с эталоном, архитектура верна, и дальше это работа,
а не исследование.

## Что не реализовано

Ниже — не «в планах», а честный список того, чего в текущем коде нет; если часть
уже сделана, это сказано явно.

- **Многопоточность.** Внутри ядер она есть ([0077](../ai/tasks/0077-vtm-threads.md)):
  пул `pthread` в `backend_scalar.c` делит TMV/MM по строкам, RMSN — по блокам
  суммы квадратов; `VTM_THREADS=1..10` (по умолчанию — число P-ядер, на M1 Pro
  это 8; E-ядра включаются явно, см. «Декод: потоки, память и полоса»),
  `VTM_NO_THREADS` — откат на serial. Не сделано: `ATTN` и остальные операции
  остаются однопоточными, а базовый `vtm_t` не потокобезопасен (в том числе
  ленивая инициализация LUT243), одну машину нельзя использовать из двух
  потоков. В C-API (`api.h`) есть только `vtm_api_cancel()` — атомарный флаг,
  безопасный из другого потока; `vtm_api_generate()` остаётся «один поток на
  контекст» и своих потоков не создаёт.
- **Кэш промпта.** Кэш префикса есть в ядре (`vtm_cache_prefix` /
  `vtm_run_cached`, 0081), в C-ABI — опция `cache_prefix` (0087), в
  Python-бэкенде `eva` — флаг `EVA_VTM_CACHE=1` (по умолчанию выключен, 0096);
  в `tools/chat.py` кэш включён по умолчанию (`EVA_VTM_CACHE=0` выключает).
  Не сделано: кэш, разделяемый между процессами (для сессий есть отдельный
  механизм снимков — 0079/0083), и дорасчёт хвоста при промахе: несовпавший
  префикс — это полный прогон.
- **KV-кэши вне контейнера.** Вынос сделан ([0101](../ai/tasks/0101-kv-lazy-alloc.md)):
  кэши помечены `VTM_TENSOR_FLAG_KV_CACHE`, payload в файл не пишется, загрузчик
  выделяет буферы в арене. Для 1.5B это 112 МиБ памяти (ctx 2048, kv_dim 256,
  28 слоёв), но не файла; подробности — раздел «KV-кэши: не в файле». Кэп
  суммарного размера и отказ бинарям, собранным до 0101, сделаны в 0118
  ([0118](../ai/tasks/0118-kv-caps.md)); 0110 закрыт как дубликат.
- **Внимание.** `ATTN` уже блочный: онлайн-softmax блоками по 64 ключа,
  память `O(head_dim + 64)`, кольцевое окно `context_window` и законные
  позиции `>= ctx`. Батчевый prefill сделан: `q_len > 1` и
  `--prefill-batch` ([0112](../ai/tasks/0112-prefill-batch.md),
  [0114](../ai/tasks/0114-prefill-cli.md)), батчевые ядра SIMD —
  [0122](../ai/tasks/0122-batched-simd.md), для Q4 — [0162](../ai/tasks/0162-q4-prefill-batch.md).
  Не реализованы SIMD-ядра самого `ATTN`, поэтому prefill упирается в
  арифметику: батч даёт 1,1–1,5×, а не 10×.
- **Батчинг.** Одна последовательность на машину: batch-размерности нет,
  несколько промптов параллельно не обслуживаются. `q_len > 1` — это один
  запрос, а не батч.
- **Сессии KV.** Есть VTMS v1 (0079) и LRU-вытеснение (0083):
  `vtm_api_session_save/load`, снимок восстанавливается побайтово. Нет форка
  сессии, привязки сессии к запросу и сохранения состояния сэмплера: после
  `load` позиция и KV есть, а RNG/счётчики сэмплера начинаются заново.
- **Windows.** Не поддерживается: под `_WIN32` сборка останавливается одним
  `#error` со списком того, что нужно портировать (mmap/fsync каталога/pthread/
  POSIX-таймеры). Прежнего `fread`-пути больше нет. MSVC/gcc под Windows не
  проверялись; AVX2-ядра проверены только под Rosetta 2, ARMv7 и 32-битный NEON
  не поддерживаются. Порядок портирования — раздел «Портируемость».

Кроме этого, не реализованы: экспорт `quantize_embeddings: int8` из
`qat/export.py` (контейнер, компилятор и интерпретатор int8 уже умеют),
загрузчик модели в C (`.vtm` собирает `tools/vtm_compile.py`), per-call
параметры сэмплинга (только из меты при загрузке), beam search, проверка
перекрытия тензоров, SIMD для остальных операций
(ROPE/ATTN/SM/SILU/ADD/MUL/SCAL/EMB/CPY остаются скалярными). Блок
`integrity` реализован, но по умолчанию не пишется. Загрузчик доверяет
пределам `n_elements ≤ 2^30` и размеру файла ≤ 4 ГиБ — это защита от абсурда,
а не от злонамеренного OOM.

## KV-кэши: не в файле (задача 0101)

KV-кэши помечаются в таблице тензоров битом `VTM_TENSOR_FLAG_KV_CACHE` (бит 0 поля
`flags` по смещению 50 записи тензора; раньше это был резерв). У помеченного тензора
`offset = 0`, payload в секцию данных не пишется, а загрузчик выделяет буфер
`n_elements` float в арене через `calloc` (нули = пустой кэш).

Почему: кэш на весь контекст — это 28 × 2 × 2048 × 256 × 4 = **112 МиБ** для 1.5B,
то есть 13% файла пустых буферов. Замер: контейнер 1,5B-раскладки с плотными
эмбеддингами 1296,1 → 1184,1 МиБ,
загрузка 75 → 51 мс, RSS после загрузки 487,6 → 264,0 МиБ.

Совместимость: для этого расширения версия контейнера не менялась (v0.2);
v0.3 отличается только шириной смещений. Старые контейнеры с кэшами внутри
читаются прежним путём. Для старых бинарей сделан **явный отказ** (ADR 0015): писатель
ставит header-флаг `VTM_HEADER_FLAG_KV_OUT_OF_FILE` (0x0004) и `offset = 0xFFFFFFFF`, а
старый загрузчик проверяет `offset % 32 == 0` и падает с `VTM_E_FORMAT` («offset=4294967295
не кратен 32») ещё до чтения данных — вместо мусора в кэше. Суммарный размер KV ограничен
`VTM_MAX_KV_BYTES` (512 МиБ по умолчанию, переопределяется `-D`); превышение — `VTM_E_FORMAT`.

С 0176 тем же путём идут состояния рекуррентных слоёв Qwen3.5 — `CONV4`
(3 прошлых входа на канал) и `GDELTA` (`[Hv, Dk, Dv]`). Роль задаёт бит 3
`flags` (`VTM_TENSOR_FLAG_STATE`, `0x0008`), а не биты 1..2: там хранение
тритов (задача 0057). Загрузчик создаёт буфер `n_elements×4` в арене нулями,
payload в файл не пишется, кэп `VTM_MAX_KV_BYTES` общий с KV. Отличие от
KV-кэша — сброс: `vtm_reset()` обнуляет состояния, а K/V по-прежнему
перезаписывает хост (`KVW`). Подробности — [qwen35.md](qwen35.md).

## Паритет и бэкенды

Побитовый паритет с Python-эталоном даёт **только скалярный бэкенд** (`max|Δ| = 0`
на 50 случайных конфигурациях). SIMD-ядра переупорядочивают суммирование, поэтому
расходятся на 1e-5…1e-4 (медиана 6,1e-06, p95 2,6e-05, максимум 1,05e-04). При этом
**argmax не меняется** (0 смен из 50): минимальный отрыв top-1 от top-2 в наборе —
8,7e-03, то есть в 41 раз больше худшего расхождения.

Практические правила:
- `parity_random` и `parity_real` гоняют C со `VTM_BACKEND=scalar` (переопределяется
  `VTM_PARITY_BACKEND`), иначе порог 1e-5 бессмысленен;
- замер расхождения бэкендов — `tools/parity_simd.py` (числа, смены argmax, запас
  отрыва); вердикт и подробности — `docs/quantization.md`.

## Портируемость

ВТМ собрана и проверена на little-endian POSIX-хостах: macOS/ARM64 (Apple M1)
и x86-64 (Rosetta 2). Всё остальное — не «работает, но медленно», а осознанно
не поддерживается, и отказ **явный**: big-endian получает
`VTM_E_UNSUPPORTED` при загрузке, Windows — `#error` при компиляции.
Молчаливого чтения мусора нет ни там, ни там.

### Что уже сделано

- **Big-endian.** Контейнер little-endian: `u32`/`f32` лежат в файле как есть,
  и загрузчик читает их без свопинга (`rd32`/`rd_f32` в `src/vtm/loader.c`).
  В mmap-режиме он идёт дальше и отдаёт наружу `float*`/`uint32_t*` прямо в
  отображение (слова тритов, fp32-масштабы, неизменяемые fp32-тензоры) —
  свопинг в функциях чтения этого не спас бы, пришлось бы копировать всё в
  арену и потерять главный выигрыш mmap. Поэтому проверка одна и на входе:
  `VTM_HOST_BIG_ENDIAN` (`src/vtm/vtm.h`) — константа времени компиляции,
  `load_core()` смотрит её **один раз, до разбора контейнера** (не в цикле),
  и возвращает `VTM_E_UNSUPPORTED` с текстом «big-endian хост не
  поддерживается …». В little-endian сборке эту ветвь выбрасывает компилятор,
  в циклах чтения проверок нет вовсе. Эмуляция BE-хоста без BE-железа:
  `-DVTM_HOST_BIG_ENDIAN=1`; в такой сборке `tests/vtm/test_vtm.c` проверяет
  только сам отказ (остальные тесты смысла не имеют — ни один контейнер не
  должен загрузиться). SHA-256 (`src/vtm/sha256.c`) побайтовый и от порядка
  байт не зависит; аппаратное ARMv8-ядро — только LE-AArch64, но на BE оно не
  исполняется, потому что загрузка обрывается раньше. Отдельный случай —
  снимки сессий KV (`kv_store.c`): заголовок у них little-endian, а K/V лежат
  сырыми host-endian f32, то есть снимок и сейчас не переносится между хостами
  с разным порядком байт; при полной BE-поддержке это придётся либо свопить,
  либо явно объявить снимок «для того же хоста».
- **Windows.** `src/vtm/vtm.h` даёт один `#error` со списком того, что нужно
  портировать, — вместо десятков ошибок «нет `sys/mman.h`». Прежний путь
  «под `_WIN32` прочитать файл целиком через `fread`» больше не собирается:
  это и есть честный отказ — сборки под Windows не «сломана», её нет.

### Что не портировано и в каком порядке делать

| # | Что | Где | Почему нельзя «как есть» | Что нужно |
|---|---|---|---|---|
| 1 | Порядок байт | `loader.c` (`rd*`, `fill_tensor_planned`, `plan_tensor`), `kv_store.c` (снимки) | файл LE, хост BE; mmap отдаёт `float*`/`uint32_t*` в отображение; K/V в снимке — host-endian | уже есть отказ; полная поддержка = на BE всегда `can_reference = 0` (копия в арену) + свопинг при загрузке, свопинг снимков сессий, плюс тесты на BE-железе |
| 2 | `mmap`/`munmap`/`madvise` | `loader.c` | POSIX API | `CreateFileMapping`/`MapViewOfFile`; без них — `fread` целиком (память), `madvise(MADV_DONTNEED)` не нужен |
| 3 | `fsync` каталога + `rename` | `kv_store.c` (контракт — `api.h`, ADR 0008) | POSIX-гарантия «temp → fsync → rename → fsync каталога» | `FlushFileBuffers` + `ReplaceFile`/`MoveFileEx(MOVEFILE_WRITE_THROUGH)`; проверить, что снимок сессии переживает падение |
| 4 | Пул потоков на pthread | `backend_scalar.c` | `pthread_*`, `pthread_once`, `clock_gettime` | Win32 threads или `std::thread`; `VTM_NO_THREADS` уже есть как аварийный выключатель |
| 5 | POSIX-таймеры и сигналы | `main.c` (`--timeout`) | `clock_gettime`, `sigaction`/`alarm` | `QueryPerformanceCounter` + `SetConsoleCtrlHandler` |
| 6 | Сборка и CI | весь `src/vtm` | `-std=c99 -Wall -Wextra -Werror`, `__attribute__`, `ssize_t`, NEON/AVX2 intrinsics, VLA | MSVC/clang-cl или mingw, отдельный набор флагов; AVX2 — `_M_IX86`/`_M_X64` и MSVC-intrinsics; `unistd.h`/`sys/stat.h`/`sys/mman.h` → `<io.h>`/`_stat64` |

Порядок: 1 — порядок байт (отказ уже есть, дальше полная поддержка через
копию в арену), 2–3 — файлы и сохранность (mmap и атомарная запись), 4 —
потоки, 5 — таймеры, 6 — сборка/CI. Каждый шаг закрывается тестом на той
платформе, а не обещанием: BE — эмуляцией макроса и затем железом, Windows —
хотя бы компиляцией в CI (mingw).

### Чем это проверяется

```sh
cd src/vtm && make test                      # LE: полный набор
python3 -m unittest discover -s tests        # Python-эталон и инструменты

# big-endian: эмуляция хоста, BE-железо не нужно
make clean && make CPPFLAGS="-D_POSIX_C_SOURCE=200809L -DVTM_HOST_BIG_ENDIAN=1" test_vtm
./test_vtm     # big-endian: загрузчик отказал (VTM_E_UNSUPPORTED)

# Windows: ровно один #error на единицу трансляции, а не каскад
cc -D_WIN32 -I. -c loader.c
```

UBSan на текущей платформе (`-fsanitize=undefined`) указывает на
misaligned-загрузки `words[wi]`/`scales[...]` в `src/vtm/backend_neon.c`: это
цена оптимизации «TRT1 читается прямо из mmap» — слова и масштабы идут по
смещению 2 mod 4. Сборка с `-DVTM_UNALIGNED_LOADS=0` (TRT1 копируется в арену)
UBSan-чистая, но теряет mmap-резидентность тензоров: это выбор между памятью и
формальной чистотой, и решать его нужно в ядрах (загрузка слова через
`memcpy`), а не в загрузчике — отдельная задача.
