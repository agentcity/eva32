# Гибридный ассистент: малая модель + скиллы + большая модель

> Актуально на 2026-11-26.

Архитектура от 2026-11-18. Решение — [ADR 0009](adr/0009-hybrid-router.md).

## Идея

Один вход, три источника ответа. Выбор — по правилам, а не по вкусу:

```
запрос → скиллы (точный ответ из каталога)      ← детерминированно, 0 ₽
       → малая троичная модель (наш голос)       ← дёшево, локально
       → большая модель по API (сложное)         ← дорого, редко
```

Скиллы впереди модели: если вопрос про цену тарифа, ответ не должен зависеть
от фантазии модели. Малая модель — для того, что она умеет: приветствия, тон,
пересказ контекста. Большая — когда нужен общие знания, код, рассуждение.

## Контракт модулей

Пакет `eva/`, только стандартная библиотека Python.

### `eva/types.py`

```python
class Message: role: str; content: str
class Request: messages: list[Message]; meta: dict          # meta: {"user_id", "channel"}
class Route: kind: str; reason: str; confidence: float      # kind: "skill"|"small"|"big"
class Answer: text: str; route: Route; skill: str|None; usage: dict;
              cost_rub: float; latency_ms: int
```

### `eva/catalog.py`

```python
load(path) -> Catalog
Catalog.get(name: str) -> dict|None          # услуга/тариф по имени или синониму
Catalog.all() -> list[dict]
Catalog.search(text: str) -> list[dict]      # грубый поиск по словам
```

Формат `data/catalog.json`: список `{"kind": "tariff"|"service", "name", "synonyms", "price_rub", "period", "limits", "notes", "sources": ["[1]"]}`.

### `eva/skills/`

```python
class Skill:                      # протокол
    name: str
    def match(self, text: str) -> bool
    def run(self, text: str, ctx: dict) -> SkillResult | None   # {"text", "sources", "catalog_ids"}

try_skills(text: str, ctx: dict) -> SkillResult | None          # registry.try_skills
```

Скиллы v1: `pricing` (цена тарифа/услуги), `hours` (часы работы), `refunds`
(возврат), `contacts` (почта, телефон, адрес). Скилл **не зовёт модель**.

### `eva/clients/openai_compat.py`

```python
class OpenAIClient:
    def __init__(self, base: str, key: str, model: str, timeout: float = 60, retries: int = 2)
    def chat(self, messages: list[Message], max_tokens: int = 512) -> ClientResult
    # ClientResult: {"text", "usage": {"prompt_tokens","completion_tokens","cost_rub"}, "raw": dict}
```

Ошибки: таймаут, 5xx, 429 — повтор с backoff; после исчерпания — `ClientError`.

### `eva/classifier.py`

```python
classify(text: str, cfg) -> Route
```

Правила v1 (без модели): длина, наличие маркеров рассуждения («почему»,
«объясни», «сравни», «напиши код», «переведи», «посчитай»), доля латиницы,
вопрос про факт из каталога. Конфиг порогов — в `config.py`.

### `eva/router.py` + `eva/policy.py`

```python
decide(req: Request, cfg) -> Route      # skills → classifier → small/big
answer(req: Request, cfg, deps) -> Answer
```

`policy`: порядок фолбэков (small→big при ошибке; big→small при 429), бюджет
на запрос (`max_cost_rub`), таймауты. Все решения и причины — в `Answer.route.reason`.

### `eva/server.py`

HTTP на stdlib: `POST /v1/chat/completions` — совместим с OpenAI-клиентами,
в ответе дополнительное поле `"eva": {"route": ..., "skill": ..., "cost_rub": ...}`.
`GET /health`. Без внешних зависимостей.

### `eva/telemetry.py`

Каждый ответ — строка в `logs/eva.jsonl`: время, маршрут, скилл, токены, рубли,
латентность. `usage_report(path)` → агрегат по маршрутам и дням.

### `eva/cli.py`

`python3 -m eva.cli ask "..." --explain` — ответ + маршрут + цена.
`python3 -m eva.cli serve --port 8000`.

## Правила

1. Скилл никогда не вызывает модель. Если скилл не нашёл совпадения — молчит.
2. Классификатор не имеет права ходить в сеть.
3. Провайдер больших моделей настраивается через `.env`, не хардкодом.
4. Каждый ответ несёт маршрут и цену — иначе не посчитать себестоимость.
5. Без сети всё работает: клиенты подменяются заглушкой в тестах.

## Метрики под чатом (задача 0145)

Стенд сравнения (`tools/chat_server.py`) показывает под чатом панель: две
колонки метрик по выбранным моделям и строка системы. Панель обновляется после
каждого ответа, внешних ресурсов не грузит, слушает только `127.0.0.1`.

### Откуда числа

| Что | Источник |
| --- | --- |
| размер файла модели | `os.stat().st_size` того же `.vtm` |
| параметры, KV-кэш, словарь, слои, контекст | таблица тензоров и JSON-метаданные `.vtm` (читаются без загрузки модели) |
| тип хранения (trit/int8/fp16) | `kind` тензоров + заголовки сегментов TRT1/INT8 + `quantization.scale_dtype` из меты |
| источник (демо / холодный экспорт / QAT) | `base_model`, `checkpoint`, `step`, `kv_cache` из меты; без меты — эвристика «vocab 128 = демо» |
| бит на параметр | байты весов в файле × 8 / число параметров |
| RSS до/после загрузки | `/proc/self/status` (Linux) или `proc_pidinfo` (macOS) вокруг вызова фабрики бэкенда; пик — `getrusage().ru_maxrss` |
| TTFT | время от старта запроса до первого куска текста |
| prefill | то же время до первого токена (prefill + один шаг декода — рантайм не разделяет их отдельным событием) |
| декод | `elapsed_ms − first_token_ms` |
| ток/с декода | completion-токены / время декода |
| CPU запроса | `time.process_time()` до и после всего запроса (процесс, не поток: две колонки идут параллельно) |
| `VTM_THREADS` | переменная окружения; если не задана — «по умолчанию» (min(ядер, 8)) |
| load average | `os.getloadavg()` |
| свободная RAM | `/proc/meminfo` (`MemAvailable`) или `vm_stat` (free+inactive+speculative) |
| свободный диск | `shutil.disk_usage(корень репозитория)` |
| Ollama `size`/`size_vram` | `GET http://127.0.0.1:11434/api/ps` — только для локальной Ollama; в панели это строка «резидентная копия» |

Чего снять нельзя, того панель не выдумывает: API отдаёт `null`, в UI — «—».
Пример: у Ollama нет ни размера файла на диске, ни числа параметров, ни
KV-кэша в нашем смысле; у заглушек в тестах нет ни загрузки, ни холодного
старта.

### Эндпоинты

- `GET /api/models` — карточка на каждую модель реестра: `disk_bytes`,
  `params`, `vocab`, `layers`, `context`, `kv_bytes`, `kv_in_file`, `storage`,
  `source`, `bits_per_param`, `present`, `loaded`, `rss_bytes` (дельта RSS
  процесса от загрузки, у выгруженной — 0), `load_ms`, `requests` (сколько
  запросов обслужено), `load` (RSS до/после, дельта, пик, время загрузки),
  `unload` (RSS до/после, сколько вернулось, время), `cache_prefix`, `last`
  (метрики последнего ответа). В ответе также `keep_alive` — политика
  автовыгрузки. Абсолютные пути наружу не отдаются: только id из реестра.
- `POST /api/load` и `POST /api/unload` — тело `{"backend": "vtm", "model":
  "<id>"}`; ответ — те же `loaded`, `rss_bytes`, `load_ms`, `requests`, плюс
  `already_loaded`/`was_loaded`, `freed_bytes`, `unload_ms`. Неизвестная
  модель или бэкенд — 400, Ollama — 400 (`load_unsupported`: её памятью
  управляет её процесс), выгрузка во время генерации — 409 (`model_busy`).
- `GET /api/system` — `load`, `cpu_count`, `ram` (total/free/source), `disk`,
  `process` (pid, rss, peak, source), `vtm_threads` (runtime/config), `platform`.
- `POST /api/chat` — прежние события `start`/`delta`/`done`/`error`; в `start`
  добавлено `cold` (модель грузилась этим запросом), в `done` — `prefill_ms`,
  `decode_ms`, `decode_tokens_per_second`, `finish_reason` (`stop`/`eos`/
  `length`), `first_token` («холодный»/«тёплый»), `ttft_gen_ms` (TTFT без
  загрузки: при `cold` это `first_token_ms − load_ms`), `load_ms` (загрузка
  именно этого запроса; у тёплого — `null`), `cache_prefix`, `load`
  (RSS-дельта загрузки), `ollama` (из `/api/ps`); событие `end` несёт
  `metrics`: `wall_ms`, `cpu_ms`, `cpu_cores`, снимок системы и `start_memory`.

### Тонкости, которые важно знать

1. **prefill = TTFT.** Рантайм ВТМ (`vtm_api_generate`) не сообщает отдельно
   момент конца prefill; первый токен появляется после prefill и одного шага
   декода, поэтому панель называет это время prefill и честно показывает его
   же как TTFT, а не выдумывает разницу.
2. **Кэш префикса ВТМ — оценка.** C-рантайм не отдаёт счётчик попаданий
   (`vtm_api_*` его не имеет), поэтому сервер сравнивает текущий промпт с
   прошлым: попадание возможно, когда прошлый промпт целиком входит в текущий
   (кэш переиспользует всё, кроме последнего токена). В ответе стоит
   `"estimated": true`; в UI — «(оценка)». Если кэш выключен — «выключен», если
   настройка ещё неизвестна (модель не загружена) — «—».
3. **RSS-дельта честная только для ВТМ.** Модель ВТМ живёт в процессе
   `chat_server` через `ctypes`, поэтому дельта RSS «до/после загрузки» — это
   её память (вместе с токенизатором и загрузчиком). Для Ollama процесс чужой:
   `proc_pidinfo` его не видит, поэтому размер берётся из `/api/ps`, а RSS
   процесса Ollama — «—».
4. **Дельта RSS может быть 0 или отрицательной.** Если аллокатор
   переиспользовал уже резидентные страницы (или во время загрузки что-то
   освободилось), RSS не вырастет, хотя модель загрузилась. Это не ошибка
   измерения: `rss_before`/`rss_after` — сырые числа, пик процесса и
   `loaded: true` показывают, что загрузка была.
5. **CPU-время — на запрос, а не на колонку.** `time.process_time()` считает
   все потоки процесса; две колонки идут параллельно, поэтому `cpu_cores > 1`
   — норма (работали два ядра).
6. **Сеть.** Единственный сетевой вызов сервера — `GET /api/ps` у Ollama на
   `127.0.0.1:11434`, и только для реального адаптера Ollama. Тесты подставляют
   заглушки без `probe_ps`, поэтому идут без сети.

## Загрузка/выгрузка ВТМ (задача 0166)

Проблема: первый запрос платил за чтение 2,24 ГиБ с диска, и этот TTFT
сравнивался с Ollama, которая держит модель в памяти. Теперь модель можно
загрузить заранее — кнопками «Загрузить»/«Выгрузить» в шапке каждой колонки
или эндпоинтами `/api/load` и `/api/unload`. Кнопки активны только у ВТМ: у
Ollama памятью управляет её процесс, поэтому они disabled.

### Что происходит внутри

| Действие | Что делает сервер |
| --- | --- |
| `POST /api/load` | собирает бэкенд из `tools/chat.py`, зовёт `open()` у `VtmBackend` (C-контекст) и прогревает модель одним токеном через все слои: `open()` только `mmap`-ит файл, а веса в память попадают при первом forward-проходе. Вокруг — `_rss_bytes()` до/после, `time.monotonic()` для `load_ms` |
| `POST /api/unload` | зовёт `close()` у C-контекста, отпускает объект и делает `gc.collect()`; снова замеряет RSS (`freed_bytes`); кэш префикса сбрасывается |
| запрос при незагруженной модели | грузит её сам, как раньше (кнопка ничего не ломает) |
| `--keep-alive N` | по бездействию дольше N секунд выгружает модель (нить-сторож); `0` — держать всегда, без флага — выключено |

Прогрев — часть загрузки: `load_ms` включает его, а в `load` пишется
`opened`/`warmed` (что именно удалось). TTFT загруженной модели уже не
содержит ни чтения весов, ни первого прохода. Для холодного запроса
панель показывает два числа: `TTFT` (всё время до первого токена) и
`TTFT без загрузки` (`ttft_gen_ms = first_token_ms − load_ms`). Первый токен
помечается «холодным», только если модель грузилась этим запросом; после
кнопки «Загрузить» он «тёплый».

### Числа (3B Q4_1, `runs/q4/3b-q4_1.vtm` = 2,24 ГиБ, эта машина)

Замер 2026-11-25, сервер `--keep-alive 0`, вопрос из страницы, компактный
системный промпт (92 токена промпта), `max_tokens=64`. RSS — процесс
`chat_server` (`process.rss` из `/api/system`), дельта — из карточки модели.

| Сценарий | TTFT | Из него загрузка | RSS процесса |
| --- | --- | --- | --- |
| первый запрос **без** предзагрузки | 21,7 с | 9,3 с (`load_ms`) | 35 МБ → 3,76 ГБ |
| «Загрузить» (кнопка / `POST /api/load`) | — | 5,8 с | +2,17 ГиБ (дельта) |
| запрос 1 при загруженной модели | 14,6 с | 0 (`load_ms: null`) | 3,67 ГБ |
| запрос 2 (тот же вопрос) | **1,08 с** | 0 | 3,67 ГБ |
| «Выгрузить» (`POST /api/unload`) | — | 0,03 с | 3,39 → 1,36 ГБ, освобождено 1,89 ГиБ |

Что это значит:

- предзагрузка убирает из TTFT чтение весов: 21,7 → 14,6 с (−7,1 с). В
  холодном запросе 9,3 с из TTFT — это загрузка (видна как `load_ms`), у
  загруженной модели `load_ms` = `null`; остаток разницы меньше 9,3 с, потому
  что первый ответ после загрузки шумит на занятой машине (12,4 с генерации в
  холодном запросе против 14,6 с в загруженном);
- запрос 1 после загрузки платит полный prefill (92 токена, кэш префикса ещё
  пуст), запрос 2 попадает в кэш префикса и отвечает первым токеном за 1,08 с
  — в 13,5 раза быстрее; в панели это строка «кэш префикса: да»;
- выгрузка возвращает ~1,9 ГиБ; остаток (~1,3 ГБ) — освобождённые страницы,
  которые аллокатор macOS оставил себе. При следующей загрузке они
  переиспользуются, поэтому её дельта меньше: 2,17 ГиБ против 3,47 ГиБ у
  первой загрузки в чистом процессе (абсолютный RSS после загрузки в обоих
  случаях ~3,7 ГБ).

**Важно про шум.** Машина была занята параллельной задачей 0165: load average
12–40 на 10 ядрах. Повторные прогоны дали загрузку 5,8–28,7 с, TTFT первого
запроса после загрузки 14,6–53,2 с, второго — 1,08–4,55 с. Направление
стабильно (загрузка уходит из TTFT, тёплый prefilled-запрос — секунды), а
абсолютные числа на загруженной машине завышены в 2–3 раза. Панель поэтому
показывает не только TTFT, но и `load_ms`/`ttft_gen_ms`/`cache_prefix.hit`:
по ним видно, из чего сложилось время в каждом конкретном ответе.

### Как повторить

```bash
python3 tools/chat_server.py --port 8790 --keep-alive 0
# 1. статус до загрузки / загрузка / первый и второй ответ
curl -s http://127.0.0.1:8790/api/models | python3 -m json.tool | head -20
curl -s -X POST -H 'Content-Type: application/json' \
  -d '{"backend":"vtm","model":"runs/q4/3b-q4_1.vtm"}' \
  http://127.0.0.1:8790/api/load
curl -s -N -X POST -H 'Content-Type: application/json' \
  -d '{"question":"Напиши заголовок для поста о весенней скидке на стрижку","sides":[{"backend":"vtm","model":"runs/q4/3b-q4_1.vtm"},{"backend":"ollama","model":"qwen2.5:3b"}]}' \
  http://127.0.0.1:8790/api/chat | grep -m1 '"type":"done"'
# 2. выгрузка и проверка, что память вернулась
curl -s -X POST -H 'Content-Type: application/json' \
  -d '{"backend":"vtm","model":"runs/q4/3b-q4_1.vtm"}' \
  http://127.0.0.1:8790/api/unload
# 3. автовыгрузка: --keep-alive 2 и модель исчезает из «в памяти» через ~2 с
python3 tools/chat_server.py --port 8791 --keep-alive 2
curl -s http://127.0.0.1:8791/api/models | python3 -c \
  'import json,sys; print(json.load(sys.stdin)["keep_alive"])'   # 2.0
```

### Тонкости

1. **RSS-дельта — про этот процесс.** ВТМ живёт в `chat_server` через
   `ctypes`, поэтому `rss_bytes` — её реальная цена; у Ollama этой цифры нет
   (её `/api/ps` отдаёт `size`/`size_vram`).
2. **Освобождение памяти зависит от ОС.** На macOS крупные отображения весов
   возвращаются системе сразу (`freed_bytes` ≈ `rss_bytes`); мелкие
   malloc-блоки ОС может оставить себе — тогда `freed_bytes` меньше дельты,
   это честное число, а не ошибка.
3. **Нельзя выгрузить работающую модель.** Выгрузка не ждёт генерацию: если
   модель занята, ответ — 409 `model_busy`. Автовыгрузка такие модели просто
   пропускает.
4. **Кэш префикса сбрасывается при выгрузке.** Он живёт в контексте модели;
   после повторной загрузки старый промпт — не история попаданий.

## Ответ и рассуждение в UI (задача 0178)

Раньше поле ответа было `max-height: 58vh; overflow: auto` — ответ на 256
токенов обрезался, и его приходилось прокручивать в узком окне. Qwen3 при
этом печатает `<think>…</think>` прямо в поток, и рассуждение занимало экран
вместе с ответом.

Теперь (`tools/chat_server.py`, страница в `PAGE_HTML`):

- **Ответ растёт по содержимому.** У правила `.answer` `max-height: none` и
  `overflow: visible`, `flex: 1 0 auto`: панель становится выше, а не режет
  текст. Высота ограничена только у явно свёрнутого ответа.
- **Свернуть/развернуть.** Если ответ длиннее 520 px, в шапке панели
  появляется кнопка «свернуть»; она вешает на панель класс
  `answer-collapsed` (`max-height: 18rem; overflow: auto`), а текст кнопки
  меняется на «развернуть». Короткому ответу кнопка не нужна и скрыта.
- **Автоскролл при стриминге.** Каждый `delta` и кусок рассуждения тянут
  страницу так, чтобы низ блока ответов (`.grid`) был у нижней кромки окна;
  панель метрик под чатом при этом не притягивается — цель считается по
  `.grid`, а не по концу документа. Флаг `stickToBottom` снимается событием
  `scroll`, когда до этой границы больше 160 px: отлистал — не дёргаем,
  вернулся — автоскролл снова работает. У свёрнутого ответа прокручивается
  сам текст, а не страница.
- **`<think>` разбирается на клиенте.** Сервер отдаёт `delta` как есть (никакой
  фильтрации в SSE нет), страница склеивает куски и парсит тег с учётом
  разрыва между `delta`: хвост, который ещё может оказаться началом тега
  (`<thi`, `</thi`), придерживается до следующего куска. Всё внутри `think`
  уходит в отдельный `<details class="think">` с подписью «рассуждение
  (N симв.)» — свёрнут по умолчанию, раскрывается кликом. В ответ теги не
  попадают. Незакрытый `think` (поток оборвался, в том числе по `AbortError`)
  — весь остаток считается рассуждением; оборванное начало тега в конце не
  показывается. Поддерживаются `think` и `thinking` в любом регистре.
- **Без внешних ресурсов.** `<details>`/`<summary>` — нативные элементы, стили
  и логика внутри страницы; CSP не менялся (`script-src 'unsafe-inline'`,
  `default-src 'none'`).

Счётчик в подписи — символы рассуждения, а не токены: клиент токенов не
видит. Тело раскрытого рассуждения ограничено `45vh` с внутренней прокруткой:
это вспомогательный блок, а не ответ.

## Рассуждения малой модели: шаблон и бюджет (задача 0200)

Малая модель гибрида — локальная ВТМ (`VtmBackend.chat`/`stream_chat`), и до
0200 промпт для неё собирался как `role: content` + `assistant:`. Qwen в таком
промпте не видит структуру реплик и не отключает `<think>`: рассуждение идёт со
скоростью ответа, съедает `max_tokens`, и ответ не появляется. Теперь
`eva/chat_template.py` рендерит настоящий ChatML, а рассуждение по умолчанию
**выключено**:

- `enable_thinking=False` → после `assistant` пустой закрытый
  `<think>\n\n</think>\n\n` (как официальный шаблон Qwen3): модель отвечает
  сразу, весь `max_tokens` уходит ответу;
- `VtmBackend(think=True, reasoning_budget=256)` → рассуждение ограничено
  бюджетом; при исчерпании оно закрывается принудительно, и ответ
  **досказывается** вторым прогоном. `max_tokens` тогда — лимит ответа,
  полный лимит = `reasoning_budget + max_tokens` (это же — потолок C-контекста);
- шаблон подключается сам по `tokenizer_config.json` рядом с токенизатором;
  без ChatML-шаблона остаётся прежний `role: content`, ручной `prompt_builder`
  важнее автоматики;
- история диалога (`ChatSession` в `tools/chat.py`, `ChatHistory` в
  `chat_server.py`) хранит ответ **без** `<think>`: рассуждение бесполезно в
  следующем промпте и съедает контекст. Если бюджет оборвал рассуждение
  раньше ответа, в историю пишется хотя бы оно — ход не теряется.

В стенде: `python3 tools/chat_server.py --think --reasoning-budget 64`
(по умолчанию выключено). API-контракт `POST /api/chat` не менялся:
`max_tokens` в запросе — лимит ответа; бюджет прибавляется на сервере, поэтому
EVA.app и веб-страница ничего не передают и продолжают работать как раньше.
UI 0178 по-прежнему сворачивает `<think>` в «рассуждение», когда он есть.

Замеры 30B (2026-11-26, 16 ГиБ, load average 7–12, подробности и таблица —
`docs/vtm.md`, «Чат-шаблон и бюджет рассуждений»): без рассуждения TTFT
7,5–10,5 с и 4,0–6,5 ток/с, ответ без `<think>`; с `--think
--reasoning-budget 64` первое слово ответа — через 55,8 с (64 токена
рассуждения + prefill второго прогона), но ответ есть и досказан до конца.

## Женский род в первом лице (задача 0207)

Ева — девушка, но 3B не держит род из промпта и пишет о себе «я понял»,
«готов», «сделал», «уверен». Поэтому слоёв два, и оба нужны:

1. **Промпт.** Во все `prompts/system*.md` добавлено правило «Ты Ева, женщина:
   о себе — только в женском роде» с примерами «поняла», «готова», «сделала».
   В компактном промпте это одна строка (сам файл по-прежнему 3 строки), чтобы
   не раздувать prefill.
2. **Страховка `eva/ru_gender.py`.** `feminize(text)` заменяет мужские формы на
   женские **только в первом лице** — когда слово стоит после «я» (в том числе
   «я уже», «я всё», «я не», «я бы», «я же», «я так»). Список: понял, сделал,
   смог, успел, готов, уверен, рад, должен, обязан, нашёл/нашел, посмотрел,
   проверил, подумал, ответил, сказал, хотел, решил, начал, закончил, забыл,
   помнил, знал, видел, услышал, пришёл/пришел, ушёл/ушел, взял, дал, ждал,
   исправил, добавил, убрал, плюс общее правило `-лся → -лась` и возвратные
   «ошибся → ошиблась». Чужой род («он понял», «ты готов», «вы готовы»), текст в
   кавычках («…», „…“, "…"), код в бэктиках (`` `…` ``) и блоки кода не
   трогаются: это данные, а не речь Евы.

`GenderStreamer` применяет замену по словам в потоке: недописанное слово ждёт
границы (пробел/пунктуация) или `flush()`, поэтому формат событий
`start`/`delta`/`done` не меняется, а дельты не рвутся посреди слова. Место
логики одно — `eva/ru_gender.py`; подключено в `tools/chat_server.py`
(`_run_side`: дельты, текст для истории, `POST /api/tts`) и в
`tools/chat.py` (`ChatRepl.turn` — общий путь для `--once` и REPL), поэтому
история диалога и озвучка получают уже женские формы. Ядро применяет фильтр
само, если плагин `ru-gender` не найден или выключен: `feminize` идемпотентна,
поэтому двойной прогон (плагин + ядро) ничего не меняет.

Граница у страховки намеренно узкая: форма без «я» в том же предложении
(«я проверил код и исправил ошибку» → второе «исправил») не меняется — лучше
пропустить, чем переписать чужой род; такие случаи закрывает промпт.

## Свежие данные в контексте: время, курсы, котировки (задача 0208)

Модель отвечает из весов: «сейчас 2023 год», курс валюты выдумывает. Tool-calling
для 3B не решение — вызывать инструменты она не умеет. Поэтому инструмент
срабатывает **до** генерации: роутер намерений распознаёт вопрос, данные
добываются из источника, а модель получает секцию `СПРАВКА` с готовой командой
и только формулирует ответ. Детерминированно, без обучения и без tool-вызовов
в рантайме.

### Модули

| Модуль | Что делает |
| --- | --- |
| `eva/skills/fresh.py` | `now_info()`, `currency_rate(code)`, `stock_quote(ticker)`; парсеры `parse_cbr_xml()`/`parse_moex_json()`; TTL-кэш; `Fact` и `format_fact()`; `degraded_fact()` |
| `eva/skills/intent.py` | `detect(text)` → `Intent(kind, params)`; `fact_line(text)` → готовая секция `СПРАВКА`; `with_fact(messages, line)` → вставка в системный блок; страж `guard_answer()`/`FactGuardStream` (0212) |
| `plugins/ru-facts` | фильтр `filter.run`: вырезает из ответа `[Факт: …]`, `СПРАВКА:` (двоеточие обязательно), `(источник: …)` и обрезанный `[Факт` — в чате и в озвучке |
| `tools/chat_server.py` | факт в системный блок обеих колонок до генерации; `chat.facts`/`--no-facts` |
| `tools/chat.py` | то же в REPL и `--once`; `--no-facts` |

`eva/skills/fresh.py` и `intent.py` **не входят** в реестр `eva/skills/registry.py`:
у скиллов реестра контракт «никогда не ходим в сеть и отвечаем сами», здесь
наоборот — сеть разрешена, но ответ формулирует модель. Смешивать режимы в
одном реестре нельзя: потеряются офлайн-тесты и детерминированность.

| Данные | Источник | Кэш | Таймаут |
| --- | --- | --- | --- |
| дата и время | часы сервера, `Europe/Moscow` | — | — (сети нет) |
| курс валют | `https://www.cbr.ru/scripts/XML_daily.asp` (XML, windows-1251, без ключа) | 3600 с | 4 с |

Кэшируются только успешные ответы: один сбой сети не должен «залипнуть» на час.
Курс ЦБ — один запрос на все валюты, поэтому «курс валют» (USD/EUR/CNY) — это
один поход в сеть, а не три.

Ровно то, что видит модель (одна секция на все факты запроса):

```
не цитируй слово «СПРАВКА»):
26 ноября 2026, 15:30 MSK (часы сервера)
1 USD = 82,3130 ₽ (ЦБ РФ на 26.11.2026)
SBER (Сбербанк) = 285,01 ₽, за день -2,41 ₽ (-0,84 %), закрытие вчера 287,42 ₽ (MOEX ISS, 26.11.2026 15:23 MSK)
```

### Роутер намерений

`eva/skills/intent.py::detect` отвечает на два вопроса: «про что это» (`time` |
`currency` | `stock`) и «о чём именно» (ISO-код валюты / тикер). Покрыто 27 фраз,
в тестах они зафиксированы таблицей: «который час», «сколько времени в Москве»,
«какое сегодня число», «какой сегодня день недели», «курс доллара», «какой курс
евро к рублю», «сколько стоит доллар», «цена евро в рублях», «курс ЦБ на
сегодня», «курс валют», «цена акции Сбер», «сколько стоит Газпром», «котировки
Яндекса», «акции Лукойла цена», «курс акций ВТБ», «цена акции SBER» и т. д.

Названия переводятся в код закрытым списком: «доллар/бакс/$» → `USD`,
«евро/€» → `EUR`, «юань» → `CNY`, «Сбер/Сбербанк/Сбера» → `SBER`, «Газпром» →
`GAZP`, «Яндекс» → `YDEX`, «Лукойл» → `LKOH`, «ВТБ» → `VTBR` (и ещё десяток бумаг).
Падежные окончания допускаются, произвольные хвосты — нет: «сбережения» и
«магнитный» не должны становиться Сбером и Магнитом.

Порядок проверок — время → бумага → валюта: «курс акций Сбера» это биржа, а не
курс ЦБ. Осторожность важнее полноты: «сколько времени займёт доставка»,
«сколько стоит тариф Старт», «кто такой Газпром», «цена акции Ромашка» роутер
пропускает к модели — ложный факт хуже отсутствия факта.

### Секция «СПРАВКА» и правило для модели (задача 0212)

`with_fact(messages, line)` дописывает секцию в **системный** блок (если его
нет — создаёт `system`-сообщение только со справкой) и не меняет входной
список. Заголовок секции — это и есть команда модели: «используй эти данные
дословно; не говори, что данных нет; не цитируй слово «СПРАВКА»». В
`prompts/system.compact.md` и `prompts/system.assistant.md` правило продублировано
словами: бери цифры и даты только из справки, начинай ответ с цифры, не говори
«нет доступа/не могу/не имею информации», если данные есть.

Почему формулировку пришлось менять. Живой ответ 3B был таким:

> «К сожалению, я не могу предоставить актуальный курс доллара… [Факт: 1 USD =
> 82,3130 ₽ (источник: ЦБ РФ на 26.11.2026)]»

Модель не связала служебную строку `[Факт: …]` с вопросом и заодно напечатала
её пользователю. Секция с прямой командой + пост-фильтр + страж закрывают все
три ошибки: отрицание данных, утечку служебного и «не могу» при наличии цифры.

### Пост-фильтр: служебное не доходит до пользователя

`plugins/ru-facts` (`filter.run`, `priority=40`, `scope=all`) вырезает
`[Факт: …]`, `[Факт` (обрезанный), `СПРАВКА:` и `(источник: …)` из готового
текста и из **потока**: хвост, который может быть началом маркера, придерживается
до следующего куска, поэтому разрезанный между токенами `[Фа` + `кт: …` тоже не
утекает. Плагин включён в `config/plugins.json`, поэтому работает и в веб-чате
(`stream_filter(scope="chat")`), и в `tools/chat.py`, и в озвучке
(`filter_text(scope="tts")`).

Двоеточие у `СПРАВКА` обязательно, иначе фильтр съедал бы обычное слово в
ответе на вопрос «что такое справка»: «Справка о доходах — это документ»
остаётся без изменений. Заголовок секции снимается вместе с подписью только
при форме `СПРАВКА (…):`; если данные стоят на той же строке, они сохраняются.

### Страж противоречия

Если ответ всё-таки начинается с отказа («не могу предоставить», «нет доступа»,
«не имею информации», «не располагаю данными»), а справка по этому вопросу есть,
`FactGuardStream` (ядро, `eva/skills/intent.py`) подменяет ответ короткой
фактической фразой — детерминированно, без второго прогона модели. Держится
только начало ответа (до первого предложения или 80 символов), поэтому стриминг
не страдает; увидев отказ, страж глушит остаток ответа. Страж **прозрачен без
справки**: обычное «не знаю» и отказ по вопросу без факта остаются как есть.
Строки деградации («не удалось получить…») фразой не считаются — подменять отказ
нечем.

Выключается флагом `--no-facts` (в обоих инструментах) и полем `facts=False` у
`create_server`; `POST /api/chat` не изменился — страница и EVA.app ничего не
передают. При `use_system=false` факт не подкладывается: колонка просили без
системного блока. История диалога факт не хранит — он приходит в каждый запрос
заново и устаревшую цифру не тащит.

### Деградация

Любой сбой (нет сети, таймаут, HTTP-ошибка, битый XML/JSON, неизвестный код или
тикер) → `None` из скилла, а в системный блок идёт честная строка
`СПРАВКА (…): не удалось получить курс USD — нет ответа от ЦБ РФ`. Модель по
правилу отвечает «не удалось получить», а не выдумывает. Исключение наружу не
летит: чат не падает и не отвечает 500. Время не деградирует — оно считается
локально.

### Две технические ловушки

* **XML ЦБ разбирается регулярками, а не `xml.etree`.** На этом хосте сборка
  Python 3.14 сломана: `pyexpat` не импортируется, и `ElementTree`/`minidom`
  падают ещё до разбора. Формат ЦБ плоский и стабильный, фикстура настоящего
  ответа (`tests/fixtures/cbr_daily.xml`) проверяет разбор windows-1251,
  номиналы (иена — за 100 единиц) и битые блоки.
* **MOEX доверяет «Russian Trusted Root CA» (Минцифры).** macOS ей доверяет,
  а OpenSSL из Homebrew — нет: `ssl.CERTIFICATE_VERIFY_FAILED`. `fresh._http_get`
  не отключает проверку сертификата, а при такой ошибке один раз повторяет
  запрос с корнями из хранилища доверия ОС (`security find-certificate -a -p`),
  то есть ровно с тем набором, что у Safari/curl; контекст кэшируется на процесс.
  Не macOS или нет `security` — честная деградация, а не молчаливый http.

## Память диалога в чате (задача 0182)

Раньше `chat_server` собирал запрос как `[system, user]`: каждый вопрос
задавался с чистого листа, и модель не видела, о чём говорили раньше. Теперь
у каждой колонки своя история `user`/`assistant`; сравнение моделей остаётся
честным — у left и right отдельные диалоги, общий только системный промпт.

### Что уходит в модель

- запрос колонки: `[system, ...история этой колонки, user]`;
- история — только `user`/`assistant`, системный промпт в неё не
  подмешивается и не теряется при обрезке;
- ответ дописывается **после** `done` и только непустой: ошибка генерации,
  отмена или пустая выдача не растят историю (следующий вопрос не «увидит»
  пустую реплику ассистента);
- формат событий `start`/`delta`/`done`/`error`/`end` не изменился.

### Обрезка

Два лимита, оба на колонку:

| Флаг | По умолчанию | Смысл |
| --- | --- | --- |
| `--history-tokens` | `1024` | бюджет истории в токенах; `0` — истории нет |
| `--history-turns` | `8` | сколько последних реплик (пар вопрос/ответ) держать |

Старые пары выбрасываются целиком: обрубков реплик не бывает. Последняя пара
остаётся даже если одна не влезает в бюджет — иначе на длинном ответе
«второй вопрос не видит первый». Токенизатора под рукой нет, поэтому бюджет
считается по символам: ~3 символа на токен (то же правило, что в
`tools/chat.py::estimate_tokens`), и везде помечен как оценка — `estimated:
true` в API, «(оценка)» в шапке колонки. Точные токены по-прежнему приходят
из `usage` провайдера в `done`; в бюджет истории они не подставляются.

### UI и API

- в шапке каждой колонки — «история: N реплик · ~M токенов (оценка)»
  (`id="history-0"`, `id="history-1"`); при `--history-tokens 0` — «выключена»;
- кнопка **«Новый диалог»** (`id="new-0"`, `id="new-1"`) сбрасывает историю своей
  колонки; ответ на экране остаётся — он про уже закончившийся обмен;
- `GET /api/models` получил поле `history`: `{enabled, limit_tokens,
  limit_turns, estimated, sides: [{side, turns, messages, tokens, estimated}]}`
  (страница берёт счётчик оттуда: у клиента нет ни истории, ни токенизатора);
- `POST /api/reset` — тело `{"side": 0}` (слева), `{"side": 1}` (справа) или
  `{}` (обе колонки); ответ — `{"reset": [0], "history": {...}}`, где
  `history` — тот же счётчик, чтобы шапка обновилась без второго запроса.
  Другое значение `side` — 400.

### Тонкости

1. **История привязана к колонке, а не к модели.** Смена модели в колонке
   диалог не сбрасывает (это осознанно: новый вопрос к новой модели видит
   контекст). Начать заново — «Новый диалог».
2. **Счётчик в шапке — оценка.** Считается по символам содержимого реплик,
   без системного промпта и текущего вопроса. Это бюджет истории, а не
   `prompt_tokens` ответа.
3. **`<think>` сохраняется как есть.** В историю пишется то, что реально
   сгенерировала модель; клиент по-прежнему вырезает рассуждение из ответа,
   но в следующем запросе оно займёт место в бюджете (и обрежется по лимиту).
4. **Сброс во время генерации.** Если нажать «Новый диалог», пока ответ
   стримится, текущий обмен всё равно допишется после `done`. Страница не
   даёт этого сделать (`running`), API — разрешает: это не ошибка, а
   осознанный компромисс без гонки за блокировку генерации.
5. **Кэш префикса теперь попадает на втором вопросе.** История — начало
   промпта, поэтому прошлый промпт целиком входит в новый, и это честное
   попадание ВТМ, а не артефакт.

## Отмена генерации (задача 0185)

До 0185 «Стоп», закрытие окна и новый вопрос прекращали только ожидание на
клиенте: SSE-поток переставали читать, а C-рантайм дорабатывал ответ до
`max_tokens`. У процесса один C-контекст на модель, поэтому следующий запрос
упирался в «контекст ВТМ занят» и ждал брошенную генерацию — на 3B Q4_K под
нагрузкой это 29–77 с до первого токена (замеры 0184).

### Цепочка отмены

```
клиент: AbortController / «Стоп» / новый вопрос
  → POST /api/cancel {side}        (или закрытие SSE-соединения)
  → ChatHTTPServer.cancel_chats()  (или _stream_sides: обрыв/новый вопрос)
  → ChatCliAdapter.cancel()
  → VtmBackend.cancel_active()     (флаг ставится только идущей генерации)
  → vtm_api_cancel()               (atomic_int в C, безопасен из любого потока)
  → VTM_API_CANCELLED              (между токенами и между инструкциями prefill)
  → VtmCancelled → done {cancelled: true, cancel_ms}
```

- `POST /api/cancel` — тело `{"side": 0}` / `{"side": 1}` отменяет одну
  колонку, `{}` — обе. Ответ `{"cancelled": n, "side": ..., "reason": "stop"}`.
  Вторая колонка при отмене одной продолжает работать.
- Обрыв SSE теперь определяется по сокету, а не по ошибке записи: HTTP-поток
  ждёт события не дольше 50 мс и проверяет `select`/`MSG_PEEK`. Раньше, пока
  генерация молчала (prefill бывает десятки секунд), обрыв замечался только
  на первой записи, то есть уже после первого токена.
- Новый вопрос по той же модели отменяет предыдущий запрос до старта
  (`cancel_model`, `reason="superseded"`), а не ждёт его в замке адаптера.
- `cancel_active()`, а не `cancel()`: у C-ABI флаг `vtm_api_cancel` живёт до
  ближайшего `generate()`, поэтому «поздняя» отмена (ответ уже кончился)
  отменила бы следующий запрос. `cancel_active()` ставит флаг только пока
  бэкенд занят.

### Метрики

Событие `done` колонки получило поля:

- `cancelled` — `true`, если остановка пришла по запросу, а не сама;
- `cancel_ms` — мс от запроса отмены до фактической остановки (поток
  адаптера закрыт, C-рантайм вернул управление);
- `cancel_reason` — `stop` / `client_gone` / `superseded` / `teardown`.

`finish_reason` у такой колонки — `cancelled`. Отменённый (недописанный) ответ
в историю диалога не попадает: пара «вопрос/ответ» дописывается только
целиком. Поля есть и в `server.last_answers`, который отдаёт `/api/models`.

### Числа

Замер на этой машине (16 ГиБ, load average ~10), мини-модель `runs/tiny`
(4 слоя, ctx 1024) — отмена из колбэка/другого потока, бюджет задачи 100 мс:

| что мерили | значение |
|---|---|
| отмена в декоде (C-флаг → `VtmCancelled`) | **0,11 мс** медиана, 2,4 мс максимум (10 прогонов) |
| отмена в prefill (пачка `vtm_run_batch`, промпт 500 токенов) | **0,20 мс** медиана, 0,46 мс максимум |
| следующий запрос после отмены | **17,7 мс** на 32 токена; `busy=false`, «занят» не приходит |
| повтор без отмены | побитово тот же вывод (в т.ч. `cache_prefix=1`) |

На 3B Q4_K (`runs/q4/3b-q4k.vtm`, 8–30 с на брошенный ответ до 64–512
токенов, load average ~10): обрыв SSE на середине ответа → отмена доходит до
C-рантайма за **4,0 мс**; `POST /api/cancel` → `done` за **59 мс**
(`cancel_ms = 53 мс`); отмена во время prefill длинного промпта —
`cancel_ms = 28 мс`; следующий вопрос принимается сервером через **5,6 мс**
после обрыва (первый токен — 6,4 с: это его собственный prefill, а не
ожидание брошенной генерации).

## Озвучка ответов (задача 0183)

Колонка чата умеет говорить вслух: галочка «озвучивать» в шапке панели
включает озвучку **этой** колонки, соседняя остаётся текстовой. Первая фраза
ответа звучит, не дожидаясь конца генерации: текст печатается как раньше,
звук идёт параллельно.

### Сервер: `POST /api/tts`

Тело — `{"text": "...", "voice": "..."}` (`voice` необязателен). Ответ —
`audio/wav` с `Content-Type: audio/wav` и `Cache-Control: no-store`:
браузер играет RIFF/WAVE напрямую, кэшировать одноразовую фразу незачем.

Текст чистится до произносимого:

| Что | Как | Пример |
| --- | --- | --- |
| рассуждение | `<think>…</think>` вместе с содержимым (включая незакрытый — поток оборвался) | `<think>план</think> Ответ` → `Ответ` |
| markdown-ссылки | остаётся подпись, адрес не читается | `[цена](https://x)` → `цена` |
| URL | `https://…`, `http://…`, `www.…` вырезаются | `см. https://x` → `см.` |
| разметка | `*`, `#`, `` ` ``, `~` заменяются пробелами | `**Жирный** #1` → `Жирный 1` |
| пробелы | схлопываются, края обрезаются | `  а   б  ` → `а б` |

Отдельно от чистки сервера, **перед выбором TTS-движка**, текст
проговаривается словами. Ступеней две, обе общие для Silero/ElevenLabs/`say`
и идемпотентные:

1. `eva/ru_speech.py` (задача 0206) — знаки, сокращения, телефоны и email.
   Silero v4_ru молча пропускает «×», «€», «км²», «#», а `info@example.com`
   выпадает целиком.
2. `eva/ru_numbers.py` (задача 0205) — числа: Silero пропускает токены-цифры,
   и «Цена 1500 рублей» звучала втрое короче словесной формы.

| Что | Как звучит | Пример |
| --- | --- | --- |
| знаки | словами | `2 × 3` → «два умножить на три», `5 ≤ 7` → «пять не больше семь», `2^3` → «два в степени три», `≈ 5` → «примерно пять» |
| валюты | словами, с согласованием | `50 €` → «пятьдесят евро», `50 $` → «пятьдесят долларов», `50 ₽` → «пятьдесят рублей» |
| единицы | словами | `5 км²` → «пять километров в квадрате», `60 км/ч` → «шестьдесят километров в час», `₽/шт` → «рублей за штуку» |
| температура | словами | `20°C` → «двадцать градусов Цельсия», `20°` → «двадцать градусов» |
| сокращения | словами, число согласуется | `т.д.` → «так далее», `ул.` → «улица», `г.` → «город», `2 шт.` → «две штуки», `15 тыс.` → «пятнадцать тысяч», `мск` → «по московскому времени» |
| телефон | **по цифрам** | `8 999 123 45 67` → «восемь девять девять девять один два три четыре пять шесть семь» |
| email | по частям | `info@example.com` → «info собака example точка com» |
| украшения | убираются | `«Привет» ©`, `™` — беззвучно; `—`/`–`/`…` → запятая-пауза |

Числа: целые 0…10¹², дроби («1,5» → «одна целая пять десятых»),
проценты/рубли/номера, диапазоны («10-20» → «от десяти до двадцати») и даты
(«01.02.2026» → «первое февраля две тысячи двадцать шесть»). Диапазон из
дефиса между числами остаётся диапазоном: минус — это «-5» (`-` перед
числом) и знак «−» (U+2212).

Не трогаются ни одной ступенью: код в бэктиках, URL, латиница с
цифрами/знаками (`v2.0`, `GPT-4`, `--prefill`, `EVA_TTS=0`), версии и IP.
Оговорка про «#»: серверный `clean_tts_text` заменяет markdown-символы
(`*`, `#`, обратный апостроф, `~`) пробелами **до** нормализации, поэтому
через `/api/tts` решётка до речи не доходит;
прямой путь (`scripts/voice_loop.py`, `eva.tts.synthesize`) говорит
«хештег тег». Тесты — `tests/test_tts_numbers.py`, `tests/test_tts_symbols.py`.

### Ударения: «Колобо́к», а не «Ко́лобок» (задача 0222)

Silero v4_ru понимает знак ударения `+` перед ударной гласной, но без
подсказки ошибается на сказочных словах и именах. Поэтому **только на пути в
Silero** `eva/ru_stress.py::apply_stress` расставляет `+`:
`Колобок` → `Колоб+ок`, `Колобка` → `Колобк+а`, `Баба-Яга` → `Б+аба-Яг+а`.
Разметку добавляет `SileroTTS._prepare_text` после общей чистки; ElevenLabs и
`say` её не получают, а в тексте ответа пользователю плюсов нет по построению.
Откат — `EVA_STRESS=0`.

Встроенный словарь — 40+ слов и словоформ: сказочная лексика (Колобок,
Теремок, Журавль, Алёнушка, Иванушка, Царевич/Царевна, Баба-Яга, Сивка-Бурка,
Хаврошечка, Морозко, Снегурочка, Ряба, Курочка, Мышка, Лягушка-квакушка,
Вершки, Корешки, Медведь, Афанасьев, Билибин) и частые слова с «плавающим»
ударением (звонит, красивее, каталог, договор, торты, средства, документ,
километр, квартал, обеспечение). Статья хранится как «основа + ударная
часть», поэтому формы получаются из той же записи. Расширять — файл
`data/stress.txt`: строка `слово<TAB>разметка` (`Муромец<TAB>М+уромец`),
строки `#` — комментарии. Файл читается при старте с кэшем по mtime/размеру,
внешние записи перекрывают встроенные; битая строка (нет таба, разметка не
совпадает со словом, `+` не перед гласной) даёт предупреждение с номером
строки и пропускается — синтез не падает. Тесты — `tests/test_ru_stress.py`.

Лимит — 600 символов **после чистки**: длиннее — 400 `text_too_long`,
пусто после чистки — 400 `empty_text`. `voice` — имя голоса Silero
(`baya`/`kseniya`/`xenia`/`aidar`, по умолчанию `baya`); неизвестное имя —
400 `unknown_voice` со списком допустимых.

Синтез — `eva/tts.py` (задачи 0191/0193/0195/0197): **ElevenLabs**, если
задан ключ, иначе **Silero**, если установлен (`sh tools/install_silero.sh`),
иначе системный `say` (macOS) / `espeak` (Linux), иначе null. Адаптер
ничего не скачивает и не ходит в сеть; Silero
синтезирует долгоживущий worker — модель загружается один раз
(см. [ниже](#worker-модель-загружается-один-раз-задача-0195)).
Если движка нет, процесс упал или вернул не WAV — 503 `voice_unavailable`
с текстом «голос недоступен: …». Страница
показывает эту плашку у колонки, чат при этом работает как раньше.

### Клиент: фразы и очередь

- Ответ режется на фразы **по мере стрима**: конец предложения (`. ! ? …`
  с пробелом после или в конце пришедшего куска) и перевод строки. Кусок
  без точки, переваливший 600 символов, режется по последнему пробелу —
  иначе сервер ответил бы 400.
- Первая фраза уходит в `POST /api/tts` сразу, как появилась; синтез
  остальных идёт параллельно, а играют они последовательно через **один**
  `<audio>`: очередь — массив промисов, плеер ждёт готовности головы.
- «Стоп» (кнопка рядом с «Спросить») прерывает и генерацию (`AbortController`),
  и звук: очередь чистится, текущий объект-URL освобождается, поколение
  растёт — запоздавшие ответы синтеза уже не попадут в очередь. Новый вопрос
  делает то же самое до старта запроса.
- Конец ответа (`done`/`error`/обрыв) доигрывает остаток: буфер фраз
  сбрасывается в очередь, уже поставленные фразы не отменяются.
- Ошибка любого запроса синтеза — «голос недоступен» у колонки, галочка
  остаётся включаемой (сервер могли перезапустить с TTS). Запрет автоплея
  браузером показывается отдельной плашкой: текст ответа это не задерживает.

## ElevenLabs: облачный голос с откатом на Silero/system (задача 0191)

ElevenLabs даёт естественную интонацию и русскую речь через
`eleven_multilingual_v2`. Провайдер включается только при заданном ключе; без
ключа всё работает как раньше (Silero/system). Главное правило: **сбой облака
не оставляет пользователя без голоса** — `eva/tts.py` логирует причину без
ключа и автоматически синтезирует ту же фразу локальным голосом.

### Как получить ключ

1. Зарегистрируйтесь на <https://elevenlabs.io> и откройте кабинет.
2. Профиль → **API Keys** → создайте ключ. Скопируйте его один раз: целиком
   он больше не показывается.
3. Экспортируйте ключ в окружение процесса чата (не в репозиторий и не в
   `git`):

   ```bash
   export ELEVENLABS_API_KEY='sk_...'
   # необязательно: свой голос из Voice Library / GET /v1/voices
   export ELEVENLABS_VOICE_ID='EXAVITQu4vr4xnSDxMaL'
   ```

4. Запустите сервер как обычно: `python3 tools/chat_server.py --port 8901`.
   При наличии ключа автовыбор возьмёт ElevenLabs.

Голос по умолчанию — публичный `EXAVITQu4vr4xnSDxMaL` с мультиязычной
моделью. Он говорит по-русски, но с лёгким акцентом: если тембр или
произношение не устраивают, возьмите русскоязычный голос из библиотеки
ElevenLabs и подставьте его ID в `ELEVENLABS_VOICE_ID`. Голоса Silero
(`baya`, `kseniya`, `xenia`) к облачному голосу не применяются: короткое имя
игнорируется, а ID голоса ElevenLabs имеет вид длинной буквенно-цифровой
строки и может передаваться в поле `voice` запроса.

### Переменные

| Переменная | По умолчанию | Зачем |
| --- | --- | --- |
| `ELEVENLABS_API_KEY` | — (обязательна) | ключ, заголовок `xi-api-key`; без него провайдер выключен |
| `ELEVENLABS_VOICE_ID` | `EXAVITQu4vr4xnSDxMaL` | голос из библиотеки ElevenLabs |
| `ELEVENLABS_MODEL` | `eleven_multilingual_v2` | модель синтеза (русский) |
| `ELEVENLABS_FORMAT` | `mp3_44100_128` | формат ответа; MP3 играют Web Audio и AVPlayer |
| `ELEVENLABS_TIMEOUT` | `30` | таймаут одного HTTP-запроса, сек |
| `ELEVENLABS_CACHE` | `1` | `0`/`false`/`off` отключает LRU-кэш |
| `EVA_TTS` | `auto` | `elevenlabs`/`silero`/`system`/`null` перекрывает автовыбор |

Порядок автовыбора: **ElevenLabs (если есть ключ) → Silero (если установлен)
→ say/espeak → null**. `EVA_TTS=silero` при наличии ключа принудительно
оставляет локальный голос (полезно для приватных фраз и проверки без квоты).

### Контракт запроса

```
POST https://api.elevenlabs.io/v1/text-to-speech/{voice_id}?output_format=mp3_44100_128
xi-api-key: <ELEVENLABS_API_KEY>
Content-Type: application/json

{"text":"…", "model_id":"eleven_multilingual_v2",
 "voice_settings":{"stability":0.4,"similarity_boost":0.75,"style":0.0}}
```

`eva.tts.ElevenLabsTTS.synthesize_audio()` возвращает
`(аудиобайты, content_type)`, а `synthesize()` — ту же пару (или путь при
`out_path`). `/api/tts` определяет MIME **по сигнатуре**, а не по жёсткой
константе: `RIFF…WAVE` → `audio/wav`, `ID3`/`0xFFFB` → `audio/mpeg`.
Поэтому браузер получает `audio/mpeg` для MP3 и `audio/wav` для
Silero/system, и менять клиент не пришлось.

### Откат и ошибки

| Сбой ElevenLabs | Что видит пользователь |
| --- | --- |
| нет `ELEVENLABS_API_KEY` | сразу Silero/system; 503 только если локального голоса тоже нет |
| 401 (ключ отклонён) | лог «ElevenLabs отклонил ключ (HTTP 401)», аудио от Silero/system |
| 429 (квота/лимит) | лог про квоту, аудио от Silero/system |
| таймаут / сеть | лог про таймаут, аудио от Silero/system |
| пустой ответ | лог, аудио от Silero/system |

Ключ не попадает ни в `describe()`, ни в логи, ни в текст 503: причины
редактируются, секрет заменяется на `***`. Если запасного движка нет,
возвращается 503 `voice_unavailable` с понятной причиной — молчаливой тишины
нет. Откат делает `eva/tts.py`, поэтому HTTP-слой отдаёт уже готовое аудио
локального движка и не знает, что облако failed.

### Кэш и квота

Успешные ответы лежат в общем LRU на **50 записей** (ключ — текст + голос +
модель + формат). Кэш живёт в памяти процесса, общий для всех запросов
`/api/tts`, поэтому повторная фраза («стоп», «повтори», одинаковые короткие
реплики) не тратит квоту и не идёт в сеть. `ELEVENLABS_CACHE=0` отключает
кэш. Неудачи не кэшируются: следующий запрос снова попробует облако (и снова
откатится, если оно недоступно).

### Стоимость и приватность — честно

- **Текст уходит в облако.** Каждая синтезируемая фраза (после чистки от
  `<think>`, markdown и URL) отправляется на `api.elevenlabs.io`; обратно
  приходит аудио. Это не локальный синтез: без сети ElevenLabs не работает,
  и фраза покидает машину. Для конфиденциальных текстов используйте
  `EVA_TTS=silero` или не задавайте ключ.
- **Это платный сервис.** ElevenLabs тарифицирует символы/кредиты по
  подписке; бесплатный уровень ограничен. Точные цены и лимиты смотрите в
  кабинете ElevenLabs: они меняются. 429 означает, что квота исчерпана или
  превышен rate limit — сервер в этом случае бесплатно озвучит фразу локальным
  голосом (Silero/system).
- **Кэш — только в RAM.** Аудио не пишется на диск и исчезает с процессом;
  ключ хранится только в переменной окружения. Не коммитьте его и не
  передавайте в логи/чаты.
- **Качество русского** зависит от голоса и модели: `eleven_multilingual_v2`
  поддерживает русский, но акцент/произношение имён лучше проверить на своих
  фразах и при необходимости сменить `ELEVENLABS_VOICE_ID`.

### Проверка

```bash
# моки HTTP, без сети и ключа: заголовки, тело, 401/429/таймаут, кэш, откат
python3 -m unittest tests.test_tts_elevenlabs -v
python3 -m unittest tests.test_tts -v
python3 -m unittest tests.test_chat_server.TestTtsEndpoint -v

# живой сервер с ключом: mp3 и audio/mpeg
export ELEVENLABS_API_KEY='sk_...'
python3 tools/chat_server.py --port 8901
curl -s -X POST -H 'Content-Type: application/json' \
  -d '{"text":"Привет! Это Ева."}' \
  http://127.0.0.1:8901/api/tts -o /tmp/reply.mp3 -D -
file /tmp/reply.mp3       # MPEG ADTS, layer III / ID3
# без ключа тот же запрос вернёт WAV от Silero/system (audio/wav)
```

Проверено на моках: запрос уходит на правильный URL с `xi-api-key` и
`voice_settings`, ответ MP3 отдаётся как `audio/mpeg`, 401/429/таймаут/сеть
дают откат на Silero/system с записью в лог без ключа, второй одинаковый
вызов не идёт в сеть. Реальный звук ElevenLabs без ключа не проверялся.

## Silero: локальный русский нейроголос (задачи 0193/0195/0197)

ElevenLabs уводит текст в облако и платный. Silero — русская нейросеть
(модель `v4_ru`, MIT/CC), которая работает локально и бесплатно. Для EVA она
стала **единственным локальным голосом** и голосом по умолчанию, если
установлена: приватность и отсутствие квоты важнее, чем «облачный» тембр.

### Установка

```bash
sh tools/install_silero.sh          # один раз, нужна сеть
```

Скрипт идемпотентен:

1. проверяет **python3.13** (у python3.14 ещё нет колёс torch для macOS arm64);
2. ставит `torch` (+ `numpy`, `omegaconf`) в `vendor/torch-py` — отдельно от
   сломанного source-checkout в `.pylibs`, который не используется;
3. качает репозиторий и веса Silero через `torch.hub` в `vendor/silero`
   (`TORCH_HOME`, в git не попадает);
4. синтезирует «Проверка голоса», печатает JSON с `load_ms`/`synth_ms` и
   размеры каталогов.

Ориентиры по размеру: `vendor/torch-py` ≈ **780 МБ**, `vendor/silero` ≈
**40 МБ** (веса `v4_ru.pt` — 38 МБ). Повторный запуск ничего не качает и не
ломает: torch проверяется импортом, модель берётся из кэша, пробный WAV
перезаписывается.

Сеть нужна **только установщику**. Сам синтез после установки полностью
офлайн: `torch.hub.load` находит локальный кэш и в сеть не идёт.

### Голоса

Тембр задаёт модель: никакого питч-шифта, сглаживания или голосовых пресетов
нет. В селекторах страницы чата и EVA.app — ровно три голоса в одном
порядке:

| Голос | Тембр | Медианный F0* | Длительность фразы* |
| --- | --- | --- | --- |
| `baya` (**по умолчанию**) | женский, живой | ~245 Гц | 4,83 с |
| `kseniya` | женский, чуть выше | ~262 Гц | 4,40 с |
| `xenia` | женский, ниже | ~201 Гц | 4,70 с |
| `aidar` | мужской, в UI скрыт | ~130 Гц | 4,63 с |
| `eugene` | мужской, только через env | — | — |
| `random` | случайный тембр | — | — |

\* Замер на фразе «Привет, Юрий. Я Ева, и это мой голос. Как тебе такое
звучание?», WAV 48 кГц. `baya` выбран по совокупности: женский тембр EVA,
ровная интонация, нет «дикторской» подачи. Сменить голос можно селектором
(поле `voice` в `/api/tts`) или переменной:

```bash
SILERO_SPEAKER=kseniya python3 tools/chat_server.py --port 8765
```

`aidar` в селекторах не показывается, но остаётся валидным в `/api/tts` и
`SILERO_SPEAKER` — мужской голос доступен тем, кому нужен.

Образец голоса `baya` лежит в `samples/voice_silero.wav` (48 кГц, 4,83 с).

`synthesize_audio()` для Silero отдаёт обычный `audio/wav`: пост-обработки
нет, HTTP-слой определяет MIME по сигнатуре `RIFF`.

### Worker: модель загружается один раз (задача 0195)

Одноразовый `tools/silero_speak.py` (0193) платил за `import torch` и загрузку
модели **на каждой новой фразе** — 2,65 с на короткую реплику. Теперь синтез
делает долгоживущий `tools/silero_worker.py`: модель грузится один раз, дальше
процесс принимает фразы по протоколу «JSON-строка на строку» (stdin → stdout).

```
python3.13 tools/silero_worker.py --speaker baya --sample-rate 48000
  ← {"ok": true, "ready": true, "pid": 4242, "load_ms": 1958, "rss_mb": 320}
  → {"text": "Привет", "speaker": "baya", "out": "/tmp/reply.wav"}
  ← {"ok": true, "ms": 41.2, "duration_s": 1.19, "pcm_bytes": 114240}
  → {"cmd": "ping"}       ← {"ok": true, "pong": true, "pid": 4242}
  → {"cmd": "shutdown"}   ← {"ok": true, "bye": true}
```

- **Ошибка фразы не убивает процесс**: пустой текст, чужой голос, сбой модели →
  `{"ok": false, "error": "…"}`, следующая строка обрабатывается как обычно.
  Перезапуск нужен только на падение/таймаут.
- **Prewarm** (необязательно): `prewarm_silero_worker()` поднимает worker
  фоном до первой фразы и догревает TorchScript коротким пробным синтезом.
  После этого первая настоящая фраза идёт **0,04–0,18 с** вместо ~3 с.
- **Почему пайп, а не UNIX-сокет в `/tmp`**: пайп живёт столько же, сколько
  родитель, не оставляет файлов и не конфликтует между двумя чат-серверами.
  Жизненным циклом управляет `eva/tts.py` (см. ниже).
- **HTTP-слою ничего не меняется**: `synthesize_audio()` отдаёт обычный
  `audio/wav`.

### Как устроен синтез

`eva.tts.SileroTTS` не импортирует torch в процессе чата: модель живёт в
worker'е, который запускается как

```
python3.13 tools/silero_worker.py --speaker baya --sample-rate 48000
  env: PYTHONPATH=vendor/torch-py, TORCH_HOME=vendor/silero
```

Жизненный цикл:

| Что | Как |
| --- | --- |
| старт | ленивый, при первом синтезе (или `prewarm_silero_worker()` заранее) |
| один процесс | worker — модульный синглтон: `select_engine` создаёт адаптер на запрос, процесс один на процесс чата |
| запросы | по одному (lock): протокол не помечает ответы id, параллельность перепутала бы их |
| падение | один перезапуск, повторный сбой → `TTSError` → откат на system |
| таймаут | `SILERO_WORKER_TIMEOUT` (20 с) → worker убит, фраза уходит на system, следующий вызов поднимает заново |
| ping | после `ready` клиент проверяет живость `{"cmd": "ping"}` |
| выход | `atexit`: `shutdown` → `SIGTERM` → `SIGKILL` (иначе 800+ МБ torch остались бы висеть) |
| повтор фразы | LRU-кэш адаптера (16 записей), worker не трогается вовсе |

Внутри worker'а `torch.hub.load` тот же, что у одноразового скрипта
(`v4_ru`, `trust_repo=True`), а `PYTHONPATH` выставлен ровно на
`vendor/torch-py`: чужой torch из site-packages или `.pylibs` в процесс не
попадает. Профилирование TorchScript отключено (`SILERO_JIT_PROFILING=0` по
умолчанию): первый `apply_tts` от этого не медленнее, зато второй и следующие
идут 0,03–0,25 с вместо ~0,85 с, а звук остаётся **бит-в-бит тем же**
(сверено по PCM одной и той же фразы). `SILERO_JIT_PROFILING=1` возвращает
поведение torch по умолчанию.

Одноразовый путь остался: `SILERO_WORKER=0` заставляет адаптер запускать
`tools/silero_speak.py` на фразу (отладка и аварийный обход, если worker на
машине почему-то не работает).

### Время и память — честные замеры

M1 Pro, macOS, `baya`, 2026-11-26. Одно и то же железо, одна и та же фраза
«Привет, Юрий. Я Ева, и это мой голос. Как тебе такое звучание?» (4,83 с
аудио):

| Сценарий | 0193: процесс на фразу | 0195: worker |
| --- | --- | --- |
| первая фраза после старта чата (ленивый старт) | 3,85 с | **2,6–3,3 с** |
| первая фраза после `prewarm_silero_worker()` | — | **0,10–0,17 с** |
| вторая фраза (2,30 с аудио) | 2,65 с (короткая) | **0,04–0,08 с** |
| третья фраза (1,61 с аудио) | ~2,5 с | **0,03 с** |
| повтор той же фразы (LRU-кэш) | 0,4 мс | **0,2–0,6 мс** |
| RSS | 550–790 МБ на фразу | **0,84–0,93 ГБ**, один процесс |
| idle CPU | — | **0,00–0,03 %** (0–0,002 с CPU за 3–8 с простоя) |

Из чего складываются 2,6–3,3 с первой фразы: старт worker'а 1,3–1,8 с
(импорт torch 0,8–1,2 с + загрузка модели 0,7–1,1 с) и первый `apply_tts`
~1,2 с (TorchScript оптимизирует граф на первом вызове; на второй фразе этой
цены уже нет). То есть **цель «первая фраза ≤2 с» ленивым стартом не
достигается** — 2,6–3,3 с; достигается она prewarm'ом: worker поднимается
фоном при старте сервера (готов через 2,4–3,1 с), и первая фраза идёт
0,10–0,17 с.

Почему не «поднять worker при импорте `eva.tts`»: импорт модуля не должен
запускать процесс на 800 МБ (тесты, CLI, `--help`). Поэтому prewarm — явный
вызов (одна строка) из сервера/голосового цикла; до него работает ленивый
старт.

Диалог из 5 фраз по 2 с аудио: было 3,85 + 4×2,65 ≈ **14,5 с**, стало
0,15 + 4×0,05 ≈ **0,35 с** (с prewarm) или 2,6–3,3 + 4×0,05 ≈ **2,8–3,5 с**
(ленивый старт). Модель при этом грузится ровно один раз — повторных
800 МБ нет: PID worker'а не меняется на 20 фразах подряд, RSS выходит на
плато ~0,9 ГБ и не растёт.

### Выбор движка и откат

Порядок автовыбора: `EVA_TTS` → **ElevenLabs (если ключ) → Silero (если
установлен) → system → null**. Явный `EVA_TTS=silero|...` перекрывает
автовыбор.

- Нет python3.13/torch/модели/весов → `SileroTTS.available()` = `False`,
  автовыбор спокойно уходит на system; в лог ничего не падает.
- Worker упал или не поднялся → один перезапуск; если и это не помогло,
  `eva/tts.py` логирует причину и **откатывается на system**. Если
  локального голоса нет — понятная ошибка, а не тишина.
- Worker завис (не ответил за `SILERO_WORKER_TIMEOUT`) → процесс убивается,
  фраза синтезируется системным `say`, следующий вызов поднимает worker
  заново.
- `EVA_TTS=silero` при неустановленном Silero → `TTSUnavailable` с текстом
  «запустите `sh tools/install_silero.sh`» (явный выбор не подменяется).

### Переменные

| Переменная | По умолчанию | Зачем |
| --- | --- | --- |
| `EVA_TTS` | `auto` | `silero`/`system`/`null`/`elevenlabs` перекрывает автовыбор |
| `SILERO_SPEAKER` | `baya` | голос: `baya`/`kseniya`/`xenia`/`aidar`/`eugene`/`random` |
| `SILERO_PYTHON` | python3.13 из PATH/Homebrew | интерпретатор для torch |
| `SILERO_TORCH_DIR` | `vendor/torch-py` | каталог вендорного torch |
| `SILERO_MODEL_DIR` | `vendor/silero` | кэш модели (`TORCH_HOME`) |
| `SILERO_SCRIPT` | `tools/silero_speak.py` | одноразовый синтезатор (путь 0193) |
| `SILERO_WORKER` | `1` | `0` — не использовать worker |
| `SILERO_WORKER_SCRIPT` | `tools/silero_worker.py` | скрипт worker'а |
| `SILERO_WORKER_TIMEOUT` | `20` | таймаут запроса к worker'у, сек |
| `SILERO_WORKER_START_TIMEOUT` | `30` | таймаут старта (torch + модель), сек |
| `SILERO_JIT_PROFILING` | `0` | `1` — вернуть profiling-executor TorchScript |
| `SILERO_CACHE` | `1` | `0`/`false`/`off` отключает LRU-кэш повторных фраз |
| `SILERO_THREADS` | `4` | потоков torch на синтез (`OMP_NUM_THREADS`) |
| `EVA_STRESS` | `1` | `0`/`false`/`off` отключает ударения (задача 0222) |
| `EVA_STRESS_FILE` | `data/stress.txt` | внешний словарь `слово<TAB>разметка` |

### Приватность

После установки Silero **не ходит в сеть**: текст, аудио и модель остаются на
машине. В отличие от ElevenLabs, фраза не покидает устройство. Установщик —
единственное место, где нужна сеть (torch и веса). Модель лежит в `vendor/`
и в git не попадает.

### Проверка

```bash
# моки: протокол worker'а, рестарт, таймаут, lock, откат; torch не импортируется
python3 -m unittest tests.test_tts_silero -v
python3 -m unittest tests.test_tts tests.test_tts_elevenlabs -v

# протокол worker'а руками: ready → фраза → shutdown (модель уже установлена)
printf '%s\n' \
  '{"cmd":"ping"}' \
  '{"text":"Проверка голоса.","speaker":"baya","out":"/tmp/worker.wav"}' \
  '{"cmd":"shutdown"}' | \
  PYTHONPATH=vendor/torch-py TORCH_HOME=vendor/silero \
  python3.13 tools/silero_worker.py
file /tmp/worker.wav      # WAVE audio, 48000 Hz, mono, 16 bit

# замеры через адаптер (первая фраза — ленивый старт, вторая — тёплая)
python3 - <<'PY'
from eva.tts import SileroTTS, silero_worker_info
engine = SileroTTS()
first = engine.synthesize_timed("Привет, Юрий. Я Ева, и это мой голос.", "/tmp/a.wav")
second = engine.synthesize_timed("Добрый вечер. Чем помочь?", "/tmp/b.wav")
print(f"первая {first.synth_ms:.0f} мс, вторая {second.synth_ms:.0f} мс, {silero_worker_info()}")
PY

# то же с prewarm: worker готов фоном, первая фраза ~0,2 с
python3 - <<'PY'
from eva.tts import SileroTTS, prewarm_silero_worker
engine = SileroTTS()
prewarm_silero_worker(engine).join(60)
r = engine.synthesize_timed("Привет, Юрий. Я Ева, и это мой голос.", "/tmp/c.wav")
print(f"первая фраза после prewarm: {r.synth_ms:.0f} мс")
PY
```

Тесты не импортируют torch: `Popen` подменяется эмулятором пайпов (ready,
ping, фразы, падения, зависания), а протокол самого worker'а проверяется
in-process на фейковом backend'е.
