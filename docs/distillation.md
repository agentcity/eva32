# Дистилляция в троичную модель: как и сколько

Состояние на 2026-11-18. Контекст: `docs/quantization.md` (зачем триты), `docs/trit-format.md`
(формат), `docs/trit-emulation.md` (замеры эмуляции).

## Исходная логика

Троичность даёт **пятикратное сокращение памяти** при паритете по скорости на бинарном CPU
(замерено: 0,82× по времени, 5× по объёму). Значит модель, которая раньше требовала стойку
с восемью H100, может поехать на машине за 100–200 тыс ₽.

Но в триты нельзя «пережать» 284B: тернарные веса получают обучением. Значит нужна **меньшая
модель, обученная заново** — и она не будет равна DeepSeek по знаниям. Вопрос: хватит ли её
на 80% запросов чата.

## Три способа получить троичную модель

| Способ | Что даёт | Качество | Время |
|---|---|---|---|
| Округление обученной (PTQ) | цифру деградации | рушится | 1 день |
| QAT с нуля (как BitNet) | полноценную троичную | как у BitNet | месяцы, триллионы токенов |
| **Дистилляция + QAT** | троичную под нашу задачу | между ними | **6–8 недель** |

Наш путь — третий: берём готовую маленькую модель как инициализацию, учим её быть троичной
и одновременно учим у DeepSeek на наших данных.

## Как это делается по шагам

### 1. Выбрать ученика (1–2 дня)

- Размер: **1–3B**. 3B — верхняя граница для CPU-сервера: 3B в тритах ≈ 0,6 ГБ весов,
  1B ≈ 0,2 ГБ.
- Архитектура: лучше взять готовую instruct-модель с тем же токенизатором, что у учителя
  (если учитель доступен по API — токенизатор не важен, важна только текстовая пара).
- Практично: Qwen2.5-1.5B/3B или Llama-3.2-1B/3B как база. Русский у Qwen лучше.

### 2. Собрать данные (1–2 недели, самое дорогое по времени)

- 50–100 тыс. русских вопросов из реального чата (обезличенных) + синтетика по каталогу услуг.
- Учитель (DeepSeek) отвечает на каждый → получаем пары «вопрос → хороший ответ».
- **Фильтр качества**: выкинуть ответы с отказами-не-по-делу, с иноязычными вставками,
  с выдуманными ценами (у нас для этого уже есть проверки из eval).
- Дедупликация и перемешивание с 20–30% общего русского текста, чтобы модель не «схлопнулась»
  в один стиль.

Объём: ~100 тыс. пар × ~300 токенов ≈ **30 млн токенов**. Это мало для pretraining, но много
для SFT-дистилляции.

### 3. Перевести линейные слои в троичные (3–5 дней)

- Тернарными делаем только `Linear` в attention и FFN: `W ∈ {-1,0,+1}` с масштабом на блок
  (absmax по 128–256 элементам).
- **Не трогаем**: эмбеддинги, layernorm, выходной слой, роутеры (если MoE).
- Forward: `y = Σ trit_i · x_i · scale` — сложения и вычитания.
- Backward: **STE** (straight-through estimator) — градиент проходит через квантователь как
  тождественный, веса обновляются в fp32/bf16 и квантуются заново каждый шаг.

### 4. Обучение (1–2 недели, GPU)

- Loss: **KL-дивергенция к логитам учителя** (лучше) или cross-entropy на его текстах (проще,
  если учитель только по API).
- LR: маленький (1e-5…5e-5), warmup, cosine. Тернарный QAT нестабилен: большой LR убивает
  модель за сотню шагов.
- Батч: 1–2 млн токенов на шаг-эпоху суммарно; 2–3 эпохи.
- Регуляризация: 20–30% общих данных в миксе, иначе забывание инструкций.

### 5. Оценка (1 неделя, итеративно)

- Наш набор (150 строк после расширения) по категориям.
- Слепой срез 50 ответов людьми.
- Сравнение с qwen 3B в Q4 — это **планка**: если тернарная 3B хуже, смысла нет.
- Инварианты: язык, отказ, «не выдумывать цену» — обязаны держаться.

## Сколько это стоит

Допущения (менять при пересчёте): аренда H100 — 250 ₽/час, API учителя — $0,5 за 1M выходных
токенов, курс 90 ₽/$. Тариф провайдера надо проверить перед стартом — это единственная строка,
которая может сдвинуться вдвое.

### Пилот на 1B

| Статья | Сколько | Деньги |
|---|---|---|
| Данные: 10 тыс. пар ≈ 3 млн токенов | 1 неделя | 150–500 ₽ через API |
| Обучение QAT | 8 GPU-часов | 2 000 ₽ |
| Оценка (наш набор + слепой срез) | 2–3 дня | 0 (или 500 ₽ за аренду 1×H100) |
| **Итого** | **2–3 недели** | **2–4 тыс ₽** |

### Полный цикл на 3B

| Статья | Сколько | Деньги |
|---|---|---|
| Данные: 100 тыс. пар ≈ 30 млн токенов | 1–2 недели | 1 400 ₽ через API / 12 000 ₽ на своём 8×H100 |
| Обучение, 3 итерации по 20 GPU-часов | 60 GPU-часов | 15 000 ₽ |
| Эталон V4.1 для сравнения | 8×H100, 6 часов | 12 000 ₽ |
| Оценка и разметка | 1 неделя | 0–10 000 ₽ (если наёмный разметчик) |
| **Итого** | **6–8 недель** | **30–60 тыс ₽** |

### Но главная строка — не GPU

Деньги на железо здесь маленькие: **десятки тысяч**. Дорого — время инженера:
6–8 недель на данные, QAT-обвязку, отладку и итерации. Если это наёмный ML-инженер,
смета вырастает на **300–600 тыс ₽** и именно она определяет бюджет, а не аренда.

Поэтому порядок работ такой, чтобы не платить за время дважды:

1. пилот за 2–3 недели и 2–4 тыс ₽ — проверяет саму идею;
2. только потом полный цикл.

### Что в смету не входит

- RAG и инструменты (это orioncode, отдельный бюджет);
- прод: мониторинг, деградация, стоимость диалога;
- дообучение под русский после дистилляции — отдельная итерация.

### Что может сдвинуть смету вверх

- QAT не сходится с первого раза → 2–3 повторных прогона (+10–20 тыс ₽);
- данные плохого качества → пересборка пар (+1–2 недели);
- если учителя нельзя дёргать по API и он нужен локально → аренда 8×H100 на дни,
  а не на часы.

## Где это ломается

1. **Дистилляция учит стилю, а не знаниям.** Ученик будет уверенно говорить нашим голосом и
   не знать фактов, которых не было в данных. Знания — из RAG, не из весов.
2. **Коллапс.** Модель, обученная только на ответах учителя, теряет способность рассуждать.
   Лечится миксом общих данных и проверкой на вопросах вне домена.
3. **Нестабильный QAT.** Тернарные веса + высокий LR = мусор. Нужны маленький LR, warmup и
   ранняя остановка по нашему набору.
4. **Русский проседает сильнее английского** — мерить надо именно на русском.
5. **Ожидание «как DeepSeek».** 3B не станет 284B. Реалистичная цель — 80% типовых вопросов
   продукта, остальное через API или фолбэк.

## Что делаем первым

**Пилот на 1B**, а не сразу 3B:

1. 10 тыс. пар «вопрос → ответ» (неделя, дешевле всего).
2. Тернарный QAT на 1B: 10–20 GPU-часов.
3. Замер нашим набором + сравнение с qwen 1.5B Q4.

Если 1B тернарная проходит инварианты и не хуже Q4 по фактам — масштабируем на 3B.
Если нет — видно за две недели и за ~10 тыс ₽, а не за два месяца.

## Почему не V4.1: цифры

Факты из карточки модели (проверено на HF 2026-11-18):

- **552B параметров**, активных **8B на prefill** и **16B на decode** (CED-архитектура);
- весов сейчас **510,3 ГБ** (90 файлов, ревизия `314113f8…`, MIT);
- отдельно **Engram** — 196B параметров условной памяти, читаются разреженно;
- KV-кэш ~890 байт на токен (FP4), то есть контекст почти бесплатен по памяти.

### Сколько было бы в тритах

| | Вес | Комментарий |
|---|---|---|
| Основные веса | **109 ГБ** | `552B × 1,585 / 8` |
| Engram | **39 ГБ** | 196B параметров |
| Итого | **~148 ГБ** | влезает в сервер на 192–256 ГБ |

Память тут не приговор: машина за 150–250 тыс ₽ физически вместит такую модель.

### А скорость — приговор

На токен читается `16B × 1,585 / 8 = 3,17 ГБ` активных весов:

| Пропускная способность | Скорость |
|---|---|
| 2,6 ГБ/с (наш скалярный кодек) | 0,8 ток/с |
| 10 ГБ/с | 3,2 ток/с |
| 50 ГБ/с | 15,8 ток/с |
| 100 ГБ/с | 31,5 ток/с |

То есть даже в лучшем случае это «человеческое чтение», а не чат с очередью. И это без prefill:
16B активных — это ещё и вычисления на каждый токен контекста.

### Главное препятствие — не память, а обучение

Тернарные веса нельзя загрузить — их нужно **вырастить**. Оценка QAT для 552B даже на 100 млрд
токенов: `6 · 552e9 · 1e11 ≈ 3,3 × 10^23` FLOPs — **около 26 лет на одной H100**, или сотни
H100 на месяцы. Это не наш масштаб и не наш бюджет.

### Дообучение V4.1 (если «хочется именно её»)

LoRA не уменьшает веса:

- FP8-веса 510 ГБ → нужно 8×H100 только чтобы их разместить, реально 16–32 с активациями;
- QLoRA (4 бита) ≈ 255 ГБ → минимум 4×H100, практически 8;
- аренда такого узла — сотни тысяч рублей в сутки.

### Что из этого следует

1. **V4.1 в тритах — не для нас.** Не потому что память, а потому что обучение.
2. **Дообучать V4.1 — тоже не для нас.** Это кластерная задача.
3. **Реально:**
   - арендовать 8×H100 на часы — снять эталон и прогнать eval;
   - использовать V4.1 как **учителя** (API) для дистилляции в 1–3B;
   - дообучать (LoRA) **маленькую** модель — это одна H100 и 10–30 тыс ₽.

Ирония в том, что 552B «влезает в память» ровно тогда, когда мы уже не можем его обучить.
Поэтому путь к «своей троичной Еве» — не сжатие V4.1, а дистилляция её поведения в модель,
которую мы способны обучить сами.

## Конвейер данных: что уже работает

Код в `distill/`, запускается без GPU и без ключей.

```bash
make test          # 12 юнит-тестов фильтров
make distill-mock  # прогон на заглушке: видно, что фильтры отсекают
make distill       # настоящий учитель: TEACHER_BASE / TEACHER_KEY / TEACHER_MODEL
```

Пайплайн: вопросы (`distill/questions.txt` или `eval/golden.jsonl`) → учитель →
фильтры → дедупликация → `distill/out/pairs.jsonl` + отчёт по причинам отказов.

### Что отсекают фильтры

| Фильтр | Почему |
|---|---|
| `invented_price` | цена без каталога — выдумка; обучать на этом нельзя |
| `foreign` | иероглифы или длинная латинская фраза в русском ответе |
| `length` | ответ короче 40 или длиннее 4000 символов |
| `bad_question` | пустой вопрос или длиннее 2000 символов |
| дедуп | одинаковые вопросы в разной записи («Сколько стоит?» / «сколько стоит ?») |

Прогон на заглушке: из 10 вопросов прошло 4, отброшено 6 (выдуманная цена — 6, длина — 2,
чужие языки — 2; сумма больше числа отброшенных, потому что у пары бывает несколько причин).

### Чего здесь ещё нет

- учитель не подключён: нужен `TEACHER_BASE`/`TEACHER_KEY`, а мок отвечает заранее
  заготовленными фразами;
- нет генерации вопросов из каталога услуг — пока берём готовый список и золотой набор;
- фильтры эвристические: они ловят явную грязь, а не тонкую ложь. Половину разберёт
  человек на этапе разметки;
- нет проверки на «ответ не по вопросу» — для этого нужен судья-модель или человек.

## Железо для QAT: H100 не нужен

QAT упирается в **память**, а не в скорость счёта: нужно держать bf16-копию весов, fp32-мастер
и состояния оптимизатора. Считаем по конфигам Qwen2.5:

| Модель | bf16 | fp32 мастер | Adam fp32 | Итого | С 8-bit Adam |
|---|---|---|---|---|---|
| 1.5B | 3,1 ГБ | 6,2 ГБ | 12,3 ГБ | **21,6 ГБ** | **12,3 ГБ** |
| 3B | 6,2 ГБ | 12,4 ГБ | 24,7 ГБ | 43,3 ГБ | **24,7 ГБ** |

Плюс активации ~1–3 ГБ в зависимости от батча и длины контекста.

Отсюда:

- **пилот 1.5B** — влезает в **RTX 4090 24 ГБ** (или 3090) с 8-bit Adam и gradient checkpointing;
- **3B** — нужен 48 ГБ (L40S, RTX A6000) или две 4090 с ZeRO-2;
- **H100 не даёт памяти**, только скорость.

### Время и деньги

`1.5B × 30 млн токенов × 3 эпохи = 8,1·10^17` FLOPs:

| Карта | Часов чистого счёта | Аренда (ориентир) |
|---|---|---|
| RTX 4090 | ~5 | 500–900 ₽ |
| A100 40 ГБ | ~2,6 | 500–800 ₽ |
| H100 | ~0,9 | 400–600 ₽ |

**Итоговая цена почти одинаковая** — потому что цена аренды растёт вместе со скоростью.
Выбирать надо по памяти и доступности, а не по «мощности»: H100 быстрее, но за него платят
столько же за час работы над той же задачей.

Для 3B добавляется ~10 часов на 4090 при 8-bit Adam + ZeRO, или ~5 часов на A100 80 ГБ.

### Покупать или арендовать

Точка окупаемости = цена карты / цена аренды:

| Карта | Цена | Аренда | Окупается за |
|---|---|---|---|
| RTX 4090 24 ГБ (новая) | 300 тыс ₽ | ~100 ₽/ч | 3000 часов |
| RTX 3090 24 ГБ (б/у) | 140 тыс ₽ | ~100 ₽/ч | 1400 часов |
| RTX 3060 12 ГБ | 45 тыс ₽ | ~60 ₽/ч | 750 часов |

Пилот на 1.5B — это **8 часов аренды, то есть ~800 ₽**. Покупка карты за 300 тыс ₽
не окупается никогда при таком темпе: при 8 ч/мес — 31 год, при 20 ч/мес — 12 лет.

Отсюда три варианта, и они про разные задачи:

1. **Аренда 4090 сейчас** — 800 ₽ за пилот, ноль обязательств. Разумный выбор.
2. **Купить б/у 3090 (~140 тыс)** — оправдано, если обучение станет регулярным: 100+ часов
   в месяц, то есть полная занятость на этом. Тогда окупается за год.
3. **Купить CPU-сервер (128 ГБ, ~100–150 тыс)** — это не для обучения, а для **инференса**
   готовой троичной модели: она влезает в память без GPU. Но покупать его имеет смысл только
   после того, как модель покажет качество.

Скрытые расходы владения: электричество (~0,5 кВт), шум, драйверы, гарантия, и через три года
карта устареет. Аренда всего этого не имеет.

**Apple Silicon для обучения не годится:** нет места под мастер-копию и Adam (22–43 ГБ),
плюс скорость. Для инференса готовой троичной модели — годится (0,9–1,4 ГБ в памяти).

### Что выяснилось на живом учителе (polza.ai, V4.1-Flash)

Первый прогон на 34 строках золотого набора показал две вещи, которые меняют конвейер:

1. **Без контекста учитель увиливает.** На «сколько стоит тариф Старт» он отвечал
   «уточните, о каком сервисе речь, у тарифов разных CRM цены разные», а на «что входит в
   Бизнес» — «пришлите название компании». Формально честно, для обучения бесполезно: ученица
   выучит отнекиваться вместо ответа.
2. **Без нашего системного промпта он врёт про происхождение** — выдал «работаю на языковой
   модели OpenAI» и не ставил ссылки `[n]`.

После того как в запрос добавили `prompts/system.ru.md` и контекст:

| Метрика | Без промпта | С промптом |
|---|---|---|
| принято пар из 34 | 20 | **23** |
| ответов со ссылкой `[n]` | 0 | **9 из 10** |
| «чужой вендор» | 2 | **0** |

Стоимость: ~680 входных и ~120 выходных токенов на вопрос (системный промпт занимает
большую часть входа). На 100 тыс. пар это ~68 млн входных и ~12 млн выходных — то есть
заметно дешевле прежней оценки в 30 млн выходных.

### Чего не хватает для масштабирования

Контекстных вопросов пока 11 из 34 — остальное это проверки без фактов. Чтобы собрать
100 тыс. пар, нужен **банк вопросов с контекстом из каталога orioncode**: услуги, тарифы,
условия, сроки. Без продукта данных дальше золотого набора не уехать — это следующая
внешняя зависимость.
