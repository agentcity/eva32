# Подключение orioncode к EVA32

Практическая инструкция для стороны orioncode: как завести EVA32 отдельным
OpenAI-совместимым провайдером, что приходит в ответе и что делать, когда
сервер отвечает не 200.

Контракт API — [docs/hybrid.md](hybrid.md), решение о гибриде —
[ADR 0009](adr/0009-hybrid-router.md), эксплуатация —
[docs/hybrid-runbook.md](hybrid-runbook.md). Сверено с кодом на 2026-11-18;
что осталось непроверенным — раздел 12.

## 1. Коротко

| Параметр | Значение |
|---|---|
| Base URL | `http://127.0.0.1:8010/v1` |
| API key | любая непустая строка, сервер её не проверяет |
| Model | `eva-hybrid` |
| Протокол | OpenAI Chat Completions (`POST /v1/chat/completions`) |
| Дополнительное поле ответа | `eva` — маршрут, причина, цена, латентность |
| Стрим | зависит от версии сервера: см. раздел 9.3 и smoke-скрипт |

Порт **8010**, а не 8000: `8000` на этой машине занят прод-`vLLM`
([docs/hybrid-runbook.md](hybrid-runbook.md), раздел 3). Порт задаётся флагом
`--port`; маршрутизация от него не зависит.

## 2. Пример конфига провайдера

В репозитории нет схемы конфига orioncode, поэтому ниже — смысловой минимум.
Имена полей в вашей схеме могут отличаться; переносите значения, а не
дословный JSON.

```json
{
  "name": "eva-hybrid",
  "type": "openai",
  "base_url": "http://127.0.0.1:8010/v1",
  "api_key": "eva-local-key",
  "model": "eva-hybrid",
  "stream": false,
  "timeout_s": 90,
  "max_retries": 2
}
```

| Поле | Почему так |
|---|---|
| `type` | провайдер OpenAI-совместимый; отдельного клиента EVA не нужно |
| `base_url` | оканчивается на `/v1`; путь `/chat/completions` клиент добавляет сам |
| `api_key` | непустая строка-заглушка; EVA не проверяет `Authorization` |
| `model` | `eva-hybrid` — имя-метка, а не выбор модели внутри гибрида |
| `stream` | `false` — безопасно на любой версии; `true` — только если smoke показывает PASS |
| `timeout_s` | больше таймаутов моделей (по умолчанию 30 с малая, 60 с большая) |
| `max_retries` | повторять только 5xx/сетевые ошибки, не 4xx |

Клиенты, читающие стандартные переменные OpenAI, можно направить так:

```bash
export OPENAI_BASE_URL=http://127.0.0.1:8010/v1
export OPENAI_API_KEY=eva-local-key
```

Модель всё равно передаётся в запросе: `model: "eva-hybrid"`.

Минимальная проверка, что конфиг рабочий (тот же запрос, что делает клиент):

```bash
curl -sS -X POST http://127.0.0.1:8010/v1/chat/completions \
  -H 'Content-Type: application/json' \
  -H 'Authorization: Bearer eva-local-key' \
  -d '{"model":"eva-hybrid","messages":[{"role":"user","content":"Сколько стоит тариф Старт?"}]}' \
  | python3 -m json.tool
```

Ожидается `200`, непустой `choices[0].message.content` и объект `eva`
(раздел 7).

## 3. Base URL

- `http://127.0.0.1:8010/v1` — если orioncode и EVA32 на одной машине.
- `/health` живёт **вне** `/v1`: `http://127.0.0.1:8010/health`.
- Если сервер слушает не loopback, используйте адрес машины:
  `http://<host>:8010/v1`; для этого сервер запускают с `--host 0.0.0.0`
  (флаг `python3 -m eva`).
- В контейнере `127.0.0.1` — это сам контейнер, а не хост. На Docker Desktop
  нужен `http://host.docker.internal:8010/v1`; на Linux — адрес хоста в сети
  контейнера. Это самая частая причина «сервер недоступен».
- Base URL без завершающего `/`: `.../v1`, а не `.../v1/` и не
  `.../v1/chat/completions`. Полный путь формирует клиент.

## 4. Ключ

- Подойдёт любая непустая строка: `eva-local-key`, `sk-local`, `x`.
- Сервер не проверяет `Authorization` и не отдаёт `401` из-за ключа. Ключ нужен
  только потому, что OpenAI-клиенты требуют непустое поле.
- Не переиспользуйте боевой ключ другого провайдера: EVA его не проверяет, но
  он попадёт в конфиг и может утечь.
- `VLLM_API_KEY` из `.env.example` к EVA отношения не имеет: гибрид читает
  только `EVA_*`.
- Наружу в интернет сервер без аутентификации не выставляйте: своей проверки
  ключей, квот и TLS у него нет (раздел 12). Для внешнего доступа — reverse
  proxy с аутентификацией и TLS.

## 5. Модель

- `eva-hybrid` — значение по умолчанию (`eva/server.py`, `DEFAULT_MODEL`) и
  единственная запись в `GET /v1/models`.
- Сервер принимает **любое** непустое имя модели и возвращает его же в поле
  `model` ответа. Имя не выбирает малую/большую модель и не влияет на маршрут:
  маршрут выбирает гибрид.
- `small` и `big` — внутренние маршруты, а не модели в `/v1/models`. Не
  пытайтесь запросить их как отдельные модели.
- Если клиент требует, чтобы имя было в списке `/v1/models`, используйте
  ровно `eva-hybrid`.

## 6. Первый запрос без стрима

```bash
curl -sS http://127.0.0.1:8010/health
curl -sS http://127.0.0.1:8010/v1/models

curl -sS -X POST http://127.0.0.1:8010/v1/chat/completions \
  -H 'Content-Type: application/json' \
  -H 'Authorization: Bearer eva-local-key' \
  -d '{"model":"eva-hybrid","messages":[{"role":"user","content":"Сколько стоит тариф Старт?"}]}' \
  | python3 -m json.tool
```

`/health` отвечает `200`, даже если модели ещё не настроены: маршрутизатор
собирается лениво. Поэтому «health ok» **не значит** «чат работает»; это
проверяет smoke-скрипт (раздел 10).

## 7. Ответ и поле `eva`

Ответ повторяет формат OpenAI и дополнен объектом `eva`:

```json
{
  "id": "chatcmpl-1a2b3c4d5e6f",
  "object": "chat.completion",
  "created": 1763440000,
  "model": "eva-hybrid",
  "choices": [
    {
      "index": 0,
      "message": {
        "role": "assistant",
        "content": "Тариф «Старт» — 990 ₽/мес [1]. Лимиты: до 3 сотрудников; 100 услуг в каталоге. ..."
      },
      "finish_reason": "stop"
    }
  ],
  "usage": {"prompt_tokens": 0, "completion_tokens": 0, "total_tokens": 0},
  "eva": {
    "route": "skill",
    "reason": "skill: pricing — детерминированный ответ из каталога, модель не вызывалась",
    "confidence": 1.0,
    "skill": "pricing",
    "cost_rub": 0.0,
    "latency_ms": 2
  }
}
```

| Поле `eva` | Смысл |
|---|---|
| `route` | `skill`, `small` или `big` — кто фактически ответил |
| `reason` | человекочитаемая причина решения; сюда же попадают причины фолбэков |
| `confidence` | уверенность классификатора, 0…1 (у скилла 1.0) |
| `skill` | имя скилла (`pricing`, `hours`, `refunds`, `contacts`) или `null` |
| `cost_rub` | оценка стоимости **этого** запроса в рублях |
| `latency_ms` | сколько заняла обработка на сервере, мс |

### Как читать маршрут

- `skill` — ответ собран скиллом из каталога. Модель не вызывалась,
  `cost_rub = 0`, `usage` нулевой, `skill` заполнен. Это самый точный и
  дешёвый маршрут.
- `small` — ответила малая локальная модель. Цена считается по
  `EVA_SMALL_PRICE_PROMPT` / `EVA_SMALL_PRICE_COMPLETION`.
- `big` — ответила большая модель по API. Цена считается по
  `EVA_BIG_PRICE_PROMPT` / `EVA_BIG_PRICE_COMPLETION`.
- `reason` читайте при разборе: в нём видно, почему выбран маршрут и был ли
  фолбэк (например, «большая → малая при 429»). На каждом втором запросе один
  и тот же фолбэк — повод смотреть конфиг или классификатор, а не код клиента.
- `route = "unknown"` — маршрут не определён: сервер другой версии или
  маршрутизатор вернул ответ без маршрута. Не строите на этом поле логику
  доступа, это диагностика.

### Как читать цену

- `cost_rub` — оценка по тарифам из `.env`, а не счёт провайдера. Если цены в
  `.env` устарели, цифра врёт; сверяйте `EVA_*_PRICE_*`.
- Это цена **одного** запроса. Для стоимости пачки суммируйте `cost_rub` по
  ответам.
- `usage` — обычные токены OpenAI. У скиллов там нули, потому что модель не
  вызывалась; цена у них тоже нулевая.
- Цену нельзя восстановить из `usage` без знания тарифа: берите готовый
  `cost_rub`.
- Разбивка по маршрутам и дням — `tools/usage_report.py` по
  `logs/eva.jsonl`. Важно: на 2026-11-18 HTTP-сервер в этот файл не пишет
  (телеметрия есть отдельным модулем, проводка в сервер не сделана); если
  агрегат нужен сейчас, сохраняйте `eva.cost_rub` на своей стороне.

## 8. Чем отличается от vLLM-провайдера

| Свойство | vLLM | EVA32 |
|---|---|---|
| Что это | движок инференса одной модели | маршрутизатор: скиллы → малая → большая |
| Поле `model` | выбирает загруженные веса; имя должно существовать | метка, возвращается как есть; на маршрут не влияет |
| `/v1/models` | реальные модели | одна запись `eva-hybrid` |
| Кто отвечает | всегда модель | скилл, малая или большая — по правилам |
| Доп. поля | нет | `eva` с маршрутом и ценой |
| Цена запроса | нет в ответе; считают по GPU/времени | `eva.cost_rub` в каждом ответе |
| 429 | лимит/перегрузка приходит клиенту | 429 большой модели поглощается политикой: клиент обычно получает 200 и фолбэк в малую |
| 5xx | ошибка движка | 500 только при внутренней ошибке/недоступной модели; текст с request-id |
| Аутентификация | часто требует ключ | `Authorization` не проверяется |
| Стрим | OpenAI SSE | SSE, если версия сервера с задачей 0025; иначе 400 `unsupported_stream` |
| Другие эндпоинты | бывают `/v1/completions`, embeddings и др. | только `/health`, `/v1/models`, `/v1/chat/completions` |

Практический вывод: EVA32 можно подключить как обычного OpenAI-провайдера, но
нельзя рассчитывать, что `model` переключает модель, что ответ всегда
сгенерирован моделью и что `usage` отражает реальные токены на маршруте
`skill`. Всё остальное — стандартный chat completions.

## 9. Ошибки: 500, 429, 400

### 9.1. 500 — внутренняя ошибка EVA32

Формат:

```json
{
  "error": {
    "message": "Внутренняя ошибка сервера. Повторите запрос позже; если не поможет, сообщите код 1a2b3c4d5e6f.",
    "type": "server_error",
    "code": "internal_error",
    "param": null
  }
}
```

Что делать:

1. Повторить 1–2 раза с backoff (0,5 → 1 → 2 с): часть ошибок — разовый
   таймаут или перезапуск модели.
2. Сохранить request-id из `error.message` — по нему ищут запись в логе
   сервера.
3. Проверить причину на сервере: чаще всего это маршрут `small`/`big`, а
   модель не настроена или недоступна. `/health` при этом может отвечать
   200 — он не проверяет модели.
4. Не повторять бесконечно: если 500 идёт серией, это конфигурация
   (`EVA_SMALL_BASE`, `EVA_BIG_BASE`/`EVA_BIG_MODEL`) или упавший провайдер.

`/health` + успешный чат-запрос — единственный надёжный признак готовности;
smoke проверяет оба.

### 9.2. 429 — лимит, но не от EVA32

- Сам сервер EVA32 **не отдаёт 429**: в коде ответов 429 нет. Если вы видите
  429, это прокси, балансировщик или клиентский rate-limiter, а не гибрид.
- 429 от большой модели обрабатывается внутри: политика откатывает запрос на
  малую модель, клиент получает `200` с `eva.route = "small"` и причиной
  фолбэка в `eva.reason` (если малая настроена и доступна; иначе будет `500`).
- Поэтому «лечить» 429 на стороне orioncode не нужно; смотрите долю `big` и
  `reason` в ответах. Если 429 приходит от вашего прокси — соблюдайте
  `Retry-After`, если заголовок есть, и не ретрайте сразу.
- 429 при массовых запросах — сигнал лимита на стороне прокси/инфраструктуры,
  а не повод менять клиент.

### 9.3. 400 и другие 4xx

- `400` — ошибка запроса: битый JSON, пустой `messages`, неизвестный
  `Content-Type` и т.п. Повтор без исправления бесполезен; читайте
  `error.code`.
- `400 unsupported_stream` — версия сервера без SSE (сборка до задачи
  0025). Отправляйте `"stream": false`; это не поломка гибрида.
- `404` — неверный путь (например, `/v1/completions`: его нет).
- `405` — неверный метод (`GET` на chat completions).
- `411` — нет `Content-Length`; `413` — тело больше 1 МиБ.
- `401` от EVA не бывает. Если пришёл `401`, его вернул прокси/шлюз перед
  сервером.

### 9.4. Таймауты

- Клиентский таймаут держите не меньше 90 с: сервер ждёт малую модель до 30 с,
  большую до 60 с, плюс повторы внутри клиента.
- Слишком короткий таймаут orioncode обрывает запрос, который сервер ещё
  обрабатывает; повтор создаёт лишнюю нагрузку и может стоить денег.
- Сервер не отдаёт `202`/асинхронных заданий: ответ приходит в том же
  соединении.

## 10. Как проверить, что всё работает

### 10.1. Поднять сервер

```bash
cd /path/to/eva32
python3 -m eva --port 8010
```

Если нужны модели/ключи из `.env` (сервер сам `.env` не читает):

```bash
cd /path/to/eva32
set -a
. ./.env
set +a
python3 -m eva --port 8010
```

Проверка скиллов работает и без моделей: вопрос про тариф отвечает `pricing`
из каталога, сеть не нужна. Для маршрутов `small`/`big` нужны доступные
`EVA_SMALL_BASE` и `EVA_BIG_BASE`/`EVA_BIG_MODEL`.

### 10.2. Smoke-скрипт

```bash
python3 scripts/integration_smoke.py --url http://127.0.0.1:8010
echo "exit=$?"
```

Что проверяется:

1. `GET /health` — 200 и `status=ok`;
2. `GET /v1/models` — в списке есть `eva-hybrid`;
3. `POST /v1/chat/completions` без стрима — непустой ответ, объект `eva`,
   допустимый `route`, неотрицательный `cost_rub`; печатаются маршрут,
   причина, скилл, токены, цена и латентность;
4. `POST /v1/chat/completions` со стримом — SSE-чанки, `delta.content`,
   финальный `[DONE]`. Если сервер ещё без 0025 и отвечает
   `400 unsupported_stream`, проверка печатает **SKIP** с пояснением и не
   считается провалом; exit-код остаётся 0.

Код возврата: `0` — всё прошло (SKIP стрима допустим), `1` — есть `FAIL`.
Скрипт только на стандартной библиотеке, ставить ничего не нужно.

Пример успешного прогона (сервер с SSE):

```text

      model=eva-hybrid, uptime=0.184 с
```

итог — `3 PASS, 1 SKIP, 0 FAIL`, exit 0. Это нормально для версии до 0025.

### 10.3. Ручные проверки

```bash
curl -sS http://127.0.0.1:8010/health
curl -sS http://127.0.0.1:8010/v1/models
```

Если smoke недоступен, минимальный признак жизни — `health`, а минимальный
признак пригодности — ответ чата с полем `eva` (раздел 6).

## 11. Чек-лист изменений на стороне orioncode

- [ ] Добавить провайдера с `base_url = http://127.0.0.1:8010/v1`.
- [ ] Прописать любой непустой API key; не использовать боевые секреты.
- [ ] Указать `model = eva-hybrid` (или любое имя, если клиент не сверяет
      список моделей).
- [ ] Оставить `stream = false`, пока smoke не покажет PASS для стрима.
- [ ] Поставить клиентский таймаут ≥ 90 с.
- [ ] Ретраить только 5xx/сетевые ошибки; 4xx не повторять.
- [ ] Не завязывать логику на `model`: маршрут выбирает сервер.
- [ ] Читать `eva.route`, `eva.reason`, `eva.cost_rub`; неизвестное поле
      игнорировать, если клиент его не понимает.
- [ ] Не проксировать через шлюз, который вырезает незнакомые поля ответа или
      превращает SSE в буфер.
- [ ] Проверить сеть из того же контейнера/пода, откуда ходит orioncode
      (не только с ноутбука).
- [ ] Запустить `scripts/integration_smoke.py` против того же URL и приложить
      вывод к приёмке.

Ничего в самом EVA32 для подключения менять не нужно: это обычный
OpenAI-совместимый эндпоинт.

## 12. Ограничения и риски

- **SSE зависит от версии.** Проверенная сборка от 2026-11-18 уже отдаёт SSE;
  на другом развёрнутом сервере может стоять версия без 0025 и отвечать `400
  unsupported_stream`. Решает smoke: PASS — можно `stream=true`, SKIP — только
  `false`.
- **Нет аутентификации и TLS.** Ключ не проверяется; сервер рассчитан на
  localhost или доверенную сеть. Для внешнего доступа обязателен reverse proxy
  с аутентификацией и TLS.
- **Один процесс, без HA и квот.** Это не пул реплик: перезапуск сервера рвёт
  соединения; балансировки и ограничения частоты на стороне EVA нет.
- **Только три эндпоинта.** `/v1/completions`, embeddings, tools/function
  calling, vision и прочее не реализованы; не включайте их в провайдера.
- **`cost_rub` — оценка, не счёт.** Она считается по ценам `.env`; при
  неверных `EVA_*_PRICE_*` цифра не совпадёт с биллингом провайдера.
- **`/health` не проверяет модели.** Зелёный health и 500 на чате — нормальная
  пара для ненастроенной малой/большой модели; смотрите smoke и лог сервера.
- **Телеметрия не подключена к HTTP.** `logs/eva.jsonl` и
  `tools/usage_report.py` существуют, но текущий сервер туда не пишет; для
  отчётности сохраняйте `eva.cost_rub` на клиенте.
- **RAG (0024) и классификатор зависят от версии.** Ответы и распределение
  маршрутов могут измениться; после обновления сервера повторяйте smoke.
- **Порт 8010 — пример.** Если у вас другой `--port`, меняйте и base URL;
  `8000` занят прод-`vLLM`.
