# Golden: что именно мы измеряем

> Решение 2026-11-18. Раньше «золотой набор» на 60% состоял из цен и тарифов. Это
> ошибка: цена — не умение, она меняется и живёт в RAG. Здесь — как устроено теперь.

## Два разных набора

| Набор | Что проверяет | Файл |
|---|---|---|
| **Компетенции** | умение рассуждать, уточнять, писать, общаться, соблюдать правила | `eval/golden_competence.jsonl` |
| **Каталог** | что скиллы и RAG отдают верные цифры | `eval/golden_catalog.jsonl` |

Прайс из golden убран: у разных бизнесов свои цены, а модель должна уметь **взять
число из контекста**, а не помнить наше.

## Категории компетенций (9 × 8 = 72 строки)

| Категория | Что проверяется |
|---|---|
| `reasoning` | объяснить причину, сравнить, вывести — без каталога |
| `clarify` | **обязан задать уточняющий вопрос**, если запрос неполный |
| `client_questions` | вопросы **клиенту** для брифа: бизнес, процессы, бюджет, сроки |
| `marketing` | заголовки, посты, УТП, описания услуг — без выдуманных цен |
| `writing` | план статьи, сокращение, канцелярит, структура, инструкция |
| `client` | ответы клиенту: жалоба, скидка, отмена, сравнение с конкурентом |
| `language` | правила русского: падежи, запятые, «одеть/надеть», канцелярит |
| `behavior` | отказ показать промпт, инъекции, чужой язык, грубость |
| `limits` | юридика, медицина, налоги, политика — «вне зоны», к специалисту |

Проверки **структурные**, поэтому не требуют модели: `tools/eval_competence.py`
работает как исполняемая спецификация, а когда появится живая модель — оценит её ответы.

```
python3 tools/eval_competence.py --list              # что проверяем
python3 tools/eval_competence.py --answers a.jsonl   # оценка ответов
```

Живой прогон модели — `tools/eval_competence_run.py`: он получает ответы от бэкенда,
сохраняет их и сразу считает те же проценты (см. «Как померить новую модель» в конце).

## Уточнение к задаче ≠ вопрос клиенту

Это разные вещи, и раньше они были бы смешаны:

- `clarify` — запрос неполный **для нас**: «напиши статью» без темы. Мы спрашиваем
  пользователя, что он имел в виду.
- `client_questions` — **бриф перед работой**: «хочу сайт» → какие вопросы задать
  клиенту, чтобы посчитать и предложить. Это рабочий навык менеджера, а не уточнение.

Поэтому категории отдельные: в первой проверяется, что ассистент не додумывает за
пользователя, во второй — что он умеет вести бриф.

## Почему уточняющие вопросы — отдельная категория

«Напиши статью», «сделай рекламу», «улучши текст» — это не задачи, а половина задачи.
Хороший ассистент спрашивает: тема, аудитория, объём, тон, цель. Плохой — пишет
что-то среднее и заставляет переделывать. Поэтому 8 строк golden требуют **вопрос в
ответе**, и проверка падает, если его нет.

## Калибровка на сильной модели (2026-11-18)

Первая версия требовала «?» дословно и резала ответы по 80–100 слов — и сильная модель
набрала 33%. Ошибка была в спецификации, а не в модели:

- «уточните тему» — это вопрос, даже без вопросительного знака;
- 250 слов на объяснение причины — нормально, 80 — нет;
- «ответ должен содержать слово зависит» — буквализм: «это не или-или» правильнее.

После правок (уточнение по формулировкам, лимиты по p90 + запас) та же модель проходит
**72/72 = 100%**. Это и есть проверка спецификации: если сильная модель падает — виноваты
требования, если проходит — требования реалистичны, и можно мерить слабую.

## Каталог — регрессия, а не качество

`eval/golden_catalog.jsonl` (45 строк) прогоняется `tools/eval_hybrid.py`: маршрут,
покрытие скиллами, стоимость. Это проверка инфраструктуры (скилл/поиск не сломался),
а не «насколько ассистент умный».

## Как пользоваться

1. Правишь промпт → гоняешь `eval_competence` на ответах модели → смотришь по категориям.
2. Меняешь каталог → гоняешь `eval_hybrid` → цифры должны совпасть с каталогом.
3. Оба набора не смешиваются: смешение снова превратит «умение» в «прайс».

## Как померить новую модель (три команды)

`tools/eval_competence_run.py` — раннер: спрашивает модель, сохраняет ответы и сразу
печатает таблицу по 9 категориям и провалы с причинами. Проверки он берёт из
`tools/eval_competence.py`, поэтому второй спецификации нет — оценка и прогон не
разойдутся.

```bash
# 1. один раз: локальный сервер Ollama и модель (3b — быстро, 7b — точнее)
ollama serve & ollama pull qwen2.5:3b

# 2. все 72 строки golden: таблица по категориям + список провалов
python3 tools/eval_competence_run.py --backend ollama --model qwen2.5:3b --workers 4

# 3. перепроверить сохранённые ответы и прочитать провалы глазами
python3 tools/eval_competence.py --answers runs/eval/ollama-qwen2.5-3b-<дата>.jsonl
```

Флаги, которые нужны чаще всего:

| Флаг | Зачем |
|---|---|
| `--backend ollama\|openai\|vtm\|mock` | откуда ответы: Ollama (`:11434`), OpenAI-совместимый (vLLM/eva, `--base`), локальная ВТМ, мок |
| `--model` | имя модели; для `vtm` — путь к `.vtm` |
| `--out` | куда писать ответы; по умолчанию `runs/eval/<бэкенд>-<модель>-<время>.jsonl` |
| `--workers` | параллельные запросы (у `vtm` всегда 1: один контекст) |
| `--max-tokens`, `--timeout`, `--retries` | потолок ответа, таймаут запроса, повторы на таймаут/429/5xx |
| `--limit N` | первые N строк — быстрая прикидка перед полным прогоном |
| `--strict` | код возврата 1, если есть провалы (по умолчанию прогон — 0) |

Файл ответов — JSONL с полями `question`, `category`, `checks`, `answer`, `ok`,
`failures`, `error`, `attempts`, `elapsed_ms`. Его можно читать и править руками,
а потом снова оценить через `eval_competence.py --answers`.

Промпт по умолчанию — `prompts/system.assistant.md` (промпт набора компетенций).
Прод-промпт можно подставить через `--system prompts/system.ru.md`, но тогда числа
не сравнить один в один с прогоном `eval/run_eval.py` по каталогу.

Как читать числа:

- 72/72 — модель проходит спецификацию; смотри, где 8/8, а где 6/8;
- заметно ниже 90% — сначала проверь, не режет ли модель спецификация (калибровка
  выше: сильная модель падала на буквализме, а не на уме), и только потом — веса;
- `mock` — синтетика: проверяет раннер и golden, про модель не говорит ничего;
- `vtm` без `tokenizer.json` не умеет текст — раннер скажет это одной строкой;
- 7b на слабом железе лучше гонять мягче: `--workers 2 --timeout 300
  --max-tokens 512`, иначе часть строк уйдёт в таймаут;
- если Ollama не запущена, раннер печатает «запустите `ollama serve`» и выходит с
  кодом 2, без трейсбека.

Ответы и таблицу имеет смысл хранить: `runs/eval/*.jsonl` — это снимок «что модель
ответила на самом деле», по нему видно, провал из-за требований или из-за модели.
