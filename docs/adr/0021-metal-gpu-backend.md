# ADR 0021. GPU-бэкенд на Metal: CPU остаётся, но тяжёлое уходит на GPU

Дата: 2026-11-26
Статус: принято, реализация — задачами 0192+ (по фазам)
Связано: [0016](0016-vtm-4gib-limit.md), [0020](0020-clients-and-cloud.md)

## Контекст

Замеры 0189 на одной машине (M1 Pro, один промпт 3B Q4_K):

| | prefill | декод |
|---|---|---|
| мы, CPU int8-GEMM | 18,1 ток/с | 12,8 ток/с |
| llama.cpp, CPU | 37–39 ток/с | — |
| ollama, **Metal GPU** | **182–393 ток/с** | **56,5 ток/с** |

Вывод, который дороже любых дальнейших оптимизаций CPU: **разрыв в 10–20 раз —
это GPU**. Попытка догнать его на CPU упирается в железо: 3,09 Г MAC на токен при
60–70 Г MAC/с на процесс дают потолок 18–20 ток/с, тогда как GPU даёт 310+ Г MAC/с.

## Решение

1. **GPU — не замена CPU, а его ускоритель.** Появляется бэкенд `metal` рядом с
   `scalar`/`neon`: те же операции, другой исполнитель. Остаётся выбор бэкенда
   (`VTM_BACKEND=metal|simd|scalar`) и автоматический откат, если Metal недоступен.
2. **На GPU уходит то, что считается матрицами:**
   - GEMV/GEMM для kind 6/7 (Q4_K/Q6_K) и int8-таблицы lm_head;
   - prefill — целиком пачкой (одна GEMM на слой);
   - декод — GEMV по строкам.
   Attention, KV, RMSNorm, softmax, сэмплинг остаются на CPU (маленькие, латентные).
3. **Zero-copy на unified memory.** Apple Silicon делит память: контейнер
   mmap'ится, и `MTLBuffer` создаётся без копирования (`newBufferWithBytesNoCopy`
   на выровненный регион). Иначе 1,9 ГБ весов копировались бы на каждом запуске.
4. **Координация, а не «или-или».** На слой: CPU готовит активации и параметры,
   GPU считает матрицы асинхронно; пока GPU занят слоем N, CPU делает attention и
   нормализацию. Пайплайн на 2–3 командных буфера вперёд.
5. **Диспетчер по замеру, а не по вере.** Мелкие формы (K/V-проекции 256×2048) на
   GPU могут быть медленнее из-за накладных; порог подбирается замером на машине.
6. **Только Apple — сейчас.** Для Android позже понадобится Vulkan/OpenCL; контракт
   бэкенда (`vtm_backend.h`) один, поэтому это будет второй исполнитель, а не
   переписывание.

## Фазы

| Фаза | Что | Цель |
|---|---|---|
| 1 (0192) | GEMV Q4_K/Q6_K + lm_head на Metal, zero-copy буферы | декод ≥30 ток/с |
| 2 | GEMM prefill пачкой на GPU | TTFT 64 токена ≤0,5 с |
| 3 | гибридный планировщик CPU+GPU, attention на GPU при длинном контексте | декод ≥45 ток/с |

## Последствия и риски

- Появляется зависимость от Metal (macOS 13+, `MTLCreateSystemDefaultDevice`).
  Без GPU всё работает как раньше — откат на NEON обязателен и проверяется тестами.
- Точность: int8-dot на GPU может отличаться порядком суммирования; паритет
  проверяем как «argmax + Δlogits ≤1e-2», побитовость (как у CPU-пачки) не обещаем.
- Память: GPU-буферы не должны дублировать веса; следим за footprint через
  `MTLDevice.currentAllocatedSize`.
- Сложность: MSL-ядра надо поддерживать отдельно от NEON; тесты `--check`
  расширяются на новый бэкенд.
