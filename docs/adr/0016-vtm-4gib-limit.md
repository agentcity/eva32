# ADR 0016. Предел контейнера 4 ГиБ и что делать с моделями > 14B

Дата: 2026-11-24
Статус: принято (ограничение зафиксировано, расширение отложено)
Задачи: 0135, 0141

## Контекст

Формат `.vtm` v0.2 хранит смещения и размеры в `u32`: поле `offset` записи тензора
и общие размеры секций. 32B-раскладка Qwen2.5 (64 слоя, hidden 5120, vocab 151936)
в тритах занимает **7 429 384 288 Б = 6,92 ГиБ** — больше 4 ГиБ.

Замеры на 7B/14B (mac arm64, SIMD):
| Форма | Файл | Граф + запись | 1 токен |
|---|---|---|---|
| 1.5B | 0,34 ГиБ | 0,23 + 0,33 с | 309 мс |
| 7B | 1,53 ГиБ | 0,47 + 0,58 с | 1201 мс |
| 14B | 3,03 ГиБ | 0,67 + 1,14 с | 2867 мс |
| 32B | 6,92 ГиБ | — | **невозможно** |

## Решение

1. **Формат не менять сейчас.** 32B в тритах на нашем железе даёт ~1 ток/с — то есть
   даже при наличии формата это не рабочая конфигурация. Тратить version bump на
   недостижимый сценарий нерационально.
2. **Явный отказ с числами.** Компилятор считает размер до записи и отказывает:
   «раскладка 6,92 ГиБ > 4 ГиБ; нужен u64-смещения (v0.3) или шардинг». Молчаливой
   порчи файла не бывает.
3. **14B — верхняя граница** для v0.2. 7B/14B компилируются и запускаются.
4. **Расширение — отдельная задача (0141)** с ADR при реализации: варианты
   (а) v0.3 с `u64` смещениями (формат + загрузчик), (б) шардинг модели на
   несколько `.vtm` с общим интерпретатором.

## Следствия

- 32B/70B в ВТМ сейчас невозможны — и это осознанно, а не «не успели».
- Для тестов «насколько умна» большие модели идут через ollama (GGUF), не через ВТМ.
- Если понадобится 32B в ВТМ, критерий — сначала скорость (int8-dot/AVX-512),
  потом формат: иначе получим файл, который считается минуту на токен.

## Альтернативы

- **Поднять u32 → u64 сразу.** Ломает ABI записей (52 байта → 60), версию и все
  читатели; выгода только для недостижимых конфигураций.
- **Шардинг без смены формата.** Позволяет 32B, но требует изменений в интерпретаторе
  (межшардовые ссылки на тензоры) — большая правка ради 1 ток/с.
