# ADR 0003: Своя виртуальная троичная машина вместо bitnet.cpp

- Статус: accepted
- Дата: 2026-11-18
- Контекст: исполнение троичной модели

## Контекст

Мы собрали и запустили bitnet.cpp на 2B-модели: работает, но

- диктует свой формат весов (`i2_s`, `tl1`) — наш `.trit` не подходит;
- ядра спрятаны, оптимизированный путь включается только их же квантователем;
- тянет весь llama.cpp как зависимость;
- при переносе на другое железо (фотоника, ПЛИС) менять нечего — всё внутри форка.

Замер: на дефолтном пути 3,7 ток/с, без масштабирования по потокам — то есть
быстрый путь там есть, но нам он не подконтролен.

## Решение

Своя машина VTM: **компилятор графа → байткод `.vtm` → интерпретатор → бэкенд**.
Инструкция фиксированного размера 16 байт, тензоры адресуются индексами таблицы,
операции — `TMV`, `ATTN`, `RMSN`, `ROPE`, `SM`, `SILU`, `MM`, `EMB`, `KVW`,
`SAMP`, `ADD`, `MUL`, `CPY`, `SCAL`, `HALT`. Контракт бэкенда — набор указателей
на функции с фолбэком на скалярную реализацию.

## Альтернативы

| Вариант | Почему нет |
|---|---|
| Остаться на bitnet.cpp | формат и ядра не наши, перенос на другое железо невозможен |
| Форк llama.cpp | тот же груз зависимостей, только с нашим логотипом |
| ONNX Runtime | троичные веса не поддерживаются как тип; переносим то же отсутствие контроля |
| Чистый Python-рантайм | скорость на порядки хуже, для продукта не годится |
| Только HF-инференс на GPU | противоречит цели «дешёвое железо» |

## Последствия

- **Месяцы работы**, а не дни: нужны RoPE, GQA, KV-кэш, BPE-токенизатор,
  отладка численных расхождений.
- Мы отвечаем за собственные баги и производительность.
- Зато: формат наш, бэкенд меняется без перекомпиляции модели, и появляется
  точка для будущего железа.
- Пересматриваем, если: появится открытый рантайм с нативными тритами и C-ABI,
  либо если сроки продукта потребуют работающего инференса раньше, чем мы
  допишем свой (тогда — временно bitnet.cpp как чёрный ящик).
