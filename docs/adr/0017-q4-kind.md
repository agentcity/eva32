# ADR 0017. kind 5 (Q4) без поднятия версии контейнера

Дата: 2026-11-24
Статус: принято
Задачи: 0151, 0152, 0153

## Контекст

Контейнер `.vtm` знал триты (kind 0), fp32/fp16/bf16 (kind 1–3) и int8 с
масштабами по блоку 128 (kind 4). Модели из Ollama приходят в GGUF с Q4_0/Q4_1:
4 бита на вес плюс масштаб на группу 32. Без такого вида «7B Q4» в ВТМ не
загрузить: материализация 7B в fp32 — это ~28,7 ГБ RAM (задача 0152).

## Решение

1. **Новый kind 5** — самодостаточный Q4-сегмент по `offset`, по образцу
   INT8/TRT1: `"Q4_0"`/`"Q4_1"` | version u8 (=1) | flags u8 (бит 0 — fp32-
   масштабы, иначе fp16) | `n_values u64` | `n_groups u32`; затем масштабы,
   у Q4_1 — `n_mins u32` и массив `min`, затем упакованные нибблы.
   `scale_offset = 0xFFFFFFFF`.
2. **Раскладка группы 32 значения = 16 байт**: байт `j` хранит значение `j`
   в младшем ниббле и `j+16` в старшем. Это раскладка GGML Q4_0: импорт GGUF
   (0153) не перепаковывает веса, а ядра (0152) читают строку теми же 16
   байтами. `Q4_0`: `w = (nibble − 8) · scale`; `Q4_1`:
   `w = nibble · scale + min`.
3. **Загрузчик не материализует fp32**: упакованные байты остаются в
   `vtm_tensor.words`, fp32-масштабы — в `scales`, `min` — в `q4_mins`;
   `f32 == NULL`, `kind == 5`. В mmap-режиме нибблы (и fp32-масштабы/min на
   платформах с невыровненными загрузками) читаются прямо из отображения.
4. **Q4_1 обязателен для импорта GGUF**, но не является «Q4_0 с догадкой»:
   если `n_mins != n_groups` или массива min нет — `VTM_E_FORMAT`, а не
   молчаливое симметричное чтение.

## Версия формата

Версия контейнера остаётся **2**. `kind` — это значение одного байта в записи
тензора, а не версия раскладки: старые контейнеры (kind 0..4) читаются
прежним путём. Старый загрузчик уже отвергает любой незнакомый kind
(`VTM_E_FORMAT`, «неизвестный kind 5») **до чтения данных**, поэтому тихой
порчи весов нет — это тот же tripwire, что в ADR 0015 для KV-кэшей.

Поднятие версии сломало бы чтение всех старых контейнеров новыми бинарями
сразу, а выигрыша не дало бы: одна проверка `kind` уже даёт и прямую
совместимость, и внятный отказ старому бинарю.

## Альтернативы

- **Поднять версию контейнера.** Отвергнуто: ломает все старые файлы ради
  нового вида тензора; byte-kind и tripwire дают то же дешевле.
- **Материализовать Q4 в fp32 при загрузке.** Отвергнуто: 7B — 28,7 ГБ RSS,
  задача 0152 существует ровно чтобы этого не делать.
- **Переиспользовать kind 4 с флагом «4-битный».** Отвергнуто: у int8 другой
  блок масштаба (128), другой размер q (1 байт) и другая семантика
  (`q ∈ −127..127`); флаг внутри сегмента сделал бы парсер ветвистым и
  сломал бы старые int8-читатели.
- **Хранить масштабы в `scale_offset` как у raw-тритов.** Отвергнуто:
  у Q4 уже есть заголовок сегмента; отдельная таблица масштабов потребовала
  бы второго `offset` и проверок перекрытия, а сегмент остаётся атомарным.
- **Q4_1 не поддерживать (только Q4_0).** Отвергнуто для формата: 0153
  импортирует GGUF Q4_1; ядра 0152 уже принимают `mins`/`asym`. Цена —
  один `n_mins` и массив min в сегменте.

## Следствия

- Старый бинарь на Q4-контейнере: **внятный отказ** `VTM_E_FORMAT`
  («неизвестный kind 5»), а не мусорные веса.
- Новый бинарь читает старые контейнеры без изменений; контейнеры без Q4
  пишутся байт-в-байт как раньше.
- Загрузчик обязан отдавать упакованные данные; ядра 0152 читают их на лету,
  интерпретатор не получает fp32-копию. Q4-тензор нельзя использовать как
  плотный `kind 1..3`: старый interp без Q4-ядер падает с `VTM_E_TENSOR`.
- Q4_1 требует `q4_mins`; если ядро их не передало, оно обязано вернуть
  ошибку (`vtm_q4_*` с `asym=1` и `mins=NULL` → `-1`), а не считать Q4_0.
- Цена: 4,5–5 бит на вес (fp16/fp32-масштабы). Для 7B с fp32-масштабами это
  ~4,375 ГБ, то есть **выше предела 4 ГиБ** u32-смещений (ADR 0016); с
  fp16-масштабами — ~3,94 ГБ, влезает. Для 7B писать fp16-масштабы.
- `vtm inspect` в этой задаче не обновлялся (вне зоны): kind 5 показывается
  как `?`, но загрузка и прогон работают; имя вида — отдельная правка CLI.
