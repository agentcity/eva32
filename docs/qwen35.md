# Gated Delta Net в ВТМ: линейное внимание Qwen3.5

> Актуально на 2026-11-26. Задача [0176](../ai/tasks/0176-gated-delta.md),
> этап 1a — **только Python-эталон**. Разведка 35B — [moe-recon.md](moe-recon.md),
> MoE — [moe.md](moe.md), контейнер и опкоды — [vtm.md](vtm.md).

## Зачем

Вся линейка Qwen3.5 — гибрид: 30 слоёв из 40 считают `linear_attention`
(Gated Delta Net), каждый 4-й — обычное полное внимание. Без этой механики
недоступны 9b/27b/35b; 27b (17–20 ГБ) в 16 ГиБ не влезает, поэтому цель —
**qwen3.5:9b** (6,6–7,6 ГБ). Параметры из `config.json` 35B-A3B (аналогично 9b),
подробно — в [moe-recon.md](moe-recon.md):

| Параметр | Значение |
|---|---|
| `layer_types` | 30 × `linear_attention` + 10 × `full_attention` |
| `linear_conv_kernel_dim` | 4 |
| `linear_num_key_heads` / `linear_num_value_heads` | 16 / 32 |
| `linear_key_head_dim` / `linear_value_head_dim` | 128 / 128 |
| `mamba_ssm_dtype` | float32 (состояние) |

Этап 1a даёт **эталон истины**: `tools/vtm_ref.py` исполняет `CONV4` (0x12) и
`GDELTA` (0x13). C-часть (`src/vtm/interp.c`) отложена: файл держит задача 0181.
Пока нет C, нет и импортёра/компилятора под Qwen3.5 — считать реальные веса
нечем; но формулы, раскладка состояния и паритетный тест уже зафиксированы.

## Механика

### CONV4 (0x12) — короткая свёртка по q/k/v

Причинная depthwise-свёртка с ядром 4: у каждого канала свой набор из четырёх
весов, выход зависит только от этого канала. Один токен за инструкцию:

```
s = [x_{t-3}, x_{t-2}, x_{t-1}, x_t]        # первые три — состояние, нули на старте
y[c] = Σ_{j=0..3} w[c, j] · s[j, c]
state ← [x_{t-2}, x_{t-1}, x_t]             # сдвиг на один токен
```

`w[c, j]` соответствует весу `Conv1d` из HF: у `linear_conv1d.weight` форма
`[width, 1, kernel]`, то есть `w[c, j]` — это `weight[c, 0, j]`; свёртка
причинная (`padding_left = kernel − 1 = 3`), смещения (bias) нет.

Ширина канала у Qwen3.5: `Hk·Dk·2 + Hv·Dv = 16·128·2 + 32·128 = 8192`
(q, k и v идут одним потоком). Состояние — `3 × 8192 × 4 = 96 КиБ` на слой,
`× 30 = 2,8 МиБ` на модель. Это ничтожно рядом с весами и с KV полного
внимания (ниже).

| Поле | Что |
|---|---|
| `a` | `x` `[width]`, fp32 |
| `b` | `w` `[width, 4]`, fp32 |
| `c` | состояние `[3, width]`, fp32, флаг `STATE`, payload'а в файле нет |
| `dst` | `y` `[width]`, fp32 |
| `imm` | 0 (резерв) |

Проверка: неверное `w`/состояние — `ValueError` с текстом, а не «почти то же».

### GDELTA (0x13) — шаг gated delta rule + выходной гейт

Рекуррентное правило (arXiv 2412.06464, gated delta rule; частный случай
delta-правила Schlag et al. 2021 с глобальным затуханием):

```
S_t = α_t · S_{t-1} · (I − β_t · k̂_t k̂_tᵀ) + β_t · v_t k̂_tᵀ
    = α_t · S_{t-1} + β_t · (v_t − α_t · S_{t-1} k̂_t) · k̂_tᵀ
o_t = S_t · q̂_t
y_t = rmsnorm(o_t) ⊙ norm_w ⊙ silu(z_t)
```

где `k̂ = k/√(k·k+eps)`, `q̂ = q/√(q·q+eps)`, `α = exp(g)` (g — **лог**
затухания, `α ∈ (0,1]`), `β = sigmoid(beta)`, `silu(z) = z/(1+e^{−z})`,
`rmsnorm` — по `Dv` внутри value-головы (как `RMSNormGated` в Qwen3-Next).

**Раскладка состояния.** В статье `S` имеет форму `[Dv, Dk]` и `o = S q`;
в ВТМ состояние объявлено `[Hv, Dk, Dv]` — это транспозиция, формулы
эквивалентны. В индексах (именно так считает эталон и должен считать C):

```
u[dv]      = Σ_dk S[dk, dv] · k̂[dk]                     # u = k̂ᵀS
γ[dv]      = v[dv] − α · u[dv]
S_t[dk,dv] = α · S_{t-1}[dk,dv] + β · k̂[dk] · γ[dv]
o[dv]      = Σ_dk S_t[dk,dv] · q̂[dk]                     # o = S_tᵀq̂
y[dv]      = o[dv]/√(mean_dv(o²)+eps) · norm_w[dv] · silu(z[dv])
```

Важно: выход считается по **обновлённому** состоянию `S_t` (а не по
`S_{t-1}`), а `β` умножает всю дельта-поправку. `eps` — из `imm` (`imm/1e6`,
0 — без эпсилона); он же используется в выходном RMSNorm, иначе было бы два
разных эпсилона в одной инструкции.

**Гейт идёт в архитектуре, не в статье.** В статье 2412.06464 нет выходного
RMS-гейта: это деталь Qwen3-Next (`RMSNormGated(x, gate) = x/rms(x)·w·silu(gate)`),
перенесённая в Qwen3.5. Если у реального Qwen3.5 гейт иной (например,
`sigmoid` вместо `silu`), меняется одна строка в конце `GDELTA` — на
рекуррентность и состояние это не влияет. Состояние от гейта не зависит вообще.

**Масштаб q.** В Qwen3-Next после L2-нормировки q умножается на `1/√Dk`
(`scaling`). В опкоде этого множителя нет: выходной RMSNorm инвариантен к
общему масштабу `o`, а `o` линеен по `q̂`, поэтому `1/√Dk` сокращается точно
(в fp — до округления). Это проверено в тесте `test_l2_norm_of_q_and_k`
(выход не зависит от длины q/k, если направление то же).

| Поле | Что |
|---|---|
| `a` | `q` `[Hk, Dk]`, fp32 (общий для групп value-голов) |
| `b` | `k` `[Hk, Dk]`, fp32 |
| `dst` | `y` `[Hv, Dv]`, fp32 |
| `c` | **первый из шести** подряд идущих тензоров банка |
| `imm` | `eps × 1e6` (0 — без эпсилона) |

Банк (`c`..`c+5`) — часть ABI, как у `MOE`:

| Индекс | Тензор | Форма | Смысл |
|---|---|---|---|
| `c` | состояние | `[Hv, Dk, Dv]` | флаг `STATE`, payload'а нет, f32 |
| `c+1` | `v` | `[Hv, Dv]` | вход |
| `c+2` | `beta` | `[Hv]` | логит: `β = sigmoid(beta)` |
| `c+3` | `g` | `[Hv]` | лог затухания: `α = exp(g)` |
| `c+4` | `z` | `[Hv, Dv]` | гейт перед `silu` |
| `c+5` | `norm_w` | `[Dv]` | вес выходного RMSNorm |

`Hv` обязано делиться на `Hk`; value-голова `h` берёт key-голову
`kh = h / (Hv/Hk)`. Остальные формы проверяются, ошибка — `ValueError`.

### Состояние и контейнер

Состояние — такой же буфер «вне файла», как KV-кэш (задачи 0101/0118): в
таблице тензоров только `name`/`kind`/`dims`, `offset = KV_NO_OFFSET`, payload
0 байт, заголовок контейнера получает `VFLAG_KV_OUT_OF_FILE`. Роль задаёт
`VTM_TENSOR_FLAG_STATE` (бит 1). Читатель создаёт буфер нулями; `execute`
выделяет новый интерпретатор на вызов, поэтому **сброс состояния = новый
`execute`** (в C это будет `vtm_reset`).

Память состояния на слой и на модель (f32):

| Что | На слой | 30 слоёв |
|---|---|---|
| GDELTA `[32, 128, 128]` | 2 МиБ | 60 МиБ |
| CONV4 `[3, 8192]` | 96 КиБ | 2,8 МиБ |

Для сравнения: KV полного внимания (10 слоёв, 2 kv-головы × `head_dim` 256,
K и V, f32) — 4 КиБ на токен на слой, 40 КиБ на токен на модель: 1,25 ГиБ при
ctx 32k и ~10 ГиБ при ctx 262k. Гибрид удешевляет **линейные** слои, но
длинный контекст всё равно упирается в полные — это отдельный риск/задача.

## Ручная проверка (этап 1a)

Обе операции проверены «на бумаге» и в тесте
[`tests/test_gated_delta.py`](../tests/test_gated_delta.py) (17 тестов):

```
$ python3 -m unittest tests.test_gated_delta -v
...
Ran 17 tests

OK
```

**CONV4.** `width = 2`, `w = [1,10,100,1000]` и `[2,20,200,2000]`, входы
`[1,1], [2,1], [3,1], [4,1]`:

| t | s | y (канал 0) | y (канал 1) |
|---|---|---|---|
| 0 | `[0,0,0,x0]` | `1000·1 = 1000` | `2000·1 = 2000` |
| 1 | `[0,0,x0,x1]` | `100·1 + 1000·2 = 2100` | `200·1 + 2000·1 = 2200` |
| 2 | `[0,x0,x1,x2]` | `10·1 + 100·2 + 1000·3 = 3210` | `20 + 200 + 2000 = 2220` |
| 3 | `[x0,x1,x2,x3]` | `1 + 20 + 300 + 4000 = 4321` | `2 + 20 + 200 + 2000 = 2222` |

Состояние после `t=3` — `[x1, x2, x3] = [2,1, 3,1, 4,1]`; тест сверяет и его.

**GDELTA.** `Hk = Hv = 1`, `Dk = Dv = 2`, `q = k = [1,0]`, `β = 0.5`
(`beta = 0`), `α = 1` (`g = 0`), `z = [1,1]`, `norm_w = [1,1]`,
`silu(1) = 1/(1+e⁻¹) = 0.7310585786`:

| Шаг | v | S после шага | o | y |
|---|---|---|---|---|
| 0 | `[2,4]` | `[[1,2],[0,0]]` | `[1,2]` | `[0.4623620423, 0.9247240846]` |
| 1 | `[4,2]` | `[[2.5,2],[0,0]]` | `[2.5,2]` | `[0.8073191449, 0.6458553159]` |

Шаг 1 показывает дельта-поправку: `u = S₁k̂ = [1,2]`, поэтому
`γ = v − αu = [3,0]`, а не `v = [4,2]`. Отдельно проверены: L2-нормировка
(`q=[3,0], k=[0,5]` → `q̂ ⟂ k̂`, выход 0), затухание (`k=v=0`, `g=ln 0.5` →
состояние ровно вдвое меньше), две value-головы на одну key-голову, гейт
`silu` и `norm_w`, форма Qwen3.5 (32 × 128 × 128).

**Про «нулевое состояние → нулевой выход».** В честной формулировке это
неверно: при `S = 0` правило даёт `S_t = β·k̂ᵀv` и
`o = β·(k̂·q̂)·v`. Ноль на выходе будет только если `v = 0`, `q ⟂ k` или
`silu(z) = 0`. Тесты проверяют именно эти случаи, а не ложное свойство.
Сброс состояния проверяется иначе: повторный `execute` даёт те же числа, что
первый прогон (остатка прошлого прогона нет), в том числе после длинного
прогона и после чтения контейнера из файла.

## Что осталось для C (этап 1b)

Опкоды 0x12/0x13 и флаг `VTM_TENSOR_FLAG_STATE` уже объявлены в
[`src/vtm/vtm.h`](../src/vtm/vtm.h), но реализации в C нет. Порядок:

1. `op_conv4`/`op_gdelta` в `src/vtm/interp.c` (scalar double, запись в f32) —
   по формулам выше; сверять с `tools/vtm_ref.py`, а не наоборот.
2. Загрузчик `src/vtm/loader.c`: буфер состояния в контексте (как KV),
   `offset == KV_NO_OFFSET`, `VFLAG_KV_OUT_OF_FILE` для контейнера с
   состояниями, проверка кэпа `VTM_MAX_KV_BYTES` вместе с KV.
3. `vtm_reset()` обнуляет состояния (KV сбрасывает хост — как и раньше).
4. `--trace-summary`: `CONV4`/`GDELTA` в счёте опкодов и в чтениях/записях
   (в `interp.c` уже есть упоминание GDELTA в разборе пачки — проверить).
5. Тест паритета Python↔C на случайных тензорах, порог ≤1e-6; состояние —
   f32 на каждом шаге, иначе длинный прогон разойдётся.
6. Компилятор и импортёр Qwen3.5: `linear_conv1d` (веса `[width,1,4]`),
   `A_log`/`dt_bias` → `g = −exp(A_log)·softplus(a + dt_bias)` в компиляторе,
   `beta = sigmoid(b)`, раскладка банка, `layer_types`, mRoPE, MoE (0172).
7. `docs/vtm.md`: строки таблицы опкодов 0x12/0x13 — сейчас
   `tools/check_vtm_docs.py` красный (в `vtm.md` 17 опкодов, в `vtm.h` 19;
   после этапа 1a и Python-энума тоже 19). Правится в C-задаче, не здесь.

## Источники и допущения

* Gated Delta Networks: Improving Mamba2 with Delta Rule — arXiv
  [2412.06464](https://arxiv.org/abs/2412.06464) (Yang, Kautz, Hatamizadeh,
  ICLR 2025): рекуррентная форма gated delta rule, L2-нормировка q/k.
* Delta rule — Schlag, Irie, Schmidhuber, «Linear Transformers Are Secretly
  Fast Weight Programmers» (2021): `S ← S + β(v − Sk)kᵀ`.
* Выходной RMS-гейт — архитектура Qwen3-Next (`RMSNormGated`, `silu`), в
  статье 2412.06464 его нет; в 1a взят как есть.
* Конфигурация Qwen3.5 — из `config.json` 35B-A3B, см.
  [moe-recon.md](moe-recon.md). Сети на этапе 1a не было: формулы сверены с
  публичным описанием по памяти и проверены ручными примерами, а не с
  эталонным кодом Transformers. Расхождения с реальным Qwen3.5 возможны
  только в деталях гейта/параметризации `g` (см. риски).

## Риски

1. **Бит `STATE` пересекается с хранением тритов.** `VTM_TENSOR_FLAG_STATE =
   0x0002` — это же бит 1 из `VTM_TENSOR_FLAG_STORAGE_MASK = 0x0006`
   (`native`-триты, задача 0057). Python различает по `kind` (STATE только у
   fp), и C обязан делать так же; сейчас `loader.c` проверяет
   `flags & VTM_TENSOR_FLAG_OUT_OF_FILE` (0x0003) **до** разбора `kind`,
   поэтому нативный трит будет принят за буфер вне файла. Варианты: перенести
   STATE на свободный бит (0x0008) или проверять `kind` раньше флага. Это
   блокер C-этапа, а не 1a.
2. **Гейт и параметризация `g` не сверены с реальным Qwen3.5** (нет сети).
   Если гейт `sigmoid`, а не `silu`, или `α` считается иначе, меняется хвост
   операции/компилятор, но не рекуррентность и не раскладка состояния.
3. **`√Dk` для q.** В опкоде множителя нет; он сокращается выходным RMSNorm
   математически, но при реальных весах это надо подтвердить паритетом с
   HF-реализацией (там масштаб применяется до правила).
4. **f32-состояние и длинный контекст.** Каждый шаг округляет `S` до f32;
   на 262k токенов ошибка накапливается. Паритет с C требует округления
   состояния на каждом шаге, а не только на выходе.
5. **Длинный контекст упирается в полное внимание**: 10 слоёв × 40 КиБ/токен
   на модели — 10,5 ГиБ при 262k. Линейные слои этого не решают; нужен
   квантизованный/постраничный KV или меньший ctx.
6. **Нет импортёра/компилятора Qwen3.5** — реальные веса не проверены, имена
   и формы тензоров (conv1d, `A_log`, `dt_bias`, `norm`) взяты по аналогии с
   Qwen3-Next; возможны расхождения.
7. **Скорость Python-эталона**: на слой — `Hv·Dk·Dv = 0,52 млн` пар
   «умножить-сложить» за проход, а проходов по состоянию три (u, обновление,
   o) ≈ 1,6 млн; 30 слоёв — ~47 млн MAC на токен. Годится только для
   паритета, не для инференса.
8. **Один `eps` на L2-норм и RMSNorm.** Если в C понадобится разделить,
   придётся добавить ключ в мету (сейчас `imm` — единственный параметр).
9. **`check_vtm_docs.py` уже красный** (docs/vtm.md без 0x12/0x13) — следствие
   объявлений первого исполнителя, к 1a отношения не имеет; закрывается в C.
