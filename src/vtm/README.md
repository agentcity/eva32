# VTM — скалярный интерпретатор (этап 2)

Реализация `docs/vtm.md` на C99 без внешних зависимостей (только `libm`).
Здесь же зафиксированы решения, которых в спеке не было: без них Python-эталон
и C-интерпретатор не сойдутся.

## Сборка и проверка

```bash
cd src/vtm
make            # libvtm.a + vtm
make test       # тесты из tests/vtm/test_vtm.c
./vtm           # справка, код 2
./vtm bench     # LUT243 против прямой распаковки
```

Флаги: `-std=c99 -O2 -Wall -Wextra -Werror`.

## Соглашения v0.1 (важно для Python-эталона)

### Заголовок 32 байта

```
0   magic "VTM1"
4   version u16 = 1
6   flags u16          бит 0: raw-триты хранят масштабы fp32 (иначе fp16);
                       бит 15 (0x8000): неоднозначный n_scale — это 160
8   n_instr u32
12  n_tensors u32
16  n_program u32      размер программы в байтах (= n_instr*16; 0 = не проверять)
20  program_offset u32 расширение Python-эталона; C игнорирует
24  meta_offset u32    расширение Python-эталона; C игнорирует
28  meta_len u32       расширение Python-эталона; C игнорирует
```

Последние 12 байт спека называет резервом. Python-эталон кладёт туда
`program_offset`/`meta_offset`/`meta_len`; C их не читает и находит
программу как `file_size - n_instr*16`, поэтому оба варианта совместимы.

Программа лежит **в конце файла**: `program_off = file_size - n_instr*16`.
Поэтому секция данных имеет размер `program_off - data_start`, а `offset` в
таблице тензоров — смещение от `data_start` (не от начала файла).
`data_start = align32(32 + n_tensors*44)`, `offset` обязан быть кратен 32.

`n_program` в спеке назван, но не расшифрован. Каноническое значение —
размер программы в байтах. Загрузчик принимает 0 (не проверять) или
`n_instr*16`.

### Таблица тензоров, 44 байта

```
0   name[24]      NUL обязателен
24  kind u8       0 trit, 1 f32, 2 f16, 3 bf16
25  ndim u8       1..4
26  dims u16[4]   dims[0] — старшая ось
34  offset u32    от data_start, кратен 32
38  scale_offset u32
42  reserve u16
```

Триты (kind 0) поддерживаются в двух раскладках:

1. **TRT1-сегмент** (`scale_offset == 0xFFFFFFFF`): по `offset` лежит
   `"TRT1"`, version u8 = 1, flags u8 (бит 0 — fp32-масштаб), n_trits u64,
   n_scale u32, затем `n_scale` масштабов, затем `ceil(n_trits/160)*8`
   слов pack20. `n_trits` обязан равняться произведению dims.
2. **raw** (`scale_offset != 0xFFFFFFFF`): по `offset` лежат слова, по
   `scale_offset` — масштабы. Ширина масштаба берётся из флага заголовка.
   Оба смещения кратны 32.

**Блок масштаба.** `docs/trit-format.md` фиксирует 160 тритов на масштаб,
а Python-эталон (`tools/vtm_ref.py`) — 128 (блок QAT; упаковочный блок при
этом всё равно 160 = 8 слов). C читает оба варианта:

* `n_scale == ceil(n_trits/128)` и не равно `ceil(n_trits/160)` → 128;
* `n_scale == ceil(n_trits/160)` и не равно `ceil(n_trits/128)` → 160;
* если числа совпали (маленький тензор) → 128, как канон Python;
* флаг заголовка `0x8000` (расширение C) принудительно выбирает 160 —
  Python-эталон его не ставит и не проверяет.

В таблице тензора это поля `n_blocks` (число 160-тритовых блоков хранения),
`n_scales` (число масштабов) и `scale_block` (128/160). Raw-раскладка
использует 160 — это расширение C, Python её не пишет. Бэкенд получает
`scale_block` через `tmv_blocks`; старый `tmv` считает 160.

f32/f16/bf16 при загрузке приводятся к fp32 в арене. На big-endian файл
читается побайтово, формат от платформы не зависит.

### Инструкция, 16 байт

```
0  opcode u8
1  flags u8
2  dst u16
4  a u16
6  b u16
8  c u16
10 padding u16      (в каноне 0; загрузчик игнорирует)
12 imm i32
```

Поля из спеки в сумме дают 14 байт; два байта — выравнивание `imm` до 4
байт (как в обычной C-структуре и в Python-эталоне `<BBHHHH2xi>`).
**imm пишется по смещению 12, а не 10.**

### Поля инструкций

| Op | dst | a | b | c | imm |
|---|---|---|---|---|---|
| `TMV` | y | W (trit) | x | — | — |
| `MM` | Y | A | B | — | — |
| `RMSN` | y | x | w | — | eps×1000 |
| `ROPE` | y | x | heads | — | смещение позиции |
| `SM` | y | x | — | — | смещение causal |
| `SILU` | y | x | — | — | — |
| `MUL` | y | a | b | — | — |
| `ADD` | y | a | b | — | — |
| `EMB` | y | E | — | — | token id |
| `KVW` | K-кэш | K | V-кэш | V | смещение позиции |
| `ATTN` | out | Q | K | V | q_start (только кэш) |
| `SAMP` | token-буфер | logits | — | — | режим (0) |
| `CPY` | y | x | — | — | — |
| `SCAL` | y | x | — | — | k×1000 |
| `HALT` | — | — | — | — | — |

В спеке у `MUL`/`ADD` написано `c = a·b`; буква `c` там означает
результат, а не поле. Приёмник — всегда `dst`.

### Позиция и токен — регистры хоста

У машины два целых регистра:

* `m->position` — база позиции (`vtm_set_position`);
* `m->input_token` — токен для `EMB` с флагом `VTM_FLAG_EMB_INPUT`
  (`vtm_set_token`, по умолчанию `-1`).

Все позиционные операции считают

```
pos = m->position + imm
```

Для одиночного прогона с `position = 0` это ровно `imm`, как в спеке.
Хост перед каждым `vtm_run()` двигает `position`; так один байткод
исполняется по токенам без ветвлений.

`EMB` без флага `VTM_FLAG_EMB_INPUT` берёт `imm`; с флагом — `input_token`,
а `imm` игнорируется (можно писать `-1`).

### ROPE

Стандартный RoPE из Llama/HF (`rotate_half`). Голов `b`, длина головы
`head_dim = n_elements / heads` (чётная). Для головы `h` и `i` из
`0..head_dim/2-1`:

```
theta = pos · 10000^(-2i/head_dim)
y[i]          = x[i]·cos(theta) - x[i+half]·sin(theta)
y[i+half]     = x[i+half]·cos(theta) + x[i]·sin(theta)
```

Флаг `VTM_FLAG_ROPE_INTERLEAVED` (0x02) переключает на пары `(2i, 2i+1)`
(GPT-NeoX). По умолчанию — половинки, как в Qwen/Llama. В обоих случаях
поворот идёт внутри каждой головы независимо.

### SM (softmax)

По последней оси: `cols = dims[ndim-1]`, `rows = n_elements/cols`.
Максимум вычитается, сумма и экспоненты считаются в `double`.
С `VTM_FLAG_CAUSAL` элемент `j` строки `r` остаётся, только если

```
j <= r + (m->position + imm)
```

остальные обнуляются после softmax. Если строка замаскирована целиком —
нули. Для 1D-тензора `rows = 1`, и causal-маска с offset 0 оставляет только
первый элемент; на полной последовательности это обычное `j <= r`.
Alias `dst == a` разрешён: максимум и сумма считаются до записи.

### ATTN

Масштаб `1/sqrt(head_dim)`, softmax как в SM, накопление в `double`.
GQA: `n_heads % n_kv_heads == 0`, голова `h` идёт в `kvh = h / (n_heads/n_kv_heads)`.

Две раскладки, различаются рангом `b`/`c`:

1. **Обычная, 3D**: `Q [n_heads, q_len, d]`, `K/V [n_kv_heads, kv_len, d]`,
   `out [n_heads, q_len, d]`. `q_start = kv_len - q_len` (нужно
   `q_len <= kv_len`). С `CAUSAL` ключ `j` виден строке `i`, если
   `j <= q_start + i`. `imm` не используется.
2. **С кэшем, 2D**: `K/V [ctx, n_kv_heads*d]`, `Q/out` — 3D.
   `q_start = m->position + imm`, валидны ключи `0 .. q_start+q_len-1`
   (нужно `q_start+q_len <= ctx`). С `CAUSAL` — та же формула
   `j <= q_start + i`.

`out` не должен совпадать с `Q/K/V`. Сложность наивная
`O(n_heads·q_len·keys·d)`, без потоков.

### KVW

`dst` — K-кэш `[ctx, kv_dim]`, `a` — K-вектор `[kv_dim]`,
`b` — V-кэш `[ctx, kv_dim]`, `c` — V-вектор `[kv_dim]`,
`imm` — позиция. `pos = m->position + imm`, `0 <= pos < ctx`.
Слой задаётся самими тензорами (у каждого слоя свой кэш), отдельного поля
layer нет. Кэш — обычный fp32-тензор, аллоцируется в общей арене.

### EMB и SAMP

`EMB`: `E [vocab, dim]`, `y [dim]`, копирование строки. Статический id —
`imm`; динамический — `input_token` при флаге `VTM_FLAG_EMB_INPUT`.

`SAMP` v0.1: `imm == 0` — жадный argmax ровно как в Python-эталоне
(`best = logits[0]`, затем только строгое `>`; NaN не побеждает).
`imm != 0` — зарезервировано под температуру/top-k и возвращает
`VTM_E_UNSUPPORTED`. Если задан `dst`, id кладётся в `dst->f32[0]` как
float. Callback получает `(token, position)`; возврат не 0 — вежливая
остановка прогона (`vtm_run` вернёт `VTM_OK`).

### Бэкенд

`vtm_backend` из спеки: `tmv` получает поток слов pack20, масштабы (уже
fp32), `x`, `rows`, `cols`; `tmv_blocks` дополнительно получает
`scale_block` (128/160). Для каждой строки слова идут по плоскому
row-major потоку; граница блока масштаба не обязана совпадать с границей
строки. Если `tmv_blocks == NULL`, интерпретатор использует `tmv` только
для 160, а для 128 падает обратно на скалярный LUT. Любое поле `NULL`
означает «взять скалярную реализацию». По умолчанию —
`vtm_backend_scalar_lut`.

### Память

* Файл читается в память целиком (пока без mmap), предел 4 ГиБ.
* Все данные тензоров копируются в **одну арену**, начало выровнено на 64,
  каждый тензор — на 64; слова тритов идут первыми, масштабы — после них.
* `vtm_free()` освобождает арену, таблицу тензоров, инструкции и саму
  машину. Временные `malloc` есть только в ATTN (`scores`) и освобождаются
  в той же функции.
* KV-кэш — обычные тензоры в арене; отдельной арены в v0.1 нет.

## Замер TMV: LUT243 против прямой распаковки

Apple M1 Pro, Apple clang 17, `-O2`, скалярный C. Обе реализации дают
побитово одинаковый результат (расхождение 0).

| Матрица | Блок | LUT243 | direct | LUT быстрее |
|---|---:|---:|---:|---:|
| 128×128, 2000 ит. | 160 | 0,010 мс; 1611 Мтрит/с | 0,058 мс; 281 Мтрит/с | **5,73×** |
| 128×128, 2000 ит. | 128 | 0,026 мс; 640 Мтрит/с | 0,075 мс; 217 Мтрит/с | **2,94×** |
| 512×512, 300 ит. | 160 | 0,182 мс; 1440 Мтрит/с | 1,381 мс; 190 Мтрит/с | **7,58×** |
| 512×512, 300 ит. | 128 | 0,415 мс; 631 Мтрит/с | 1,390 мс; 189 Мтрит/с | **3,35×** |
| 1024×1024, 100 ит. | 128 | 1,589 мс; 660 Мтрит/с | 5,566 мс; 188 Мтрит/с | **3,50×** |

Блок 160 — быстрый путь: 8 слов = ровно один масштаб. Для 128 граница
масштаба попадает внутрь слова (128 не кратно 20), поэтому ядро считает
частичные суммы блоков поэлементно; отсюда ~2,6× медленнее на трит, но
LUT всё равно быстрее direct в 3–3,5×. Оба пути дают одинаковый результат
(расхождение LUT/direct: 0).

Почему LUT: на слово pack20 прямой путь делает 20 делений на 3, LUT — 4
деления на 243 и 4 выборки из таблицы 243×5 (1,2 КБ, живёт в L1). На
больших матрицах разрыв для блока 160 — 6–8×, для 128 — 3–3,5×
(добавляется работа с границей внутри слова).
Пропускная способность чтения низкая (0,13–0,32 ГБ/с) потому, что
скалярный код упирается в декодирование, а не в память — это тот же
вывод, что в `docs/trit-emulation.md`.

## Сверка с Python-эталоном

Синтетика `tools/vtm_compile.py --synthetic` (mlp и полный слой с
RoPE/KVW/ATTN, размер 128, seed 1) прочитана C-интерпретатором и сверена
с `meta["expected"]["logits"]`: максимальное расхождение **4,99e-10**,
argmax совпал (66 для mlp, 48 для attn). Это же подтверждает раскладку
инструкции (imm по смещению 12), блок масштаба 128 и семантику ATTN/ROPE.

## Что проверяют тесты

* контрольные векторы `docs/trit-format.md` побитово, round-trip 1000 тритов;
* half/bf16 (нормали, субнормаль, inf, округление);
* корректный `.vtm`: заголовок, таблица, имена, TMV 2×3 с ответом вручную,
  TMV на 320 тритах (два блока по 160) и на 300 тритах (три блока по 128,
  граница внутри слова); raw-раскладка тритов;
* битые файлы: обрезка на байт, короткий заголовок, чужая магия/версия,
  offset за границей, абсурдные `n_tensors`/`n_instr`, слово > 3^20−1,
  плохой `n_program`; путь через реальный файл (`mkstemp`) и обрезанный
  файл — только ошибка, без падения;
* RMSN (`x=[3,4]`, `w=[1,2]`, eps=1), SM (1D и causal 2D с offset),
  ROPE (half-split и interleaved), MM, EMB (статический и динамический),
  KVW + ATTN по кэшу, ATTN causal, SILU/ADD/MUL/SCAL/CPY, SAMP и callback,
  f16/bf16-входы, fallback на скалярный бэкенд при пустой структуре.

## Известные ограничения v0.1

* Только скалярный C; SIMD нет. ATTN/MM — наивные тройные циклы.
* SAMP — только greedy; температуры/top-k/seed нет.
* Нет ветвлений: генерацию в цикле делает хост, вызывая `vtm_run()`.
* Нет токенизатора и загрузчика модели: только контейнер `.vtm`.
* Нет mmap, потоков, контрольных сумм и проверки перекрытия тензоров;
  LUT инициализируется лениво, API не потокобезопасен.
* Нет чтения `meta` (JSON): `rope_theta` жёстко 10000, `scale_block` при
  неоднозначности считается 128, `meta["sample_seed"]` игнорируется.
* SAMP — только greedy; температуры/seed/top-k нет.
* `n_program` — только размер (или 0); смещение программы не принимается.
* Загрузчик доверяет `n_elements` ≤ 1 ГиБ и общему размеру файла ≤ 4 ГиБ;
  это защита от абсурда, а не от злонамеренного OOM.
